## 要解决什么问题

让助手读“共计一百一十四点四八元”，既要金额读对，又要音色稳定、及时开始发声。声音像参考人却漏词，与内容正确却机械，是两种不同失败。

本页以公开的 **Qwen3-TTS-12Hz** 权重为主，句子和排错场景用于帮助理解。[返回 Qwen](/nlp/qwen/)。

## 结构与数据流

文字与已经生成的语音码沿特征通道组成双轨输入；Qwen3 骨干先预测当前帧的主码本，再由 MTP 模块补充其他码本，最后由流式解码器把这些编号还原成波形。参考声音还可以通过说话人编码器提供音色条件。

报告 Figure 3 中的 0 表示主码本，1 到 15 表示其他码本；虚线代表可选条件。

## 先把声音变成编号

神经语音 tokenizer 先将录音压缩成一串离散码。本报告的 **“12Hz”是型号名称，实际时间步频率为 12.5Hz**，约每 80ms 一帧。每帧不只一个数字，而有多层码本：一层偏语义，另外 15 层 RVQ 逐步补充声学细节。训练第一层时，模型使用 WavLM 的表示作为教师信号；15 层残差量化则逐层补上尚未表达的声音信息。

可以类比先确定内容轮廓，再一层层补充声音细节。每个码本都是学习得到的向量字典，语义与声学信息也可能有重叠。

假设这段声音正好 4 秒，约有 50 帧，每帧 16 个码本位置，总共约 800 个离散索引。骨干按帧预测主码本，MTP 再预测其余码本，因此这 800 个索引由两个层次分工生成。

### 一帧的 16 个编号怎么生成？

可以把生成想成两层接力：较大的 Talker 先决定这一帧的第 0 个码；随后较小的 Code Predictor 以已有信息为条件，补出同一帧其余 15 个码。再进入下一帧时，Talker 会利用前面生成的语音信息继续预测。

这里有个容易误会的细节：[官方实现的固定版本](https://github.com/QwenLM/Qwen3-TTS/blob/d8146d5/qwen_tts/core/models/modeling_qwen3_tts.py)中，Code Predictor 通过生成过程逐步产生剩余码本。**不用让较大的 Talker 为同一帧跑 16 次，不等于 15 个剩余码完全并行或没有计算开销。** 具体耗时还与预测器、采样设置、硬件和推理引擎有关；优化后的实现可以采用不同的执行方式，应以实际测试为准。

官方 Figure 2 同时画了 25Hz 与 12Hz 两条 tokenizer 路线。25Hz 研究分支是单码本，并采用分块 DiT 等波形重建设计；这里重点讲的 12Hz 是多码本与轻量因果解码路径。不能把二者画成一条固定流水线。

## 一句话怎样逐步发声

### 文本 token 与语音帧，不是一一配对

文字“共计一百一十四点四八元”经过文本 tokenizer；语音使用另一种码序列。一个词可能拖长、停顿或连读，文字 token 的数量不等于声学帧数。

双轨设计把文字与声学条件组合，支持流式文字输入与语音输出。这不是字字固定 80ms，也不是必须先等整段回答全部写完才能出声音。把所有文字预先给齐的离线调用，与实际逐步输入文字的延迟，要分别测。

两条 tokenizer 路线对“什么时候能开口”的处理不同。报告中的 25Hz 分支每 8 个码作为一块，还需要向前看一块：语言模型先产生 16 个码，才能开始解码第一块。12Hz 分支的解码器只依赖已有内容，理论上拿到一帧就能解码；实际首包等待还要看计算设备、分包方式与并发。

拿报告的分块设置算一遍：25Hz 的每个码对应 40ms，8 个码代表 320ms 的声学内容；由于后面的 BigVGAN 还需要约 130ms 的右侧上下文，**第一包实际约包含 190ms 声音**，后续稳定输出的每包约为 320ms。这里说的是每包声音的长度，和从发起请求到听见第一包的等待时间是两回事；计算过程、排队与网络也会影响等待。

### 音色从哪里来，要看具体权重

| 类型           | 条件与用途                       | 公开规格与边界                             |
| -------------- | -------------------------------- | ------------------------------------------ |
| Base           | 参考录音的声音克隆，可作适配基础 | 0.6B、1.7B；具体参考文本与模式看接口       |
| CustomVoice    | 选预设音色，部分规格支持风格指令 | 0.6B、1.7B；风格指令由 1.7B 支持           |
| VoiceDesign    | 用自然语言描述想要的声音         | 1.7B；不是拿任意 Base 加一句描述就完全等价 |
| Tokenizer-12Hz | 声音与码本之间转换               | 独立权重，不单独完成任意文本合成           |

例如“温和、语速稍慢”是风格条件，目标金额是文字内容，参考音频是声音身份线索。条件混在一个调用里，职责却不同。TTS 的 Base 是分支内部命名，不是只会文本续写的通用 Base。

假设需要为报账助手配置声音：已经有得到授权的参考录音，想沿用其中音色，可以从 Base 的声音克隆接口入手；希望让预设声音读得更温和，可以选支持风格指令的 1.7B CustomVoice；只有“年轻、轻快的女声”这样的文字描述，则使用 VoiceDesign。三者都要再检查金额是否读对，不能只凭音色选型判断任务完成。

报告讨论了两种利用参考声音的方式：一种从参考音频提取说话人表示作为条件；另一种同时提供参考音频及对应文字，让模型在上下文中利用这对示例，论文称其更有利于保留韵律。可以把前者理解为提供“谁在说话”的线索，后者还展示“这段文字原来怎样被说出来”。具体接口和适用检查点要看模型卡；两种方式都不保证陌生文本、语言或录音环境下音色与韵律完全一致。

比较这两种方式时，应保持目标文字、参考说话人和推理配置一致，再分别测内容是否念对、声音相似度和韵律自然度。若参考文字本身转写有误，上下文示例也可能带来错误线索，因此要先校对文字与音频是否匹配；这是建议的对照实验，不是这里已经跑出的结果。

## 数据与训练

### tokenizer 与语音生成器，先分开理解

tokenizer 学压缩与重建。12Hz 报告描述语义教师、残差量化、波形／频谱与对抗相关目标；目的是让码既保留内容又能重建声音。它不是拿“正确汉字”给每个码本编号。

例如把一段“请稍等”的录音压成编号再还原：训练时，WavLM 提供表示，帮助第一层码本保留语义；多尺度梅尔频谱重建损失要求还原的声音在不同时间尺度上贴近原录音；判别器则学习区分真实声音与重建声音，生成器据此改善听感。它们共同训练的是**语音编码器和重建器**；之后从新文字预测这些编号，还要训练另一套语音生成模型。以上例子只解释训练分工，不是报告中的原始样本。

生成器学习在文字与声音条件下预测语音码。报告将预训练分为三段：第一段使用超过 500 万小时的多语言语音数据建立文本与语音对应；第二段用经过质量筛选的材料继续预训练；第三段增加长语音采样，并把最大 token 长度从 8,192 增至 32,768。这里的小时数和长度描述的是报告中的训练过程，不是用户可以输入的字符数或单次一定可生成的语音时长。长句能力不仅是推理时把上限调大。

### 后训练怎样同时照顾听感与稳定性

报告介绍 DPO、基于规则奖励的 GSPO，以及针对声音的轻量微调。DPO 用偏好对，规则奖励可针对能检查的目标，声音适配改善身份与表现。不能把“用了 RL”当成只检查文字答案的数学 RLVR。

业务样本要同步保存文字、录音、采样率、切段和条件。金额读错先查数字文本规范与对应录音；说话人很像却漏字，增加音色样本未必对症。若比较微调收益，必须保留同权重、同条件的未适配基线。

## 评测怎么看

### 用同一句话拆出四张成绩单

| 维度 | 教学场景                         | 怎样核对                               |
| ---- | -------------------------------- | -------------------------------------- |
| 内容 | 114.48 被念成 114.8              | 人工核对，ASR 回识别辅助；数字规范固定 |
| 音色 | 前半段像参考人，后半段漂移       | 说话人相似性与盲听，检查长句切片       |
| 表达 | 内容正确但“稍慢”没执行           | 风格遵从、自然度与独立听者判断         |
| 速度 | 早出一个短声音包，随后长时间停顿 | 首包、包间断续与完整完成时间分别统计   |

识别器也会错；ASR 回识别正确，不代表发声自然。说话人相似度高，也不证明金额念对。MOS 或偏好测试需说明材料、听者与安排，跨论文直接比较可能不公平。[语音质量](/evaluation/speech-quality/)另读。

报告表 5 的一个具体例子是 Seed-TTS 的零样本声音克隆 `test-en`：12Hz 的 1.7B-Base 列出 WER 1.24%，同表的 0.6B-Base 为 1.32%；在 `test-zh` 上分别是 0.77% 和 0.92%。这项指标衡量朗读内容与目标文本的一致性，音色和听感还需要单独评价。官方仓库描述其评测设置为 bfloat16、最多生成 2,048 个 token，Seed 测试使用自动语言选择；复现时还要固定检查点、参考音频及其他采样参数。报告在长语音内部测试中使用 Qwen3-ASR 进行回识别；如果识别器自己漏掉某些读错的地方，自动分数也可能遗漏问题，因此关键数字和否定词仍应人工抽听。

### 声音编码器的重建分数，不是整套 TTS 的分数

把已有录音编码成离散码，再从这些码还原声音，测的是 tokenizer 能否保留原录音信息；从新文字生成语音，还需要上游模型先预测出合适的码。就像先检查录音文件压缩后能否还原，再检查配音员能否把一篇新稿念对，是两道不同的题。

[报告表 4](https://arxiv.org/html/2601.15621v1)在 LibriSpeech test-clean 的 2620 条语音上比较重建。Qwen-TTS-Tokenizer-12Hz 使用 16 层码本、每秒 12.5 帧，说话人相似度为 0.95；表中 Mimi 为 0.87。这里的相似度由 WavLM 说话人验证模型计算，不是“95% 的听众认为完全相同”。它适合观察参考声音的表示是否保留，也要结合内容可懂度、听感和真实生成测试。

### “实时率低”为什么仍可能等很久

若假设合成 4 秒声音花 2 秒，RTF＝0.5。但两秒全花在开始前，与先出首包再持续输出，用户体验不同。这个算式不是本模型实测速率，不能据此宣传延迟。

报告表 2 提供了并发变化的例子：12Hz、0.6B 在并发为 1 时，语言模型产生首包语音码需要 93 毫秒，tokenizer 解码需要 4 毫秒，合计 97 毫秒；并发提高到 6 时，分别为 294 毫秒、5 毫秒，合计 299 毫秒。同表的 1.7B 在并发为 1 时合计 101 毫秒。

12.5Hz 表示每个码帧约 80 毫秒的音频内容；报告为降低调度开销，把 4 帧打包为约 320 毫秒的语音包。**320 毫秒是包内声音的时长，不是用户等待首包的时间**；系统可能比实时更快地生成和解码这段声音。论文采用内部 vLLM 引擎、指定优化和单个计算资源，实际部署还要考虑网络和应用流程。

固定硬件、并发、精度、文本长度、流式输入方式、参考录音与解码配置，再报告 p50／p95 等延迟分位数。官方的低延迟结果也必须连同其测量条件阅读。

## 应用与错例

先听原始参考录音与 tokenizer 重建；重建已失真，问题可能在表示／解码。再看完整生成：漏数字查文字、对齐和停止；长句重复查分句与历史条件；音色漂移查参考质量与声音适配。不要统一写成“音质不好”。

从开发池补难例后，用未见文本和独立说话人回归，既测金额，也测普通句子。完整方案见[TTS 案例](/cases/tts/)。

### 把一个数字错读拆成可操作的检查

假设原文是“114.48 元”，听到的却像“114.8 元”。先确认送入系统的文字有没有被上游格式化：小数点、货币单位和数字规范如果已经丢失，重训发声模型解决不了输入问题。再对照合成音频与参考文本，区分实际漏读、发音含混和自动识别器听错。必要时让两位听者独立记录听到的金额，再核对结果，避免用同一个识别模型既生产标签又裁判结果。

如果错误集中在长句末尾，分别测试完整句和按标点切分的短句；同时统计漏词、停顿和首包等待。短句更准不代表可以无限切分：切得过碎可能破坏连贯语调或增大请求开销。选择切分策略时，应在独立文本上比较内容准确、自然度与延迟，而不是只听一条样本。

### 音色克隆的参照也需要检验

同一说话人的参考音频如果混有背景音乐、回声或者其他人声，系统可能把这些条件当作声音的一部分。先试听并检查长度、采样率和是否存在多位说话人，再用多条未见文本测相似度和内容准确性。音色相似、句子准确与用户是否授权使用该声音是不同问题；评价前要明确音频来源和使用范围。

## 比较与面试追问

**12Hz、12.5Hz、采样率各是什么？** 前者是型号命名，中间是码帧频率，最后是波形每秒采样点数。

**为什么 16 个码本不等于 16 倍主骨干串行步骤？** 主码本与其他码本有分层预测设计，需看骨干与 MTP 的职责。

**与 F5-TTS 有什么不同？** [F5-TTS](/audio/f5-tts/)在连续声学表示上做流匹配；本页公开 12Hz 路线主要是离散码建模，不能因为都能克隆声音就画成相同架构。
