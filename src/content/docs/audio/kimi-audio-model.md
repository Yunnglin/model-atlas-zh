## 要解决什么问题

想象一段语音里有人说“雨停了吗”，背景还传来雨声。只把语音转成文字，可以得到问题，却可能丢掉判断天气所需的声音；只识别出“有雨声”，又可能不明白用户到底问什么。语音助手需要同时处理语言内容和声音线索，必要时还要把回答说出来。

Kimi-Audio 是 2025 年发布的音频基础模型，公开了模型、代码和评测工具。它支持语音识别、音频问答、声音描述和语音对话等任务。模型输出可以是文字，也可以包含生成的语音；但能生成语音不意味着它一定能实时打断、理解任意语言，或在所有录音条件下可靠工作。下面用雨声问答说明模型各部分怎样配合。

## 结构与数据流

整体可以分成“把声音表示出来、理解并决定输出、把音频表示还原为声音”三步。模型既可以接收音频，也可以接收文字；如果任务只需要文字，音频生成部分不一定参与。配图是教学简图，省略了任务提示、文字输入以及分块细节。

### 一个声音，两种表示

音频是随时间变化的波形。如果直接把每个采样点都送给语言模型，一段录音会产生很长的序列。Kimi-Audio 使用混合输入：一条路径提取离散的语义音频 token，另一条路径用预训练 Whisper 提取连续声学特征。前者可类比简短的索引，后者提供更丰富的声音信息；它们是训练得到的数字表示，并非人类手写的“词语列表”和“音色情绪标签”。

论文使用 12.5 Hz 的离散语义 token，也就是平均每秒约 12.5 个位置。连续 Whisper 特征原本为 50 Hz，经适配器下采样到 12.5 Hz 后，与离散 token 的嵌入逐位置相加，再送入音频语言模型。十秒音频按这个速率约有 125 个位置；这只是帮助理解序列长度的估算，不包含任务标记、补齐或其他实现开销。12.5 Hz 不等于音频波形采样率，不能理解为每秒只录 12.5 个声音采样点。

为什么保留两条路径？离散表示有利于压缩和预测，连续特征可以补充声学线索；但“补充”不等于保证完美保留说话人、情绪或背景音。嘈杂环境、重叠说话和音频质量都会影响结果。[Whisper](/audio/whisper/) 可以帮助理解语音特征提取与转写的关系。

### 同一个主干，两种输出

音频语言模型先用共享 Transformer 层处理输入，再分出文本头和音频头：文本头预测文本 token，音频头预测离散音频语义 token。论文说明共享层与文本头从预训练文本语言模型初始化，音频头随机初始化。一个任务可要求文字答案，也可生成相应音频；“同一个模型”不意味着所有模块只有一套参数或两种输出始终同步完美。

用户问“雨停了吗”，模型需要结合语音问题与背景声生成答案。若只输出“没停”，文本头的结果可以直接显示；若还要朗读，音频头预测的 token 不是可以直接播放的波形，还需要后续解码。文本答案正确而生成语音漏字，是不同于听错雨声的另一类错误。

### 从音频 token 到波形

论文中的音频解码器使用流匹配模块，将 12.5 Hz 语义 token 条件转换成 50 Hz 梅尔频谱，再通过声码器生成波形。可以把梅尔频谱想成描述声音随时间变化的一张表，声码器再把这张表还原成可以播放的声音；它不是简单地把每个语义 token 直接读成一个汉字。

为了降低生成等待，解码器可按块处理。只看过去可能使块与块之间出现断续，论文因此引入前瞻：生成当前块时参考下一块开头的少量 token，只保留当前块对应的频谱。论文举例使用后续 4 个语义 token：按 12.5 Hz 粗略估算约 0.32 秒的内容，实际首包延迟还取决于 token 生成、分块调度和系统实现。前瞻需要等到这些未来 token，改善边界的同时会增加一定等待。分块生成能力不等于已经证明整套应用支持用户随时打断的全双工对话；真实延迟还包括录音、网络、推理和播放。

可以把它想成接力朗读：第一位读完“明天上午”，第二位接着读“十点开会”。如果两段分别生成而不看相邻内容，接缝处可能不自然；让第一段提前参考下一段开头，有机会把语调衔接好，但需要先等到一小段后续内容。论文还让当前块参考之前的频谱和语义 token，具体效果需要听实际生成的音频。

## 数据与训练

### 从原始录音构造训练材料

论文报告音频预训练数据包含约 1300 万小时原始音频，覆盖有声书、播客、采访以及环境声和音乐等。这个数字描述数据规模，不是用户人数，也不意味着每一小时都带人工校对的标签。原始录音常有噪声、混响、多人重叠和缺失文字，需要经过处理才能用于不同训练任务。

团队使用语音增强、说话人分段、语言识别和转写等处理步骤。语音增强可以让人声更清楚，却也可能去掉背景中的雨声或音乐；论文因此在预训练时以 1:1 混合原始与增强音频。自动识别标签仍可能听错词、分错说话人或删掉有效声音，训练数据应抽样检查，不能把机器转写自动当作无误的标准答案。

论文描述的转写流程只保留英语和普通话片段进一步转写；原始音频包含多语言信息，并不等于所有语言都有同等质量的转写或识别表现。保护说话人隐私、检查数据授权、按来源去重和划分测试集，对实际构建数据同样必要。

### 预训练与监督微调

Kimi-Audio 从预训练文本语言模型出发，继续在文字、音频和音频文本配对任务上训练。论文设计单模态预测、音频与文字之间的映射以及交错任务，让模型既学习音频表示，又学习语音和文字之间的关联。报告给出预训练配方：音频和文本各使用 5850 亿 token，按七类任务配置不同权重；这是训练时处理的 token 数，不是 5850 亿小时录音或不同录音数量。前期 Whisper 连续特征模块在约 20% 的预训练 token 阶段冻结，之后再参与训练；这里说的是报告中的训练策略，不是部署时要求重新训练 Whisper。

这些任务的区别，可以用一段分成两截的录音来理解。**映射任务**给出第一截声音，让模型预测这截对应的文字；然后再给第二截声音，预测第二截文字。反过来，也可以给文字并预测对应的音频语义 token。训练时只对需要预测的目标部分计算损失，不要求模型把给定的输入重新背一遍。**交错任务**则可以给第一截声音，让模型预测下一截的文字或音频 token；它练的是接续另一段内容，与逐段转写同一段声音不是一回事。实际训练还包含不同模态组合，这里只是简化示例，方便看清两类目标。

论文的一种音频到文字与音频交错预训练任务，还处理了两种输出的速度差：同一段回复通常需要的音频 token 多于文本 token。作者在音频语义 token 前加入 6 个特殊空白 token，让音频分支的预测稍晚开始，以帮助对齐两路输出。6 个位置按 12.5 Hz 约相当于 0.48 秒的序列长度；这是训练序列中的对齐设计，用户实际听到首段语音还要经过生成、解码和系统调度。

报告称监督微调使用约 30 万小时数据，覆盖音频理解、转写和语音对话等任务。团队为识别任务构造 200 种自然语言指令、为其他任务构造 30 种指令，并在训练中随机选择，让模型学会依据不同说法完成任务。例如同一段雨声，提示“请转写说话内容”与“背景有什么声音”需要不同答案。训练数据若只提供文字转写，模型可能学会忽略非语音声音；若问答标签编造雨声，也会把错误带入模型。论文还使用合成语音和对话材料，合成数据便于扩大覆盖，却需要检查发音、情绪和对话真实性。

把语义 token 变成声音的解码器还要单独训练。论文先用预训练数据中的约 100 万小时音频训练流匹配模型和声码器，再以 0.5 至 3 秒的动态块长做分块微调，最后用高质量单说话人录音继续微调。这个流程帮助理解“会选择回答内容”和“能把回答自然地说出来”为何是两部分：前者主要依赖音频语言模型，后者还取决于解码器与声码器。检查生成语音时，两部分都值得分别排查。

## 评测怎么看

语音识别关注“说的话是否转对”，常用词错误率 WER：替换、删除和插入的词数相加，再除以参考词数。假设参考句有 10 个词，模型替换一个、漏掉一个，且没有额外插入，WER 是 20%。这只是算例；分词、大小写、数字和标点归一化都会改变分数。[WER](/evaluation/wer/) 有更详细的说明。

论文表格报告 Kimi-Audio 在 LibriSpeech test-clean 和 test-other 上的 WER 分别为 1.28 和 2.42；这是特定英文数据集及论文评测流程的结果，不是所有真实通话的错误率。中文、方言、会议重叠声和电话噪声需要独立测试。比较时要明确模型版本、数据切分、预处理、提示词及归一化规则。

同一份 Kimi-Audio 报告的表 4 中，Qwen2-Audio-base 在这两个测试集分别为 1.74 和 4.04；但 [Qwen2-Audio 自身报告](https://arxiv.org/abs/2407.10759v1)表 2 给出的对应值是 1.6 和 3.6。两篇报告的测试实现和配置未必完全一致，不能把各自最好的数字直接拼成一张统一排行榜。对比时优先使用同一评测工具、预处理、提示和版本，或明确写出未能统一的条件。

报告表 5 同时列出 MMAU 的音乐、声音和语音三项：Kimi-Audio 分别为 61.68、73.27、60.66，表中 Qwen2.5-Omni 为 62.16、67.57、53.92。它在声音和语音分项较高，音乐分项则略低；这组数字是该报告的设定下的模型对照，不是对全部音乐或环境声任务的结论。

### 小声说话也要单独测

图书朗读与耳语听起来很不一样：耳语中的声音更弱、发声方式也不同。另一份 [AmphionASR 技术报告](https://github.com/AmphionTeam/AmphionASR/blob/main/main.pdf)在耳语测试集上比较多个系统：Kimi-Audio-7B-Instruct 在中文 wEar 上的 CER 为 1.48%，在英文 WTIMIT 上的 WER 为 10.95%。两个数字使用不同语言、测试集和计数单位，不能相减当作语言难度差，也不能与上面的 LibriSpeech 成绩直接排名。

报告还列出其他模型在相同耳语测试中的结果，帮助观察模型面对特殊声学条件时的差异；具体结果仍受音频、预处理、文本归一化和解码设置影响。如果业务是医院安静环境里的语音输入，就应另外收集经授权的小声说话样本，按说话人划分测试，并分别检查普通说话、低音量和耳语的识别表现。

音频理解不能只看 WER。雨声问答应检查是否识别出雨、是否理解了问题、回答是否有依据；音乐或报警声任务还需验证非语音线索。生成语音则要分别听内容是否与文字一致、是否漏字、音质是否自然、块边界是否突兀，以及首段到达时间和完整回复耗时。自动分数与人工听评都需要注明样本和方法，不能用一项分数证明所有体验。

构造测试时，应按说话人或录音来源划分开发集与独立测试集，避免同一人、同一录音的近似片段同时用于调参与验收。加入不同麦克风、距离、背景声、语速以及无足够证据的样本，记录错误类型，而不仅报告平均值。

## 应用与错例闭环

假设语音助手把“明天改到十点”听成“明天改到四点”。先保存经授权的原始录音、转写、模型版本、输入处理和生成回答；检查录音是否截掉前音、背景是否遮挡、模型是否转写正确但理解错了数字，或播放环节漏说。数字、日期和姓名等关键字段应有明确复核策略，不能只看整体 WER。

收集脱敏后的相似错例，如不同口音的“十”“四”、电话噪声和多人重叠，并人工校对答案；先尝试改善采集、提示或关键字段确认，再决定是否需要训练。用独立说话人复测关键字段错误、普通转写质量、背景声问答与响应时间，防止只在原录音上变好。

## 比较与面试追问

**12.5 Hz 是每秒 12.5 个波形采样点吗？** 不是，是语义音频 token 的帧率；原始波形采样率远高于此。

**输入只有离散音频 token 吗？** 不是。模型将离散 token 嵌入与下采样后的连续 Whisper 特征相加。

**生成 token 后是否直接得到可播放语音？** 还需要流匹配解码出频谱，再由声码器生成波形。

**分块流式解码是否保证全双工低延迟？** 不保证。前瞻、录音、网络和系统调度都会影响延迟与打断体验。

**ASR 低错误率能代表音频理解和语音质量吗？** 不能；转写、背景声判断、回答正确性与生成语音需要分别评测。
