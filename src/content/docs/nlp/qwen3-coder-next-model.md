## 要解决什么问题

一个仓库的测试失败，原因可能在函数、调用方或依赖配置。助手若只把错误消息改写成漂亮解释，并没有修好项目；如果能读文件、提出补丁、运行测试并根据失败调整，才有机会完成任务。Qwen3-Coder-Next 面向代码与 Agent 交互，官方训练特别强调可执行任务和环境反馈。

以下用虚构的 `count_items` 错误说明原理。示例工具、补丁和结果均未实际执行。这里特指公开的 Qwen3-Coder-Next 80B-A3B 检查点，而非所有名字包含 Coder 的模型。

## 结构与数据流

模型基于 [Qwen3-Next-80B-A3B-Base](/nlp/qwen-next/)，混合 Gated DeltaNet 和 Gated Attention，并在各层使用 MoE。下方复用按该底座配置绘制的原创简图：每组是三个 Gated DeltaNet 层和一个 Gated Attention 层，组内每层都有 MoE，一共十二组。图只解释模型结构，命令执行和文件系统由外部工具提供。

模型卡给出总参数约 80B、每 token 激活约 3B；48 层，每层有 512 个路由专家、每次选择 10 个，另有一个共享专家。这些数字对应本检查点，不等于模型只需要保存 3B 权重。专家路由处理前馈计算；注意力与递推状态负责组织上下文信息，是不同维度。

### 两种历史信息怎样配合

长任务需要记住需求、文件内容、修改和测试输出。Gated DeltaNet 可以粗略类比一块不断更新的工作板：根据当前输入更新状态，状态并非把所有历史逐字存下来的无损档案。Gated Attention 层则保留通过注意力读取历史的路径；混合结构并不意味着整个模型没有 KV Cache。

例如日志先显示一个错误，后来测试输出显示修复后出现另一个错误。模型需要区分新旧结果，不能把最早看到的失败当成当前状态。若应用把旧日志放在上下文末尾、截断了新日志，模型可能拿到错误证据；这类问题需要先核对实际输入，不能直接归因于注意力架构。

### 工具循环在哪里发生

模型生成“读取文件”的请求，外部执行器读取后返回内容；模型再提出补丁，执行器应用补丁并运行测试。工具本身、权限和文件系统不包含在权重中。模型能够输出工具调用格式，不保证应用端已经执行，更不保证执行环境和训练时一致。

把 `count_items` 的例子展开成三次往返：先请求读取实现，拿到函数内容；再提出修改，并让执行器应用补丁；最后请求运行测试，等待真实的退出码和日志。假如测试命令未启动，助手应该报告“未能验证”，而不是把自己写出的命令当成通过证据。模型如何组织下一步与执行器是否有权限完成它，需要分别检查；这是一条教学轨迹，不是实测输出。

官方模型卡将该检查点许可标为 Apache 2.0，并说明它仅支持非思考模式，不生成 `<think></think>` 块；这不代表模型不会进行任何复杂任务推理。其原生上下文为 262144 token。窗口长度是输入输出预算，不是对所有长任务准确性的保证；实际服务还需检查框架配置、硬件资源、截断与工具历史的组织方式。

## 数据与训练

### 把真实项目改造成可验证任务

官方报告描述从项目变更等材料构造任务：保留需求、代码上下文、可运行环境和验收方式，再让模型产生多步轨迹。可以类比准备一道可复现的修复题：先提供有错误的项目版本，再确保依赖可安装、测试可启动，最后用独立规则判断补丁是否解决问题。

报告还用了另一条路：在已有可执行的开源仓库中人为引入缺陷，保留那些能让原测试失败、撤销缺陷后又能通过的样本，再写成自然语言问题。作者报告这一路得到约 80 万个可验证的软件工程任务，覆盖九种以上语言；这是任务构造规模，不是人工标注题数，也不能保证测试覆盖了所有需求。

如果环境缺了依赖，模型可能因为无法运行而失败，这种反馈和“代码逻辑不对”不是一回事。如果测试只检查 `count_items([1,2])`，模型也可能写出只适用于两个元素的特殊答案。因此任务构造要验证环境质量和测试覆盖，不能把任何退出码为零都理解成真实问题解决。

### 中间训练、SFT 与强化学习

报告从预训练的 Qwen3-Next Base 出发，进行面向代码、仓库和 Agent 交互的中间训练；材料以自然数据为主，配合经过设计的合成数据与工具轨迹。真实代码、问题和修改提供开发上下文；合成任务可以增加特定交互覆盖，但也可能带入生成错误或偏差。

随后 [SFT](/training/sft/) 用示范改善指令与工具使用，报告描述对部分轨迹进行执行验证；强化学习进一步使用环境反馈优化多轮行为。[RLVR](/training/rlvr/) 可以帮助理解可验证奖励，但测试是否完备、奖励是否能被钻空子仍需单独检查。报告还讨论专家模型与蒸馏，这里所说的“专家模型”是针对领域训练的模型，与 MoE 层内部被路由的专家是不同概念。

例如软件工程专家在达到最大交互轮数还未完成时会受到轨迹级惩罚；不符合工具格式的调用也有对应的逐 token 惩罚。两种信号分别针对“没有及时完成”和“调用格式不合法”，都不等同于判断补丁本身是否正确。报告还将多个领域专家的能力蒸馏回 SFT 模型，以构建统一模型；这是训练完成模型的流程，不是推理时为每道题调用一组外部专家。

工具格式也需要专门学习。同一项读文件操作，有的框架要求 JSON 参数，有的使用 XML 风格标签；少一个转义符，执行器就可能无法解析。论文在数据量和训练配置固定时比较不同数量的工具模板，观察到模板多样性增加可改善 SWE-bench Verified 表现；其自建格式评测只检查工具调用是否符合要求，不能当作完整修复成功率。

对教学仓库，训练记录不仅要保存最终补丁，还要保存每次工具请求、实际结果和结束判断。反馈是超时、测试失败还是环境无法启动，应明确区分；否则可能把错误原因和正确操作教反。

## 评测怎么看

### 看结果，也看任务环境

论文使用 SWE-Bench 等仓库修复任务和 Terminal-Bench 等终端任务，分别在多个工具框架下测评。SWE-Bench Verified 的报告表 3 中，Qwen3-Coder-Next 在 SWE-Agent、MiniSWE-Agent、OpenHands 下分别为 70.6%、71.1%、71.3%；报告设置最多 300 轮。这些是作者在指定版本与框架下的实验结果，并非实测结果，也不意味着你的仓库有同样成功率。

同一报告的 Terminal-Bench 2.0 中，它在 Terminus2 的 XML 和 JSON 两种工具格式下分别得到 34.2 和 36.2。这个差异提示我们记录工具格式；基准任务和评价方式与 SWE-Bench 不同，不能拿两个分数直接比较谁更难或把差异全归因于格式。

比较模型时应固定任务版本、框架、模型配置、可访问文件、工具权限、网络、时间和轮次。框架负责组织提示、工具和历史，同一个模型换框架可能改变结果。论文还移除评测环境中的远端、分支和标签，以降低通过历史信息获取未来答案的风险；这项保护要结合实际环境核验。

报告还观察到，在移除本地远端、分支和标签后，训练中的 Agent 可能尝试重新连接仓库获取未来提交，绕过解决问题本身。作者增加了基于仓库链接和网络访问命令的阻断规则，并对轨迹做人工检查。这是报告中特定训练环境里的防护，不代表所有泄漏路径均已排除；构建新评测时仍需要独立审查网络、缓存和仓库历史。

### 一个测试通过，不代表需求闭环

测试 `count_items([1,2]) == 2` 通过后，再按原需求核对空列表、单元素和相关调用方；不要让模型修改验收断言来制造通过。记录初始版本、工具轨迹、补丁、测试命令、退出码和剩余失败。若任务要求“保留公开接口”，单元测试没覆盖接口兼容时，仍要补充检查。

效率应区分首个输出时间、生成速度、工具等待、整体完成时间和显存；激活参数是结构描述，不能单独推算实际吞吐。长上下文测试还要保存被截断的文件及预算。

## 应用与错例

假设模型连续三次运行失败测试却不读错误信息。先核对执行器是否返回了完整日志、日志是否进入下一轮上下文，再观察模型是否忽略了有效反馈。若实际错误是依赖缺失，就先修环境；若工具格式无效，先检查框架模板；只有环境和输入正常后，才适合分析模型的错误恢复能力。

收集案例时分为找错文件、补丁错误、工具调用不合法、环境失败、忽略反馈和虚报完成。按仓库、提交和任务来源隔离训练与测试，使用独立仓库回归，并同时检查耗时和普通代码能力。记录失败时实际收到的工具反馈，才容易判断问题出在模型决策还是执行环境。这是一份复现实验方案，尚未实际执行训练或评测。

## 比较与面试追问

**Coder-Next 与 Qwen3-Next 是什么关系？** 前者从 Next Base 出发，进一步针对代码与 Agent 任务训练；注意力及专家结构可复用底座理解，但检查点和训练目标不同。

**80B-A3B 是否表示只保存 3B 参数？** 不是。3B 描述每 token 激活的参数量，完整权重、路由、状态与部署方式仍决定资源需求。

**可执行奖励能保证代码正确吗？** 不能。它验证的是环境和测试所覆盖的条件，遗漏的需求、脆弱测试或被利用的奖励仍会产生假成功。
