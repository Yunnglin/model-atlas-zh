## 要解决什么问题？

假设一个线上服务的账单导出任务运行缓慢。助手需要读代码、找出瓶颈、设计实验、修改实现、跑正确性测试和性能测试。如果测试没通过，还要读日志并重新调整；每轮操作都会改变当前状态。仅会生成一段看起来像样的代码，不足以完成这个任务。

官方把 GLM-5.3 的改进重点放在复杂编程与长流程任务上，并表示它和 [GLM-5.2](/nlp/glm52-model/) 使用同一基座，差异来自继续后训练。可以把基座看作已经学过大量通用材料的学生，后训练则让学生在更具体的任务和反馈中继续练习。这里“同一基座”不表示最终权重完全相同，也不表示后训练只修改了某个单独的小模块。

下文账单案例是教学构造，不是官方任务或实际运行结果。模型需要配合工具系统才能读取文件、运行命令；模型生成工具请求本身不等于工具已经执行。

## 结构与数据流

输入的需求、代码片段和历史工具结果会被分成 token。模型使用已有上下文预测后续 token；输出可能是文字，也可能是符合工具协议的请求。外部程序检查权限、执行请求、返回真实结果，再由模型继续处理。模型的判断与工具程序的真实操作要分开记录。

_图：5.2 语言骨干示意。5.3 沿用这一基座，并在此基础上继续后训练；不同版本的最终权重不同。层数与专家配置也可在 [5.3 官方配置](https://huggingface.co/zai-org/GLM-5.3/raw/main/config.json)中查看。_

公开配置沿用 `glm_moe_dsa` 结构。部分层使用[混合专家](/foundations/moe/)：路由器对每个 token 选择若干专家，并结合共享专家参与计算。可以想成一个团队有许多工作组，一次任务只调动其中几组，但这些组不是人为命名的“数据库专家”或“账单专家”。256 个路由专家、选择 8 个是配置字段；它们描述模型内部计算，不意味着一台机器只需存放这 8 个专家的全部权重。

### 稀疏注意力和 IndexShare

当助手持续读取代码和日志时，上下文会不断增长。DSA 稀疏注意力先用索引器挑选可能相关的历史位置，再对选出的部分执行更细的注意力计算。像先查书的索引再看具体页码；索引器有开销，也可能没选中关键线索。公开配置中的选择上限是 2,048，不能理解为整个输入只允许 2,048 个 token。

在 5.2 的官方介绍中，IndexShare 让相邻稀疏注意力层复用同一索引结果，减少重复索引的计算；5.3 配置也列有索引复用频率等字段。复用的是选择结果，并不是把多层整个注意力和全部计算都合并为一层。官方 5.2 介绍的效率数字对应特定长度和测试，不代表 5.3 在任何硬件和任务上都有同样的端到端加速。

举个简化例子：第 3 层先选出值得看的历史位置，第 4、5、6 层沿用这份位置清单，第 7 层再重新挑选。每层仍用自己的参数计算注意力，就像几位同事参考同一份资料目录，却各自完成自己的分析。这个顺序可从配置中的 `indexer_types` 看出。

MoE 的选择对象是参与计算的专家，稀疏注意力的选择对象是要重点读取的历史位置；二者解决不同问题。长上下文配置说明模型能够接受的最大位置范围，不能保证它准确理解每一条历史日志。比如关键性能基线可能在早期输出中，应用若截断或摘要遗漏，之后的优化就可能拿错误版本比较。

### 思考预算与工具系统

官方模型卡提供 `reasoning_effort` 的 `low`、`high`、`max` 等设置，并说明评测复现使用默认 `max`。这让应用在部分服务和实现中选择不同思考预算；预算更高会改变耗时与 token 消耗，效果需结合具体任务测量，不能保证每道题都更好。模型卡还说明聊天模板的思考内容处理选项；不同框架和版本应检查实际支持情况。

模型卡特别提示，聊天模板中 `clear_thinking` 默认是 `false`，并建议普通聊天场景显式设为 `true`。可以把它理解为整理历史消息时决定如何处理已有思考内容：这个选项会影响后续输入的组成，不能与 `reasoning_effort` 控制本次思考预算混为一谈。迁移应用时，应记录模板版本和实际输入，而不是仅改参数名后假定所有框架行为一致。

账单优化时，模型可以先请求读性能测试脚本，随后提出修改，再请求运行测试。执行器可能返回“依赖安装失败”：这只说明测试没跑完，不能说业务代码已经通过。下次模型的上下文应包含真实错误和当前文件状态，而不是模型猜测的成功结果。

## 数据与后训练：同基座不等于同训练

官方发布说明称，GLM-5.3 使用与 5.2 相同的基座，在后训练中扩大环境、任务种类和训练算力；它提到利用 IndexShare、面向长任务的 SAO 和 slime 异步训练基础设施。5.2 已介绍这些技术，不能把它们说成 5.3 新发明。官方没有在模型卡中完整公布 5.3 所有训练样本、各任务配比、奖励公式与超参数，因此无法只靠跑分重建训练流程。

一个通用教学方案可以帮助理解：准备一个可运行的账单仓库、明确目标和验证脚本，让模型在隔离环境中读代码、提出补丁、执行测试并获取反馈；如果测试失败，环境把失败信息返回，模型继续尝试。训练可利用完整行动轨迹与结果反馈，但模型必须区分“真的变快”和“只是删除了工作”。这个方案说明原理，不是声称官方采用了同一仓库、数据或奖励设计。

### 为什么异步训练有用，也有代价？

长程任务有等待：运行测试、编译依赖或检索代码可能花很久。若训练工作必须等每个任务同时结束，就像厨房要等最慢的一桌吃完才能开始下一轮。异步训练让轨迹生成和参数更新在一定程度上并行，减少等待；它仍需处理样本生成时的模型和训练时模型版本不一致、环境失败以及长轨迹占用资源等问题。

奖励还要防止投机。若只看耗时，模型可能跳过校验、缩短处理的数据量，得到表面上更快的成绩。合理评测应先检查正确性、数据完整性和边界行为，再比较同条件下的性能。官方资料介绍了针对长程智能体的训练工作，但不能推断每个任务都使用同一种验证器或者任何长任务都能自动验证。

## 评测：把成绩和条件一起读

官方模型卡表中，GLM-5.3 在 Terminal Bench 3.0 为 **28.3**，GLM-5.2 为 **4.6**；DeepSWE v1.1 分别为 **66.9** 和 **46.2**。前者围绕终端环境任务，后者关注软件工程任务；数字来自官方给定的评测设置，模型、工具框架、预算、采样和基准版本都会影响结果，不能当成任意工作中完成任务的概率。

例如模型卡对 Terminal Bench 3.0 使用 Claude Code 2.1.207、`max` 思考预算、400K 上下文和最多 128K 输出；每题独立运行三次并报告平均结果，每次最多 600 个智能体轮次、10 小时。这个设置给系统较长的尝试时间，与一次性回答或短超时评测不能直接比较。DeepSWE 则使用 mini-swe-agent，每题限时 6 小时；即使都是代码任务，也要分别注明框架和时间预算。

模型卡还报告 CyberGym 为 **84.5**，前代为 **77.2**。官方使用 1507 个任务，每题运行一次，在隔离环境中测试，任务没有设定时间上限，也不能自由访问互联网。例如，让模型检查一段程序是否存在已知安全问题，得分反映的是它在这套测试条件下的表现；换成线上服务的固定时间预算，结果未必相同，也不能用单个数字替代人工安全审查。官方还提到内部 Z.ai Code Bench 比 5.2 提升 50%；这是该内部基准的相对变化，不是所有代码任务均提升 50%。

对长流程工作，除了最终是否完成，还可以比较在固定时间与调用预算下的正确率、有效实验次数、耗时、token 使用和错误恢复。复现时保留模型权重版本、提示、工具框架、沙箱、基准提交及随机采样参数；对比多个版本时保持相同条件，发现缺失或偏差要明确记录。一个单次成功的演示不能证明可靠性。

## 应用与错例：把数据闭环跑起来

账单导出项目可以先建立隔离数据集：选取真实但经过处理的仓库快照，记录输入规模、预期结果、权限和测试方法，按项目或时间分开开发与测试。提供只读文件、受限修改和测试工具，并记录每次请求、命令、返回日志和修改的文件。

评测先确认导出金额、条数、时区和权限结果一致，再测相同输入及相同机器上的耗时和资源消耗。若模型宣称“快了一倍”，却是因为只处理一半数据，应归为正确性失败，而非性能成功。还应测试零数据、跨月和重复请求，检查对其他功能的影响。

如果独立测试发现模型把缓存命中时的旧结果当成新结果，先复现并查看它读到的日志、当前版本与测试数据；区分数据不足、模型误解、工具结果过期和评分器漏洞。针对根因改进演示样本、工具提示或验证脚本，随后用未参与修改的样本复测，避免让测试集变成训练材料。这个闭环是可复现的教学计划，未实际执行。

## 与相近版本比较

GLM-5.2 引入并公开介绍长上下文相关结构与训练方案；5.3 官方强调相同基座上的后训练扩展。GLM-5.3-Flash 是另一个有自己结构和模态定位的型号，不能把本页参数或能力直接套过去。

模型卡显示的 GLM-5.3 License 与前代部分型号所用 MIT 不同，尤其包含特定规模的模型即服务业务相关条件；是否适用应阅读完整许可文件，而不是仅依据“权重开放”作判断。部署时还要考虑完整权重、上下文缓存、通信和运行框架，不能只看每个 token 激活的专家数量。

## 面试追问

**同一基座为什么能有不同能力？** 后训练会继续改变模型参数和行为，数据、任务、反馈和优化都可能影响结果；单看模型结构无法确定各因素的贡献。

**IndexShare 是共享整层注意力吗？** 不是。它复用的是索引器选择结果，其他注意力计算仍需执行。复用可能降低索引开销，实际收益依赖任务与实现。

**上下文达到 1M 就能可靠利用全部信息吗？** 不能。窗口大小描述容量限制，信息位置、历史管理、稀疏选择和任务难度都会影响有效使用，应在目标任务上测量。
