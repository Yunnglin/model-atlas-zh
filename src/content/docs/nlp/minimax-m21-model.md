## 要解决什么问题

假设一名开发者需要把网页里的价格表改成支持多币种：数据接口用 Python，前端用 TypeScript，已有用户还要求不能破坏旧格式。助手需要理解两个文件之间的关系，修改代码并运行测试。如果只生成一段漂亮的代码，却不检查原有接口或者忽略测试失败，任务并没有真正完成。

MiniMax-M2.1 在 [MiniMax-M2](/nlp/minimax-m2-model/) 基础上进一步进行后训练，官方重点介绍多语言编程、工具使用和长程任务。模型本身输出文字或工具请求；代码执行、浏览器和文件系统属于外部系统。下文的多币种任务是教学示例。

理解这个版本可以依次看网络结构、训练任务的构造，以及模型和工具组成的系统怎样评测。

## 结构与数据流

M2.1 是自回归解码器模型：接收已有文本与对话历史，逐步预测后续 token。官方权重配置列出 62 层、256 个本地专家、每个 token 选择 8 个专家，以及 48 个查询头和 8 个键值头。专家是前馈网络中的可训练模块，路由按输入选择部分专家参与；不能把它们理解成已经由人指定职责的独立程序员。

![MiniMax-M2.1 语言主干：输入经过 62 层，每层以因果注意力和稀疏专家处理，再预测下一个 token。](/figures/minimax-m2/backbone.svg)

这张教学图依据 [M2 系列技术报告](https://arxiv.org/abs/2605.26494)和 [M2.1 配置](https://huggingface.co/MiniMaxAI/MiniMax-M2.1/raw/main/config.json)绘制。每层先用注意力读取上下文，再用专家网络加工表示；图中省略了残差与归一化等细节。

总参数约 230B、每 token 激活约 10B。少量激活可以降低每次前馈计算量，但部署仍需考虑完整权重、缓存和跨设备通信，不能只按 10B 来计算显存。注意力中的多组查询共享键值头，有助于降低缓存成本；它不是把长文档中的无关信息自动删除。具体基础结构可先阅读 [M2 页面](/nlp/minimax-m2-model/) 和 [MoE](/foundations/moe/)。

以这份配置为例，48 个查询头、8 个键值头意味着平均 6 个查询头共享一组键和值。读同一份日志时，这些查询头可以关注不同线索，却不必各自缓存一整套键值；它们并不因此变成同一个头。实际节省多少显存取决于缓存格式、上下文长度和推理实现。

官方配置中的最大位置数是 196608，不等于每个服务都允许如此长的输入，也不保证所有位置都能被准确理解。部署时应检查输入、输出总预算、工具结果占用、推理框架以及长上下文测试结果。关于工具对话，模型卡还要求保留思考与工具调用相关内容以支持交错思考；接入时应按所用版本协议传递，而不是自行丢弃必要的历史。

### 一次修改需要模型和工具配合

多币种任务中，模型可能先请求读取前后端文件，再提出补丁、请求运行测试。执行器负责检查权限并实际运行命令，随后把标准输出、错误和退出状态传回模型。模型继续处理失败结果，必要时修改代码，再给用户说明做了什么。图中的工具是模型外部组件，不是模型拥有文件系统或浏览器的证明。

如果模型回复“测试全部通过”，却没有执行记录，这只是模型生成的一句话；如果执行器运行的是错误目录里的测试，日志存在也不足以证明目标项目通过。可靠系统需要对照任务、工作目录、命令、退出状态和补丁，并对外部文本保持警惕。工具请求未通过授权或执行失败时，系统应如实反馈，而不是假装操作成功。

## 数据与训练

### 从真实代码改动构造练习

官方 M2.1 后训练分享介绍，团队从代码仓库的提交和合并请求中构造软件工程任务，准备可运行环境，并按任务类型设计验证。比如一个真实修复涉及空币种时报错：在修复前运行相关测试应失败，应用参考修复后应通过；其他原本通过的测试也应继续通过。前者常称失败到通过，后者帮助发现修复带来的回归。

这像给学生准备一套可重复运行的实验，而不仅是提供标准答案。实际构造并不总能自动成功：依赖版本可能失效、原始问题缺少必要信息、测试未覆盖真实需求。需要检查参考补丁、运行环境及问题描述是否一致，并对数据进行筛选；可执行不等于测试完全覆盖，也不能保证所有样本都无泄漏。

官方还描述使用不同智能体脚手架采样轨迹。脚手架可以负责组织系统提示、工具、上下文和运行循环；模型在一个框架表现好，不保证换到另一个就同样稳定。训练和评测应留意任务来源以及同源仓库的重复，避免把相似修改同时放进训练和测试。

### 从零开发与代码修复不同

修复已有缺陷常有预先写好的测试；从零开发一个网页时，功能和视觉要求可能无法全部提前写成固定断言。官方分享介绍专家参与制定任务与评分细则，并让验证智能体在沙盒中部署应用、通过浏览器操作界面，再根据要求评分。它检查的是实际交互结果，而非只看静态源码或模型的自我评价。

假设要做一个多币种价格表，评分细则可以检查：切换币种后数值是否改变、输入错误是否提示、窄屏是否仍可操作，以及旧数据是否正常显示。自动验证器也可能点错、漏测或误判视觉效果；专家设计的规则和人工抽样依然重要。不能把“验证智能体给高分”等同于产品已通过真实用户验收。

### 长程任务与强化学习

官方分享还介绍 WebExplorer：从一条可以检索的线索出发，通过探索和改写构造需要多步查证的问题，用于长程搜索任务。任务必须可解，过度模糊可能让问题失去唯一答案；筛选和核验旨在降低这种风险，并不能保证生成任务永远正确。

在强化学习方面，团队称截至 M2.1 主要沿用 CISPO，并适配多轮工具场景。直观地说，模型会基于任务反馈调整生成策略，[CISPO](/training/cispo/) 对重要性采样权重进行裁剪，以控制更新幅度；具体训练还要处理工具结果噪声、异常轨迹和训练与推理之间的差异。它是训练算法的选择，不是模型的一种新注意力层，也不能据此声称所有工具调用一定正确。

举个只用于理解的例子：某条工具请求在采样时概率是 0.1，在当前策略下为 0.3，那么新旧概率之比是 3。如果配置允许的权重上限是 1.2，这条样本用于计算更新时的权重会被截到 1.2；具体上限由训练配置决定。它限制的是这部分权重，不能单凭这个例子说模型整体更新幅度有固定上限，也不能替代对完整目标函数的理解。

官方还介绍 Forge 训练框架负责衔接智能体执行、轨迹记录与奖励计算。框架如何组织日志是工程问题，奖励是否能准确反映任务成功是另一个问题。初版 M2.1 的全部数据样本、精确比例与每个训练步骤的超参数并未完整公开；不能把后续版本的做法自动补写成这一版本的事实。

## 评测怎么看

官方模型卡报告 SWE-bench Verified 为 74.0，表中 M2 为 69.4；官方说明默认使用 Claude Code 脚手架，覆盖默认系统提示，并报告 4 次运行的平均结果。这是特定框架和测试条件下的结果，不等于任意仓库中 74% 的修复都可靠。模型、脚手架、工具和测试环境共同影响结果。

同一模型在模型卡的其他脚手架下，SWE-bench Verified 数字也不同：Droid 为 71.3，mini-swe-agent 为 67.0。它们提示我们要记录框架而不是只报模型名，但不能只凭这些数字断言某个框架在所有任务中都更好。数据集版本、提示、工具权限和重试次数需要一致才能做更有意义的比较。

同一模型卡还对照了有无上下文管理的 BrowseComp：M2.1 分别为 47.4 和 62.0。官方方案在 token 使用超过上下文窗口的 30% 后，保留第一条模型回答、最近五条模型回答及工具输出，丢弃其余内容。这个例子说明搜索成绩不仅受模型影响，还与长任务中如何整理历史信息有关。

对于从零应用开发，官方 VIBE 评测通过部署和交互来检查网页、移动端等任务。模型卡报告 M2.1 的 VIBE 平均分 88.6，这是官方自建基准和自动验证流程下的结果；评价细则、验证智能体、运行环境和任务分布都影响分数，不能将其当作真实用户满意度。引用任何成绩时应标明是哪一个基准和版本。

把总分拆开看更有帮助：模型卡给出的 VIBE-Web 为 91.5、VIBE-Android 为 89.7，分别针对网页和 Android 应用；官方说明通过容器部署、实际交互与验证智能体评分，最终结果取三次运行的平均值。它们不是用户投票，也不能把网页分数直接解释成上线后问题解决率。比如上面的价格表，光检查界面能否打开还不够，还要操作币种切换并检查显示结果。

另一个例子是 Terminal-bench 2.0：官方使用 Claude Code 和内部评测框架，修复环境问题，并移除了超时限制，结果取四次运行平均。工具可以运行更久，和保留原始超时的测试便不是完全相同的条件；比较别家的分数前，要先核对时间限制和环境设置。

在多币种例子中，可分别统计补丁能否应用、功能测试是否通过、旧接口回归是否通过、页面交互是否正确，以及工具失败后的恢复能力。假设 20 个构造任务中 15 个通过功能测试、12 个同时通过独立回归，两项分别为 75% 和 60%；这是计分示例，并非模型实测。

## 应用与错例闭环

假设助手完成了币种切换，但把历史订单的原始货币字段覆盖掉。先保存任务、模型版本、仓库状态、提示、工具日志、补丁和测试结果，检查需求是否说明历史记录不可改写、测试是否覆盖旧订单、助手是否真的运行了正确的测试。再确认是需求缺失、误解接口、测试盲区还是执行环境配置错误。

收集不同货币、空值、四舍五入和历史数据迁移的脱敏案例，由开发者写出期望行为；按项目或缺陷来源隔离开发集和独立测试集。先补回归测试并改善工具约束，再根据重复错例决定是否需要新训练数据。每轮检查成功率、误改、授权、工具调用次数和耗时。这是可复现的实验方案，不表示已经进行实际训练或运行评测。

## 比较与面试追问

**M2.1 是重新训练的全新底座吗？** 官方分享描述其在 M2 基础上进一步后训练；具体未公开细节不能推断。

**修复代码为什么要有失败到通过和通过到通过两类测试？** 前者检查目标问题是否得到解决，后者帮助发现修复引起的回归。

**验证智能体评分为什么不能替代人工？** 它可能漏测、误操作或误判评分细则；需结合独立测试和人工抽样。

**CISPO 是 MoE 路由算法吗？** 不是，它是强化学习策略优化方法；MoE 路由决定专家参与，二者处理不同问题。

**模型卡配置 196608 就等于所有 API 都支持这个输入长度吗？** 不等于。部署框架、服务配置和输入输出预算都可能不同。
