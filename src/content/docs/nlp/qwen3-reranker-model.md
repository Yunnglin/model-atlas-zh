## 它解决什么问题

员工问：“试用期能休假吗？”公司知识库先找出三段材料：A 讲试用期请假规则，B 讲转正后的年假，C 讲产品试用活动。三段都有“试用”或“假”，却只有 A 直接回答问题。检索系统如果把 B 和 C 放在前面，后面的问答模型就可能参考错材料。

Qwen3 Reranker 做的是**第二次排序**：把问题和每一份候选文档放在一起，逐对判断相关程度，然后按分数排列。它像一位看过题目后逐篇阅卷的编辑：先把候选交给它，它才能比较；它不负责从整个图书馆中独立找出所有材料，也不负责直接生成答案。

实际系统通常先用 [Qwen3 Embedding](/nlp/qwen3-embedding-model/) 等模型做第一轮召回，再让 Reranker 精排。Embedding 可以提前把每段文档变成向量并建立索引，面对新问题时快速找出一批候选；Reranker 则需要针对问题逐个处理候选，计算更贵，但有机会看清问题与文档之间更细的关系。上面的 A、B、C 是教学例子，实际顺序取决于模型与文本，不是实测结果。

## 结构：问题和候选一起评分

### 从输入到分数

官方模型把任务说明、问题、候选文档拼成一段符合聊天模板的输入。例如任务是“找出能回答员工问题的段落”，问题是“试用期能休假吗”，候选是“试用期间可以按照公司规定申请事假”。这三个部分一起交给 Qwen3 解码器：文本先被分词，再经过多层 Transformer，最后在指定的回答位置预测下一个 token。

此处模型不是写一段长解释，而是比较下一个 token 为 `yes` 和 `no` 的两个原始分数。官方示例从对应位置取出这两个 logits，只在它们之间做 softmax，得到 `yes` 的归一化分数：

`相关性分数 = exp(yes 的 logit) / (exp(yes 的 logit) + exp(no 的 logit))`

例如两个 logit 分别是 2 和 0，计算结果约为 0.88；这只是公式演示，不是模型对假期问题的实测。换一个候选再运行一次，才能比较两个候选。模型卡中的模板、分词器、截断方式与读取位置都应一起遵循：如果把模板改坏、取错位置，得到的数字可能仍然看似合理，排序却已经变差。

分数限制在 0 到 1，并不自动意味着“这段材料有 88% 的概率真实”或“答案正确率是 88%”。它是在这个输入格式下 `yes` 相对 `no` 的模型分数，也不代表在整个词表里生成 `yes` 的原始概率。不同任务、指令、候选分布可能改变分数分布；要设置拒答阈值，需要用业务数据单独校准，不能拿 0.5 当作通用真理。

批量评分时，官方 Transformers 示例使用左侧填充，并读取每条输入最后一个位置的 logits。可以把填充理解成在短材料前面垫空白，让不同长度的输入都在右端对齐：这样最后一个位置仍是每条输入的回答提示末尾。如果自行改成右侧填充，却仍机械地取最后位置，短输入最后可能是填充位置，分数就不再对应预期的回答位置。采用其他填充方式时，要按注意力掩码找到各条输入的有效末尾，并在真实批次中检查。

### 为什么一起看更细，但也更贵

Embedding 通常分别编码问题和文档，文档向量可以提前算好；Reranker 把二者放到同一次模型输入中。比如它可以直接看到问题里的“试用期”与文档里的“转正后”不一致。这里的“交叉编码”说的是问题和候选联合处理，底座仍是 Qwen3 的自回归解码器，不是说它必然用了 BERT 式双向编码器。

论文表 1 给出的 0.6B 规格为 28 层，4B 和 8B 均为 36 层；它们的层数相同不代表参数量相同，因为隐藏宽度等配置也不同。官方 0.6B Transformers 示例为了演示将 `max_length` 设成 8192，而模型报告列出的序列长度为 32K。实际输入可按使用的部署框架、模板和目标长度配置。

如果第一轮给出 100 个候选，就要处理 100 对问题与文档；批处理能改善硬件利用率，但不会让这些输入凭空消失。候选数量、文本长度、模型规格和并发都会影响延迟与资源消耗，尤其长文本的成本可能明显增加。实践中通常比较不同召回数及 0.6B、4B、8B 的效果和速度，而不是默认越大越划算。

32K 是整个输入序列的预算，并不是“文档可以占满 32K，问题和提示另外算”。过长材料会被截断或需要切块；如果“试用期不适用”恰好落在被截掉的末尾，排序结果可能有误。切块也不能太碎，否则否定词、前提和结论被拆开，同样会改变含义。

## 训练：怎样教它判断相关

论文中的基础训练样本可以想成一张卡片：任务说明、一个问题、一段相关材料，以及若干不相关材料。模型使用高质量监督数据进行训练，让相关对更倾向 `yes`，不相关对更倾向 `no`；论文还描述了后续的模型融合阶段。官方没有公开足以完整复现所有训练细节的配方，不能据此推断具体业务数据占比或未经披露的训练参数。

好样本不仅要有明显不相关的材料，还要有“看起来很像、实际上答非所问”的难负例。对假期问题，产品试用活动也许太容易排除；转正后的年假更容易混淆，因为同样讨论员工和休假，却缺少试用期这个关键条件。训练时加入这种区分，能让模型有机会学到比关键词重合更细的关系；是否有效仍需测试，而不是保证所有场景都正确。

训练时，正例使用 `yes` 作为目标 token，负例使用 `no`。论文中的监督目标是在整个词表分布中最大化正确标签的概率；这与上文推理时单独取出 `yes` 和 `no` 两个 logit 进行归一化的过程相联系，但两者的分母不同。比如某个正例的完整词表概率 `p(yes)=0.8`，该位置的负对数损失约为 0.223；若降到 0.2，损失约为 1.609。通过这种示范，模型学习区分相关和不相关的候选。

难负例也要小心误标。另一份文档如果写的是“试用期事假申请办法”，可能同样能回答问题；只因为它不是标注员最初选中的那一段，就把它当负例，会教模型压低真正有用的材料。数据整理时应允许一个问题对应多条相关证据，并复核疑似负例；同一文档的不同切块也可能包含重复答案。

Qwen3 Embedding 与 Reranker 的训练不要混为一谈。官方说明 Embedding 先经历大规模弱监督对比训练，再做监督训练和模型融合；Reranker 则直接使用高质量监督数据训练并进行融合。论文中的海量弱监督数据量属于 Embedding 的训练描述，不能直接说成全部用于 Reranker。若要在自己的领域继续微调，先做小规模人工标注与独立评测，再决定全量训练还是 LoRA 等方式；这是实施建议，并不是声称官方发布模型采用了某个未公开的 LoRA 配置。

## 评测：把召回和重排分开看

假设有十个问题，每题都有一段已标注的正确材料。如果第一轮的前 20 条候选里，八个问题包含正确材料，那么这个简单示例的召回命中率是 8/10。对剩下两个问题，Reranker 再聪明也无法把没收到的材料排上来；此时应先检查文档是否入库、切块是否完整、权限过滤是否正确、召回表达是否匹配。

如果正确材料已经在候选里，再检查它的排名。例如唯一正确材料原来排第 5，经重排后排第 2，其倒数排名从 1/5 变成 1/2。把各问题的倒数排名取平均得到 MRR；如果一个问题有多条相关材料、相关程度不同，也可以用 nDCG 等指标衡量相关内容是否靠前。指标要和标注方式相匹配，不能把单一分数直接当成最终问答正确率。

官方论文采用了一个重要的控制条件：先用 Qwen3-Embedding-0.6B 为每个问题召回前 100 条，再用不同重排器处理同一批候选。论文表 4 中，英文检索集合 MTEB-R 的 0.6B、4B、8B 重排结果分别为 65.80、69.76、69.02；中文检索集合 CMTEB-R 分别为 71.31、75.94、77.45。它们是论文给出的聚合评测结果，不是正确率，也不能直接换算为自家知识库的收益。英文集合中 4B 高于 8B，说明更大模型并非每项都更好；两组结果的任务和条件也不宜混为一谈。

### 重排一定比原来的顺序好吗？

不一定。还是看同一张[论文表 4](https://arxiv.org/html/2506.05176v1)：在 MTEB-Code 这一组代码检索任务中，Qwen3-Embedding-0.6B 的原始排序得分为 75.41，把它的前 100 个候选交给 Qwen3-Reranker-0.6B 后，得分为 73.42；换成 4B 或 8B 重排器则分别为 81.20 和 81.22。

这像是先由图书管理员挑出 100 本书，再请不同阅卷人排序：候选一样，不同阅卷人的专长和失误仍可能改变结果。它提醒我们保留“只召回、不重排”的基线，在目标数据上比较增益与延迟；这组分数不意味着 0.6B 重排器在所有代码任务上都会变差。

这里的代码检索任务使用 **nDCG@10**：它奖励相关文档排得更靠前，再根据理想排序归一化。举个简化例子：某个问题只有一篇相关文档，排第一时得分是 1；如果排第二，约为 `1 / log₂(3) = 0.63`；如果排第五，约为 `1 / log₂(6) = 0.39`。排到前十之外则该题在这个截断范围内得分为 0。多条文档相关或相关程度不同时，计算会汇总各位置的收益后，再除以该题理想排序的收益。这些数字只为解释指标，不是模型实测，也不能直接和 MRR 当作同一个分数。

论文中的 FollowIR、代码检索和长文检索覆盖了不同能力，但单一公开榜单不能代表所有场景。对自己的系统，应固定候选集、分块方式、权限范围、输入模板和版本，分别记录召回覆盖、重排指标、端到端回答质量以及延迟；训练和测试样本还要按文档来源或版本隔离，避免同一政策的近似副本同时进入两边，造成过于乐观的结果。

## 应用：一次错例怎样改

假设重排后“转正后年假”仍排在“试用期假期”之前。先记录问题、候选材料、文档版本、切块内容、模型规格、任务说明与排序分数。接着依次检查：正确段落是否在候选中？是否被截掉了试用期限制？候选是否来自过期版本？标注是否把多个有效段落错判成一正一负？这些问题的处理方法并不相同，直接增加训练数据可能掩盖原因。

如果是切块丢了前提，可以调整切块并重新建立索引；如果正确材料从未召回，可以尝试关键词与向量混合检索；如果材料完整进入候选却反复排错，可以补充试用期与转正等易混淆样本，先验证指令或小规模微调。最后在事先保留的独立样本上复测，同时查看不同部门、文档长度、政策版本和用户权限下的错例，防止只修好一条示例。

这里的重排只判断文本是否适合回答问题，不负责确认政策是否生效。版本、有效期和访问权限应由检索系统或业务规则处理；即便文本排第一，最终回答仍需给出出处，并在证据不足时允许拒答。上述流程是可复现的实验设计，不是已执行的业务训练或线上效果声明。

## 面试追问

**为什么既有 Embedding，还要 Reranker？** 两者分工不同：前者便于预先编码大量文档并快速召回，后者联合读取问题和候选进行细排。后者更贵，而且不能修复召回遗漏。

**它输出的是 yes/no，为什么还能排序？** 实际使用的是两个 token 的归一化分数，而非只看最后生成的文字；分数可以比较同一请求下的候选，但不自然等于真实概率。

**如何判断瓶颈在召回还是重排？** 先看正确材料是否进入固定数量的候选，再看进入后排得如何。只有把这两步分开，才能知道该改索引、切块、召回策略还是重排模型。

**多语言能力是否意味着每种语言一样好？** 不是。官方声称支持百余种语言，但不同语言、领域和文本长度应分别评估；任务指令也要作为配置记录，并对不同写法进行对照。
