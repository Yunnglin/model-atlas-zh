## 要解决什么问题

一个代码助手收到大型仓库中的报错：测试显示订单金额错误，但问题可能散落在计算函数、折扣规则、数据库字段和最近的修改记录里。助手要阅读多份文件，找到证据，提出补丁，再运行测试。任务越来越长时，模型不仅要处理大量输入，还可能生成多轮工具请求与推理内容。

DeepSeek-V4-Pro 是 2026 年发布的开放权重文本模型。官方模型卡列出 1.6T 总参数、每个 token 约 49B 激活参数和 1M token 上下文。这里讲最初的 Pro；[V4-Flash](/nlp/deepseek-v4-flash-model/)和 V4.1 Flash 使用不同配置。仓库情境、代码问题与后文算例均是教学构造，不是实测。

## 结构与数据流

输入经过分词、模型层和输出头，逐 token 生成文字。若需要读取文件或执行测试，模型生成工具请求，由外部应用真正执行并返回结果；文件系统不属于模型内部。下方教学图展示 Pro 的注意力层组织，省略残差、位置编码、层内投影及专家路由细节。[Transformer](/foundations/transformer/)和 [MoE](/foundations/moe/)适合先补基础。

### 不同注意力层如何看历史

报告列出 Pro 共有 61 层：前两层使用 HCA，后续层交替使用 CSA 与 HCA；这些注意力层还有滑动窗口分支。HCA 和 CSA 都在序列维度压缩历史表示：HCA 使用较高压缩比例，CSA 使用较小压缩比例，并借助索引器选取候选条目。局部窗口帮助处理附近的上下文。可以把它想成既参考附近代码，又通过不同粒度的索引寻找较远的项目文件；模型使用的是向量表示，不是人工整理好的目录。

报告中的 Pro 配置，CSA 压缩步长为 4、候选上限 1024，HCA 压缩比例为 128，局部窗口为 128 token。它们不是 1024 个文件或 128 行代码：token 的切分随内容变化。CSA 的压缩表示有相邻块重叠与可学习权重，不能把它简化为互不相干的四词平均。Flash 的前两层和 CSA 候选数量不同，比较时要按型号核对。

如果报错信息在一个文件、真正修复点在另一个文件，索引没有选中相关内容、输入被截断或工具返回过期版本，都可能导致失败。支持百万 token 不保证模型一定准确利用全部输入；压缩、筛选和长程信息位置都需要具体评测。

### 专家路由和缓存是两笔账

Pro 的每个 MoE 层有一个共享专家、384 个路由专家，每个 token 选择六个路由专家。49B 激活参数表示单步参与计算的规模，不表示只需存储 49B 权重。完整专家权重如何分布到设备，以及专家之间的通信，都影响实际部署。专家也不是预先贴上“数据库专家”“前端专家”的小聊天机器人。

报告中每个 Transformer 块都有 MoE，前 3 个 MoE 层采用哈希路由。这个层内路由方式与后训练时分别训练的数学、代码等完整教师模型是两种不同的“专家”，不能按名称混为一谈。

注意力缓存则保存历史信息以便后续复用；它与权重、临时激活及运行框架占用是不同账目。V4 的压缩和稀疏机制可以减少部分长上下文计算与缓存，但索引器、数据搬运和局部窗口仍有成本。论文还使用 mHC 组织受约束的残差信息流；这属于层间表示与训练稳定性的设计，不是额外的工具调用。

## 数据与训练

### 从预训练到长上下文

报告称 V4-Pro 在约 33T token 上预训练，语料涉及网页、数学、代码、多语言和长文档；T 表示万亿 token，而不是文件数量。模型逐步适应更长的输入，最终支持 1M token。训练中还涉及优化器、混合精度和跨设备通信等工程选择；一个总 token 数无法单独解释能力，也不代表每种语言或代码仓库覆盖均衡。

可以构造“订单金额错误”的教学样本：问题描述、相关代码、测试与正确补丁形成一组材料，但它不是官方训练样本。真实数据还应考虑依赖版本、测试隔离、仓库授权和重复内容；若测试集中包含训练仓库的近似题，结果可能高估新项目的表现。

### 后训练：学会遵循任务与反馈

预训练主要学习续写，后训练进一步让模型响应指令并处理交互任务。V4 报告描述专家模型提供任务数据，并在后训练中使用在线策略蒸馏（OPD）；具体流程可理解为学生在自身生成的上下文上接受教师信号，但不能把它简单说成“复制老师每个参数”。[蒸馏](/training/distillation/)和 [SFT](/training/sft/)分别解释相关基础。

报告先为不同领域分别做 SFT 和基于 GRPO 的强化学习，得到独立的领域教师；统一学生再在自己生成的轨迹上对齐这些教师的输出分布。比如遇到代码修复题时，可以由代码领域教师提供相关训练信号。该例是帮助理解教师选择，不表示一项任务只调用一个教师或实际生产路径完全如此。蒸馏阶段使用教师的概率信号，也不等于把所有教师权重直接相加。

更具体地说，学生先按自己的策略生成一段修复轨迹；在这些学生实际走到的上下文位置，训练再比较学生和相关教师对整个词表的预测分布。报告使用以学生分布为前项的反向 KL，并说明采用全词表 logit 蒸馏，而不是只记录学生最终选中的那个词。这样学生不仅能看到教师认可的输出，也能学习教师对其他候选的相对判断；但保留完整分布需要额外计算和数据传输。这个过程发生在训练时，最终使用统一模型时不必为每个回答现场调用所有教师。

对于代码助手，示范轨迹可能包括读文件、修改、运行测试和根据报错修正。工具返回有时失败或不完整；如果训练材料只包含完美轨迹，模型可能不擅长处理依赖安装失败、测试超时等问题。模型生成“测试通过”不等于测试真的运行，应用应保留可核验的工具结果。

报告的后训练还使用量化感知训练：对 MoE 路由专家权重和 CSA 索引器的查询、键路径采用 MXFP4，并让训练适应精度损失。可以把它想成在练习时就用较少刻度的尺子，提前适应测量误差；这不意味着模型所有权重和运算都变成 4 位。实际显存与速度仍取决于所用权重、硬件和推理框架。[量化](/training/quantization/)介绍相关权衡。

## 评测怎么看

官方模型卡在基础模型表中列出 Pro-Base 的 MMLU 5-shot 为 90.1，Flash-Base 为 88.7；两者规模和配置不同，这是官方设置下的知识基准对比，不是企业代码修复成功率。报告同时比较普通和更高推理强度的模式；更多推理预算可能提升部分困难任务表现，也增加输出 token 和延迟。

针对仓库修复，应分开测是否定位正确文件、补丁能否应用、新增测试能否通过、旧功能是否退化，以及是否正确报告失败。假设 20 个虚构任务中 16 个补丁成功应用，但只有 12 个通过独立测试，分别为 80% 和 60%；这只是计分例子。公开测试通过仍可能遗漏边界，应使用隔离环境与隐藏测试，避免模型靠硬编码迎合已知用例。

长上下文评测还应把关键代码或错误日志放在不同位置，插入相似文件和旧提交，检查证据定位与引用是否稳定。效率比较固定检查点、硬件、精度、框架、并发、输入输出长度和缓存状态，分别记录首 token、生成速度、工具耗时与显存。官方图表中的计算或缓存比例并不自动等于每个应用的端到端加速。

报告给了一个便于理解的长上下文比较：在 1M token 条件下，Pro 单步生成的等效 FP8 计算量约为 V3.2 的 **27%**，KV 缓存约为其 **10%**。把它想成一本很长的资料册：压缩和筛选让模型每次翻阅的计算与缓存账目变小，但索引、专家计算、网络通信和工具执行仍要花时间。这是报告所列条件下的计算与缓存比较，不等于回答速度必然提升到原来的 3.7 倍，也不是模型质量相同的证明。

## 应用与错例

假设助手修复了订单金额，却误改了税费计算。先保存用户任务、仓库版本、模型提示、读取过的文件、补丁和测试日志；检查是检索遗漏、需求误解、依赖不一致，还是测试覆盖不够。若工具没运行或失败，先修环境并重新验证；若测试本身没覆盖税费边界，单纯重试模型也不能发现问题。

下一轮按仓库和提交来源区分开发集与独立测试集，补充相似字段、空值、金额精度和旧功能回归。比较改提示、检索或训练后的通过率、误改率、耗时和调用次数，同时保留未调整的基线。这个流程是复现实验设计，尚未执行模型训练或评测。

## 比较与面试追问

**Pro 和 Flash 使用相同层数吗？** 不同。报告列出 Pro 61 层、前两层 HCA；Flash 43 层、前两层纯滑动窗口，CSA 候选数量也不同。

**49B 激活参数代表部署只需要 49B 权重吗？** 不代表。专家权重仍需保存或按部署策略调入，还要计算缓存与通信。

**百万 token 上下文能保证修好大型仓库吗？** 不能。输入是否完整、证据筛选、工具权限、测试质量和模型推理都影响结果。

**为什么需要同时看成本和成功率？** 高推理强度或多次尝试可能提高某些任务的成功率，但也会增加耗时和 token；比较必须固定预算或一并报告成本。
