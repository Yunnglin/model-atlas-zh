## 要解决什么问题

你给同事一份程序，请他实现“找到订单中金额最大的商品”。他不光要认识编程语言，还要理解已有的数据结构、空列表如何处理，以及金额相同时需要返回什么。要是项目有自己的类型、依赖和测试，他还得看周围的代码。代码模型面对的也是类似问题：它输出的是文本，但使用者关心的是程序能否在特定环境中正确运行。

DeepSeek-Coder-V2 是 2024 年提出的代码模型系列。它从 [DeepSeek-V2](/nlp/deepseek-v2-model/) 的中间训练检查点出发，继续学习大量代码、数学和自然语言，再通过后训练提升指令遵循与编程能力。系列包含较大的模型和 Lite 模型；Base 是继续预训练后的底座，Instruct 是经过指令等后训练的版本。选择时不要把它们的能力、大小或评测成绩混为一谈。

例如，给模型 `def max_price(items):` 和一条需求，它可以续写函数体；但输出正确与否仍需检查空输入、异常类型和项目接口。模型没有凭一句话自动读取仓库，也不会因为生成代码就天然执行了测试。以下例子均为教学构造。

## 结构与数据流

把指令、函数签名和允许的代码上下文整理成输入后，模型将其拆成 token。它利用先前 token 的信息，逐步预测下一个 token，直到输出结束。它不是先在脑中画出完整程序再一次性打印；生成过程中也可能写出语法正确但逻辑错误的实现。[Transformer](/foundations/transformer/) 和 [注意力机制](/foundations/attention/) 解释这种信息传递的基础。

模型采用 DeepSeek-V2 家族的解码器结构，包括多头潜在注意力 MLA 与混合专家网络 MoE。MLA 用压缩表示组织注意力缓存；MoE 将前馈计算分给不同专家，由路由机制为输入选择参与的专家。可以把专家想成分工不同的工作台，但“专家”是训练出来的网络，并不保证一个专门负责 Python、另一个专门负责 SQL。

大模型总参数约 236B，每个 token 激活约 21B；Lite 约 16B，总激活约 2.4B。激活量有助于理解单次计算，但部署通常还要保存或调度整套权重，不能以 21B 或 2.4B 直接估算全部显存。批量、精度、缓存长度、专家分布与硬件之间的通信都会影响真实成本。模型的 128K 上下文上限也不是免费空间：更长输入会增加缓存与计算，还可能让关键文件淹没在无关内容中。

配图把外部测试画在模型右侧，是为了强调执行器是额外系统。代码能否读写文件、访问网络、安装包或使用密钥，取决于执行环境的权限，并非模型结构的一部分。实际运行不可信代码时应隔离环境、限制资源，并保护测试答案与私有数据。

### 从续写到中间补全

普通续写像在文章末尾接着写；中间补全则更像填空：已知函数前面的定义和后面的调用，补上中间缺失的实现。假设前缀定义 `def add_tax(price, rate):`，后缀是调用和打印结果，中间要补 `return price * (1 + rate)`。模型需要同时考虑两侧内容，而不仅仅看光标前面的代码。

论文在继续预训练中对 16B Lite 同时使用下一 token 预测和 PSM 格式的 FIM，FIM 比例为 50%；236B 的预训练目标则只使用下一 token 预测。论文还在 16B 的指令微调中加入 FIM，以保留补全能力。具体使用时要按对应模型卡和接口的格式提供前缀、后缀及特殊标记；不要把教学示例当作官方原始训练样本。

PSM 就是先摆放前缀（Prefix）、再摆后缀（Suffix），最后才让模型写中间内容（Middle）。在上面的税价例子中，函数签名和后续调用已经出现在输入里，生成时模型只需要补缺口；它看到后缀是因为后缀被提前放入输入，并不是打破了自回归的注意力规则。

## 数据与训练

### 先有通用底座，再持续学习代码

论文从已经看到约 4.2 万亿 token 的 DeepSeek-V2 中间检查点出发，继续训练约 6 万亿 token，合计约 10.2 万亿 token。继续训练的数据配比约为代码 60%、数学 10%、自然语言 30%。这里的 token 是训练中使用的计量单位，不等于独立网页、项目或用户人数；重复采样也可能计入训练使用量。

为什么不是全部换成代码？代码任务依赖自然语言理解、数学推理以及对用户要求的判断；保留多种材料有助于维持这些能力。代码数据质量同样关键：重复仓库、自动生成文件、错误示例、许可和隐私信息都可能影响最终效果。公开报告提供训练方法和规模，但不等于公开了每个训练样本，因此不能凭空列出某个仓库一定在训练集中。

论文称训练数据覆盖 338 种编程语言。这说明材料涉及的语言范围，并不保证每种语言的数据量、质量或模型能力相同；遇到冷门语言和项目特定框架，仍要用自己的测试衡量。模型支持长上下文，也不代表它对上下文中每个位置都能同样准确地检索和推理。

报告提到，收集得到的代码相关语料约为 1,170B token，也就是约 **1.17 万亿**；这描述的是语料规模。后续训练时按比例混合和采样，报告的 6 万亿 token 是继续训练的使用量，两者不是同一个统计口径。

上下文长度的扩展也分阶段：论文先使用 32K 长度训练 1,000 步，每批 1,152 条序列；再使用 128K 长度训练 1,000 步，每批 288 条，并提高长文本数据的比例。这里的 128K 指模型可处理的上下文预算；在真实项目中，检索到正确的文件和保持输入质量仍同样重要。

### 指令微调和强化学习各做什么

预训练更像让模型读大量材料并学习续写；监督微调（SFT）给它看“需求—合适回答”的示例，帮助它按任务要求组织输出。例如同样是排序代码，用户要求解释复杂度时需要文字和代码，要求只输出函数时则应遵守格式。SFT 示例的覆盖与质量会影响结果，示范答案本身有错也会误导模型。

论文还描述使用 GRPO 做推理相关的强化学习。对于同一道题，可以让模型产生一组候选，用奖励信号比较候选的相对好坏，再调整生成策略；这种组内比较避免了单独训练传统价值模型的做法。它不是只靠模型自己说“我对了”，奖励的可靠性依赖训练流程和数据。

尤其要分清代码执行和奖励模型：论文描述利用编译器反馈构造代码偏好数据，并训练推理奖励模型，随后用该奖励模型提供反馈。它不同于简单宣称“每次生成都直接用隐藏测试的通过数作为奖励”。奖励模型也可能偏爱看起来合理但实际错误的程序，所以仍需要独立执行测试。参考 [GRPO 解释](/training/grpo/) 时，应注意不同后续模型可能使用不同奖励设计。

## 评测怎么看

代码评测不能只看生成文本像不像标准答案：两个不同实现可能都正确，而看着整洁的实现也可能把边界条件写错。HumanEval 给定函数描述和签名，让模型生成实现，再执行测试；常见指标 pass@1 关注一次采样得到的候选是否通过。其数值取决于测试、提示、采样和模型版本，不等同于真实工程任务的成功率。

在论文所述零样本设置中，使用贪心解码，236B Instruct 的 HumanEval Python 为 90.2%，16B Lite Instruct 为 81.1%。这是论文的特定实验结果，不是说它们能修复所有项目中相应比例的缺陷。其他基准、语言、提示模板或采样次数下，结果可能不同；比较模型前应确认是否使用同一测试集和执行协议。

中间补全还有专门的单行测试。论文表 6 中，16B Lite Base 在 Python、Java、JavaScript 上的行级完全匹配分别为 80.0%、89.1%、87.2%；评测只取生成结果中第一行，并按论文定义比较文本。它适合观察补全习惯；对于有多种等价写法的代码，还可以配合执行测试检查功能。

仓库补全实验采用的是另一套协议：论文在 RepoBench v1.1 选取 2023 年 12 月数据，考察不同上下文长度及跨文件排列，只生成最多 64 个新 token，并选取第一个非空、非注释行计算完全匹配。这更接近“补出下一行”的能力，不能拿来等同于多轮修改仓库或让工具自动修复问题。该时间筛选降低了已知数据重合风险，也无法证明不存在任何语义相似内容。

再看一个构造示例：让模型实现取最大金额，公开示例只有两个正数，它返回正确答案；隐藏测试加入空列表、负数、相同金额和小数精度。假设十个独立任务中六个通过全部测试，教学算例的通过率是 60%，不是该模型的实测成绩。应保留每道题的测试代码、依赖版本、超时设置和失败日志，才能复核结果。

仓库级任务更复杂：补丁是否能应用、原有测试是否仍通过、是否破坏接口、是否引入安全问题，都要分别评估。模型看到的文件范围、能否调用工具、允许尝试几次以及总时间预算也要固定；不能将允许多次运行和修复的系统，与一次生成的模型直接比较。注意测试泄漏：同仓库的相似题若同时出现在调参和测试中，分数会虚高。

## 应用与错例闭环

假设一个客服系统需要从订单列表计算最高价格。先给模型最小必要上下文：数据结构、空列表处理约定、类型要求和现有函数签名；把私有代码发给外部服务前，还要确认数据使用与权限。让模型输出补丁后，在隔离环境运行格式检查、单元测试和项目测试，由人检查关键逻辑。

如果空列表时报错，先分类原因：需求没有规定返回值、上下文漏掉项目约定，还是模型忽略了明确要求？保存输入、模型版本、生成参数、补丁及测试日志，再补充边界样本。若问题来自需求缺失，应先改善任务描述；若模型稳定忽视明确要求，可考虑收集高质量示例并进行适当微调。

数据应按项目或任务来源划分开发集与独立测试集，而不是把同一仓库的近似代码随机拆到两边。改动后同时检查目标错例、其他语言与普通功能是否退化，并记录调用次数、延迟及硬件成本。这里是可复现的实验设计，不代表已经实际训练、部署或评测。

## 比较与面试追问

**Coder-V2 和通用 V2 是什么关系？** 它从 V2 的中间检查点继续训练，增加代码和数学相关学习；两者不能看成完全独立从零训练的架构。

**MoE 激活 21B，是否只需加载 21B 权重？** 不能这样估算。每次选择部分专家参与计算，但部署要考虑完整权重、缓存、路由和通信。

**HumanEval 高分能证明仓库修复能力吗？** 不能。函数题与多文件修改需要的信息、工具和验证方式不同；评测协议也必须对齐。

**GRPO 和代码测试是什么关系？** GRPO 是优化方式；如何得到奖励是另一层设计。该论文使用执行反馈构造偏好数据训练奖励模型，不能笼统等同于所有代码任务都直接使用规则奖励。

### 多次尝试的覆盖率不是单次成功率

另一项 [Large Language Monkeys 研究](https://arxiv.org/abs/2407.21787)用 DeepSeek-Coder-V2-Instruct 和 Moatless Tools 处理 SWE-bench Lite：报告中的单次尝试覆盖率是 15.9%；每题允许 250 次独立尝试时，至少有一次成功的覆盖率为 56%。一次尝试本身是一条模型与工具交互的多轮轨迹。两个数字使用的采样预算不同，56% 不能写成“单次成功率”；比较时还要记录工具、测试、计算成本及最终如何选出正确候选。能生成正确方案，不代表系统一定能在真实使用中可靠识别它。
