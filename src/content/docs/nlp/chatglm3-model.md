## 要解决什么问题

假设你问助手：“上海今天多少度，适合穿什么？”模型可以理解问题并写出自然语言，但当前天气是外部变化的信息。一个完整应用要把问题交给模型，识别它请求的天气查询，调用允许使用的工具，再把真实返回送回模型，让模型组织答案。

[ChatGLM2](/nlp/chatglm2-model/)已经提供中英文对话和多查询注意力；ChatGLM3 在此基础上发布了新的模型权重和对话格式，官方示例展示工具调用与代码执行。模型负责生成请求和后续回答，应用程序负责检查参数、执行工具并记录结果。

## 结构与数据流

官方 [ChatGLM3-6B 配置](https://huggingface.co/zai-org/chatglm3-6b/blob/main/config.json)列出 28 层、4096 维隐藏表示、32 个查询头、2 组键值头和 8192 的配置长度。输入文字和角色标记经过分词，进入多层语言模型，再按已有内容逐步预测后续 token。

生成时缓存历史键和值，下一步不必从头重新生成所有历史。按一个请求、8192 token、BF16 缓存估算，28 层两组 128 维键值头需要 `28 × 2 × 2 × 128 × 8192 × 2` 字节，约 **224 MiB**。这个数只计算键值缓存，模型权重和运行时工作区还要单独计入；实际实现也可能采用不同格式或缓存布局。

这个缓存数字从哪来？32 个查询头共用 2 组键值头，平均每 16 个查询头共享一组。假设其他条件不变、改成 32 个独立键值头，同样的算式会得到约 3584 MiB；两者相差 16 倍。这是按配置做的存储量对照，不是在同一设备上测出的延迟，也不包含权重、计算工作区和并发请求。实际输入只有 4096 token 时，在上述假设下缓存估算约为 112 MiB，说明对长对话而言缓存会随已保存 token 数增长。

同一个模型既能输出普通文字，也能输出带角色和工具名称的消息。是否将消息解释成工具请求，是由应用和模型使用的模板共同决定的。模型本身不自带天气服务器、网络权限或 Python 执行器；这些能力需要外部环境连接。

### 一次工具调用怎样走完

官方[提示格式说明](https://github.com/zai-org/ChatGLM3/blob/main/PROMPT_en.md)使用 `<|system|>`、`<|user|>`、`<|assistant|>` 和 `<|observation|>` 等角色标记。工具定义与用户问题进入上下文后，模型可以输出一条带工具名称和参数的助手消息；外部程序运行工具，将结果包装成 observation，再让模型继续输出。

以天气查询为例：用户问“北京今天多少度”，模型请求 `get_current_weather` 并给出地点；工具返回温度 22 摄氏度，应用把这个返回作为观察结果交回；模型再说“查询结果是 22 摄氏度”。这个过程里，生成工具请求和真正收到工具结果是两件不同的动作。

如果模型把地点写错成上海，即使工具成功返回数据，最终答案仍可能答错。调试时应分别记录输入问题、工具名称、参数、执行状态、返回内容和最终回答，才能分清是模型选错工具、参数错误、外部服务失败，还是模型读错结果。

官方格式中，工具名称跟在助手角色标记后面，工具的返回则放在 observation 消息里。可以把这看成一张交接单：助手先写“请查北京天气”，执行器填写“查到 22 摄氏度”，助手再依据结果答复。这个例子里的天气数值是用来说明消息流转的，并非实际查询结果；不同框架的封装方式可能不同，接入时应核对对应模板和解析器。

### 为什么模板不能只看成装饰

一条多轮对话可以包含系统指令、用户问题、助手回答和工具观察。角色标记帮助模型区分每段内容的来源，工具名称告诉应用应该处理什么请求。若把 observation 误当作用户新问题，或者丢掉前面工具定义，模型收到的上下文会改变，后续行为也可能变化。

实际应用可以先从一个简单任务开始：给出两条数字，让模型请求计算工具求和；执行器检查参数后计算，再将结果交回。然后加入工具超时、参数缺失和多个候选工具等情况，检查模型是否能根据真实返回继续处理，而不是只看一次顺利演示。

## 数据与训练

官方模型卡介绍 ChatGLM3 基础模型使用更多样的数据、更充分的训练步数和训练策略；公开说明没有给出可以完整复现所有语料与后训练的明细。理解这类模型可将训练分成两个问题：基础模型怎样从大量文本学习预测后续内容，对话模型又怎样学会按角色、任务和工具格式回应。

官方后来的技术报告说明，ChatGLM2 和 ChatGLM3 两代都从头进行预训练。因此，“三代在二代基础上改进”说的是技术路线和能力的延续，不能理解为三代一定从二代权重继续训练。相比之下，对话模型如何将工具样本混入训练、各类样本的比例，公开资料没有给出完整配方。

[下一 token 预测](/foundations/next-token/)提供一种理解方式：在对话样本中，模型看到系统说明、用户问题和回答前缀，预测后面的目标 token。监督数据可以包含普通回答，也可以包含工具请求与工具结果之后的继续回答。不同训练框架会定义哪些角色位置参与损失计算；工具返回通常由外部环境提供，需要在数据中保留正确角色和边界。

给自己的应用准备样本时，一条完整记录可以包括用户任务、可用工具定义、模型请求、实际工具返回和最终答案。例如天气接口返回错误时，示范应展示如何说明查询失败或请求重试；如果只保留最终的“查询成功”，模型很难从数据中学习错误处理。

长文本也需要区分版本。官方仓库列出默认对话和 Base 为 8K，另外提供 32K 与 128K 的长文本对话检查点。切换检查点后，推理模板、可接受的输入长度和设备资源应配合对应版本设置；做对照时记录权重与输入长度，方便解释结果。

## 评测：基础模型与工具系统分别测什么

官方仓库给出 ChatGLM3-6B-Base 在 GSM8K、MATH、BBH、MMLU、C-Eval 等数据集的结果。例如 Base 的 MMLU 为 **61.4**、C-Eval 为 **69.0**；仓库说明选择题采用 zero-shot，数学任务采用 zero-shot CoT，BBH 使用 3-shot。这些是该 Base 检查点及其提示方式下的结果。

官方还比较两个长文本模型在 LongBench 上的表现：ChatGLM2-6B-32K 的平均结果为 **41.5**，ChatGLM3-6B-32K 为 **50.2**。这两行对应的都是 32K 版本，表中还分摘要、单文档问答、多文档问答等类别。平均分有助于观察整体变化，分项可以帮助发现改善主要发生在哪里。

进一步看分项，官方表中单文档问答由二代的 37.6 变为三代的 45.8，多文档问答由 34.7 变为 46.1。这能帮助定位两代长文本模型在该评测中的变化。实际用于阅读合同或论文时，还可以把答案证据放在开头、中间和末尾，检查模型是否找到正确段落，并测试多份文档中存在相似数字时能否区分来源。

工具调用要设计另一套评测：题目需要列出可用工具、正确参数和允许访问的环境。先看模型是否选择合适工具，再验证参数、工具是否成功执行、最终回答是否忠实使用结果。相同模型换了工具定义、提示或超时限制，完成率也可能变化，所以报告时应记录这些条件。

## 应用与错例

天气助手若回答了错误城市的温度，可以先查看模型生成的城市参数；若参数正确、工具实际返回了另一个城市的数据，就检查执行器和接口；若返回正确而最终答案写错，则重点检查模型处理 observation 的过程。这三个问题需要不同修复方案。

对高频错例可以添加参数校验、完善工具描述，或构建包含错误反馈的训练样本。独立测试集应保留没有参与调整的新问题，并覆盖城市同名、日期缺失、接口超时和无查询权限等情况。除了最终正确率，也应记录工具调用次数和等待时间，观察一次改动是否让系统变得更慢。

## 比较与面试追问

**ChatGLM3 输出工具请求就等于工具运行了吗？** 还需要外部程序解析请求、检查权限、执行并返回 observation。

**ChatGLM3 和 ChatGLM2 的 6B 都使用两组键值头吗？** 这两个官方配置都列出 32 个查询头和 2 组键值头；其他检查点应按自己的配置理解。

**8K、32K 与 128K 是同一份默认权重的不同叫法吗？** 官方分别列出不同检查点。比较长文本任务时，记录使用的版本、输入长度和实际评测设置。
