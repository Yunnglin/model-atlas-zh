## 模型卡：先认识它

| 项目       | Kimi K2 Thinking                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 发布时间   | 2025 年 11 月，属于 Kimi K2 系列后续的推理与工具使用版本                                                    |
| 类型与模态 | 文本语言模型；接收文字和工具定义，生成回答或工具请求；实际工具由外部执行器提供                              |

## 它解决什么问题？

让助手修复一个 CSV 导入错误，并不是让它只写一个函数。它可能要先看报错、检查文件格式、找出读取代码、修改实现、运行测试，再根据新错误调整。每次操作都要等待程序或用户返回结果，而下一步又依赖上一步的结果。

Kimi K2 Thinking 面向这样需要多步推理和工具交互的任务。它在回答过程中可以交错产生思考内容和工具请求，再把工具返回的信息纳入后续生成。可以把它看成一位能边查资料边改方案的助手：它提出“下一步查什么”，真正的浏览、读取或执行由外部程序完成。模型生成了一个调用请求，不代表工具已经运行，也不代表目标已经完成。

这里介绍的是 2025 年 11 月的 K2 Thinking 权重，而不是 7 月发布的 [Kimi K2 Instruct](/nlp/kimi-k2/) 或之后的 [Kimi K2.5](/omni/kimi-k25-model/)。后面使用的 CSV 问题、工具结果和数字都是教学例子，没有实际运行这个模型。

## 结构：MoE、MLA 与工具各管什么

模型仍是按前文逐步生成 token 的语言模型。输入的用户请求、工具说明以及已返回结果，经过词嵌入和一系列网络层，得到下一个 token 的分布。系统不断生成，直到产生工具调用、最终回答或达到配置的停止条件。[Transformer](/foundations/transformer/)和[下一 token 预测](/foundations/next-token/)可先帮助理解这个基本过程。

![Kimi K2 Thinking 主干示意：61 层中的首层使用稠密前馈，其余 60 层使用混合专家；各层结合 MLA 注意力。](/figures/kimi-k2-thinking/backbone.svg)

这张图把模型卡中的语言主干整理成一条路线：文本和工具返回先进入词嵌入，经过 61 层后，模型为下一个 token 打分。每层都处理注意力和前馈计算；首层的前馈是稠密网络，后面 60 层使用专家网络。工具请求是否真正执行，则取决于外部程序。图示依据是[官方配置](https://huggingface.co/moonshotai/Kimi-K2-Thinking/blob/main/config.json)。

### 每个 token 并非经过全部专家

混合专家可以类比一间有很多工位的加工厂。模型卡列出每个相关层有 384 个路由专家；处理某个 token 时，路由器选其中 8 个参与，还有共享专家。这里的专家是可训练的前馈网络模块，不是人手指定的“搜索专家”“Python 专家”；同一个输入在不同层也可能选择不同模块。

1T 是整个模型的参数规模，约 32B 是每个 token 激活的参数规模，两者不是一个意思。每次只用部分专家可以减少单次计算，但部署通常仍需保存或提供全部可能被选中的权重。显存、专家并行、通信和推理框架决定实际设备需求，不能简单以 32B 权重预算部署整个模型。

### MLA 和长上下文

模型卡把注意力机制列为 MLA，也就是多头潜在注意力。可以先把它理解为对历史信息的表示与缓存做整理，帮助模型在生成时访问先前上下文；它和决定哪些专家参与计算的 MoE 解决的是不同问题。关于低秩压缩和位置处理，可进一步读 [DeepSeek-V2 的 MLA 解释](/nlp/deepseek-v2-model/) 与 [MoE](/foundations/moe/)。

256K 上下文意味着模型配置允许容纳很长的序列，不意味着所有服务都提供相同上限，也不等于模型一定能准确利用其中每一处信息。一次修复任务中，源代码、工具说明、测试输出和模型生成内容都会占用空间；如果后面的工具输出挤掉了早先需求，模型可能基于不完整材料继续修改。记录实际输入和截断情况，比只看宣传中的最大窗口更有用。

### 工具执行在模型之外

假设模型提出读取 `import.csv` 的请求，应用先校验参数与权限，再由执行器读取文件，最后把结果放回对话。模型看到“首行是字段名”后提出修改；执行器应用补丁、运行测试，并返回测试通过或报错。模型根据结果继续，直到给出结论。调用格式、工具允许的路径、执行超时和网络权限都由应用配置，不随权重自动出现。

官方模型卡说明 Thinking 沿用 K2 Instruct 的工具调用设置，需要在请求中提供可用工具定义。具体框架如何串接调用仍有区别：有的会保留每次返回，有的会压缩或隐藏旧结果。工具失败、执行器故障、权限不足和模型逻辑错误要分别记录，不能看到最终失败就断定模型不会编程。

## 与 K2 Instruct 有什么区别？

K2 Instruct 侧重指令与工具使用，K2 Thinking 则更强调生成较长的推理过程，并在其中继续调用工具。它们共享相近的 K2 系列骨干配置，但两个检查点、后训练目标和推理预算不同。官方模型卡给 Thinking 列出的上下文为 256K；原始 K2 Instruct 配置的上下文长度与具体更新版本应分别查看，不能把一个数字套给所有 K2 权重。

这也不表示 Thinking 在任何问题上都值得用更长的预算。一个日期格式转换可能很快能完成；大型代码修复可能需要多轮检查。让模型多写推理会消耗 token，推理文字本身也可能包含错误：它写了“测试已通过”，仍需查看工具真正返回的退出状态。要选择是否使用更长推理，应在任务成功率、成本、响应时间和错误类型之间做比较。

官方模型卡把 Thinking 描述为在思考与函数调用之间交错训练的模型，但没有完整列出所有新增训练数据、任务占比和超参数。原始 K2 报告里的预训练和智能体数据构造有助于理解家族背景，不能直接当成 Thinking 逐阶段训练配方，更不能把没有公开的奖励公式写成事实。

## 训练：数据、反馈与 INT4

原始 K2 技术报告介绍了大规模预训练和面向工具使用的后训练。把网页、代码或对话变成下一 token 训练样本，是学习通用语言和代码能力的一类方式；后续的工具轨迹则能让模型练习“观察结果，再决定下一步”。[SFT](/training/sft/)解释示范轨迹如何提供监督，[RLVR](/training/rlvr/)解释可验证结果怎样提供奖励。这些是理解训练方法的入口，不代表官方已公布 Thinking 每个阶段的实现细节。

一条教学轨迹可能从“导入时金额字段异常”开始，包含读取文件、检查分隔符、修改解析器和运行多种测试。好的训练材料不能只保存一个最终“通过”，还应保留实际命令、返回值和需求：文件路径错了、依赖安装失败、断言本身错误，反馈原因并不一样。如果只检查一种 CSV，模型可能学到绕过样例的方法，而不是稳健地处理带引号的逗号、空行和缺失字段。

Thinking 的另一个公开特点是原生 INT4。官方说明在后训练阶段对 MoE 组件使用量化感知训练，并将其权重以 INT4 方式量化。通俗地说，训练时就考虑低精度表示可能带来的误差，使部署时更容易用低位权重计算；不是简单地把整个模型的所有数都变成四位整数。注意力、激活、缓存以及其他组件仍有各自的数据类型和开销，具体要看实际实现。[量化](/training/quantization/)有一个舍入与裁剪的直观例子。

[官方配置文件](https://huggingface.co/moonshotai/Kimi-K2-Thinking/blob/main/config.json)给出的量化配置以 32 个权重为一组、采用对称 INT4；它同时把注意力、共享专家和输出头等模块列入排除项。KV Cache 的量化配置为空，因此查看显存时还要分别考虑注意力缓存和未量化的模块。这里的 32 是量化分组大小，不是每次选中的专家数：路由专家仍按模型卡中的 8 个来选。

官方报告在其低延迟设置下约两倍的生成加速，并称性能损失可忽略；这属于对应硬件、内核和测试条件下的报告，不是任意显卡、批量或任务都会无损加速。模型卡指出评测以 INT4 精度报告；比较其他模型时也要记录精度、服务框架和硬件。把量化权重转换成较高精度格式，不会自动找回量化前被舍入掉的信息。

## 评测：把工具和预算一起看

模型卡在 HLE 文本题上报告：无工具设置为 **23.9**，使用搜索、代码解释器和网页浏览工具时为 **44.9**。两者面对的工具权限和推理过程不同，不能把差距单独归因于模型权重，也不能把 44.9 当成所有开放问题的正确率。HLE 带工具评测中，官方说明最多 120 步，并使用指定的评审模型；搜索结果质量、浏览可用性和判分提示都会影响最终成绩。

评测环境里的访问范围也会改变结果。官方发现，允许浏览 Hugging Face 可能让模型接触到部分基准内容，因此正式比较时阻止访问该站点；不阻止访问时，报告的 HLE 结果是 51.3。这个对照提醒我们：搜索工具能帮模型查证，但如果它能直接找到测试题或答案，就无法只凭最终分数判断模型对新问题的解决能力。自己的测试应记录哪些网站可访问，并检查答案来源。

同一模型卡的 BrowseComp 带工具结果为 **60.2**，SWE-bench Verified 带工具结果为 **71.3**。前者更关注检索和综合公开信息，后者测试软件问题修复；指标、任务和执行环境不同，不能拿两个数字相减判断哪种能力更强。模型卡说明，除 Terminal-Bench 外的代码任务使用团队自建、基于 SWE-agent 改造的评测脚手架，并对 5 次独立运行取平均；不能把 SWE-bench 的这一实现描述成直接使用官方脚手架。这个结果也不等于每个真实仓库有同样的修复概率。

评测细节还包括采样温度和预算：官方说多数测试采用温度 1.0、256K 上下文；无工具的 AIME 与 HMMT 采用 32 次结果的平均值。模型卡还分别列出不同任务的思考 token 上限，所报告的基准成绩使用 INT4 精度。报告中的 Heavy Mode 会并行生成多条轨迹后再综合结果；它和单条轨迹使用的计算量不同，不能只看分数而不看预算。

官方还说明，当多次工具输出使输入超过上下文限制时，其评测采用隐藏此前工具输出的管理策略；网页聊天模式则可能只开放部分工具并减少调用步数。换一套工具、搜索服务或上下文管理方式，结果可能明显不同。因此实际选择模型时，除了总分，还要记录工具权限、每次尝试的 token、轮次、耗时和失败原因。

## 应用：从错例回到改进

假设助手改完 CSV 解析器后显示“全部测试通过”，但上线样本中带引号的逗号仍被拆成两列。首先保存经授权的输入、模型版本、工具调用、补丁与测试结果；检查是否没有运行相关测试、测试覆盖不足，还是模型修改了错误的位置。模型说了什么和执行器实际返回什么应分别记录。

接下来补充覆盖引号、空文件、缺失列和异常编码的样例，按来源或项目划分开发集与独立测试集，避免只是记住某个文件。可以先改善任务说明和测试覆盖，再比较是否需要更多示范或训练；更新后分别观察功能正确率、旧行为是否退化、工具调用成本与权限违规。上述步骤是可复现的教学方案，不是已经执行的实验。

## 面试追问

**K2 Thinking 的 32B 激活参数，是否意味着只需要加载 32B 权重？** 不一定。不同 token 可能选到不同专家，系统通常要提供完整专家权重，还要考虑缓存和通信。

**长推理与工具调用是一回事吗？** 不是。前者是模型生成中间推理内容，后者是外部执行器实际运行某个工具；二者可以交错，也都可能出错。

**INT4 是否表示整个模型的激活、缓存和权重都是 4 位？** 不能这样推断。模型卡描述的是对 MoE 组件的权重量化，其他部分及计算精度需看实现。

**官方 HLE 带工具分数能直接代表单模型的无工具能力吗？** 不能。工具、搜索、评审和预算都是评测系统的一部分，应连同分数一起报告。
