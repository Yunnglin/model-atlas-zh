## 要解决什么问题

客服收到“我被扣了两次款”，系统需要决定交给账单、技术还是账户团队。让模型先写一篇解释，再从里面提取标签，多了格式解析和解释歧义。TypeSafe Jev 的目标是直接给程序可用的类型化判断与概率。

下面的工单、概率与评分都是教学构造，没有调用 Jev。它与基于 Qwen 的 OmniJev 是不同项目；公开说明未披露的内部结构，不从名字推断。

## 结构与数据流

先准备 state，也就是当前可见材料：工单文字、交易记录摘要和有关规则。再定义问题及允许的答案，模型返回对应结果，应用代码决定如何处理。当前官方说明中的 Jev 接收文字、JSON 和文字数组，不能据 System One 的名称认为它已经支持音视频。

可以类比给一位分诊员一张事先设计的表格。表格约束了答什么，是否看懂材料仍要训练与验证；写得整齐不会让判断自动正确。

### 一次分流判断包含哪些参与者

假设用户说“同一笔订单扣了两次”。应用先从业务系统读取订单和交易记录，将可用信息整理为 state，并说明哪些记录缺失；然后提出“是否出现重复扣款”等具体命题。模型返回概率与类型化结果，应用再结合确定性的订单规则、阈值和人工复核策略做下一步。模型的输入只是应用交给它的信息，系统没有提供的交易记录不会自动出现在答案里。

可以把这条流程分成三层：**事实准备**决定有没有足够证据，**模型判断**负责解释有限问题，**应用处置**决定发送给谁以及是否执行后续操作。若账单数据库提供了错误记录，就算模型忠实理解也可能得出错误结论；若模型概率符合协议，但应用对所有请求一律自动退款，业务规则依然可能造成错误。结构化返回减少了自由文本解析的歧义，不保证上下文、标签或行为本身正确。

### 内部结构公开到什么程度

官方把 Jev 描述为对 state 和预定义问题输出类型化判断的模型，并说明其训练面向概率校准；这些信息有助于理解接口契约，却不足以画出可信的内部 Transformer 层图。[社区文章](https://zhuanlan.zhihu.com/p/2095524421255557442)用 API 行为讨论了可能的模型形态，但也包含推断。诸如底层一定采用某种因果掩码、选项在网络中具体如何排列、概率究竟从哪一层读出，都不能当作已证实事实。

可以对**外部数据流**画教学图：输入材料 → 问题定义 → 结构化预测 → 应用规则与人工复核；图中的方框是职责边界，不代表官方内部网络模块。将接口行为、厂商公开说法、第三方假设分别标出来，比用一张看似完整的网络图掩盖未知更适合学习。

### 三种答题纸，不是三种聊天措辞

| 类型   | 教学问题                       | 怎样理解输出                       |
| ------ | ------------------------------ | ---------------------------------- |
| Choice | 账单、技术、账户，交给谁？     | 在已定义候选里作选择，读取对应概率 |
| Noul   | 这条消息是否提出退款请求？     | 对一个真假命题给概率               |
| Score  | 客户情绪是平静、着急还是愤怒？ | 在有顺序的尺度上评分，不是无序类别 |

“提到了退款”和“符合退款政策”是不同问题。客户说“我不想退款，只问一下”，关键词出现不代表提出申请。给程序的候选和命题定义，和输入事实一样重要。精确输出字段以各类型接口为准，不把示意表当真实响应格式。

Score 的输出可以落在两个等级之间。按照官方的定义，如果三个等级编号为 0、1、2，模型分别给出 0.2、0.6、0.2 的概率，分数就是 $0\times0.2+1\times0.6+2\times0.2=1$。这个分数是等级编号的概率加权平均，不是 100% 确信第二档正确；另一组概率 0.5、0、0.5 也会得到 1。使用时应一起读取概率分布与置信信息，再按具体业务规则处理。这里的数字只是算例，接口字段和定义以 [Score 官方说明](https://docs.typesafe.ai/primitives/score)为准。

还要区分“选项概率”和接口的 `confidence`。按照[官方说明](https://docs.typesafe.ai/confidence)，Choice 和 Score 的 `confidence` 是根据整个概率分布算出的集中程度，不是另一个独立的正确率；Noul 则返回命题为真的概率，没有单独的 `confidence` 字段。比如三个选项概率为 0.6、0.3、0.1，最高概率是 0.6，Choice 的官方置信度计算结果却是 0.4。选阈值时先确认使用哪个量，再在自己的数据上验证，不能把两者混为一谈。

## 数据与训练

TypeSafe 将公开训练路线称为 RLCD，即面向校准决策的强化学习，强调对结果与不确定性的优化。它不等于把聊天输出限制成 JSON，也不能从这个名称补造具体骨干、层数、奖励公式或完整数据比例。

教学适配材料应区分三件事：用户表达、外部证据、业务规则。例如“被扣两次”是用户声明，“两笔同订单交易”才是另一份证据；缺交易记录时不能把用户声明直接当已核实事实。

例如一条历史工单被核实为重复扣款，它才可以按明确标注规则作为该命题的正例；用户只是怀疑重复扣款但账单尚未查清时，不应自动标为正例。标注需要记录事实来源、证据何时可用和不同标注者如何处理不确定情况。否则模型可能学到“用户说两次就判定两次”的捷径，概率再精确也只是对错误标签的精确拟合。

对 RLCD，官方的公开表述强调用结果训练校准决策；它没有披露足够细节来重现损失、优化器或奖励实现。对外部团队来说，可以学习 [RLHF](/training/rlhf/) 与 [RLVR](/training/rlvr/)作为不同训练信号的背景，但不应将这些方法简化为绝对互斥的模型类型，或假设 Jev 的具体配方已经开源。

如果要训练或校准分流器，标签应由一致规则和可靠标注产生；训练、阈值选择、最终测试分开。测试集不能被反复用于挑出最漂亮的阈值。

## 评测怎么看

### 概率好不好，不能只看选没选对

构造一组 100 次被赋予约 0.9 置信度的分流判断，若只对 60 次，模型在这一组明显过于自信；这不等于每个 0.9 判断都应该单独“正确 90%”。校准说的是一组预测的频率关系。

准确率看选项，Brier 或 NLL 等还评价给真值多少概率，可靠性图看不同概率组的表现。Brier 可理解为概率预测与真实结果的平方误差，NLL 则会惩罚给真实结果很低概率的预测。它们不是同一个分数。把全部结果压成低置信度可能改变某些指标，却不证明判断能力变强。

### 一个 Brier 分数例子

假设只看“是否重复扣款”这个二分类命题，四次预测概率是 0.9、0.8、0.2、0.1，对应真实结果为 1、0、0、0。Brier 分数是四个平方误差的平均：$(0.1^2+0.8^2+0.2^2+0.1^2)/4=0.175$。其中第二次高置信误判贡献最大；这只是人为构造的算例，不是 Jev 的实测表现。

Brier 同时受校准与区分能力影响，单看一个总分还不够。可以按置信区间画可靠性图，标明各组样本数与不确定性，再分别检查账单、技术、账户及新出现的类别。某个类别样本极少时，单个分桶会很不稳定；模型整体校准好，也不保证每一类别或每种语言都校准好。

### 自动化还要看覆盖率与代价

教学规则可以要求最高概率超过开发集选定阈值才自动分流，其余复核。报告自动覆盖了多少、自动部分错多少、每类工单召回多少。只提高阈值后说自动准确率更高，却不报有多少工单被转人工，会隐藏取舍。

## 应用与错例

关键词误判先补否定和转述对照；证据缺失先补 state，不必先重训；高置信度仍经常错，再做目标域校准与类别检查。候选未覆盖真实类型时，要检查该问题类型提供的拒答或回退机制，而不是强迫任何输入都归入一个已知类别。

一个完整的改进闭环可以先收集经授权的工单、可访问的订单证据和人工核验结果，按时间或用户隔离训练、开发与测试；之后定义命题和标签规则，在开发集选择人工复核阈值，最后只在独立测试集报告覆盖率、误路由率与各类别表现。上线后的错误按“输入缺证据、命题定义模糊、模型理解错误、阈值不合适或工具故障”分类，再决定补数据、改规则还是暂停自动处理。

例如把两次扣款的订单号拼错导致 state 缺少其中一笔，修复数据接入比增加模型训练样例更直接；若状态完整但模型在“未退款”与“已退款”的否定句上反复判断错误，则应收集经核验的困难样本并在独立数据上回归。以上是教学设计，未实际运行，也不意味着服务支持任意用户重新训练底层模型。

模型给概率后，代码仍可检查确定性条件、记录版本并执行路由。类型化判断只承担其中一步，不自动代表整套业务流程已经可靠。

## 比较与面试追问

**输出 0.9 是否表示这一单肯定正确？** 不是。校准是对多次预测的统计要求；单例仍可能出错。

**与 [OmniJev](/omni/omnijev/) 是同一模型吗？** 不是。它们属于不同项目；应分别核对权重、模态、训练和输出约定，不从名字推断继承关系。

**JSON 输出与决策模型一样吗？** JSON 约束格式；决策和概率目标还要单独学习与评测。

**概率校准好，就能自动批准所有退款吗？** 不能。还需业务规则、证据、代价和适用范围，校准也不保证单个答案正确。

**能据接口推断 Jev 使用哪一代 Qwen 吗？** 不能。公开资料没有支持的内部实现保持未知。共享概念见[概率校准](/evaluation/calibration/)。
