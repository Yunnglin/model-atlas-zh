## 解决什么问题：能不能把工作持续做下去？

让助手给一个排序函数写初版，可能只需要一轮回答。但让它“为老系统增加账单导出功能”，工作就长得多：先理解项目，再核对需求、改接口、补测试、看失败日志、修复边界问题，最后告诉人哪些验证已做、哪些没有做。每一步都可能改变对问题的理解。

官方将 GLM-5.1 定位于长流程的代码与智能体任务，强调在多轮尝试中分解问题、运行实验并根据结果调整。这个定位不意味着模型会一直变得更好，也不意味着所有任务可无人监督。模型必须配合提供文件、运行环境、预算和权限的应用才能完成工作。下面的账单例子是教学构造，不是官方实验或实际运行记录。

## 结构与数据流

GLM-5.1 是逐个生成 token 的语言模型。模型看到用户需求和已有工具结果后，可能继续生成自然语言，也可能生成约定格式的工具请求。工具请求交由外部执行器校验并执行，结果作为新的输入送回模型。它不像普通聊天界面那样只回答一次，而是通过多轮输入输出参与整个工作流。

公开配置标识为 `glm_moe_dsa`：有 256 个路由专家，每个 token 选 8 个路由专家，另设一个共享专家；`index_topk` 为 2,048。配置还包含压缩键值表示的相关参数；可结合前代 [GLM-5](/nlp/glm5-model/) 与[注意力机制](/foundations/attention/)阅读。配置能告诉我们结构字段，却不能独立证明两个版本的训练数据完全相同，也不能说明每一处性能提升的原因。

从配置看，GLM-5.1 的主干有 78 层：前 3 层采用稠密前馈网络，之后 75 层使用 MoE 前馈网络；隐藏宽度为 6144，注意力有 64 个查询头。每个 MoE 层各有 256 个路由专家，并为每个 token 选择其中 8 个；共享专家也参与计算。下图把每层的主要步骤展开，省略了归一化、残差和多 token 预测层。

![GLM-5.1 语言主干示意：78 层中前 3 层使用稠密前馈，后 75 层使用混合专家前馈，逐步预测下一个 token。](/figures/glm5-family/backbone.svg)

比如账单需求被切成若干 token，路由器会分别给每个 token 选专家；它不是为整段文字只选一次。选中专家处理后的结果与共享专家的结果汇合，再进入后续层。实际部署可以把不同专家放在不同设备上，批量中的 token 需要按路由结果分发、计算和回收，因此设备通信和各专家的负载会影响速度。

### 路由专家：按需请人帮忙

[MoE](/foundations/moe/) 可以想象成一个大型工作室：团队里有很多组，路由器根据当前输入选择几组参与这次处理，共享部分也参与计算。这里的专家是模型学出来的神经网络模块，不是人工事先指定的“导出账单专家”。路由器可能为输入中的不同 token 选择不同模块。

总参数表示全部权重规模，激活参数描述某个 token 计算中参与的部分。即使一次只使用一部分专家，部署也要考虑整个专家池的存储、分片、通信、缓存和精度；不能用激活参数直接算出服务器需要的显存。GLM-5 报告说明其 744B 统计包含 MTP 层、不含词嵌入和输出层；Hugging Face 的 GLM-5 和 GLM-5.1 页面都显示约 754B。不能拿前代报告的数字与 5.1 页面数字相减，当作新增参数量。

### 稀疏注意力：先筛线索，再仔细读

一轮轮读取文件和执行测试后，历史会变长。DSA 使用索引器选择与当前 token 可能相关的历史位置，再在选出的范围内进行精细注意力计算。类比查资料时先翻目录找页码，再阅读对应段落：目录本身也有计算成本，挑错页码仍可能漏掉重要信息。2,048 是配置中的选择上限，不是说输入超过 2,048 个 token 就被截断，也不是保证总能找到正确线索。

MoE 挑选的是参与计算的专家；稀疏注意力挑选的是要重点读取的历史位置；压缩键值表示则关系到保存和读取历史信息的方式。这三件事各自处理不同瓶颈。更长的上下文让系统能放进更多材料，却不会自动判断材料的可靠性，也不保证所有位置都被正确利用。

以账单导出为例，需求写在第一个消息、错误日志出现在第十轮，而权限规则藏在很早读过的文件里。如果应用丢掉规则、提供过期文件，或模型选错线索，即便窗口尚未用完也可能修错。应保存文件版本、关键约束和重要执行结果；历史压缩后也需要验证是否遗漏关键细节。

## 数据和训练：哪些是事实，哪些只是教学方法？

GLM-5.1 模型卡链接了 GLM-5 技术报告作为系列背景。前代报告描述了基座预训练、中期训练、监督微调与强化学习，并讨论可验证环境和异步智能体训练；5.1 的新增训练数据与完整配方尚未公开。

下面是理解长任务训练的**通用例子**。先准备账单项目、历史需求、工具环境和符合预期的示范轨迹；监督微调可以让模型学习怎样按格式请求工具、读反馈、提交解释。之后可以在隔离环境中让模型尝试修改代码，用单元测试、集成测试或人工评价反馈，为进一步优化提供信号。这只是训练思路，不是官方公布的 5.1 具体配方。

奖励设计要格外小心。假设只奖励“测试变绿”，模型可能删除失败的测试，或者硬编码当前样本。更有用的验证还要检查实际输出、边界条件、未授权修改，以及测试是否真的运行。一次工具超时也不能直接当成模型不会写代码；应保留环境状态和错误日志，区分执行环境失败、工具调用错误和业务逻辑错误。

### 长任务为什么更难训练？

短题可以生成答案后立即判分；长任务要在多轮行动后才知道是否解决问题。一个账单问题可能从读取代码开始，到最后才发现时间范围少算一天。此时要判断错误来自最初误解、工具返回、代码修改还是测试不足，单个最终分数很难告诉我们。

前代 GLM-5 报告介绍过将轨迹生成与训练更新解耦，以减少等待长耗时环境导致的资源空转。异步会产生旧模型生成的数据，需要控制策略差异；保留生成时的 token 信息也可避免重新分词造成轨迹对不齐。理解这些机制有助于理解系列训练背景，但不能据此断言 5.1 使用完全相同的训练数据、阶段顺序或超参数。

## 评测：看分数，也看工作条件

官方模型卡报告 GLM-5.1 在 SWE-Bench Pro 上为 **58.4**，GLM-5 为 55.1；Terminal-Bench 2.0 在 Terminus-2 设置下分别为 **63.5** 和 56.2；NL2Repo 分别为 **42.7** 和 35.9。它们测试的任务不同：仓库问题修复、终端操作和从需求生成仓库，并不是同一张试卷。分数是官方表中对应设置的结果，不能推断任何项目都有相同成功率。

官方表里还有一组值得拆开看的结果：Terminal-Bench 2.0 使用 Terminus-2 时，GLM-5.1 为 **63.5**；另一行标为“最佳自报结果”，使用 Claude Code 时为 **69.0**。这两行告诉我们框架是评测条件的一部分，却不能只凭这张表断定框架本身造成了全部差距：任务配置、运行次数与预算也需要核对。就像同一位厨师换了一套厨房设备，还需要确认食材和时间是否一样，才能判断差异从哪里来。

同一基准也会因工具框架、提示、上下文管理、模型版本、资源预算和环境变化而不同。例如模型卡还给出 Terminal-Bench 2.0 使用 Claude Code 的自报结果，不能与 Terminus-2 那行混作同一种设置。比较之前至少确认任务版本、运行框架、次数、预算和评判方法；不同基准之间更不能仅看数值大小。

模型卡还列出一些通用推理成绩，并非每一项都比前代高：例如 AIME 2026 表中 5.1 为 95.3、5 为 95.4。单项分数受抽样和设置影响，不应由微小差距判断普遍能力，更不能从工程任务进步推导所有任务都进步。

对于长程任务，最终测试通过与否只是终点，还应记录：第几轮找到关键文件；测试失败后是否改变策略；每轮工具调用有无实际进展；花费多少时间、token 和执行次数；最终说明是否与真实日志一致。用固定预算比较，才能区分模型能力和单纯增加尝试次数。

## 实践：从失败案例回到下一轮数据

假设团队要评估账单导出功能，先固定一份项目快照、需求和运行环境，要求导出包含日期、币种与金额，并正确处理跨月、空账单和无权限用户。给模型受限的读取、修改及测试工具，记录每轮请求与执行结果。验证集应与用于示范或调整提示的数据分开。

第一次运行中，模型可能在本地时区跨月边界漏掉一天。检查轨迹时不要只贴上“日期计算差”的标签：先看需求是否写清时区，模型有没有读取相关日期处理代码，工具是否返回了旧文件，测试是否覆盖夏令时和跨月边界。不同原因对应不同改进：需求不清就补充规范，测试缺失就补边界样本，模型忽略规则则增加针对性案例。

下一轮应保留独立样本重新评测，同时检查普通日期、权限控制和性能有没有退化。模型表示“已运行测试”时，必须核对真实工具日志；若依赖安装失败，应明确写出未验证，而不是把构建失败说成业务逻辑通过。这个流程可以解释数据、训练、评测、应用和错例改进的联系，并不代表官方使用同一场景。

## 面试追问

**问：5.1 与 5 的结构字段相近，为什么评测还可能不同？** 权重、训练数据与训练过程都会改变能力，推理框架和评测设置也会影响最终结果。结构字段相似只能说明部分结构配置相近，不能单独确定性能变化来自哪里。

**问：为什么长程任务不能只看一次成功？** 一次成功可能来自运气或大量尝试，还可能忽略成本、错误修改和未覆盖的边界。应在独立任务上重复评测，记录预算、成功率、耗时、成本与失败类型。

**问：模型调用工具是不是模型自己有权限执行命令？** 模型生成的是工具请求；应用负责鉴权、执行和返回结果。只有执行日志和验证证据才能说明命令是否真的运行、结果是否可靠。
