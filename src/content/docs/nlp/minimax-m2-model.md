## 要解决什么问题

想象一个代码助手接到任务：“订单金额为空时，结算页面会报错，请修复。”它不能只写一段看似正确的代码，还要找到相关文件、确认已有接口、修改实现、运行测试，并根据失败结果继续修正。这个过程涉及语言模型、执行工具、代码仓库和测试环境，任何一环出错都可能导致任务失败。

MiniMax-M2 于 2025 年 10 月发布，重点面向编程与多步工具任务。这里讨论初版 M2，不把后来的 M2.1、M2.5、M2.7 的成绩和后训练细节自动套到它身上。官方开放权重，提供本地部署和工具调用资料；应用还需自己选择推理框架、工具权限和验证流程。

以下订单问题、代码和数字都是教学构造，不是运行模型得到的结果。举例的目的，是把“模型会生成一个计划”和“系统实际完成并验证修改”区分开。

## 结构与数据流

根据后来发布的系列技术报告，M2 是 62 层仅解码器 Transformer。输入任务和历史上下文后，模型根据此前 token 逐步生成下一个 token；输出可能是文字、代码，也可能是符合接口约定的工具请求。[Transformer](/foundations/transformer/) 可以帮助理解基本的注意力与前馈网络。

![MiniMax-M2 语言主干：输入经过 62 层，每层使用因果自注意力和稀疏专家前馈网络，再预测下一个 token。](/figures/minimax-m2/backbone.svg)

图中将每层主要的注意力和专家计算串起来，省略了残差、归一化和多 token 预测细节；层数与头数来自[官方模型配置](https://huggingface.co/MiniMaxAI/MiniMax-M2/blob/main/config.json)。

### 全注意力与 GQA

报告描述 M2 各层采用全注意力：在因果约束下，当前位置可以关注可见的先前位置。它不表示模型能看到尚未生成的未来内容，也不保证模型一定注意到长文里正确的证据。M2 使用分组查询注意力 GQA，报告给出的配置为 48 个查询头和 8 个键值头；多个查询头共享键值头，有助于减少缓存开销，但注意力计算和缓存仍会随上下文、实现和并发产生显著成本。

举个估算：配置中每个键值头的维度是 128。假设单条请求缓存 8192 个 token，62 层都保存 K、V，且缓存使用 BF16，那么缓存约为 `62 × 2 × 8 × 128 × 8192 × 2` 字节，即 **1.94 GiB**。相同假设下，长度增至 16384 token 时约为 3.88 GiB。这里仅计算键值缓存，不包含权重、临时工作区或并发请求；实际框架也可能使用不同精度和缓存策略。

这与 MiniMax-Text-01 的混合注意力路线不同。模型使用全注意力是一个设计取舍，不能仅凭架构名称判断它在所有长度、设备和任务上都更快或更准。对于长仓库任务，应实际测试关键文件放在不同位置、重复片段干扰以及上下文截断造成的影响。

### MoE 不等于只需要加载激活参数

M2 的前馈部分采用混合专家网络（MoE）：报告列出 256 个专家，每个 token 选择其中 8 个参与。可以把路由想成调度员根据当前信息挑选几组工位，但专家是训练得到的网络，不能假定一个专门负责 Python、另一个专门负责 Java。

总参数约 229.9B，单 token 激活约 9.8B。前者大致描述整套模型权重的规模，后者描述一次计算参与的参数规模；它们不是互相矛盾。部署时仍要处理完整权重、精度、缓存、专家分布与设备间通信，不能以 9.8B 直接估算显存。[MoE](/foundations/moe/) 进一步解释路由与负载均衡。

报告还描述多 token 预测模块可用于推测解码的候选生成。可以把它理解为先让草稿机制尝试提出后续内容，再由目标模型验证；是否获得速度收益要看实现、接受率、硬件与负载。它不代表模型一定一次就正确生成多个 token，也不能将报告中的方法当成所有部署框架默认启用的功能。

这套草稿模块也经过训练。系列报告记载，预训练先用一个 MTP 模块；继续训练的衰减阶段，将其扩展到三个，并用主模型权重初始化。团队先短暂冻结主模型、只训练新增模块，待损失稳定后再一起训练。这样可以把过程想成先让新助手熟悉工作，再与原团队共同磨合。报告称推理时三个模块可以提出草稿，由主模型验证；训练中增加这些模块并不意味着用户每次请求都会自动启用这一优化。

### 写请求和执行是两回事

模型可以输出“查找报错文件”的工具请求；外部执行器解析、检查权限、运行搜索并返回结果，然后模型再生成下一步。对于订单错误，一个合理的轨迹可能是：读取错误日志 → 找到处理空金额的函数 → 修改代码 → 运行相关测试 → 根据输出修正。工具被调用后仍可能失败、超时、返回不可信内容或没有权限，应用必须记录真实结果，而不能只相信模型说“我测过了”。

配图把执行器画在模型之外。文件读取、命令执行、浏览器和网络权限均由应用决定；在真实仓库里运行生成的命令应限制权限并保留日志。模型可以在中间交替生成分析和工具请求，但输出的分析也可能遗漏问题，并不是安全或正确性证明。

## 数据与训练

### 预训练让模型学会基础续写

系列技术报告称 M2 使用约 29.2 万亿 token 预训练，并描述 192K 的最大训练上下文。预训练主要让模型从大量序列中学习预测后续内容，形成语言、代码等基础能力；token 是文本计量单位，不等于独立文件或独立用户数量。对具体数据清单、各来源比例和每条样本是否被使用，不能在没有公开依据时推测。

这 29.2T token 分为两个主要阶段：论文记载，恒定学习率阶段使用约 19.9T token；后续衰减阶段使用约 9.3T token，同时把上下文从 8K 逐步扩到 32K、192K。长文本材料包括连续代码、较长 PDF，以及按主题拼接的文档。把长文分阶段引入，可以帮助模型练习处理较长的输入。

报告还提到除下一 token 预测外使用多 token 预测目标。训练目标是一种学习信号，并不意味着模型已经理解每个项目的真实依赖，或能自动访问私有仓库。训练语料中的代码可能包含旧接口、缺陷或过时范式，模型生成的补丁仍需要在目标项目上验证。

### 智能体后训练关注整个轨迹

仅有代码续写能力还不够。代码助手需要理解任务、选择合适工具、接收执行结果并决定是否继续修改；因此可以用包含任务、环境、动作和反馈的轨迹训练模型。一个教学样本可能让模型先运行相关测试，看到空值异常后修改函数，再次测试并解释结果。只有把工具返回和最终产物与任务对应起来，才能判断它是真修复，还是只写了看似合理的说明。

后来的系列报告介绍了面向代码与其他智能体任务的数据和强化学习系统，但这些流程在 M2 到后续版本之间持续演进。它能帮助理解系列方向，却不能据此断言初版 M2 使用了后来每一项数据流水线、奖励细节或所谓自我演进能力。初版的完整后训练数据、配比与每阶段具体参数并未由发布资料逐项公开；不清楚的地方应保留空白。

奖励设计也有难点。只奖励“测试通过”，模型可能删掉测试或写一个只适配公开样例的补丁。更可靠的实验会保留独立测试、检查补丁范围、验证安全边界并观察其他功能是否退化；即便如此，测试覆盖仍有限。这里是在说明如何设计实验，不是声称官方初版训练一定采用了这些具体规则。

## 评测怎么看

官方模型卡报告 M2 的 SWE-bench Verified 为 69.4，Terminal-Bench 为 46.3。两个基准衡量的任务、环境和框架不同；模型卡说明 SWE-bench 使用 OpenHands 上的指定脚手架、128K 上下文及最多 100 步，不进行额外测试时扩展；Terminal-Bench 则在指定框架下运行并取 8 次平均。数字反映的是模型加工具系统在该协议中的结果，不能直接当作任意生产仓库的修复成功率。

模型卡页面还有一项 **Terminal-Bench 2.0：30** 的评测元数据。它与正文表格中的 **Terminal-Bench：46.3** 不是同一条成绩：基准版本和评测记录不同。就像两次考试的题目不同，不能用这两个数直接计算模型进退步；要比较时先核对版本、任务和运行设置。

SWE-bench 类任务通常给模型一个代码仓库和问题描述，让它输出补丁并执行测试；Terminal-Bench 更强调在终端环境中完成任务。比较模型时需要核对版本、脚手架、容器、命令权限、最大步骤、重试次数、测试集和成本。某个模型分数高，可能同时受到提示、工具实现和可用时间的影响；直接把不同系统的单个数字排成绝对能力榜不可靠。

对订单空金额问题，可以同时统计：定位正确文件、补丁是否符合接口、相关测试是否通过、独立回归测试是否通过、是否误改无关文件，以及耗时和工具调用次数。假设 20 个构造任务中 14 个通过独立测试、其中 12 个没有引入额外回归，两项比例分别为 70% 和 60%；这只是教学算例，不是模型实测。

长上下文测试也应覆盖“证据存在但位置不同”和“缺少证据”两类问题。能装下 192K token 只说明容量设定，不保证在长记录末尾仍能正确找到代码或日志，也不意味着任何服务会提供相同窗口和输出限制。

按模型配置的 196608 个位置举例：如果对话、仓库片段和工具结果已经占了 190000 个 token，理论上只剩 6608 个位置供后续生成；模板和其他开销也会占用空间，实际可用额度以部署框架为准。因此长任务需要保留必要的错误日志和测试结果，并及时整理无关输出；不能只把更多材料一直追加进上下文。

## 应用与错例闭环

假设模型修复空金额时直接把所有空值改为 0，测试通过了一个正常订单，却破坏了退款业务。首先保留任务、代码版本、提示、工具调用、补丁、测试输出和运行环境。检查需求是否明确区分缺失值与真实零元、测试是否覆盖退款、模型是否只修改了一个分支，以及测试命令是否真正执行。

接着按业务类型收集脱敏样例，补充空值、零元、负数、退款与不同币种，并由工程师确认预期行为。按项目或问题来源划分开发与独立回归集，避免把同一个缺陷的近似样本同时放到两边。可以先完善需求、工具权限和测试，再决定是否需要收集轨迹训练；改动后观察修复率、误改率、工具失败恢复、耗时与硬件成本。这是一套实验设计，尚未实际训练或评测。

## 比较与面试追问

**10B 激活参数意味着只要 10B 权重显存吗？** 不意味着。完整专家权重、缓存、精度与分布式调度都要计入。

**全注意力是否能看到未来 token？** 在自回归生成的因果约束下不能；它可以关注可见的历史位置。

**模型说测试通过就代表真的通过吗？** 不代表。应查看执行器实际运行的命令、退出状态和独立测试日志。

**SWE-bench 69.4 可以直接预测公司项目修复率吗？** 不能。项目、脚手架、测试、权限与预算都会改变结果。

**后续 M2.7 的自我演进能力属于 M2 初版吗？** 不应直接归属；需要分别核对版本和公开证据。
