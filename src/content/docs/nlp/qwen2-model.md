## 要解决什么问题

一家跨境商店同时收到中文、英语和西班牙语消息。用户先说“包裹没有送到”，又补充“昨天邻居已经代收”。助手要理解后一句改变了当前状态，而不是只看见第一句就启动退款。这个情境涉及多语言理解、跨句关联和遵循业务规则，也说明同一个任务中有不止一种失败方式。

Qwen2 于 2024 年 6 月发布，是 Qwen1.5 之后的文本模型系列。官方提供不同参数规模的基础模型与指令模型，并发布 57B-A14B 稀疏专家模型。下面以虚构的客服场景为例，沿着公开资料理解它的结构和训练。

## 结构与数据流

图展示的是两类型号共同的因果生成主路径，省略归一化、残差和位置编码等细节。稠密前馈和专家前馈是**不同型号的结构选择**，不是每个 Qwen2 模型都同时运行两套网络。更通用的概念见 [Transformer](/foundations/transformer/) 和 [MoE](/foundations/moe/)。

### 从消息到回答

用户的多轮消息经过聊天模板和分词变成 token。模型读取前文，在每个位置通过因果注意力联系此前的线索，再通过前馈网络加工表示。最后它对词表产生下一 token 的分布，生成一个 token、追加到上下文，再预测后一个。例如它输出“已”“确认”“代收”时，实际 token 的切分不一定和这三个词一致。

注意力允许后面的位置参考前面的消息，却不能直接读取尚未生成的答案。训练时，正确文本已知，在因果掩码约束下可以并行计算多个位置的预测损失；在线生成时，新的结果还不存在，必须一步步接续。对话能力还取决于后训练和消息格式。

### 分组查询节省的是哪一部分

Qwen2 使用分组查询注意力。粗略想象多位客服各自提出查询，但共享一部分历史记录索引；共享的是键和值的表示，并不是几位客服必须给出同样的答案。生成时缓存历史键值，下一步可以复用；减少键值头的数量，通常有利于控制缓存占用。[KV Cache](/foundations/kv-cache/)解释缓存与权重、激活内存为何是不同账目。

以 [Qwen2-7B-Instruct 配置](https://huggingface.co/Qwen/Qwen2-7B-Instruct/blob/main/config.json)为例，它有 28 层、28 个查询头和 4 个键值头，因此每 7 个查询头共享一组键值头。不同型号的头数可能不同。 如果用它练习参数高效微调，可以参照 [LoRA 的 Qwen2 参数算例](/training/lora/)；这是教学配置，不代表官方使用该配置训练了模型。

做一笔近似账：假设只有一条长度为 32768 token 的序列，K 和 V 都用 BF16，每个数占 2 字节，忽略框架额外开销。该型号每头 128 维，因此 KV 缓存约为 `28 层 × 32768 token × 4 个 KV 头 × 128 维 × 2（K 和 V）× 2 字节 ≈ 1.75 GiB`。假设其他条件不变、改用 28 个 KV 头，则约为 12.25 GiB。这只是缓存估算；完整显存还包括权重、激活和运行时开销。

输入变长或并发增加时，缓存占用也会上升；实际占用还取决于精度和运行框架。

### Dense 和 57B-A14B 怎么比较

稠密模型的相关前馈层对每个 token 使用同一组参数；MoE 把前馈计算组织成多组专家，由路由器选择其中一部分。57B 是该型号的总参数数量量级，A14B 表示每步约 14B 激活参数，不表示只需要存储 14B 权重。其他专家不参加当前 token 的计算时，依然需要按部署方案存放或调入；设备之间还可能发生通信。

MoE 是“哪些前馈参数参与计算”，GQA 是“注意力如何组织查询和键值”，两者可以同时存在。专家是否形成特定分工，需要通过路由分析确认。

Qwen2 报告说明 57B-A14B 从 Qwen2-7B 稠密模型扩展而来：以稠密前馈权重初始化并构造专家，再继续训练。这种做法叫 upcycling：用已有加工模块作为专家的起点，再让它们继续学习。

具体看[技术报告表 1 和第 2.2.2 节](https://arxiv.org/html/2407.10671)：57B-A14B 在 MoE 前馈层有 64 个路由专家，每个 token 选其中 8 个；另外还有共享专家，表中列出 8 个共享专家的等价宽度，**不包含在那 8 个被选中的路由专家里**。可以把共享专家想成每单都参与的通用处理，把路由专家想成按当前内容挑选的处理模块，最后由模型组合它们的结果。

报告还说明如何从稠密前馈层得到细粒度专家：复制原前馈权重，打乱中间维度后切成较小专家，并对每个专家的 50% 参数随机重新初始化，再继续预训练。这里的 50% 指初始化的参数比例。

## 数据与训练

### 数据更多不一定更有效

Qwen2 报告描述从前代约 3 万亿 token 扩大到约 7 万亿，并尝试放宽质量门槛形成约 12 万亿 token 的数据。报告称，在其对照中，扩大到 12 万亿没有带来显著性能改善，因此较大模型选择质量较高的 7 万亿数据；报告另写明：0.5B 使用 12 万亿 token 的数据集，MoE 在采用 upcycling 的基础上又预训练了 4.5 万亿 token。这个结果说明，增加低质量数据未必能改善模型。

把训练数据想成给客服准备的学习材料：一千份清晰、去重并带正确状态的对话，可能比夹杂大量重复和错误结果的更多对话更有用。实际比较还需控制训练计算、领域覆盖和测试集。

报告描述多语言数据扩展，并在预训练结束阶段加入更长文本。多语言覆盖不代表每种语言都有相同训练量或同样质量；模型也可能在语言混杂、方言、专业缩写和罕见地名上出现不同错误。应根据实际用户消息建立语言和任务切片，而不是只测英语标准题。

### 长文本阶段做了什么

官方报告描述在预训练后段把序列长度从 4096 扩展到 32768，并调整位置编码的设置，同时增加长文本数据。把最大长度写进配置，只说明接口允许尝试更长输入；若没有相应训练和正确的位置设置，不能据此声称获得相同能力。某些 Instruct 版本又公开更长上下文支持。例如 [Qwen2-7B-Instruct 模型卡](https://huggingface.co/Qwen/Qwen2-7B-Instruct)建议超过 32768 token 时启用 YaRN；其默认配置中的 `max_position_embeddings` 为 32768。官方介绍的 128K 支持不应被误读为默认安装、无需设置就保证长文效果。使用时还要核对完整型号与实际框架。

报告中的一个具体调整是把 RoPE 的基础频率从 10,000 改为 1,000,000。可以把它想成重新安排位置编码里不同变化速度的刻度，让模型在较长范围内表示位置；但单独调整这个数字不等于完成长文本训练，也不保证模型在窗口内每个位置都能正确找到证据。

对跨境客服而言，可以构造一条很长的工单：早期有“未收到”，后期又有“邻居代收”。把最终状态放在不同位置，并插入其他订单，分别检查定位、状态更新和订单归属。若输入被截断导致关键句根本没进入模型，应先修截断或检索，而不是直接判定模型不具备长程推理能力。

### 后训练与模型使用

基础模型学习续写，Instruct 模型再学习遵循指令和偏好。以客服任务为例，训练数据可以包含用户消息、先前上下文和一份符合业务规则的示范答复。偏好数据可以比较“先核对代收状态”和“忽视后文直接退款”两种回答；规则变化或缺少订单证据时，模型应有询问或转人工的出口。

报告还说明，偏好对齐先用离线偏好对做 DPO，再由当前模型生成候选、奖励模型挑选偏好对并做在线 DPO。例如，对同一个工单生成多份回复后，奖励模型从中选较好和较差的答案组成一对，再用这对数据更新模型。这里的“在线”指候选在训练过程中由当前策略产生，并不意味着需要边服务用户边拿用户真实数据训练；奖励模型的选择也需要单独检查。

报告中的后训练数据也有具体制作方法：先抽取指令主题，选择并扩展指令，再由标注者对多个候选回答排序，得到示范和偏好对。对于有明确答案的数学任务，报告描述生成多条解答，保留答案正确且被模型判断为合理的路径；代码任务则可用编译、执行和测试结果辅助筛选。**答案正确不自动证明中间推理可靠，测试通过也只证明通过了所运行的测试**。报告称 SFT 数据超过 50 万条、训练两个 epoch。

官方发布说明中，Qwen2-72B 及其 Instruct 版本使用 Tongyi Qianwen 许可，其他首发型号使用 Apache 2.0；具体检查点仍应核对模型卡与许可文件。

聊天模板、角色标记、停止条件和 tokenizer 应与模型匹配。格式弄错会出现重复回答、混入角色名或提前结束；这些问题和语言理解能力不足需要分开诊断。[SFT](/training/sft/)说明示范学习，[RLHF](/training/rlhf/)说明偏好信号的作用。

## 评测怎么看

把问题拆成几张成绩单：意图识别是否正确、是否使用最新状态、回答语言是否符合用户要求、是否遵守业务规则、是否遗漏证据。假设有 20 条客服样本，其中 18 条语言正确、15 条状态判断正确、14 条完整满足业务规则，三项比例分别为 90%、75%、70%。

比较 Qwen1.5、Qwen2 与 Qwen2.5 时固定任务、完整模型名、精度、提示模板、生成预算与候选次数。把 72B 与 7B 的结果直接归因于代际，很容易混入规模影响；将 MoE 的激活参数等同于所有存储成本也不公平。报告中的英文、中文、代码与数学基准各有题集和协议，不应把其中一个平均分当作跨境客服的业务结果。

[技术报告表 8](https://arxiv.org/html/2407.10671)中，Qwen1.5-7B-Chat 与 Qwen2-7B-Instruct 的 MMLU 分别为 59.5 和 70.5，GPQA 分别为 27.8 和 34.3。可以把它们理解为两张不同科目的成绩单：前者偏广泛知识，后者是更难的专业问答，成绩不能相加。Qwen2-7B-Instruct 的[模型卡](https://huggingface.co/Qwen/Qwen2-7B-Instruct)将 GPQA 写为 25.3；[Qwen 发布文章](https://qwenlm.github.io/blog/qwen2/)说明，指令模型成绩与技术报告不同时以技术报告为准，因此这里采用报告数字。这些成绩也不能代替客服任务评测。

对于低资源语言，要单列每种语言的样本数量和错误类型。翻译成英文再评测可以作为辅助对照，但翻译本身会改变语气与含义。手工抽查“未送到”和“已经代收”这类状态反转，比只看模型输出是否通顺更能暴露实际风险。

## 应用与错例

如果系统仍回复“尚未送达”，先保存用户原文、检索到的订单状态、提示、模型版本和回答。再问：后一句是否送进上下文？消息时间是否排错？模型是否把两个订单混在一起？工具返回的是实时状态还是旧缓存？只有确认输入和规则正确后，才考虑补充示范或调整训练。

针对确认的缺陷，建立近似但答案不同的样本：同样提到邻居，一条是“邻居代收”，另一条是“邻居没收到”。将这些样本加入开发池，再用来自不同用户和时间段的独立样本回归。不能反复拿同一测试集调提示，并把调出来的分数当作未知场景的可靠表现。

## 比较与面试追问

**57B-A14B 为什么不能当作 14B 模型部署？** 14B 描述单步激活规模，所有专家的权重与部署策略仍影响内存和通信。

**长窗口是不是保证找得到答案？** 不保证。窗口限制、截断、证据位置、干扰与任务要求都会影响结果；应分开验证输入和推理。

**Qwen2 与 Qwen2.5 的 7T、18T 能直接解释能力差异吗？** 不能。数据质量、组成、训练安排和后训练也变化。两代之间的具体对照见 [Qwen2.5 独立页面](/nlp/qwen25-model/)。

**输入中文、输出西班牙语需要什么？** 除模型会生成目标语言外，还要检查事实不变、日期与数字一致、业务规则没有在翻译过程中被改写。多语言表述流畅，并不自动保证这些细节正确。
