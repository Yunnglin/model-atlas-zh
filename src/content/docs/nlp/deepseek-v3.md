## 要解决什么问题

想增加模型能存储和处理的知识，又不想让每个 token 都经过全部参数，可以怎样做？原始 DeepSeek-V3 用 MoE 和注意力方面的设计处理这类效率问题。本页区分 V3-Base 与经过后训练的 V3 助手，不把后续同名更新混为一个版本。下面用虚构的电商售后工单解释：用户先说订单没送达，后来又补充邻居已经代收；助手需要根据最新状态答复，而不是看到“没送达”就直接退款。示例不是模型实测。

## 结构与数据流

[查看官方论文的 Figure 2 结构图](https://arxiv.org/html/2412.19437v1#S2.F2)：原图展示 MLA 与 DeepSeekMoE，下面的教学图和说明帮助理解各模块。论文图与这里的原创简图使用不同的标注和详略。

[MoE](/foundations/moe/)把部分前馈计算分配给不同专家；路由器给当前 token 选择其中一部分。专家不是人工预先标好的“数学组”“中文组”，它们通过训练形成分工。

MLA 把注意力历史中的部分信息压缩到更紧凑的潜在表示，减少缓存压力。它针对的是注意力计算和缓存组织；MoE 针对的是专家计算，两者可以同时存在。缓存的基本作用见 [KV Cache](/foundations/kv-cache/)。

论文中的原始 V3 有 671B 总参数，每个 token 激活约 37B；模型有 61 层，前三层使用普通前馈网络，之后每个 MoE 层有一个共享专家和 256 个路由专家，每个 token 选择其中八个路由专家。图只展示主路径，省略残差、归一化、层内细节和训练时的额外预测模块。

### MoE 和 MLA 分别省在哪里

例如把系统比作读档案后加工答案：MLA 改变阅读笔记怎样压缩存储，MoE 决定请哪些加工工位继续处理。一个改变注意力表示，一个改变前馈计算，所以可以组合，不是二选一。

MLA 对 K/V 的部分联合信息做低秩压缩，同时单独处理与旋转位置相关的分量。直观上存较紧凑的共同表示，需要时再参与对应计算；不能把它说成截掉一半历史。实际效率还取决于投影吸收和运行实现，只有缓存更小并不能证明所有负载都更快。

把缓存量换成具体数字：原始 V3 在每个注意力层中，将键值联合信息压缩为 **512 维**，另外保存 **64 维**的位置相关键。按照论文中的缓存方案，如果每个数用 BF16 的 2 字节保存，一条 8,192 token 的序列在 61 层里约需要 `(512 + 64) × 8,192 × 61 × 2` 字节，约 **549 MiB**。这是为理解 MLA 做的缓存估算；模型权重、临时工作区及框架实现产生的其他占用要另外计算。

512 维向量是键和值共享的压缩表示，不能把它看成 512 个已经独立展开的注意力头。计算时模型通过投影将它用于各头；64 维位置相关键单独保存，使位置编码能够参与注意力计算。[官方报告第 2.1.1 节](https://arxiv.org/html/2412.19437v1)展示了两部分缓存与查询的关系。

路由器对每个 token 选择路由专家，另有共享专家处理共同部分。专家输出按相应权重合成。专家不是一组可单独调用的聊天机器人，“数学 token 总归数学专家”也不是人工标签保证。

### 多个模型版本别混在一起

V3-Base 是预训练底座，主要学习续写；发布的对话模型在底座之上继续接受指令微调和强化学习。同系列随后还有更新版本，它们的检查点、后训练和服务接口可能不同。比较时请记下完整型号，不要把某次 API 的表现自动归给最初的 V3 检查点。[DeepSeek-V2](/nlp/deepseek-v2-model/)解释了上一代的 MLA 和专家路由，可先读它再比较 V3。

例如订单消息经过分词和聊天模板后进入模型，每层注意力按因果约束利用之前内容，前馈模块再处理表示。最终模型依次生成回答；仓库里是否存在订单、退款是否真的执行，都需要外部工具确认。语言模型生成一句“已退款”本身不会完成退款。

## 数据与训练

报告描述预训练、SFT 与强化学习等环节，还加入多 token 预测的辅助训练目标。辅助目标让训练考虑更多后续位置，不代表使用模型时就可以忽略输出依赖、无限并行生成。

专家负载不均会导致一部分设备忙、一部分闲。报告讨论负载均衡与训练系统配合；只读模型参数规模，无法推算一次完整训练的总成本。

### 从数据到对话

论文称预训练使用 14.8 万亿 token，数学、代码及多语言数据有所扩充；预训练时最长序列为 4K，之后逐步扩展到 32K 和 128K。数据量是经该模型分词得到的数量，不等于 14.8 万亿条独立网页，也不等于知道所有资料的具体来源。长窗口让系统能够输入更多内容，但不保证模型总能在长工单中找准最后一次状态变化。

接下来是 [SFT](/training/sft/) 和强化学习。论文描述约 150 万条跨领域指令数据，并使用内部 R1 模型产生部分推理数据，结合方法控制过长和格式问题。对虚构售后案例，一条示范可以是“记录显示邻居已代收，请先向用户确认”，而不是无依据地承诺退款；这只是说明训练样本可能怎样组织，不是官方公开样本。

论文的 SFT 设置还有一个容易忽略的细节：为了减少空白，训练时可以把多条样本拼在同一条序列里，但会用样本间的注意力掩码让它们互相看不到。比如一条售后问题和一条数学题虽然排在同一个训练序列中，数学题不能借用售后题的内容作答；这样既能利用序列空间，也能维持样本边界。报告中的 V3-Base 在这批 SFT 数据上训练了两个 epoch，具体掩码方式和轮数是这次实验的配置，不是所有微调都必须照搬。

V3 的强化学习也要区分“谁给分”和“怎样更新”：论文对能直接检验的数学或代码题使用规则奖励，对需要判断答案或开放式写作的任务使用奖励模型；随后用 GRPO 在同题候选中计算相对优势并更新策略。比如一个有标准答案的计算题可以检查最终结果，一封售后解释信则不能只靠数字是否相等打分。规则也需要测试，程序通过现有用例并不保证所有边界情况都正确。

模型输出能否符合业务规则，还依赖工具返回、权限与当前政策。模型通过训练学会回答的样式，并不等同于接入订单系统后能自动核验事实。训练集、提示和外部业务系统应分别检查。

### 负载均衡为何影响训练

假设 4 个专家中，几乎所有 token 都挤到同一个，其他设备闲着，热门专家还可能成为瓶颈。V3 的辅助损失自由负载均衡用路由偏置调节选择，另有相应序列级约束；“辅助损失自由”不能扩大解释成整个训练没有任何附加目标。

路由偏置影响专家的选择，专家输出的组合权重仍基于原始亲和分数。偏置会根据近期负载调整，热门专家的偏置降低，冷门专家的偏置提高；这是一种调度机制，不是给专家贴业务标签。论文同时保留较小的序列级均衡损失，以降低单个序列出现极端不均衡的风险。

用两个候选专家举个简化例子：原始亲和分数分别为 0.70 和 0.68；如果近期第一个专家过忙，路由时分别加上 -0.05 和 +0.02，选人的分数就变成 0.65 和 0.70，第二个专家可能被选中。合并专家输出时仍依据原始亲和分数计算权重，而不是把 0.70 的路由分数直接当成输出权重。数字只是帮助理解“选谁”和“怎样合并”是两步，不代表真实路由概率或训练记录。

MTP 让模型训练时还考虑更多后续位置。原始 V3 的预测深度为 1：除了通常的下一个 token，还通过额外模块学习再往后的一个 token。普通生成仍依次产生 token；在支持的实现中，额外模块还可以提出候选，由主模型验证，以尝试推测解码加速。是否更快取决于候选接受率与实现开销，并不保证每次请求都有固定倍数。

### 混合精度与训练成本

FP8 混合精度让部分计算和数据传输使用较低精度，但关键环节仍保留更高精度以控制误差；它不是整个训练过程所有数字都压成八位。DualPipe 则尝试让计算与通信重叠，减少设备等待。把它想成厨房备菜和烧水同时进行：如果某一步远比其他步骤慢，仍可能等待。

论文列出正式训练约 278.8 万 H800 GPU 小时，其中预训练 266.4 万小时、上下文扩展 11.9 万小时、后训练 0.5 万小时；按每 GPU 小时 2 美元估算约 557.6 万美元。这里的范围不包括前期研究、架构或数据消融实验，也不应等同于完整研发预算。不同团队的硬件价格、实验次数和统计口径不同，不能用这个数字直接推断整个项目总成本。

## 评测怎么看

能力看代码、知识和推理等任务；系统侧看吞吐、通信、缓存和不同序列长度的成本。总参数与每 token 激活参数要分别报告。比较训练费用时还需注明硬件、阶段与统计范围，不能把单次报告数字当成所有研发成本。

论文表 3 中，V3-Base 的 MMLU 5-shot 精确匹配（EM）分数为 87.1，V2-Base 为 78.4；这是作者在同表所列内部评测框架下的对比。V2 原论文另一张表给出 78.5，比较时要注明出处，不能把两次评测当作完全同一实验。报告还说明 MMLU 使用基于困惑度的评测：按模型对候选选项的评分来判断选择，而不是让它自由生成一段回答后再直接比对文本。表格中的 EM 是报告列出的指标名称，理解分数时要连同这种作答方式一起看。分数差并不证明提升全由某一项架构改变带来，两代的数据、规模和训练流程也不同。V3 对话模型有另一组测试结果，不应混成基础模型成绩。

如果评测售后助手，可以分开记录：找到正确订单、识别最新状态、是否有依据、是否错误承诺退款。假设 20 条人工构造的测试里 17 条找对订单，但只有 13 条同时满足事实和业务规则，对应 85% 和 65%；这是计分示例，不是实测结果。测试还应覆盖两个订单相似、信息缺失和消息先后顺序反转的情况。

### 大容量，小激活，仍要保存大权重

若假设总容量为 100、每步用 5，计算只动用部分参数，不意味着其余参数从存储中消失。部署要看专家分布、通信与精度，不能按激活参数直接估整机内存。

比较 V3 与 Dense 时，同时记录质量、提示长度、并发和设备数；低并发的专家通信开销可能抵消部分收益。数字来自受控实验才有可比性，结构本身不承诺固定倍率。

## 应用与错例

服务高并发后速度下降，先看专家路由、设备通信、批量和上下文长度，而不是立即补训练数据。回答出错则另外查任务数据和对话模板。先保留模型精度与配置一致的基线，再验证优化是否损伤质量。

假设用户说“邻居已经代收”，助手却答“包裹未送达”。先保存完整输入、聊天模板、检索结果、模型版本与输出：后一句有没有进入上下文？订单接口是否返回了旧缓存？模型是否把两笔订单混在一起？如果输入就缺少关键句，应先修截断或检索。

确认错误原因后，把状态反转、相似订单和证据不足的案例分别加入开发集；按用户、订单或时间分组留出独立测试集。改提示、检索或训练后，既检查错误是否减少，也回归原来能正确回答的任务。这个数据到改进的过程是实验建议，尚未执行训练或评测。

## 比较与面试追问

[DeepSeek-R1](/nlp/deepseek-r1/)建立在 V3-Base 上，重点是推理后训练；它不是给 V3 助手简单改名。[Qwen3](/nlp/qwen3/)也有 MoE 规格，但具体路由、注意力和训练过程需分别读报告。

**MoE 比 Dense 总是快吗？** 不能保证，专家通信和硬件利用率会影响结果。

**MLA 与量化是同一种节省显存的方法吗？** 不是；前者改变注意力表示与缓存组织，后者改变数值存储精度。

**为什么说 V3 用了“无辅助损失”又有辅助损失？** 前者说的是主要的专家负载均衡方式；另有小的序列级辅助损失和 MTP 训练目标，不能把名字理解成整个训练只有一个损失。

**MTP 能否让模型一次无条件输出多个词？** 不能这样理解。训练提供额外预测信号；采用推测解码时仍要由主模型验证候选，实际收益取决于接受率和运行环境。

[DeepSeek-V3-0324](/nlp/deepseek-v3-0324-model/) 是后续的独立更新权重；它沿用同一架构，具体训练配方及评测应按该版本核对。
