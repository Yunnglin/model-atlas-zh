## 它解决什么问题

一个小商家希望助手帮忙处理订单：先读一段退货规则，再写一段计算退款金额的代码，最后查询订单状态。如果为阅读和代码分别使用模型，应用需要决定把请求送给谁，并处理两个系统之间的信息传递。一个同时擅长通用对话和代码任务的模型，能够让同一段上下文在多种任务间继续使用。

DeepSeek-V2.5 的官方模型卡将它介绍为结合 [DeepSeek-V2](/nlp/deepseek-v2-model/) 对话能力和 [DeepSeek-Coder-V2](/nlp/deepseek-coder-v2-model/) 代码能力的更新版。需要注意，“结合能力”是官方对模型定位的描述；公开资料没有证明它是把两份权重按某个比例简单相加，也没有公开完整配方。下文的商家订单与数字示例是教学构造，不是模型实际输出。

## 结构：一套文本主干处理多种任务

用户的文字先经分词器转为 token。因果模型根据已经给出的上下文逐步预测后续 token，生成的内容可能是解释、代码，也可能是符合某个工具协议的文字。应用可以把生成代码保存到文件，或将函数请求交给执行器；但语言模型本身不会因为写出“查询成功”就自动获得访问订单系统的权限。

官方配置把模型标为 DeepSeek-V2 架构，列出 60 层、隐藏维度 5120 和 128 个注意力头。模型卡引用的 V2 技术报告可以解释多头潜在注意力与混合专家的家族设计；报告发布早于 V2.5，不能把它当作 V2.5 每一项后训练设置的详细说明。

### MLA：保存什么，和看到了什么

问答持续多轮时，模型要使用之前的订单条款。常规自回归推理会在各层保存历史的键和值，避免生成每个新 token 时重新计算先前所有位置。历史越长，缓存也越大。多头潜在注意力（MLA）将键值信息压到较低维的表示，再供注意力计算使用；这主要是对表示和缓存的设计，不是把订单自动总结成一段可读摘要。

配置中出现 `kv_lora_rank` 等字段，是低秩键值表示的相关尺寸；不能因为包含 LoRA 这个词，就认定官方用 [LoRA 微调](/training/lora/)训练了 V2.5。长窗口也不保证模型能够无误地找到每一条规则：如果退款例外写在订单详情前面，系统应保留原文及版本，再测试模型是否正确引用。

拿一条 8,192 token 的对话做估算：配置列出 60 层、512 维压缩键值表示和 64 维位置相关键。如果推理实现逐层保存这两部分、每个数使用 BF16 的 2 字节，缓存约为 `60 × (512 + 64) × 8192 × 2` 字节，即 540 MiB。这个数只描述单条序列的假设缓存，不含模型权重、计算工作区和框架额外分配；不同框架若保存展开后的键值，实际占用也会不同。它帮助我们分清“模型支持多长输入”和“为这个输入需要多少缓存”是两个问题。

### MoE：参与计算和保存权重是两笔账

可以把混合专家想成一支大团队：输入中的每个 token 经路由规则挑选部分工作组参与，同时共享部分帮助处理常见信息。配置包含 160 个路由专家和 2 个共享专家，每个 token 选择 6 个路由专家；第一个前馈层为稠密结构。路由器学习如何选择，专家不是事先由人标注的“财务专家”或“代码专家”。

V2 报告中约 236B 总参数、21B 激活参数分别描述整个模型规模和每个 token 活跃的计算部分。它不意味着一张显卡只需装下 21B 权重：下一句话可能选到别的专家，还要考虑缓存、网络通信和计算工作区。官方卡的 BF16 本地推理示例使用 8 张 80GB 显卡，这是该示例的部署参考，不是所有量化方案或并行框架都必须满足的绝对配置。

### 代码补全与函数调用是两种交互

代码补全时，假设已有函数开头和结尾，中间缺少退款计算。模型卡展示 Fill-in-the-Middle（FIM）模板，显式标记前缀、缺口和后缀，让模型补写中间内容。输入顺序受特定模板控制，不应把普通聊天模板和 FIM 特殊标记任意拼接。补出来的代码仍需要语法检查和边界测试。

官方示例把前缀和后缀放进 `fim_prompt`：`<｜fim▁begin｜>{prefix}<｜fim▁hole｜>{suffix}<｜fim▁end｜>`。例如前缀写好 `def refund(price):`，后缀包含 `return amount`，模型的任务是补中间定义 `amount` 的代码。这些标记是模型词表里的专用格式，示例只是解释它们的位置。

函数调用则是另一件事：模型可生成符合工具协议的函数名和参数，外部应用负责鉴权、查询订单并返回真实结果。调用参数合法不代表查到的订单真实，工具调用失败也不能写成退款已经完成。官方模型卡给出工具调用和 JSON 示例；实际部署要以所用 tokenizer、模板和应用协议为准。

## 训练：什么是已知事实，什么是一般方法

V2 技术报告讨论了预训练、长上下文扩展、监督微调与强化学习。通俗地说，预训练让模型通过大量文本学习续写；[SFT](/training/sft/)用示范教模型按任务形式回答；偏好反馈或可验证奖励可以进一步改变模型的输出倾向。对代码题，程序运行与测试结果能够提供部分反馈，但测试覆盖不足时错误程序也可能通过。

V2.5 的官方模型卡强调继承两类模型的能力以及更好的指令遵循，但未列出足以复原更新版的完整数据来源、能力融合方法、训练阶段顺序或超参数。初代 V2 的 8.1 万亿 token 训练描述属于初代技术报告，不能据此宣称 V2.5 新增了同样规模的数据，也不能把后续 DeepSeek-R1 的强化学习流程倒灌到这个型号。

例如若要训练一个订单助手，可以提供“问题、完整规则、正确解释”的示范，再给代码准备覆盖正常退款、部分退款和费用边界的测试。模型漏掉优惠券时应补充相应样本，并让熟悉规则的人核对标签；这样的流程说明数据如何影响任务，不代表官方训练集包含这些案例。

## 评测：既看增强，也看退步

官方模型卡把 V2.5 与 DeepSeek-V2-0628、DeepSeek-Coder-V2-0724 分别比较：HumanEval Python 为 84.5、87.2、89.0；LiveCodeBench（01–09）为 36.6、39.7、41.8。这些是模型卡表格中的特定测试结果，不能转成“你的项目有 89% 概率正确”，也不能只凭数字判断实际工具环境和隐藏测试是否一致。

更有启发的是并非每项都上升：同表 SWE-verified 列出 Coder-V2-0724 为 19、V2.5 为 16.8。一个统一模型可能在某些通用或代码任务有提升，也可能在另一项任务低于专项模型；具体差异需要看任务和测评协议，不应只截取最有利的指标。模型卡未逐项完整列出采样预算与环境，跨其他报告比较更需谨慎。

在退款代码任务中，可以准备独立用例：正常退款、部分退款、优惠券分摊、运费归属、空订单和负数输入。记录代码能否执行、每条测试是否通过、是否误改不相关代码以及解释是否与实际结果一致。假设十个构造任务有八个程序能运行，但只有六个通过全部隐藏测试，启动率是 80%，严格通过率是 60%；这只是教学计分示例，未经模型实测。

## 应用与错例：数据如何形成闭环

假设助手生成了退款函数，却把运费也一并退还。先保存原始规则、生成代码、测试输入和执行输出，再确认规则是否写明运费可退。如果规则本身有歧义，先补充业务定义；如果规则清楚但模型漏读，应检查输入是否截断、提示是否包含例外条款，以及模型是否基于旧版本回答。

将失败按数据、代码、工具和评测问题分类：规则缺失应修数据，公式错误应增加边界用例，库存工具报错要检查权限或网络，测试期望错误则要修测试。准备下一批示范时，按商家、规则版本或代码仓库划分训练集与独立测试集，避免同一模板换个名字就出现在两边。

更新后回归常规订单和不允许退款的情况，分别记录正确率、工具执行成功率、未完成任务的说明和耗时。若涉及真实支付，退款结果应由经过验证的业务系统确定；模型生成的文字和代码只能作为待审核的建议。以上是可复现的设计方案，不是已经执行的训练或生产实验。

## 面试追问

**V2.5 结合两类能力，是否可以断言它是两模型权重相加？** 不能。官方介绍说明能力整合，但没有给出足以证实具体合并方法的完整训练细节。

**MLA 和 MoE 是否解决同一个问题？** 不是。MLA 关注注意力表示与缓存，MoE 决定每个 token 使用哪些前馈专家；两者都影响成本，但作用不同。

**为什么代码基准高，不代表每个项目都能自动修好？** 项目依赖、测试覆盖、工具权限和任务分布都不同；应固定环境并检查隐藏用例与错误修改。

**模型已经输出函数请求，订单状态就更新了吗？** 不一定。外部系统必须真正执行、返回结果并经应用核验。
