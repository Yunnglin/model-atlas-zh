## 它解决什么问题

一份采购合同很长，开头规定“验收合格后付款”，后面又写“项目延迟超过七天，需要双方重新确认日期”。如果只把其中一页交给模型，它可能漏掉另一个条件；如果把全文都放进去，模型虽然看得到，仍可能把两个日期或两家公司弄混。这里要分别解决三件事：输入能否装下、模型能否找到并理解跨页条件、系统能否在可接受的资源和时间内运行。

Qwen2.5-1M 是 [Qwen2.5](/nlp/qwen25-model/) 的长上下文分支。名字中的 1M 是上下文长度级别，并不是参数量；7B、14B 才是参数规模。官方发布的是两个单独的 Instruct 权重，不能把普通 Qwen2.5 的窗口配置改大，就说已经变成这两个模型。官方还讨论 API 模型 Qwen2.5-Turbo；它是另一种服务，本篇重点讲有公开权重的 7B 和 14B。

以下合同和算例均为帮助理解而构造，不是官方训练样本或实测结果。一个 token 不是固定的一个汉字，实际长度要由对应分词器统计。

## 结构：长文本怎样走进模型

两款开放模型沿用 Qwen2.5 的稠密解码器结构：文本经过分词变成 token，模型使用因果注意力查看当前位置之前的内容，经多层计算后预测下一个 token。它采用 RoPE 表示位置信息、GQA 分组查询注意力、RMSNorm 和 SwiGLU。它并没有因为上下文变长，就自动变成另一种图像模型或混合专家模型。

可以把上下文想成一张很长的工作台。GQA 让多组查询头共享一组键和值，减少需要保存的键值表示，但每个查询头仍可关注不同内容；这是缓存的组织方式，不代表模型把长文档自动压成一张摘要。已经处理过的键和值通常保留在 [KV Cache](/foundations/kv-cache/) 中，以便继续生成。材料越长，这部分缓存通常也越大，实际内存还受层数、精度、批量和引擎实现影响。

长文本计算至少有两个阶段：**预填充**读入提示并建立上下文表示；**解码**逐步生成答案。把 100 万 token 提示读进去时，预填充往往是明显成本；逐 token 输出时，历史缓存读取和生成长度也会影响速度。所以说“预填充加速四倍”并不等于最终答案四倍更快，也不表示使用的显存降到四分之一。

以官方模型卡给出的百万 token 部署配置为例：7B 需要至少 120GB 总显存，14B 需要至少 320GB 总显存，可以由多张 GPU 共同提供。它展示了长上下文缓存带来的资源需求；实际占用还会随精度、并发和引擎变化，不能把这些数字当成所有配置的固定门槛。

### 256K 训练，为什么可以尝试 1M

报告描述的长序列训练最大长度为 262,144 token，即 256K，而 1M 推理依靠额外的**长度外推**。可以把它理解为：学生主要在较长的练习册中学过找线索，考试时遇到更厚的册子，还需要一种处理更远位置的规则。它是模型训练与推理方法共同作用的结果，不是证明模型在所有百万长度任务中都准确。

报告使用 Dual Chunk Attention（DCA）：把序列划分成块，在计算注意力时调整相对位置信息，让某些很远的距离映射到训练时更熟悉的范围。同块位置、相邻块的近距离位置和不同块的远距离位置有不同处理；相邻块中足够近的内容仍保留短距离关系。重要的是，这个位置重映射并不等于删掉中间正文，也不等于先把每块总结后拼起来。报告实验还结合 YaRN 的注意力缩放；不同引擎是否真正实现这些处理，要查看其配置和版本。

稀疏注意力是另一层选择：为了减少预填充计算，系统挑选部分位置参与注意力计算。报告基于 MInference 并对长序列配置做了调整；它与 DCA 的位置映射解决的问题不同。具体地，报告在**挑选关键 token 时**使用更连续的位置关系，而最终计算注意力权重时仍使用 DCA 的位置编码；这两步不能混为一谈。稀疏处理可能漏掉证据，必须对照完整注意力评估质量，不能把“稀疏”理解成免费且永远无损。

## 数据与训练：从短材料逐步练到长材料

报告描述五个逐步扩展序列长度的预训练阶段：4,096、32,768、65,536、131,072，最后 262,144 token。前两个阶段沿用 Qwen2.5 Base 的训练过程，随后从其中间检查点继续进行长上下文训练。报告在不同阶段调整 RoPE 的基频，后面三个阶段的数据包含 75% 当前最大长度的序列与 25% 较短序列。这里的比例是报告所述训练配置，不是对所有版本通用的经验法则；中间检查点也不能简单等同已经发布的最终普通 Instruct 权重。

为什么不直接给模型一堆长书？自然长文里，有些下一词仅靠附近文字就能猜出来，模型未必需要利用很远的内容。报告因此结合自然长文本和合成任务，例如填补中间缺失内容、按关键词或位置找段落、重新排列段落。这些练习让跨位置联系更可能参与训练，但合成示例的质量和多样性仍需检查，不能因为数据长就断定模型学会了完整推理。

后训练也分阶段。第一阶段用不超过 32,768 token 的短指令数据进行 SFT；第二阶段混合短、长指令，最长到 262,144 token。长指令数据的一部分由 Qwen 模型围绕文档片段生成问题，再由 Qwen-Agent 结合检索、分块阅读等方式根据全文生成回答。合成回答可能存在遗漏或错误，因此它是训练数据来源的说明，不是对回答真实性的担保。[SFT](/training/sft/)解释示范与损失掩码如何配合。

报告还描述一种类似 DPO 的离线偏好优化，使用不超过 8,192 token 的短样本。在报告的长文本评测里，这一阶段表现得到改善；这不等于它一定需要长上下文 RL，也不能把这里的离线方法直接称为 GRPO 或把结果推广到所有业务任务。[DPO](/training/dpo/)讨论偏好数据的作用。

## 评测：找到线索和理解全文不是一回事

先做一项简单检索：在不同长度的材料中放入一段唯一口令，问模型口令是什么。它测的是在大量干扰文字中定位特定信息，不能证明模型能理解复杂合同。报告也使用 RULER、LV-Eval 和 LongBench-Chat 等任务，覆盖多种长上下文能力；每项成绩都依赖数据、长度、提示和评分方式。

一个具体对照来自报告表 2：在 14B 模型的逐阶段预训练实验里，128K 长度的 RULER 结果从 32K 训练阶段的 37.6，上升到 256K 训练阶段的 87.6。它们是报告中指定模型与阶段的分数，不是两款最终 Instruct 权重在所有任务上的成功率；不同训练阶段、外推配置和指标都不能随意混用。

长文本能力提升后，短任务也值得回归。报告表 6 中，14B 普通 Instruct 与 14B-1M 在 MBPP 上分别为 82.0 和 80.2，在 HumanEval 上分别为 83.5 和 88.4。它们是两套评测任务的报告成绩：有的下降、有的上升，不能只挑其中一个数字说长上下文训练一定改善或损害代码能力。比较自己的业务时，应固定模型版本、提示、采样与评分方式，同时测试长文和原有短任务。

报告还用 7B 的长文本找针实验比较推理配置：原始稀疏配置在超过 400K token 时出现明显准确率下降；结合位置选择和稀疏配置优化后，找针结果恢复大部分，同时该实验的预填充大约加速四倍。这个数字属于报告设置，与具体 GPU、引擎、输入长度和基线绑定；不能作为任意设备的吞吐承诺。

另一组速度对照更接近部署：报告在 1M token、批量 1 的设置下，用八路张量并行在 H20 上运行 14B 模型，首 token 等待从全注意力的约 12.2 分钟降到优化后的 109 秒。优化同时包含稀疏注意力和推理引擎改进；这段等待主要涉及读入长提示，生成完整回答还要另计时间。

做自己的合同评测时，不妨按材料长度、证据位置、条件数量、干扰信息和是否缺少答案分组。除最终答案外，还检查引用条款是否真实存在、多个条件是否同时保留、缺失时是否明确说不知道。比如十份合同中九份格式合规，但只有七份同时保留验收和延期条件，那么格式通过率是 90%，严格答案正确率是 70%；这是教学算例，不是模型成绩。

## 应用与错例：把答案追回原文

准备数据时，先从有权使用的文档中保留原文版本、页码或段落标识；确保训练、开发与测试尽量按合同模板或来源分组，避免几乎相同的合同跨集合泄漏。给测试问题标注证据位置、正确条件和缺失信息的处理方式。真实业务还应检查扫描件的 OCR 误差：模型读到的是 OCR 文本，原图里的数字不一定正确进入上下文。

假设系统答成“签署后 30 天”，而原文写“验收后 30 天”。先保存原始文件、解析文本、完整提示、输入 token 数、模型版本、推理配置与输出。检查证据是否在截断前、是否被文档解析错误修改；若没有进入上下文，先修解析或截断；若证据进入后仍答错，再分析是否受相似条款干扰，或长距离位置造成问题。用不同合同模板补充开发样例，修改后用未参与调参的独立数据重测，并回归短文本与没有答案的样本。

长上下文与 [RAG](/applications/rag/)也可以组合。长窗口适合容纳较多上下文，检索可以减少无关材料及成本，但检索错过证据时，生成模型无法凭空恢复。是否全量输入、检索、分段阅读或混合使用，应比较答案质量、可追溯性、延迟和资源，而不是只看窗口数字。

## 面试追问

**为什么说 1M 不等于训练长度？** 报告的训练最大长度为 256K，1M 处理还依赖推理时长度外推与相应实现。配置上允许更长输入，也不保证所有任务准确。

**DCA 和稀疏注意力有何区别？** DCA 调整分块后的相对位置处理；稀疏注意力选择部分位置参与计算，主要服务于计算效率。两者可以组合，但需要评估可能的质量损失。

**找到一条口令就说明读懂全文了吗？** 不说明。还需要测试多处证据组合、冲突条件、干扰项、缺失信息以及答案引用是否正确。

**为什么 7B 权重看起来不大，100 万 token 仍需要很多显存？** 长输入还带来 KV 缓存、激活值、计算工作区及批量开销；权重大小只是其中一部分。报告中的设备要求是特定软件和配置下的参考值。
