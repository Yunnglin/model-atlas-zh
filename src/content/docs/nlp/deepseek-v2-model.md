## 要解决什么问题

假设一家公司要让助手阅读长篇设备维修记录。技术员问：“这台机器上次更换轴承后，振动是否恢复正常？”助手需要找到正确设备、定位更换时间，再结合之后的检测结果作答。记录越来越长，系统既要尽量保持回答准确，也要考虑模型权重和历史信息占用的显存，以及多人同时提问的速度。

DeepSeek-V2 是 2024 年发布的文本模型系列。这里重点讲论文中的 **236B 总参数、每个 token 约 21B 激活参数**的型号，而不是直接把同一组数字套到 V2-Lite 上。上述维修情境及后面的数字例子都是教学构造，不是模型实测。系列脉络见 [DeepSeek 系列](/nlp/deepseek-family/)。

## 结构与数据流

[查看官方论文的 Figure 2 结构图](https://arxiv.org/html/2405.04434v5#S1.F2)：原图展示该版本的 MLA 与 DeepSeekMoE；正文配图是帮助理解数据流的原创简图。

模型整体仍是因果语言模型：输入文字分词后通过多层网络，每个位置只看当前及之前的内容，最终预测下一个 token。生成答案时重复这个步骤。图中把每层概括为注意力和前馈两块：V2 共 60 层，首层为稠密前馈，后 59 层使用 MoE。图省略残差、归一化和细节；论文 Figure 2 给出了更完整的 MLA 结构。

### 先分清两笔账

第一笔账是**模型权重**：它像整套维修手册，要存储并在运行时按部署方式放到设备上。第二笔账是 **KV Cache**：生成过程中，为已经读过的上下文保存可复用的注意力信息，避免每生成一个字就从头处理整段记录。它会随输入长度、并发请求数、层数和数据精度变化。[KV Cache](/foundations/kv-cache/)提供更一般的解释。

两笔账不能混为一谈。模型只有 21B 激活参数，不意味着仅装载 21B 参数就能原样运行完整的 236B 模型；没有被当前 token 选中的专家仍要按照分片或卸载方案保存。另一方面，即使权重放得下，并发用户和上下文增长后，缓存也可能成为显存瓶颈。

### MLA：把历史信息压缩后保存

普通多头注意力为过去每个 token 的各个头保存键和值。MLA 的核心思路是先把这部分信息投影到较低维的**潜在表示**，供键和值共同使用，并单独保留处理位置所需的部分。可以把它想成给维修记录做一份紧凑索引：每次回答依然要查历史，但不必为每个注意力头分别存一份完整索引。类比只帮助理解空间开销，不代表这个向量是一段人类可读的摘要。

位置编码不能随便省略：模型需要区分“先更换，再检测”和“先检测，再更换”。论文把需要旋转位置编码的部分与其他内容分开处理，以便结合低秩缓存与位置关系。具体矩阵推导可看[官方论文第 2.1 节](https://arxiv.org/html/2405.04434v5#S2.SS1)。

用官方配置估算一次缓存：DeepSeek-V2 有 60 层，键值压缩维度为 512，另有 64 维位置相关键。假设缓存使用 BF16、单条序列长 8,192 token，并使用保留压缩表示的 MLA 实现，需要保存约 $60 \times (512+64) \times 8192 \times 2$ 字节，即 **540 MiB**。这里计算的是 MLA 历史缓存；模型权重和计算工作区还要另算。多个请求如果各自保存完整缓存，占用也会增加。

论文把 V2 与前代 DeepSeek 67B 对照，在给定模型配置下报告 KV 缓存减少 93.3%。这不是所有硬件、所有上下文和所有框架都必然省 93.3% 的总显存：权重、临时张量和框架开销还在，而且需要实际使用压缩缓存的实现。知乎的[实现分析](https://zhuanlan.zhihu.com/p/700214123)指出，早期某些兼容实现把表示展开后缓存，因此难以得到论文描述的缓存收益；文章中的加速数字是其特定算子和设备实验，不等于端到端服务必然加速同样倍数。

**矩阵吸收是什么？** 想象注意力要计算 `查询 ×（投影矩阵 × 压缩后的历史）`。在符合维度和运算条件时，可以调整矩阵乘法的顺序，先把查询和投影矩阵结合，再与压缩历史相乘。这样不用为每个历史位置都先展开完整的键值表示。需要旋转位置编码的部分仍然单独处理；这个示意只解释计算顺序，不表示任何矩阵都可以任意交换。是否能节省时间，还取决于内核、输入长度和设备。

### MoE：不是所有专家同时工作

前馈部分采用 DeepSeekMoE。[MoE](/foundations/moe/)可以类比为一组维修顾问：每个 token 由路由器挑选部分顾问，另有共享专家参与。论文的 V2 配置中，除第一层外的 MoE 层有两个共享专家和 160 个路由专家，每个 token 选择六个路由专家；这不是六个人类意义上的固定专业岗位，也不表示每种语言必然对应一个专家。

专家分散在不同设备时，选择更多设备可能带来通信等待。V2 论文限制每个 token 的路由专家分布在最多三台设备，并在训练中使用负载均衡损失，避免少数专家过忙、其他专家缺少训练。实际速度还取决于通信、批量、专家并行和实现；激活参数少，并不自动保证任何场景都更快。

可以把这一步想成从八个维修小组里找顾问：路由器先看每个小组中最匹配的顾问，从中选出三个小组，再从这三个小组的顾问中挑出六位路由专家。六位顾问并不一定来自六台设备。这样给通信范围设了上限，但也可能错过其他设备上的某些高分专家；论文报告在其实验中限制为三台设备时，效果与不限制设备的路由大致接近，而不是说两种选择永远完全相同。训练时还用专家、设备和通信三个层面的辅助损失鼓励负载均衡，评测时不丢弃 token。

### 训练时，设备太忙怎么办？

负载均衡损失只能鼓励大家分担任务，不能保证每次都恰好均匀。假设某台设备在一个批次里接到的专家计算请求超过预算，其他设备却还空闲：如果所有设备都等最忙的那一台，整体训练会被拖慢。V2 论文采用设备级 token 丢弃策略，在超出预算时优先丢弃该设备上亲和分数较低的请求，并让约 10% 的训练序列不受丢弃影响。这里的“丢弃”指跳过相应的专家计算，不是把整段文本从训练数据中删掉。

论文评测时不丢弃 token；实际部署时采用什么容量和调度策略，需要和训练设置分开记录。这样才能理解前面的负载均衡、设备限流和丢弃策略分别在解决什么问题：[原论文第 2.2 节](https://arxiv.org/html/2405.04434v5#S2.SS2)。

## 数据与训练

### 预训练学什么

论文称预训练语料包含约 8.1 万亿 token，来自多种来源，中文数据量相对前代有所扩大。模型使用下一 token 预测：看到维修记录的前半句，尝试预测后续文本。通过大量这样的预测，参数逐步学习语言、知识和模式；并不保证模型记住某家公司的私有维修记录，也不能保证生成内容真实。

论文预训练阶段的序列长度为 4K，随后用 YaRN 等方式做长上下文扩展：扩展训练使用 32K 长度，论文评测中覆盖到 128K。训练序列长度与最终支持的窗口不是同一个数字；128K 也不等于任何位置的细节都能被准确找出。使用时还应核对服务端是否截断、提示模板占用多少空间以及输出预算。可以把目标记录分别放在开头、中间和结尾，加入相似设备的干扰记录来测位置敏感性。

### 从续写到对话

基础模型擅长续写文本，聊天模型还需要学习怎样回应指令。论文先做 [SFT](/training/sft/)：用问题和示范回答教模型回答形式，再采用强化学习做对齐。对维修任务，示范可以要求先引用检测记录，再解释是否恢复正常；这只是为了理解训练方式而构造的例子，并非官方公开的训练样本。

具体来说，论文报告 SFT 使用约 150 万条对话数据，其中约 120 万条用于有帮助性，30 万条用于安全；之后使用 [GRPO](/training/grpo/) 优化。强化学习先针对代码与数学推理使用训练得到的奖励模型，再结合有帮助性、安全和规则奖励进行偏好对齐。代码编译反馈和数学标准答案用于构造偏好数据，并不意味着 V2 的每次强化学习更新都直接运行编译器或核对标准答案。

奖励模型或偏好信号可以帮助调整回答，但不能代替可信的业务验证。若训练数据鼓励回答得很自信，模型仍可能把两台设备的记录混淆。对于缺少检测结果的输入，示范“不足以判断，请补充检测记录”也应进入评估，避免把拒绝猜测误判为失败。

## 评测怎么看

论文表 2 报告基础模型的 MMLU 五样本准确率为 78.5，DeepSeek 67B 在同一表中为 71.3。后续 V3 论文在其内部框架里重新比较时，V2 的对应数字为 78.4；两篇报告的结果应分别引用，不能假定评测细节完全相同。两者参数规模、架构和训练并不相同，不能把差距全部归因于 MLA 或 MoE。聊天模型也应与聊天模型比较，不要把基础模型和后训练模型的分数混在一起。

对维修场景，应单独记录证据定位、设备归属、时间顺序、答案事实和无法判断时的表现。假设 20 条独立样本中有 16 条找到正确设备记录，但只有 12 条完整回答正确，前者是 80%，后者是 60%；数字只是算例。人工检查时要保存输入版本和证据位置，错误答案如果碰巧写对结论，也不能直接算成证据使用正确。

对部署评测，还要固定模型版本、量化精度、硬件、框架、批量、输入与输出长度，分别测首 token 延迟、生成速度、吞吐量和显存峰值。尤其要确认是否使用压缩缓存和相关算子；只比较单个请求的速度，无法说明并发服务的整体成本。

## 应用与错例

假设助手回答“轴承更换后振动正常”，但引用的是另一台同型号机器的数据。第一步保留用户问题、模型版本、检索记录、原始上下文和答案；再依次检查设备编号是否被检索过滤、记录时间是否正确、完整证据是否进入上下文，以及生成时是否误认来源。若证据压根没检索到，先调整检索和数据质量，而不是立即判定模型需要重新训练。

接着收集容易混淆的设备编号、缺失检测数据、同一设备多次更换等例子，标明正确证据和“不足以判断”的边界。按设备或工单来源分开开发集与独立测试集，避免同一条记录的改写同时落入两边。先比较检索修改和提示调整；确需训练时再准备经过授权的示范数据，并回归普通问答与长上下文。该流程是可复现的实验设计，尚未实际运行。

## 比较与面试追问

**MLA 和 MoE 分别优化什么？** 前者主要改变注意力历史信息的表示和缓存方式；后者改变前馈层中哪些专家参数参与计算。二者同时出现，不代表节省的都是同一种资源。

**为什么 236B 总参数和 21B 激活参数都要看？** 前者关系到模型权重的存储与部署，后者描述单个 token 的计算路径规模。真实延迟还包括通信、缓存和框架开销。

**128K 上下文能保证找到每条证据吗？** 不能。窗口容量不等于有效利用能力，仍需按证据位置、干扰和截断情况评测。

**V2 和 V3 有什么联系？** 两者都使用 MLA 和专家模型，但版本配置、训练安排和能力不同。进一步可读 [DeepSeek-V3](/nlp/deepseek-v3/)，不要把某代的参数直接搬到另一代。

[DeepSeek-V2.5](/nlp/deepseek-v25-model/) 是后续独立权重，结合对话与代码能力；其更新配方应按官方资料核对。
