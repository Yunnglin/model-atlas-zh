## 它要解决什么问题

设想你让一名编程助手为已有网店增加优惠券。写出一段折扣计算函数只是开始：它还要找到订单接口、弄懂旧数据格式、修改前后端、执行测试，并在失败后查看错误。最后，如果页面能打开但订单金额算错，任务仍然失败。

MiniMax-M2.5 的目标是改善这类需要多步行动的任务。在 [M2.1](/nlp/minimax-m21-model/) 之后，官方尤其强调代码、搜索、工具使用，以及完成任务所需的时间。这里的“智能体”可以看成一个由模型、工具和运行规则组成的工作流程：模型提出下一步，外部程序执行，再把结果交回模型。模型并不天然拥有浏览器、终端或修改文件的权限。

下文以优惠券任务为例，介绍网络怎样生成下一步、训练如何使用反馈，以及系统如何检查任务结果。

## 结构：每次请一部分专家来帮忙

M2.5 是自回归解码器：把任务、已有对话和工具结果编码成 token，然后根据上文一次生成后续 token。生成到工具请求时，外部执行器可以暂停生成、运行工具，并把结果追加到后续上下文中。注意力负责让当前位置参考已有上下文；这不表示模型能像人一样永久记住整个项目。

它采用稀疏混合专家（MoE）。可以把专家想成一组可训练的计算模块，路由器为每个 token 选择其中一部分。官方配置给出 62 层、256 个本地专家、每 token 选择 8 个专家；注意力有 48 个查询头和 8 个键值头。这里的“专家”是可训练的前馈计算模块。

![MiniMax-M2.5 语言主干：输入经过 62 层，每层以因果注意力和稀疏专家处理，再预测下一个 token。](/figures/minimax-m2/backbone.svg)

上图依据 [M2 系列技术报告](https://arxiv.org/abs/2605.26494)和 [M2.5 配置](https://huggingface.co/MiniMaxAI/MiniMax-M2.5/raw/main/config.json)简化绘制。注意力负责让当前位置参考历史，专家网络负责对当前位置的表示进行进一步加工；这两步在每一层重复。

例如只估算一条序列的 BF16 键值缓存：62 层各有 8 个键值头，每头 128 维；输入 8,192 个 token 时，K 和 V 共约 `62 × 2 × 8 × 128 × 8192 × 2` 字节，即 **1.94 GiB**。这里算的是键值缓存，模型权重和其他运行开销另计；序列翻倍时，这部分缓存也随之增加。

总参数约 230B，每个 token 激活约 10B。像大型医院每次只安排部分医生会诊，能减少每次参与的计算；但医院仍要容纳全部医生。实际部署依然需要存放完整权重，并考虑显存、量化、缓存和跨设备通信，不能把它当作普通 10B 模型估算资源。配置还列有多 token 预测模块，具体推理是否使用及获得多少加速，取决于推理实现。

196608 是权重配置中的最大位置数，不是所有服务都承诺同样长度，也不是“放进去就都能正确理解”。长任务中的系统提示、工具结果、历史与输出都占预算；实际使用时应分别测试长文检索、上下文截断和任务成功率。

### 一次调用发生了什么

优惠券任务开始时，模型读到用户要求后，可能请求搜索订单逻辑；执行器查找文件并返回内容。模型再请求修改文件、运行测试，测试报错后根据日志继续调整。最后它向用户说明改动和验证结果。整个过程中的权限检查、文件读写和测试执行在模型外完成。

假如模型说“测试通过”，却没有实际执行日志，这只是生成的陈述；即使有日志，还要确认运行的目录、命令与退出状态对应当前改动。把“模型会说”与“系统做过”分开，才能避免误把解释当证据。

## 训练：让模型在可检查的环境里练习

### 任务、轨迹与奖励

普通语言模型训练常用下一 token 预测：给定前文，让模型学会预测后续内容。面向智能体的后训练进一步让模型在任务环境中尝试行动，根据结果更新策略。官方称 M2.5 在超过 20 万个真实场景环境中训练，涵盖多种编程语言和开发流程；完整任务列表、配比和样本并未公开，不能由总数推断各类任务的覆盖率。

例如训练优惠券修复时，一个环境包含项目文件、需求和可执行测试。模型尝试读取文件、修改代码并运行测试，这一串动作和返回结果称为轨迹。如果折扣功能正确、旧订单未受影响，可以获得正向反馈；若修改导致旧接口失败，则不应只因为代码看起来整洁就给高分。

训练前需要过滤不可运行的环境和不完整需求，并防止训练数据与最终测试集泄漏。测试只覆盖已写出的断言：即使所有测试通过，也可能漏掉并发下重复使用优惠券等问题。对于难以用程序直接判断的界面质量，可以结合明确评分规则和人工抽查，但自动评分器也会误判。

### 长任务为什么需要过程反馈

如果只在整个任务结束后给“成功或失败”，一条长轨迹中有几十次操作，模型很难知道是哪一步带来结果。好比学生做了一整张试卷，只知道最后总分，却不知道哪道题的思路错了。官方称在长上下文轨迹中引入过程奖励，帮助监控生成质量，同时考虑完成任务的时间。

过程奖励要谨慎设计。比如奖励“调用工具次数少”，模型可能为了省次数跳过必要测试；只奖励“测试通过”，模型可能走捷径修改测试而非修复代码。好的验证需要限制不合规行为，记录补丁并检查独立测试，还要用没参与调参的样本检查是否真正改善。官方没有完整公开全部奖励细节、数据比例和训练超参数，不能把示例当成官方实际配方。

### CISPO 与 Forge 分别做什么

官方称沿用 CISPO 进行强化学习优化，并利用过程奖励处理长轨迹。直观理解，优化算法负责根据反馈调整策略，并通过裁剪相关权重控制更新；它不负责决定网页能否打开，也不是 MoE 选择专家的路由器。关于如何实现，需要结合官方技术资料，不能仅凭名字推断具体损失函数和参数。

Forge 是衔接智能体、推理和训练的工程框架：让不同的智能体脚手架产生轨迹，再交给训练系统。后续系列报告描述异步调度和前缀树合并：多条轨迹前面若都是同一份任务说明与已有对话，可以先合并共享前缀的计算，再分别处理后续分支，最终仍分别计算每条样本的损失。它像几个人沿同一条路走到路口后再分头走，不必让每个人重复记录整段共同路线。

M2.5 发布资料已经描述树形合并训练样本及约 40 倍训练加速；后来的系列报告将相应结果写为**最高**可达 40 倍。两处都没有给出可推广到所有工作负载的平均倍数，这也不是 M2.5 在用户电脑上的推理加速。M2.5 已明确使用树形合并，但不能据此断定它使用了后续报告中的每一项优化；异步训练还需权衡生成轨迹时使用的策略与更新后策略之间的差异。

## 评测：成绩属于模型加工具的组合

官方模型卡报告 SWE-bench Verified 为 80.2%，Multi-SWE-Bench 为 51.3%，BrowseComp 在上下文管理条件下为 76.3%。前两者围绕软件仓库问题，后者侧重检索；它们回答的问题不同，数字不能直接相加，也不能解释成任意业务任务的成功率。评测涉及脚手架、工具权限、数据版本和预算，记录结果时应写清这些条件。

模型卡的评测说明称，SWE 系列基准在官方内部环境使用 Claude Code 脚手架、覆盖默认系统提示，并对四次运行取平均；BrowseComp 的 76.3% 明确带上下文管理。脚手架、提示或运行次数改变时，不能直接假设会得到同一个成绩。 官方还说明，BrowseComp 使用 WebExplorer 风格的框架：当 token 用量超过最大上下文的 30% 时，清空全部历史。想象助手已经搜集了多个网页，旧的搜索过程会被清除；这可以减少上下文占用，但也可能丢掉未另行保存的线索。因此这个成绩包含上下文管理策略的作用，不能拿来代表不清理历史的单次对话。

在两代官方模型卡列出的 Claude Code 设置中，M2.1 为 74.0%，M2.5 为 80.2%，相差 6.2 个百分点；两份说明均提到覆盖默认系统提示并平均四次运行。这为理解系列变化提供了一个对照。实际项目还需要用自己的仓库和测试评估。

同一份模型卡中，M2.5 在 SWE-bench Verified 使用 Droid 的结果为 79.7，使用 OpenCode 为 76.1。脚手架不同，提示、工具与交互循环也可能不同；这些结果不能证明某个框架在所有任务中更好。对比 M2.1 的分数时，还应核对同一数据集、评测时间、容器、运行次数与上下文处理方式。

官方还报告，在其 SWE-bench Verified 测量中，平均任务耗时从 M2.1 的 31.3 分钟降至 M2.5 的 22.8 分钟。按耗时计算约减少 27%；官方以耗时比的倒数表述为速度提高约 37%，两种比例的分母不同。这是指定任务和系统条件下的结果，不能直接推断所有 API 请求都达到相同提升。吞吐量、工具等待、并发、重试和模型输出长度都会影响实际耗时。官方 VIBE Pro 涉及应用开发，评分依赖其任务集和验证流程，也不能直接当作用户满意度。

如果自己做对比，可以准备 50 个独立优惠券任务，分别记录功能测试、回归测试、授权违规和完成时间。假设 35 个同时通过功能与独立回归，成功率是 70%；这是教学计算，不是模型实测。固定工具与预算，保留失败日志，再用同样规则比较不同版本，结论才更有参考价值。

## 应用与错例：从失败回到数据

假设一次修改正确计算了折扣，却允许同一张优惠券重复使用。先保存模型版本、输入要求、仓库快照、工具调用和测试结果；检查需求是否明确限制次数、模型是否读取了相关代码、测试是否覆盖并发，以及执行器是否运行了正确测试。

接下来收集经过脱敏的同类案例，补上并发和重复请求的独立测试，再按仓库或需求来源划分开发集与测试集。可以先改善需求模板、工具权限或检查流程；只有确认问题需要通过模型训练改善时，才进一步构造训练数据。改完后用未参与调整的样本检查成功率与误改率，避免只对一个错例打补丁。

应用时，网页内容、仓库文件和工具返回可能夹带与用户目标无关的指令。运行系统需要明确权限、隔离环境并由用户决定敏感操作，不能因为模型能调用工具就默认它拥有全部权限。

## 面试追问

**MoE 的 10B 激活参数是否意味着只需加载 10B 权重？** 不一定。每次计算只使用部分专家，但不同输入可能路由到不同专家，部署仍需考虑全部权重和通信。

**为什么强化学习需要可验证环境？** 因为反馈要能区分真正完成和看似完成。自动测试可以提供一部分证据，但其覆盖范围和可靠性仍需检查。

**过程奖励与最终奖励有什么差别？** 前者给中间步骤反馈，后者评价最终结果；前者有助于定位长轨迹，但设计不当可能鼓励走捷径。

**SWE-bench 分数代表模型单独写代码的能力吗？** 它反映指定模型、工具、脚手架和测试环境组成的系统在该基准上的表现。

**速度更快就一定更好吗？** 不一定。少运行必要检查可能更快却更容易出错，应同时看成功率、延迟、调用成本和安全约束。
