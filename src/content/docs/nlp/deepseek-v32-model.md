## 要解决什么问题

想象一个研究助手需要阅读上百页产品文档，并搜索最新变更，再回答“某个功能在哪个版本开始支持”。它不能只找到看似相似的段落，还要辨认版本、日期和来源；如果调用搜索工具，还要能根据返回结果继续判断。输入变长后，每一步都与大量历史内容计算注意力，会带来明显开销。

DeepSeek-V3.2 于 2025 年 12 月发布。它在 V3.1-Terminus 底座上通过继续训练引入 DeepSeek Sparse Attention（DSA），并加强了推理和工具使用的后训练。这里区分正式 V3.2、此前的 V3.2-Exp 和更侧重推理的 V3.2-Speciale，不把它们的成绩混在一起。下文用研究助手检索文档的例子说明它的工作过程。

## 结构与数据流

V3.2 仍是自回归语言模型：将输入拆成 token，结合此前内容逐步生成下一个 token。它沿用 V3 系列的 MLA 和专家网络；[DeepSeek-V3](/nlp/deepseek-v3/)解释模型的专家路由与训练背景。相比 V3.1-Terminus，报告指出关键架构修改是加入 DSA，而不是将整个模型重新设计为独立的搜索引擎。

官方模型文件页面的 Safetensors 信息显示约 685B 张量参数；V3 论文报告的 671B 总参数和每 token 37B 激活参数采用不同统计口径。总参数影响权重存储，激活参数反映每个 token 的部分计算路径。

### 先粗筛，再精算

假设文档有一万条历史 token，模型正生成有关版本的回答。DSA 的轻量索引器先为历史位置打相关性分数，从中选出一部分候选，再让主注意力对选中的位置做较精细的计算。它有点像先用目录找可能相关的章节，再仔细读这些章节；筛选对象是历史 token 的表示。

论文的稀疏继续训练配置中，每个查询最多选择 2048 个历史键值位置；这些位置按索引分数挑选，可能来自文档不同部分。若索引器漏掉关键证据，即使原文在上下文里，回答也可能出错。[注意力机制](/foundations/attention/)可帮助理解查询与历史信息的关系。

具体怎么打分？轻量索引器给当前 token 生成多组查询向量，也给历史 token 生成键向量；各组相似度经过 ReLU 和加权求和，得到每个历史位置的索引分数。它排序后把分数靠前的位置交给主注意力计算。索引器的头数较少，论文也提到可用 FP8 实现，目的是让粗筛足够便宜。

以五个历史位置的分数 `0.8、0.1、0.7、0.3、0.2` 为例，如果教学时把 Top-k 设为 2，主注意力会重点计算第一个和第三个位置。这个手算例子帮助理解排序；实际论文配置为 2048 个位置。

论文分析中，主注意力的计算量从随序列长度平方增长变为与序列长度和选中数量的乘积相关。索引器仍要对历史位置打分，其复杂度依然随长度平方增长，但索引器头数少、计算较轻；总耗时还受输入长度、批量和算子实现影响。

### MLA、DSA 和 MoE 管不同的事

MLA 主要组织注意力中的压缩表示和缓存；DSA 决定哪些历史位置进入主注意力的精算；MoE 决定前馈部分由哪些专家参与。三者作用不同，可以一起使用。[论文 Figure 2](https://arxiv.org/html/2512.02556#S2.F2)画出了 DSA 与 MLA 的组合，页面配图则突出粗筛和精算的关系。

如果助手要用搜索工具，模型先输出符合应用约定的工具请求，外部系统执行搜索，再把结果送回模型继续生成。搜索服务、浏览器与权限管理不在模型网络内部；模型声称“已经查到”并不能代替实际工具日志。

## 数据与训练

### 让新索引器逐步学会筛选

论文从上下文已扩展到 128K 的 V3.1-Terminus 基础检查点出发。第一步是稠密热身：保持主注意力按原方式计算、冻结除索引器外的参数，让索引器学习贴近主注意力聚合后的分布。可以把它想成让新同事先观察有经验的同事怎样挑重点，再开始自己筛选。

第二步引入稀疏选择，让主模型适应选中的位置，同时继续训练索引器。论文描述索引器与主模型分别使用对应的优化目标；主模型使用语言建模损失，索引器学习对齐注意力分布。报告给出了热身约 2.1B token、稀疏阶段约 943.7B token 的配置；这些是该工作报告的训练规模，不能理解为从零训练整个 V3.2 的全部数据量。

论文还给出了两阶段的具体批次：热身训练 1,000 步，每步 16 条 128K 序列；稀疏训练 15,000 步，每步 480 条 128K 序列。比如热身阶段按 1,000 × 16 × 131,072 计算，约处理 21 亿个 token。这里说的是训练过程中处理的 token 数，同一段数据可能重复使用，并不等于不重复的数据总量。后者同时训练索引器与主模型，让已有模型适应被筛选后的注意力路径。

热身时，主注意力会先给出各历史位置的重要程度，论文把各注意力头的分数聚合、归一化，再用 KL 散度让索引器学到相近的分布。进入稀疏阶段后，索引器仍根据所选位置对齐注意力分布，主模型则用语言建模损失适应新的计算路径。可以把前者理解为学习“找哪些段落”，后者理解为学习“用这些段落继续写答案”。

两者的训练信号也分开：论文在稀疏阶段将索引器输入从计算图中断开，索引器只由与注意力分布对齐的损失更新，主模型则由语言建模损失更新。比如索引器漏掉了一条关键版本记录，任务答案出错并不意味着这次答案损失直接穿过离散的 Top-k 排序去更新索引器；索引器还要靠自己的对齐目标学习。这里描述的是论文训练方式，不能简单套用到所有稀疏注意力模型。

### 从答题扩展到工具任务

继续预训练后，模型还要经过后训练。报告描述专家蒸馏与混合强化学习：先让不同任务上的模型产生训练材料，再结合推理、智能体任务和对齐信号训练。专家蒸馏中的“专家模型”是为特定任务训练的数据生成模型；它不等同于 MoE 层内部的路由专家。

报告将 [GRPO](/training/grpo/) 用于混合强化学习：推理和智能体任务结合规则奖励、长度惩罚及语言一致性奖励；通用任务则使用依据题目评分标准打分的生成式奖励模型。一个教学任务可以要求模型查询文档、读取工具返回、核对发布日期后回答；奖励或验证需要检查引用是否有效、是否调用了允许的工具以及最终答案是否正确。这样的例子用于解释方法，不是论文公开的原始样本。

怎样把思考与工具调用接起来？例如模型先判断需要查询发布日期，发起搜索，阅读工具结果，再决定是否需要第二次查询。论文让同一轮用户任务中的工具调用保留此前推理内容；用户开始新一轮对话时，旧推理内容会被移除，历史工具调用和结果仍保留。这样模型不用在每次工具结果返回后都从头梳理任务。

训练任务也有不同来源：论文列出约 5 万个搜索任务、约 2.5 万个代码智能体任务。搜索任务使用真实搜索接口和合成问题；代码任务从已有问题和修复记录构建，并准备可以运行测试的环境。模型要学的不只是写出工具请求，还要根据工具返回继续行动。

训练时工具返回可能很长、带错误或与之前结果冲突。训练数据可以包含失败反馈和需要重新查询的情况，帮助模型学习如何处理意外。

## 评测怎么看

要分开看三个问题：稀疏注意力有没有影响原有能力、长输入的计算成本怎样、模型能否完成工具任务。报告将 V3.2-Exp 与 V3.1-Terminus 在多项短文本和长上下文任务上比较，整体未观察到明显能力退化；这只覆盖报告中的数据和设置，不能证明任何任务都完全等价，也不能把正式 V3.2 的全部提升都归因于 DSA。

论文的 BrowseComp 搜索测试中，V3.2 Thinking 使用商业搜索接口；一些任务的轨迹超过 128K 上下文。未使用上下文管理时 pass@1 为 51.4，使用论文的 Discard-all 策略后为 67.6。论文在 token 使用量超过上下文窗口的 80% 时触发管理；Discard-all 会丢弃此前工具调用历史，腾出空间继续搜索。这样也可能丢掉之前找到的线索，适合结合任务检查是否需要重新搜索或保留摘要；两种设置的执行步数和计算成本也会不同。

代码任务的框架也会改变比较方式：报告中 V3.2 Thinking 的 SWE-bench Verified 为 73.1，使用内部代码智能体框架；Terminal-Bench 2.0 为 46.4，使用 Claude Code。论文还报告 Terminus 框架下非思考模式为 39.3。两项任务与框架不同，应分别看，而不是把两个数字当成同一实验的模式对照。论文附录还给出了较直接的模式比较：同为 Claude Code 框架，Terminal-Bench 2.0 的非思考模式为 37.1，思考模式为 46.4；这比拿 Terminus 的 39.3 和 Claude Code 的 46.4 相减更有可比性。结果仍属于论文的任务与运行设置，不能单独说明所有工具任务都能提高 9.3 个百分点。

对上面的文档任务，可记录正确找到版本的比例、引用来源是否支持结论、工具调用是否成功，以及首字延迟、总耗时和输入长度。假设 20 条构造样本中 16 条结论正确，但只有 13 条同时给出有效来源，两项分别为 80% 和 65%；这只是计分示例。将目标信息放在开头、中间和末尾，并增加旧版本干扰，可以发现不同位置与冲突证据造成的错误。

比较不同注意力实现时，还应固定设备、框架、模型精度、批量、输入与输出长度，并分别测预填充与生成阶段。索引器需要额外计算，短输入未必获得和长输入相同的收益；模型权重、缓存和工具调用时间也要分别统计。

## 应用与错例

假设助手引用了旧版文档，回答功能尚未支持。先保存问题、模型和提示版本、完整上下文、搜索结果、工具日志及最终答案。随后检查：新版资料是否被检索到？工具返回是否被截断？是否存在两个产品的同名功能？模型是否忽略了更晚的日期？证据没有进入上下文时，应先改善检索、排序或输入管理，而不是直接归咎于 DSA。

确认原因后，收集新旧版本并存、日期缺失、同名产品和工具失败的样本；按文档来源或发布时间分离开发集与独立测试集。调整检索或提示后，检查引用正确率、无依据时的拒答以及工具调用成本，再观察其他任务是否退化。这条流程将检索问题、上下文管理问题和模型回答问题分开。

## 比较与面试追问

**DSA 与 MLA 是一回事吗？** 不是。MLA 关注注意力表示和缓存；DSA 通过索引选择参与主注意力计算的历史位置。

**索引器选 2048 个位置，是否意味着其他历史被删除？** 不是。它描述一次查询的主注意力候选选择，不能据此推断整个系统永久丢弃其余上下文。

**Speciale 的成绩能直接代表普通 V3.2 吗？** 不能。它们是不同变体，推理计算预算和报告的评测条件也可能不同。

**模型输出工具请求就一定能完成搜索吗？** 不能。执行器、权限、网络与工具返回都在模型外部，需要查看真实调用和结果。
