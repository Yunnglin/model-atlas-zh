## 先看它想解决的问题

假设你让助手修一个老项目里的支付问题。需求文档、调用日志、历史工单和几十个代码文件加起来很长。助手不仅要找到造成重复扣款的地方，还要检查是否有类似漏洞、写测试、运行测试，并说明哪些风险仍未解决。

[GLM-5.1](/nlp/glm51-model/) 已经面向长程工程任务。GLM-5.2 进一步提供百万 token 级别的上下文配置，并改进稀疏注意力中的索引复用。直观地说，面对长材料时，它想减少“每一层都重新找一遍相关内容”的重复工作。

下文用支付场景说明它如何处理长任务。

## 结构：专家负责计算，索引负责找材料

GLM-5.2 是自回归解码器：先把文本转为 token，再根据前文逐步生成后续 token。注意力让当前 token 参考之前的内容；混合专家（MoE）让每个 token 只使用部分前馈计算模块。两者都可能被称为“稀疏”，解决的问题却不同：前者挑选要看的历史位置，后者选择参与计算的专家。

官方配置列有 256 个路由专家、每 token 选择 8 个路由专家和共享专家。可以想象一个大团队每次派部分成员处理任务，但专家只是可训练的计算模块，不能直接理解为人类划好的支付专家或安全专家。完整部署仍要存储权重并考虑通信、缓存和并发，不能只按每次激活量估算总资源。

GLM-5.2 的官方配置列出 78 层解码器、6144 维隐藏表示和 64 个注意力头。前 3 层使用稠密前馈，后 75 层使用 MoE 前馈；每个 MoE 层包含 256 个路由专家、每个 token 选择其中 8 个，另有一个共享专家。图中的主干步骤也适用于 5.1 的对应配置；两代使用各自的模型权重。

### 稀疏注意力像先查目录

当支付日志很长，模型每次处理当前位置都需要找出值得关注的历史。DSA 用索引器为当前位置挑选一批历史位置，再对候选做更细致的注意力计算。官方配置中的 `index_topk` 为 2048，表示相关选择配置；它不意味着每一轮都只能记住 2048 个 token，更不能据此证明百万长度的所有任务都能答对。

索引器本身也需要计算。如果模型每层都对漫长历史重新打分，找目录的成本也会累积。GLM-5.2 的 IndexShare 在多个稀疏注意力层之间复用索引：官方模型卡描述每四层共享索引，配置中可以看到 full 与 shared 的交替模式。这里复用的是被选中的位置索引，不是把四层的注意力输出直接复制成一样；各层仍需要做自己的后续计算。

按配置中的 `indexer_types` 从第一层开始数，前 7 层标记依次是 `full、full、full、shared、shared、shared、full`。结合 IndexCache 论文的解释，`full` 层重新挑选位置，`shared` 层沿用前面最近一次选择：因此第 4 至第 6 层复用第 3 层的索引，第 7 层再生成一份新索引。每层仍使用自己的表示计算注意力，复用的是位置清单。

举个缩小的例子：当前需要回答“退款允许几天内发起”，某组中的索引器从历史中选中位置 12、36 和 80；接下来几层沿用这份位置清单，但每层仍用自己的表示计算这些位置对当前回答的作用。若位置 36 是已经废弃的旧规则，而新规则恰好未被选中，复用并不能自动纠正这个选择。因此评测既要看长文本能否输入，也要看关键信息放在不同位置、混有旧规则时模型是否仍能找到正确依据。例子只说明机制，实际索引数量及实现以具体配置为准。

可以类比四位审计员一起检查账本：第一位先找出相关页面，其他几位沿用页面清单，但每人仍按自己的规则检查内容。节省的是重复查找的部分；如果相关位置选择不佳，后续复用也可能沿用遗漏，所以需要评估质量而非只看速度。

官方模型卡报告在 1M 上下文条件下，IndexShare 将每 token 相关 FLOPs 降低 2.9 倍。这个数字有明确条件，不能写成整个服务或每次请求必然快 2.9 倍。设备、批量、缓存、内存带宽和工具等待都影响端到端延迟。相关研究论文名为 IndexCache，讨论跨层复用；它的实验模型和加速数字也应与 GLM-5.2 的具体报告分开。

### MTP 与推测解码

官方还称改进了多 token 预测（MTP）层，配合推测解码时，接受长度最多提高 20%。可以把它想成先草拟几个接下来可能出现的词，再由目标模型验证；验证不通过的部分不能直接当成最终结果。接受长度提高不等于所有任务速度提高 20%，具体收益依赖推理框架、任务、采样设置和硬件。支持这一机制的部署方式需要单独确认。

### 百万上下文与实际使用

官方配置的 1048576 是位置数。实际应用还要为系统提示、工具结果、已有对话和模型输出分配预算；服务的限制可能更小。在这个范围内容纳支付日志，不代表每条日志都对答案有贡献。错误信息可能被遗漏、同名字段可能混淆，甚至无关文本可能干扰决策。应在不同位置插入关键证据，测试查找、综合和引用是否正确，而不只检查接口能否接收长输入。

## 训练：区分已公开与合理设计

官方模型卡引用 [GLM-5 技术报告](https://arxiv.org/abs/2602.15763)，前代报告讨论预训练、监督微调、强化学习及智能体基础设施。它提供理解系列背景的入口，但并不是 GLM-5.2 完整训练账本：不能把前代报告的数据量、奖励函数或超参数直接认定为本版本的数据与配方。

以支付案例理解一个可能的训练环境：任务描述要求保证同一订单不会重复扣款，环境提供代码仓库、可控的数据库和测试。模型提出读取文件、修改代码、运行测试的请求；执行器返回真实结果；验证程序检查重复请求、异常恢复和旧功能。这段任务、工具调用及结果共同构成可记录的轨迹。这里描述的是教学设计，不声称是官方使用的具体样本。

若仅奖励“测试通过”，助手可能通过删掉测试或写死示例得到高分。可增加独立的隐藏测试、限制测试文件修改，并人工抽样检查补丁；但测试依然可能遗漏并发、网络重试或边界数据。训练集和评测集还应按项目及问题来源隔离，防止同一缺陷的相似版本混入两边。

长上下文训练也不是简单把窗口调大。任务要包含有用的远距离证据、无关干扰和需要跨文档组合的信息；评测必须检查模型是否真的引用了正确材料。官方模型卡没有完整披露训练数据的混合方式和长程奖励配方。

## 评测：把分数和条件一起读

官方模型卡报告 GLM-5.2 在 SWE-bench Pro 得分 **62.1**，GLM-5.1 为 **58.4**。前者评测采用 OpenHands、定制提示、400K 上下文与指定生成设置；这是模型加脚手架、工具和测试环境的结果，不是任意真实项目的成功率。SWE-bench Pro 与 SWE-bench Verified 是不同基准，不能拿两个分数直接相减。

同一模型卡报告 Terminal-Bench 2.1 的 Terminus-2 结果为 **81.0**，另一个 best reported harness 结果为 **82.7**。前者使用 256K 上下文、指定时间和资源限制，后者对应不同脚手架及预算；两个数字提醒我们记录评测条件，不能只凭分数断言某个框架普遍更好。需注意，GLM-5.1 模型卡将其 63.5 标为 Terminal-Bench 2.0，而 GLM-5.2 模型卡将同一数值列在 2.1 对照表；两张卡的标签不一致，不能仅凭数值相同断言测试协议完全相同。NL2Repo 的 **48.9** 评估从需求到仓库的任务，和终端操作或缺陷修复又是不同问题。

具体说，模型卡为 Terminus-2 设置每题最多 4 小时、500 个 episode、4 个 CPU 和 8 GB 内存；82.7 则来自 Claude Code 脚手架，输出上限为 131,072 token、不设总时间上限，并取 5 次运行的平均值，两者保留每题 CPU 和内存约束。可以把它看成同一位参赛者在不同工具和比赛时限下作答：分数有参考价值，但不能把差距全部归因于模型或某一个工具。

模型卡中 HLE 与 HLE-with-tools 分别报告 **40.5** 和 **54.7**，使用的是纯文本子集，后者有工具条件；不同配置的分数不应被当成单纯的模型内部能力。读任何成绩时，先问数据集版本、提示、工具、预算、运行次数和评分方式，再决定是否可以比较。

自己的支付评测可以准备未参与调参的工单：按问题来源隔离项目，分别检查缺陷是否修复、旧流程是否仍正常、是否误改权限、工具调用是否真实执行，并记录时间和费用。假设 40 个任务中 28 个同时通过独立功能与回归测试，成功率是 70%；这是说明计算方法的虚构数字，不是 GLM-5.2 实测。

## 应用与错例闭环

假设模型修复了单次重复提交，却没有处理两个请求同时到达的情况。先保存仓库版本、任务描述、模型与脚手架配置、提示、工具日志、补丁和测试结果。排查需求是否明确要求并发安全、测试是否真正覆盖并发、模型是否看到数据库约束，以及运行的命令是否对应当前代码。

收集脱敏的相似错例，补充并发请求和失败重试的独立测试，明确期望行为。先完善需求、工具限制和回归测试；如果多项目仍反复出现同类错误，再考虑构造训练数据。改动之后，用没有参与调整的仓库复测成功率、误改率、延迟和人工审查成本，不能只验证一条原始错例。

实际智能体还会读取外部网页和仓库内容，其中可能夹带误导性指令。应用需要约束工具权限、隔离环境并保留执行证据；模型提出的命令不等于已经得到授权或已经成功执行。

## 面试追问

**IndexShare 与 MoE 的稀疏是一回事吗？** 不是。前者减少跨层重复挑选历史位置的索引计算，后者选择参与前馈计算的专家。

**每四层共享索引，就是四层的结果都一样吗？** 不是。共享选出的历史位置索引，各层后续的注意力计算仍然不同。

**1M 上下文就能保证模型找对信息吗？** 不能。窗口长度是容量配置，检索和综合的准确率需要按任务、信息位置及干扰情况评估。

**接受长度提升 20% 等于端到端速度提高 20% 吗？** 不等于。还要看验证开销、硬件、批量、框架和任务。
