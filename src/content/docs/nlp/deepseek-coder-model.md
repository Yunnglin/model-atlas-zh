## 要解决什么问题

想象你正在写购物车代码：前面已经定义 `items` 和价格字段，光标后面还有调用这个函数的测试。你需要补上计算总价的一行。这时只看光标前面不够，后面的调用也会告诉你函数返回什么类型。如果再涉及其他文件中的折扣规则，模型还得看到相关定义，否则只能猜。

代码模型可以把这些上下文和需求当作文本输入，逐 token 生成代码。它像一位能根据样例给出建议的搭档，但不会自动读到整个仓库，也不会因输出了代码就自动执行测试。IDE 或应用需要主动选取并提供上下文；模型能生成不代表代码能够编译、通过测试或符合业务约定。本文代码情景均为教学构造。

## 结构与数据流

初代 DeepSeek-Coder 使用仅解码器的 Transformer。输入经分词器拆成 token，模型根据前文预测下一个 token，循环生成直到结束。[Transformer](/foundations/transformer/) 和[注意力机制](/foundations/attention/)可帮助理解它怎样利用已看到的内容。对于函数续写，输入可能是签名、注释和部分代码；输出则是随后可能出现的代码。

论文描述旋转位置编码 RoPE，以及 33B 模型使用分组查询注意力 GQA；GQA 让多组查询共享部分键值表示，通常有利于减少缓存，但收益取决于硬件和实现。不应把 33B 的该项细节直接套用到所有规格。与 V2 的专家路由和 MLA 不同，初代正文讨论的是稠密解码器；后代架构的变化请看 V2 页面。

论文给出三种主要规格的具体配置：1.3B 使用 24 层、隐藏维度 2048、16 个注意力头；6.7B 使用 32 层、4096 维和 32 个头；33B 使用 62 层、7168 维和 56 个查询头，并采用 8 组键值头的 GQA。例如 33B 每 7 个查询头共享一组键值头，计算注意力时查询仍各自独立，缓存则不必为每个查询头保存一套 K/V。

### 中间补全：先看后文，再补空白

普通续写好比给一句话接尾巴；中间补全（FIM）则要给定空白之前的前缀和之后的后缀。例如前缀是 `def total(items):`，后缀是 `print(total(cart))`，中间缺少函数体。系统先按模型要求用特殊标记组织前缀与后缀，再让模型生成缺失部分。这样后面的调用也能作为条件，但模型仍可能忽略它或误判返回类型。

原论文采用前缀、后缀、中间内容的 PSM 格式：训练时把已有文本拆成三段，重排成前缀、后缀、要预测的中间段，并使用特殊标记区分。模型实际依然逐 token 预测下一项；它并没有获得在正常生成时直接看到未来 token 的魔法。推理时应按对应检查点提供的 FIM 格式构造输入，不要把标记混进普通用户文本后假设模型一定理解。

例如官方 6.7B Base 示例先放 `<｜fim▁begin｜>` 和函数前缀，再放 `<｜fim▁hole｜>` 和后缀，最后以 `<｜fim▁end｜>` 引出要生成的中间部分。把“已知后缀”移到生成目标之前，模型就能在自回归生成中使用它；完整格式可查看[官方代码示例](https://github.com/deepseek-ai/DeepSeek-Coder#2-code-insertion)。

### 仓库上下文如何进入模型

假设 `checkout.py` 调用 `discount.py` 的函数。将相关函数签名、约定和调用点按合理顺序提供给模型，比只给一句“实现折扣”更有机会写出兼容代码。仓库级训练让模型接触跨文件的依赖关系，但实际使用时仍受 16K token 上下文、检索质量和输入顺序限制；整个项目通常无法完整放进去，读取权限也由外部工具决定。

当自动检索给出了旧版本函数定义，模型可能生成看似合理却无法运行的调用；当接口文件根本没有进入上下文，它也可能编造不存在的方法。因此需要记录提供给模型的文件版本、路径和范围，再结合测试定位错误，不应把“看过仓库级数据”当成理解任何仓库的保证。

## 数据与训练

### 从代码仓库整理样本

论文报告初代模型从头训练约 2 万亿 token，数据约为 87% 源代码、10% 与代码相关的英文自然语言、3% 与代码无关的中文自然语言。训练材料覆盖 87 种编程语言，但各语言数据量并不相等；覆盖某种语言不意味着该语言的表现与 Python 一样。token 是训练量单位，不等于代码行数、项目数量或独立用户数量。

团队收集公开仓库并进行规则过滤、依赖解析、仓库级去重和质量筛选。仓库级组织的目的，是尽量保留文件间关联：比如先看到被调用函数的定义，再看到调用它的代码。仓库级去重可以减少相近项目带来的重复，但并不能证明没有任何重复、错误、敏感信息或许可问题。用于实际微调的数据还需要单独检查授权、隐私和组织策略。

具体来说，论文先解析文件间的依赖，再按依赖关系组织文件并在文件开头加入路径注释；随后将连通子图中的文件拼成训练样本。遇到循环依赖时，论文用改造过的排序策略处理，而不是假装所有项目都能严格排出先后。这样模型在训练时有机会先看到被调用的定义、再看到调用，但真实项目的构建、运行时依赖不一定都能靠静态分析捕获。

论文也描述对已知测试集按文本片段做去污染检查。类似代码可能以其他形式出现，或测试集本身有训练阶段无法发现的重复，因此这类过滤只能减少风险，不能证明没有所有潜在泄漏。自己的验证集应按项目、来源或时间分组，避免把同一仓库的近似函数同时放进训练和测试。

### 续写、FIM 和指令微调

训练既包含普通的下一个 token 预测，也包含 FIM 样本。论文在 1.3B 和 Python 子集上比较不同 FIM 比例：较高 FIM 比例有助于对应的填空任务，但可能牺牲普通续写表现；最终使用约 50% 的 PSM FIM 比例，在任务之间做权衡。这个比较是在特定实验和基准下得到的结果，不是所有模型、语言都适用的最优比例。

基础模型 Base 主要学习代码和文本的分布。Instruct 则在 Base 上继续用指令数据微调，帮助它按照“写一个函数并解释复杂度”这样的要求组织回复。两者回答格式不同，使用时应检查模型卡和对话模板；评价 Base 的代码续写与 Instruct 的指令回答，也不能把提示方式和成绩直接混为一谈。

长上下文也不是只改一个配置数字：论文描述调整 RoPE 的缩放和频率后，以 16K 长度再训练 1000 步。虽然作者讨论了理论上的更长范围，实际报告中更可靠的范围是 16K；把文件塞进窗口并不保证模型一定找到其中的关键信息。指令微调阶段，论文报告共使用 2B token、每批 4M token，学习率初始值为 1e-5，含 100 步预热；这些数字描述的是论文实验，不是所有代码模型的通用配方。

## 评测怎么看

HumanEval 给出函数描述或签名，让模型生成代码后运行测试。论文报告的多语言 HumanEval 表中，初代 33B Base 的 Python pass@1 为 56.1%，33B Instruct 为 79.3%；论文使用贪心解码，并用统一脚本和环境比较模型；这些是不同模型和提示条件下的报告结果，不是说它们能解决对应比例的所有真实工程问题。pass@1 衡量单次候选是否通过任务测试；采样、测试集和执行环境不同会影响结果。

测试通过也不等于程序在所有输入都正确。例如需求是汇总购物车金额：公开测试只有两个正常商品，模型写的代码通过了；另一个测试加入空列表、折扣字段缺失、负数和小数精度，错误才出现。应为每个场景检查预期行为，尤其区分需求没写清楚与模型忽略明确要求。隐藏测试应独立保留，不要把答案或测试实现直接提供给模型。

单行 FIM 评测关注缺失位置能否补成期望的代码，往往用文本完全一致等指标；实际代码可以有多种正确写法，因此文本不一致也未必功能错误。跨文件补全更考验相关定义是否进入上下文，论文还用 CrossCodeEval 比较；它与整仓库 issue 修复、IDE 响应时间和安全性并非同一个指标。

论文还在 DS-1000 测试数据科学库相关代码：33B Base 的平均 pass@1 为 40.2%，其中 NumPy 为 49.6%，Pandas 为 25.8%。这提示同一模型在不同库上的成绩也会相差很大；不同数据集的提示、候选生成和执行条件不同，不能把 DS-1000 的平均值与 HumanEval 分数直接相减，当成能力变化。

例如论文的跨文件实验对 6.7B Base 使用 CrossCodeEval 提供的 BM25 检索结果，限制输入为 2048 token、生成最多 50 token，其中跨文件上下文最多 512 token，并报告完全匹配和编辑相似度。对同一个模型，Python 的完全匹配从不加检索的 9.53% 到加检索的 16.14%；这同时改变了模型能看到的资料，不能说模型权重因此变好，也不能推广为所有仓库的提升幅度。

比较模型时，应固定版本、提示和模板、可见文件、采样参数、候选次数、运行环境与超时。若一个系统可运行测试并反复修补、另一个只允许生成一次，它们消耗的工具和时间预算不同。执行生成代码时应使用隔离环境、限制网络和资源，并审查可能访问私有信息或修改文件的操作。

## 应用与错例闭环

假设补全出来的总价函数对普通输入正确，但购物车为空时报错。先保存模型和模板版本、前后文、生成代码、依赖版本和测试输出。检查是需求未规定空列表返回值、上下文缺少约定，还是模型看到约定却没遵守；不同原因对应不同改进，不必第一时间重新训练。

根据错例补充空列表、缺失字段、错误类型和精度边界样本，由工程人员核对预期值。把同一项目或相似模板留在同一个数据分组，保留独立测试；先试改检索、提示和测试，再决定是否需要微调。改动后检查目标错例与其他任务是否退化，并记录延迟、计算成本和人工修改量。这是可复现的实验方案，不代表已经实际运行。

## 比较与面试追问

**FIM 是否让模型变成双向注意力？** 不一定。它把前缀和后缀整理到生成目标前面，解码器仍按自回归方式预测中间段。

**仓库级训练后就不需要检索文件了吗？** 不是。模型只能使用当前输入和自身参数中的信息；特定项目的最新接口仍要由应用提供。

**Base 与 Instruct 有什么区别？** Base 主要面向续写等基础能力，Instruct 通过指令微调更适合按需求回答；使用模板与评测条件也不同。

**初代与 Coder-V2 是同一结构吗？** 不是。初代从头训练稠密模型，V2 基于 DeepSeek-V2 中间检查点继续训练并采用 MoE；具体规格与训练量应分别核对。

**HumanEval 高分就能保证代码安全？** 不能。测试覆盖有限，也不替代权限控制、安全审查和真实业务评测。
