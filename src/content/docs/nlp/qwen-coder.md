## 要解决什么问题

“写一个函数”与“修好一个仓库”不同。仓库里的错误可能来自依赖、配置、调用位置或测试本身。Qwen-Coder 的学习重点，是从代码序列预测走到读取环境反馈、修改与验证。

下面沿一个**虚构小项目**走：`count_items(["a", "b"])` 应返回 2，当前实现却用了 `len(items)-1`。代码和工具轨迹是教学材料，没有在本站执行，也不是官方评测样本。[返回系列](/nlp/qwen/)。

## 结构与数据流

模型仍根据输入生成 token：可以是补全代码、解释，也可以是工具调用。外部执行器才真正打开文件、运行测试或修改环境。Qwen3-Coder 包含 MoE 型号；Coder-Next 明确基于 Qwen3-Next-80B-A3B-Base，采用混合注意力与 MoE。

总参数、激活参数与 Agent 不是一个分类层次：前两项关乎网络计算，后者关乎模型与工具怎样循环工作。官方结构／训练资料从[仓库与报告入口](https://github.com/QwenLM/Qwen3-Coder)阅读，不使用品牌图或成绩海报充当网络结构图。

## 先分清补全与修仓库

### 中间补全：为什么前后都能给，仍是自回归

假设给出：

```python
# 前缀
def total(price, count):
    # 待补内容
# 后缀
    return amount
```

希望补的是 `amount = price * count`。FIM 训练会按相应格式重新组织前缀、后缀和待补片段，让模型在已给两侧条件下生成中间内容；**不是取消了因果掩码让它偷看目标答案**。具体特殊 token 和次序按该代训练格式，不能随便拼字符串冒充官方模板。

### 真实修改：模型需要看到执行结果

| 教学步骤 | 工具／输入             | 应留下什么证据             |
| -------- | ---------------------- | -------------------------- |
| 定位     | 读失败测试和函数文件   | 实际文件版本、错误断言     |
| 假设     | 判断 `-1` 可能错误     | 与需求的对应，而不只猜补丁 |
| 修改     | 将错误计数改为目标行为 | 补丁及修改范围             |
| 验证     | 跑相关与必要回归测试   | 命令、环境、退出状态、输出 |
| 完成判断 | 对照原始要求           | 测试通过之外，是否遗漏约束 |

只给最终正确代码，能教会一类映射；保留这些轨迹，才有条件学习何时查、怎样修与怎样判断完成。模型说“测试通过”与工具实际返回通过是不同证据。

## 数据与训练

| 主线          | 主要学习内容                                     | 不能只背的标签                   |
| ------------- | ------------------------------------------------ | -------------------------------- |
| CodeQwen1.5   | 早期代码预训练、补全与指令                       | 不是通用聊天提示的别名           |
| Qwen2.5-Coder | 多规格代码、FIM、指令与执行相关能力              | 代码数据与普通散文数据的分布不同 |
| Qwen3-Coder   | MoE、代码与 Agent 任务                           | 不只是参数更多                   |
| Coder-Next    | 可执行任务合成、环境交互与 RL 等，基于 Next 底座 | 架构与训练任务都需对照           |

代码预训练学语法、库与项目模式；SFT 学需求到修改；工具轨迹与执行反馈又提供不同信号。测试结果可进入奖励，但**现有测试没有覆盖的行为不会自动被验证**。不能只要模型让几个已知测试变绿，就把奖励叫“完整正确性”。

训练材料需记录仓库、提交、依赖、任务、工具消息与结果，隔离同仓库近重复和评测补丁。报告中的任务合成与后训练路线，不能被简化为“多抓一些 GitHub 文件”。

## 评测怎么看

### 函数对了，不等于仓库任务完成

函数基准可以检查候选能否通过测试；仓库任务还受检索、环境、工具、补丁和验收影响。固定 harness、工具权限、网络、依赖、超时、重试次数与 token 预算，再比较模型。

对于这个教学计数任务，至少包括两元素、空列表、一元素等边界。如果原需求还要求输入类型校验，那几条计数测试通过仍不足以证明需求全完成。不能在看到模型输出后，临时删掉对它不利的测试。

### 同时保留成功与花费

记录单次成功率、失败类别、工具次数、耗时与输出量。多次尝试后的 pass@k 与首次成功不同；某个 harness 的成绩也不是仅由权重决定。[语言模型评测](/evaluation/llm-benchmarks/)说明协议差异。

可把任务失败分成：没找到代码、误解需求、改错逻辑、执行环境失败、没有验证。只有部分失败适合补代码训练数据，依赖没装好应先修环境。

## 应用与错例

编造库函数时，检查版本与实际文档；改错文件，查检索和仓库上下文；测试通过却没有完成目标，补行为验收；工具返回错误却被忽略，保留相应恢复轨迹。

改进后用独立仓库任务回归，保留未适配模型和同环境基线。不要只把旧补丁换个变量名当新测试，更不要把官方榜单数字当本站实测。

## 比较与面试追问

**FIM 与 BERT 填空相同吗？** 都利用两侧条件，但输入组织、架构与生成目标不同。

**工具调用是模型内部执行代码吗？** 模型生成请求，执行器执行，结果再成为新输入。

**Coder-Next 为什么不只是更大的 Coder？** 读 [Next](/nlp/qwen-next/)看混合注意力，再看环境交互训练；结构、数据、工具和预算一起决定表现。
