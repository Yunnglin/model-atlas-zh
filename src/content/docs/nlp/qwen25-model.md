## 要解决什么问题

假设一份合同写着：“甲方为星河公司；付款期限为验收完成后 30 日。”我们希望助手返回甲方和付款期限，并且按照固定 JSON 格式输出。这个任务看似只要找到几个字，实际包含识别主体、理解条件、计算日期起点、决定字段以及组织格式。模型可能把甲方和乙方弄反，也可能输出合法 JSON，但把“验收后”说成“签署后”。

Qwen2.5 是 2024 年 9 月发布的 Qwen 文本模型系列。这里讲公开的 **Qwen2.5 文本模型**，不把 Qwen2.5-VL 的图像编码器或 Omni 的语音模块算进来。官方发布包含不同规模的 Base 和 Instruct 权重；Coder、Math 是针对不同任务训练的分支，并不是普通聊天模型只改了个名字。每个权重的许可和上下文配置需查看对应模型卡。[Qwen 系列](/nlp/qwen/)列出家族位置，[Qwen2.5-VL](/omni/qwen-vl/)则从发票例子解释视觉输入。

这里的稠密结构指表中开放权重的文本型号。官方技术报告还介绍了用于 API 服务的 Qwen2.5-Turbo 和 Qwen2.5-Plus MoE 型号；不能因为它们同属 Qwen2.5，就推断与这些开放的稠密权重结构相同。

下面用一份虚构合同贯穿讲解。

## 结构与数据流

这是一张依照官方技术报告绘制的教学简图，省略残差连接、归一化、位置编码、注意力头和张量形状；它帮助看清数据往哪走，不替代完整架构图。开放的 Qwen2.5 文本系列使用稠密的 decoder-only Transformer。模型把输入切成 token，映射成向量，经过多层解码器，最终为词表中的候选计算分数，再选出下一个 token。输出一个 token 后，它会加入已有上下文，模型继续预测下一步。

### 用合同例子走一遍

如果提示以“甲方是”结尾，模型可能继续输出“星河公司”。这里的“下一个 token”不是天然等于一个汉字或一个词，具体怎么切由 tokenizer 决定。例如“星河公司”可能被切成一个或多个片段；推理时模型处理的是这些编号及其向量，应用层再把结果还原为文字。[分词](/foundations/tokenization/)介绍字符、词和 token 的区别。

每层里的因果注意力允许当前位置参考此前输入，不允许偷看尚未生成的后文。可以想象正在逐格填写表格：当前格可以查看左边已填过的内容和给出的合同，但不能先看下一格的标准答案。注意力把“甲方”和“星河公司”等位置的线索关联起来；前馈网络继续处理每个位置的表示。多个层重复进行这些工作，并不是只有一层在读合同、另一层单独负责答案。

### GQA、位置和前馈层分别做什么

Qwen2.5 使用分组查询注意力 GQA。假设教学网络有 8 个查询头、2 组键和值，四个查询头共享一组键值。像多位读者使用共同索引，各自仍可以提出不同查询；它主要减少推理中需要保留的键值缓存，并不意味着所有查询得到同一个答案。这个 8 和 2 只是解释例子，不是所有 Qwen2.5 型号的头数。具体规格应查对应配置。[KV Cache](/foundations/kv-cache/)解释为什么历史越长，缓存越占资源。

实际 [Qwen2.5-7B-Instruct 配置](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct/blob/main/config.json)是 28 层、28 个查询头和 4 个键值头；与 Qwen2-7B-Instruct 具有相同的这些配置字段。模型改进还涉及数据与训练，不能仅凭这几个字段相同就认为两代模型完全一样。

这组头数也能用来估算缓存：7B 的隐藏维度为 3584，28 个查询头，每头 128 维。假设单条输入有 8192 个 token、K 和 V 均用 BF16 存储，仅 28 层键值缓存需要 `28 × 2 × 4 × 128 × 8192 × 2` 字节，即约 **448 MiB**。同样条件下，输入增加到 32768 token，是原来的四倍，缓存也增长到约 **1.75 GiB**。这是帮助理解长度和缓存关系的估算；模型权重、中间张量、批量和框架管理空间需要另算。

RoPE 给查询和键提供位置信息，使模型能够区分词序。把“甲方通知乙方”和“乙方通知甲方”互换时，词出现过并不够，次序关系也很重要。RMSNorm、SwiGLU 和残差连接分别参与数值调整、前馈变换和信息传递；把它们比作流水线部件有助于入门，但没有任何一个部件单独保证模型能理解合同。

### 训练时为什么不用一个字等一个字

训练材料的正确后续已知，可以把完整序列送进模型，在因果掩码下并行计算各位置的预测损失。掩码禁止当前位置使用未来文字；目标答案仍作为训练监督存在。推理时没有标准后续，只能把已生成结果接回去继续预测，因此长回答会逐步产生。[下一 token 预测](/foundations/next-token/)进一步说明这个差别。

## 数据与训练

### 预训练：先学习一般语言与知识模式

官方报告称预训练数据集规模从前代约 7 万亿扩大至约 18 万亿 token，并强调知识、代码、数学和多语言材料。这里统计的是数据集中的文本单位，不代表各规格都按完全相同的次数处理每条数据，也不等于公开了全部原始数据、每个样本或可复现的全部处理流程。数据去重、质量过滤和语言构成都会影响结果，所以不能把能力变化全部归功于 token 数增长。

拿合同任务作类比：预训练可以让模型熟悉大量语言、格式和常见关系，但它不会自动知道某家公司的真实审批规则。企业规则若没有放进输入、检索结果或适当训练材料，模型不能凭空知道规则刚刚发生的变化。事实与时间敏感的信息仍需查证。

### 后训练：从续写变成按要求回答

Base 模型擅长按前缀延续文本，但不一定遵循对话格式。Instruct 模型在已有基础上使用监督微调与偏好对齐等方法，让回答更贴近指令。一个教学 SFT 样本可以把合同和问题作为输入，示范答案写成 `{"party_a":"星河公司","payment_condition":"验收后30日"}`。生成式 SFT 通常仍用下一 token 的预测损失，只是选择了示范答案作为希望模型学习的输出。[SFT](/training/sft/)解释示范数据如何构造。

官方系列技术报告提到超过 100 万条 SFT 样本，以及包括 DPO 和 GRPO 的多阶段后训练。它描述的是系列训练方法，不能据此断定每个公开检查点都使用了完全相同的数据和训练步骤；具体型号没有公开的配方仍应视为未知。

偏好训练可以比较两份候选：一份保留“验收后”，另一份漏掉触发条件。好的标注应指出具体差异，而不是只因为 JSON 漂亮就选它。这个对照是解释思路，不代表官方训练使用过这两份材料。训练数据若包含大量相同模板的合同，测试集也照搬模板，即使公司名称换了，结果依然可能高估泛化。

[报告第 4 节](https://arxiv.org/html/2412.15115)将后训练分成离线偏好学习和在线强化学习：前者使用已有偏好对进行 DPO；后者使用奖励模型评分，并以 GRPO 更新策略。报告称在线阶段每个问题采样 8 个回答，并优先处理回答评分差异更大的问题。可以想象对同一份合同生成 8 个 JSON，再比较这些回答的评分：如果有的保留了“验收后”、有的漏掉条件，一组回答就可能提供区分信号。奖励模型的分数是训练信号，不等于人工逐条核实的合同事实；这个合同例子只是讲解，不是官方样本。Qwen2 报告中的在线阶段则是用奖励模型选出偏好对继续做 DPO，两代不能简单写成相同算法。

### 长上下文不是开关

较长上下文让输入容纳更多条款，但“放得下”和“找得准”是两件事。需要确认模型版本、推理框架、位置配置以及实际截断情况。某份合同在前页定义验收、后页描述付款，如果检索只送入后页，模型无法可靠推断缺失条件。若两页都在上下文中仍答错，再检查距离、干扰条款和推理能力。以 [Qwen2.5-7B-Instruct 模型卡](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct)为例，默认配置为 32768 token，更长输入需要按工具文档配置 YaRN；静态缩放也可能影响短文本效果。1M 版本有单独的训练与推理方案，不应把普通权重改个长度配置就宣称等价。具体见 [Qwen2.5-1M](/nlp/qwen25-1m-model/)。

## 评测怎么看

### 把格式、事实和缺失处理分开计分

构造 10 份互不重复的合同：如果 9 份输出是合法 JSON，但只有 7 份的字段和条件全部正确，格式合法率是 90%，严格任务成功率是 70%。这两个数来自构造的例子，不是 Qwen2.5 的实际成绩。还需要单独统计字段缺失时是否如实标记、引用的证据是否支持答案，以及甲乙方交换时是否跟着改变。

评分器也可能出错。例如“验收完成后三十日”和“验收后 30 天”在某些任务协议中可视为同义，但“签署后三十日”不能因为天数相同就算正确。先写清规范化规则和证据要求，再运行评测；答案提取失败、模型答错和数据标注有歧义应分开记录。

论文表 8 给出了同为 7B Instruct 的代际对照：Qwen2 在 MATH 上为 52.9、HumanEval 为 79.9；Qwen2.5 分别为 75.5 和 84.8。这是[技术报告](https://arxiv.org/html/2412.15115)中两项任务的测试结果，数学与代码任务各有自己的数据和评分规则，合同抽取仍需使用合同样本单独评估。Qwen2 的 GPQA 成绩及官方资料的使用顺序见 [Qwen2](/nlp/qwen2-model/)。

### 比较模型要控制什么

比较 Qwen2 与 Qwen2.5 时，尽量对齐模型规模、Base 或 Instruct、提示模板、上下文长度、生成预算和抽样方式。参数量不同、允许重试次数不同或使用了外部检索，都会影响结果。报告中的 MMLU、代码和数学题反映各自测试条件，不等于企业合同任务必然达到相同比例的正确率。

建议把测试按“跨页条件、同名主体、否定条款、信息缺失、长上下文”切片。平均分改善时，也要看最关键的风险切片有没有退化。如果模型对短合同表现好、长合同失误，检查实际输入是否截断，再设计相同内容不同距离的对照，避免把截断错误直接归因于架构。

## 应用与错例

将它接入合同助手时，业务流程可以先读取文档和定位相关条款，再让模型输出字段与证据，最后由确定性程序检查格式和必填项。系统需要给“找不到相关条款”留出口，而不是强迫模型每次都给付款日期。人工复核重点应放在高风险、低置信或缺乏证据的结果上；模型输出概率本身也不能自动视为校准后的可信度。

遇到“付款期限”错误，保存合同版本、检索片段、完整提示、模型 ID、参数和原始回答。先判断证据有没有进入模型；若根本没有，优先修复检索或切分；若证据完整但关系理解错误，再考虑加入有对照的标注样本或调整训练。新样本进入开发／训练池，保留来自不同合同模板的独立测试集，避免只修好眼前的例子。

## 比较与面试追问

**Qwen2.5 和 Qwen2.5-VL 的输入是否一样？** 不一样。本页的文本模型接收文本 token；VL 还要把图像处理成可与语言模型配合的表示。视觉模块、输入分辨率和视频处理需要看对应版本。

**GQA 和 MoE 是一种东西吗？** 不是。GQA 关注注意力头怎样共享键值；MoE 关注前馈计算怎样选择专家。Qwen2.5 这批开放文本权重是稠密模型，不要把 Qwen3 或其他型号的 MoE 配置直接套进来。

**合法 JSON 就证明抽取正确吗？** 不能。格式只是输出能否解析，还要核对字段、证据与条件。用户读模型结果时，应当知道文档里找不到证据也是一种有效结论。

**为什么官方榜单提高，实际业务不一定提高？** 数据分布、标签规则、工具链、预算和指标不同。将业务验证设计成可复现对照，并保留错误分类，比直接搬用榜单更能说明问题。
