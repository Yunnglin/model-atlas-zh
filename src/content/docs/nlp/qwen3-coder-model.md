## 要解决什么问题

项目的 `count_items` 函数少算一个元素，单独写出 `len(items)` 并不等于修复任务完成：还要找到真正使用它的文件、改对位置、运行相关测试，并检查空列表是否正常。Qwen3-Coder 面向代码和多轮工具交互，目的是让模型更好地参与这类开发任务。

本页主要以官方首发的 **Qwen3-Coder-480B-A35B-Instruct** 为例，系列其他规格不能直接套用这些数字。下面的仓库、命令和失败轨迹均为教学构造，未运行对应模型或评测。

## 结构与数据流

输入可以包括需求、已经读取的代码和先前工具结果。语言模型逐 token 输出说明、代码或工具请求；实际读取文件、修改和执行测试是外部系统的工作。下方是原创教学简图，真实权限、执行环境和反馈由使用它的应用决定，图省略模型内部层细节。

官方模型卡将该检查点描述为因果语言模型和 [MoE](/foundations/moe/) 模型：总参数约 480B，每个 token 激活约 35B；62 层，每层有 160 个专家，路由激活其中 8 个。可以把专家想成很多不同工位，每次只调部分工位处理当前信息，但模型实际用的是可学习的路由与网络权重，不是人工给每个专家安排一种编程语言。

### 总参数和激活参数有何不同

“每个 token 激活约 35B”帮助理解单次计算，并不意味着只需把 35B 权重放进显存，也不是所有输入的实际算力和延迟完全相同。总权重如何分布在设备上、量化精度、专家通信、批量、上下文长度和推理框架都会影响内存与性能。用总参数比较部署体积、用激活参数讨论部分计算，是两张不同的账。

该检查点的官方模型卡注明仅支持非思考模式，不输出 `<think></think>` 块；这描述输出模式，不代表它不能完成多步代码任务。模型卡将该检查点许可标为 Apache 2.0，其他型号仍需分别核对。

模型卡还列出分组查询注意力：96 个查询头、8 个键值头。查询与键值头共享关系影响缓存和计算组织；它不代替专家路由。注意力负责在上下文中联系信息，MoE 是前馈计算的稀疏路径，不能把“8 个专家”解释成“只能看 8 个文件”。

**算一笔长上下文的缓存账。** 以一条 65,536 token 的请求为例，假设 62 层都保存 K 和 V，每个数使用 2 字节，按照配置中的 8 个键值头、每头 128 维估算：`62 × 2 × 8 × 128 × 65,536 × 2` 字节约为 **15.5 GiB**。这只是 KV 缓存的估算，不含模型权重和运行时工作区。若框架使用缓存量化、分页或多设备分布，单卡实际占用会不同；上下文翻倍时，未压缩的缓存也会随之增长。这个例子有助于理解为什么原生支持长上下文不等于任何设备都能轻松承载。

### 走一遍修复任务

用户给出需求后，外部工具可以读取失败测试、函数文件和调用方；这些内容进入模型上下文。模型提出改动，应用工具把补丁写入工作区，再运行测试，结果作为新的输入。若测试报告空列表失败，模型可以根据该反馈修改，而不是假装第一次就已经完成。

保存实际读取的文件、补丁和命令退出状态，便于检查模型如何使用工具反馈。长上下文可以容纳更多资料，哪些文件进入上下文仍由外部工具决定。

## 数据与训练

官方发布说明称该模型预训练使用 7.5 万亿 token，代码比例为 70%，并用 Qwen2.5-Coder 辅助清理和改写部分噪声数据；还混合其他材料以维持通用和数学能力。token 是分词单位，不是代码行数或互不重复的仓库数量；官方说明没有公开的具体样本、过滤规则不能自行补造。

按这两个公开数字粗算，代码约占 5.25 万亿 token，剩余约 2.25 万亿 token 来自其他材料。它们是训练过程中处理量的比例估算，不是去重后的代码库规模，也不能据此判断每种编程语言各占多少。评测业务代码时，仍要单独检查所用语言、框架和项目版本是否覆盖。

对于长上下文，官方说明该检查点原生支持约 256K token，通过 YaRN 等外推方法可以扩展；实际服务是否配置扩展、有效长度与成本要看框架和设置。窗口上限不保证模型能从任意位置找到细节，也不保证复杂跨文件推理正确。

官方发布说明给出的外推目标最高为约 1M token，而仓库模型卡中的 `max_position_embeddings` 为 262144。前者需要额外的外推方案与兼容实现，后者是该配置中的窗口字段；不能只看到 1M 就假设下载权重后在任意框架默认生效。

### 多轮训练与最终代码有什么区别

如果训练样本只含“需求 → 最终补丁”，模型可以学习一种输入到输出的映射，却不一定学会查看测试失败后调整。官方介绍后训练中的长程 Agent RL，让模型在多轮工具和环境交互中学习；任务可能包含观察、行动与反馈，而不是只有最终答案。[RLVR](/training/rlvr/) 可帮助理解可验证反馈，但具体任务、奖励和训练配置仍应以该发布材料为准。

官方发布说明称其训练系统可以并行运行 20,000 个独立环境，以支持大规模反馈收集。这里描述的是训练基础设施的能力，不代表每个任务都需要 20,000 个环境，也不说明某次实际训练同时运行了多少任务。环境之间需要隔离项目状态与依赖，否则一个任务改写的文件可能污染另一个任务的反馈。

例如同一个计数错误，好的轨迹包括找到源码、修改、测试、发现边界失败再修正。环境反馈比人工写的“应该正确”更容易检查，但测试只覆盖已有用例：若模型修改测试来绕过断言，表面成功不代表满足原需求。训练与评测都需要固定测试和判断标准。

## 评测怎么看

### 函数基准与真实项目任务

函数题通常给定签名和测试，判断候选程序是否通过；仓库任务还涉及搜索、文件编辑、工具权限、依赖和多步恢复。用同一套模型分别测试，前者成功不保证后者成功。[语言模型评测](/evaluation/llm-benchmarks/) 解释通用协议与分数口径。

对教学计数任务，至少保留空列表、一个元素、多个元素和题目明确要求的类型边界。固定不可修改的验收测试与原始需求，避免模型删掉断言却被记为成功。测试全部通过只能证明覆盖到的行为，不证明整个项目完全正确。

官方发布图给出了一个可直接观察工具预算影响的例子：Qwen3-Coder-480B-A35B-Instruct 在 SWE-bench Verified 上使用 OpenHands，最多 100 轮交互时为 67.0%，最多 500 轮时为 69.6%。两个数字对应同一模型的不同交互预算；更多轮次为模型留下更多查找、修改和处理测试反馈的机会，同时也会增加运行成本。论文式分析时应记录实际使用轮次、耗时和工具配置。

### 模型之外也要记录什么

比较代码 Agent 时，固定评测集版本、工具框架、提示、可读文件、命令权限、网络、运行时间、最大轮数与重试次数。相同权重搭配不同执行器可能得到不同结果；若一个方案能访问更多文件或多次重试，分数差异不能只归因于模型。

记录任务完成率的同时保存补丁是否应用、测试是否启动、耗时、工具调用数量和失败类别。官方报告或榜单中的成绩是特定条件下的结果，不代表用户仓库中的实际表现。

## 应用与错例

假设模型改对了计数，却在错误文件中插入重复函数。先查看工具到底读取了哪些路径、搜索结果是否指向实际调用方，再检查补丁和测试是否覆盖调用链。若测试根本没启动，优先查依赖、环境和命令，而不是把环境错误当成模型不会编程。

下一轮可以按“没找到文件、错误补丁、测试执行失败、忽略反馈、虚报通过”分组收集案例；按仓库和提交拆分开发集与独立测试集，保留不同依赖版本。固定基线后比较真实通过率和成本，并回归原有功能。这里是复现实验计划，尚未实际训练或运行。

### 回归时保留对照

修复后还应在独立版本或新任务上复测，并记录模型版本、提示、工具与依赖。若只对同一个公开补丁反复测试，可能测到的是对历史内容的记忆，而不是面对新问题的能力；同时检查未改动的接口，避免修好一个用例却破坏其他调用。

## 比较与面试追问

**为什么 35B 激活不等于只存 35B 权重？** 未激活的专家仍可能在其他 token 被路由到，部署需要考虑完整模型的存储与分布。

**Qwen3-Coder 能自己执行代码吗？** 模型生成代码或请求，文件读写和命令执行需要外部工具；只有返回的真实执行结果才能作为证据。

**与 Coder-Next 有何区别？** [Qwen3-Coder-Next](/nlp/qwen3-coder-next-model/) 的指定模型基于混合注意力 Next 底座，参数和训练路径不同；不能只凭同为 Coder 就视为同一结构。
