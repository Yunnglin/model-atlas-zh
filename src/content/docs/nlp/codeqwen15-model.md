## 要解决什么问题

你写了一个函数，想让助手补上计算总价的代码：输入单价和数量，输出两者的乘积。普通聊天模型能看到文字，但软件中的缩进、类型、函数边界和调用约定都有意义。CodeQwen1.5 通过大量代码相关材料训练，让语言模型更擅长处理代码。

本页围绕官方公开的 7B 基础模型和 Chat 模型。示例函数、错误输出和测试结果都是教学假设，未实际运行。它属于 [Qwen1.5](/nlp/qwen15-model/) 时期的代码分支，不应把后续 Qwen2.5-Coder 的训练流程直接套过来。

## 结构与数据流

下方原创简图展示：把代码或问题切成 token，送入因果解码器；模型参考前面的输入，逐步生成接下来的 token。需要运行代码时，由模型外部的执行器负责，模型本身生成的文本并不会自动执行。图省略注意力内部、残差与归一化，依据是官方模型卡，不是官方架构图。

CodeQwen1.5 基于 Qwen1.5 的 decoder 语言模型，官方基础模型卡指出其使用分组查询注意力 GQA。简单说，多组查询头可以共享较少的键和值表示，以降低某些推理阶段缓存的开销；具体实际速度仍取决于输入长度、硬件和推理实现，不能从 GQA 单独断言线上提速比例。

以官方 7B Base 配置为例，它有 32 层、32 个查询头和 4 个键值头，隐藏维度为 4096。可以把查询头理解成多个提出问题的窗口，而键值头提供可供查询的内容：这里每 8 个查询头共用一组键和值，但它们仍可分别关注不同的信息。配置中的最大位置数是 65,536，且没有启用滑动窗口注意力；代码实现中出现的 `Qwen2ForCausalLM` 是模型类名称，并不表示它是后续 Qwen2.5-Coder。

### 跟着一段代码走

假设提示为 `def total(price, count):`，后面期待一个函数体。分词器把代码拆成模型使用的 token，拆分边界可能与单词、变量名或整行代码不同。模型逐步预测，例如先输出换行与缩进，再输出 `return price * count`。这里只描述可能的生成路径，并不保证实际输出一定如此。

因果解码的意思是：预测下一个 token 时，只使用已放入上下文的输入与已经生成的内容。它可以学习 Python 的常见缩进与表达式形式，但不会因为“像代码”就自动保证逻辑正确。输入参数如果含负数、小数或货币精度要求，简单乘法是否符合业务仍需看完整需求。

### Base 与 Chat 如何选

基础模型更适合按既有文本继续生成；Chat 版本经过面向对话的训练，更适合按指令回答。官方模型卡也提示基础模型不建议直接当聊天助手使用。给基础模型补全函数和给 Chat 模型下达“解释并修改函数”是不同调用方式，比较结果时要分别固定提示模板与解码设置。

官方材料提到 64K 上下文能力。上下文窗口是模型一次可处理输入和输出的上限条件，不是保证它对窗口内每个文件都理解正确；系统实际能否启用该长度，还依赖所用配置、库版本与显存。超出窗口被截断的文件，不会因为在磁盘上存在就自动进入模型。

## 数据与训练

官方发布说明称模型在约 3 万亿 token 的代码相关数据上进行预训练，支持 92 种编程语言；这不意味着每种语言都达到相同准确率。这里的 token 不是文件数、代码行数或互不重复的仓库数；官方公开的规模也不等于完整数据清单、许可和过滤细节都公开。

为了处理跨文件的信息，团队还构造了仓库级长序列代码数据：模型不只看一小段函数，也有机会在更长的上下文里看到相邻文件和定义。可以把它想成从只读一张代码片段，扩展到读一叠相关文件；但这并不保证实际应用中每个依赖文件都会被正确选进上下文。官方还提到使用合成 SQL 数据进行预训练和微调，不能据此推算其他数据的具体比例。

代码预训练可理解为让模型见到大量程序及相关文字，通过 [下一 token 预测](/foundations/next-token/) 学习常见形式和上下文关系。它可能学到函数签名附近经常出现的返回值，也可能记住过时 API 或训练材料中的错误。遇到新的库版本时，查该版本文档和执行测试仍然必要。

Chat 版本再经过指令对齐，学习根据用户问题组织回答。具体数据配比、每条样本来源以及完整后训练细节若未在当前材料中公开，就应保持未知；不能把后续模型报告里的阶段或数据量当成第一代的事实。

### 如果自己准备业务数据

以计数函数为例，一条训练记录可以包括需求、修改前代码、正确修改、相关测试及运行环境。若只保存最终代码，模型能看到结果，却看不到错误为什么发生。对于需要读取多个文件的任务，记录依赖文件的版本和约束比只保存某个函数更有帮助。

清理训练集时按仓库和提交去重，检查许可证与来源，并将评测仓库及近重复内容隔离。比如同一个函数只改变量名就拆到训练和测试，测试可能高估对新任务的泛化。数据拆分、执行和授权都应依据实际工程完成，这里只给出方案。

## 评测怎么看

### 先定义“正确”

对 `total(price, count)`，最基本的测试可以检查整数输入：`total(3, 2)` 是否返回 `6`。再根据需求检查零数量、负数、异常输入和金额精度。只运行一个例子通过，并不能证明所有输入都正确；也不能在看到输出后删除失败用例，让分数变好。

代码生成基准通常根据自动测试判断候选是否通过。pass@1 关注单次候选的成功率；多次尝试后的 pass@k 是不同统计量，必须记录采样数量与方法。与此不同，完全匹配指标要求输出字符串与参考答案一致：`return count * price` 与 `return price * count` 在某些类型下可能行为相同，但文本不完全相同；反过来，文本相似也不能保证边界正确。

官方发布材料包含多语言代码生成与补全等评测；比较模型时必须对齐具体版本、提示、测试集、运行环境、依赖、超时和解码参数。官方榜单成绩是其协议下的结果，不代表在你的仓库也能测得同样表现。

举个看表格的例子：官方发布的 HumanEval 零样本结果中，CodeQwen1.5-7B Base 为 51.8，7B-Chat 为 83.5；同表的 HumanEval+ 分别为 45.7 和 78.7。这里先要确认模型版本和测试集，再看数值：更严格的测试可能发现原测试未覆盖的问题；不能将 Base 的分数套给 Chat，也不能把这些公开基准数字当成你的项目成功率。

官方 LiveCodeBench 测试覆盖 2023 年 9 月 1 日至 2024 年 4 月 1 日的题目。对于 LiveCodeBench，官方还特别提示：预训练语料可能包含 LeetCode 数据，因而可能对成绩产生影响。使用新的竞赛题可以降低部分已知数据重合风险，但发布日期新并不自动证明训练中没有见过相关内容。比较结果时应查看具体题目时间范围与去重方式，不能把这个成绩当作完全排除污染的证明。

### 长上下文要检查实际证据

把函数定义放在长文件前面、调用要求放在后面，测试时分别改变关键信息位置，并核对没有截断。若模型只在开头正确，可能存在长上下文利用问题；若输入在进入模型前已被截断，则先修复上下文构造。对照实验一次改变一个条件，避免同时更换模型、模板和文件内容而无法归因。

官方的 “Needle in the Code” 是一个更具体的例子：研究者将一个简单自定义函数插入较长代码库的不同位置，再要求模型在代码末尾复现它。这个测试能观察模型能否找回那段函数，却不能单独证明它能理解整个仓库并修好跨文件缺陷；后者还需要包含真实问题、补丁和测试的任务来检查。

## 应用与错例

假设模型生成 `return price + count`。先看提示是否明确要求乘法、生成代码是否粘贴到正确位置；再跑覆盖普通和边界输入的测试。若模型调用不存在的函数，检查库版本和接口；若测试未启动，则先修环境，不把它直接计为模型逻辑错误。

下一轮可加入真实需求、反例和可执行测试，按仓库来源划分独立验证集；同时回归普通代码生成和自然语言能力。不要把旧题换变量名就当作新任务。这个流程是可复现建议，尚未进行训练或运行。

## 比较与面试追问

**代码模型为什么仍用文字 token？** 代码可以按文本序列分词，模型预测 token 的方式与语言模型相通；数据分布、标记和训练任务则可以针对代码设计。

**Chat 会自己运行测试吗？** 模型生成回答或工具请求，只有外部工具实际执行并返回结果，才能获得测试证据。模型声称“通过”不等于执行结果。

**为什么长窗口不等于长期记忆？** 它描述单次输入输出的容量；超出窗口或未提供的文件无法直接看到，窗口内信息也不保证被正确使用。
