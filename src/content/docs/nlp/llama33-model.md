## 先看问题：70B 能不能替代 405B？

假设团队要给英文客服做一个助手：读一份长长的退货规则，针对客户提出的具体订单解释是否符合条件。你听说 Llama 3.3 70B 有些测试接近更大的模型，于是希望节省机器资源。正确的第一步不是把一条宣传语直接换成部署承诺，而是弄清楚：这份规则能否完整放进上下文、答案能否指出依据、错误判断会造成什么后果，以及模型在你自己的数据上表现如何。

Llama 3.3 70B Instruct 是 Meta 发布的开放权重指令模型。70B 大致表示 700 亿参数，Instruct 表示它还经过面向指令与对话的后训练。官方模型卡把它与 Llama 3.1 的 70B 和 405B 指令版放在一起比较；405B 是 **3.1 的版本**，并不是一份名为 Llama 3.3 405B 的权重。模型卡页面的模型树关联到 Llama 3.1 70B 基础模型，但这并不能让我们推断未披露的完整训练配方，也不能证明它一定由 405B 蒸馏而来。

[初版 Llama 3](/nlp/llama3-model/) 帮助理解基础模型与指令模型的区别，[Llama 3.1](/nlp/llama/) 则是阅读这些对照数据时需要认识的另一代。下面的客服流程是帮助理解的例子，不是已经运行过的实验，也不是保证模型能正确处理真实订单。

## 结构：文本进来，文本出去

图是根据公开模型卡画的教学示意，不是官方逐层架构图。输入的文字先由分词器切成 token，模型依据前面已经看到的 token，预测接下来的一个，再把生成的 token 放回上下文，继续预测后面的内容。它可以输出代码，是因为代码也能以文本 token 表示；这不意味着模型自身会执行代码或验证执行结果。

这与查数据库有一个很实际的区别：如果规则里没写订单的购买日期，模型仍能生成一段听起来完整的话。回答流畅不能证明日期真实存在。应用需要明确要求它引用提供的规则、对缺失信息说“不知道”，并在需要时连接订单查询工具，由系统核对工具返回结果。

![Llama 3.3 70B 文本骨干：分词后经过 80 个因果 GQA 和前馈解码层，最终预测下一个 token。](/figures/llama-common/llama70b-backbone.svg)

根据 [Meta 官方架构配置](https://github.com/meta-llama/llama-models/blob/main/models/sku_list.py)，3.3 70B 语言骨干有 80 层、8192 维隐藏表示、64 个查询头和 8 个键值头。每 8 个查询头共享一组键值头，单个头的维度为 128。

模型采用 GQA，也就是分组查询注意力。可以把它想成几位读者带着不同问题，共用一部分资料索引：多个查询头共享键值头，减少生成时需要保存的部分键值缓存。它仍然要计算注意力，也仍有模型权重和其他运行开销。GQA 的设计有助于降低缓存负担，不能直接据此说任意机器都能以某个固定速度运行 70B 模型。

单条请求累计 8,192 个 token、采用 BF16 保存键值时，按 `80 层 × 2（K 和 V）× 8 头 × 128 维 × 8192 token × 2 字节`计算，KV Cache 约为 **2.5 GiB**。这有助于理解长对话和并发的内存开销；模型权重与运行时工作区还需要另外计算。

假设缓存使用同样的数据类型和布局，长度翻倍到 16,384 token 时，这个估算也翻倍到约 5 GiB。它只算一条请求的键值缓存：同时服务多个人时，每个人的对话通常要各自保留缓存，实际用量还取决于缓存复用、并行方式和推理框架。这样的估算能帮我们提前比较配置，最终容量仍要用目标环境测量。

模型卡给出的 128K 是上下文窗口，不是一句“长文档都能记住”的保证。客户问题、系统指令、规则正文和模型回复都会占位置。假如客服规则装得下窗口，但关键例外被埋在长文本中间，模型仍可能漏看或误用。实践中可以把相关条款检索出来并保留出处，同时对窗口开头、中间和末尾的事实分别做测试。

## 数据和预训练：数字究竟是什么意思

模型卡的数据章节称预训练使用约 15 万亿 token 的公开可获得数据，规格表写作 15T+。token 是模型处理的文本单位，不等于字数、网页数或互不重复的样本数。这个数字也不能告诉我们每个领域的比例、每条材料出现的次数，或者每个文档的授权状态。

预训练的基本任务是预测后续 token：比如看到英文句子“Please return the item within”，模型学习预测接下来可能出现什么文字。大量这样的学习让它形成对语言、代码和部分世界知识的统计规律。它学习到的是如何根据上下文生成，不是把所有训练文本整理成可随时审计的事实库。

官方模型卡没有给出足以复现完整数据集和全部训练细节的信息。因此，我们不应把 15T 理解成此版本新收集了 15T token，也不应声称自己知道具体配比或每个训练阶段的数据组成。知识截止时间只能作为粗略的时间边界；需要新政策或实时订单信息时，还是要提供可靠的外部资料。

## 后训练：从续写变成更会遵循指令

官方说明使用了监督微调（SFT）和人类反馈强化学习（RLHF），并称微调数据包括公开指令数据与超过 2500 万条合成生成样例。合成样例指由模型或其他自动流程生成的训练例子，并不自动意味着每条样例都正确，更不代表所有例子都由人逐条审核。具体生成模型、筛选规则和各阶段配比不能从这句话推断出来。

在安全微调的数据收集上，模型卡另外说明使用人工生成与合成数据，并借助基于语言模型的分类器挑选提示和回答。例如，准备客服训练数据时，可以先让候选示例经过自动筛选，再抽查是否把正常退货咨询错误地标成不该回答的问题；这只是帮助理解的应用方案，并非 Meta 公开的具体操作配方。筛选结果仍可能有漏判或误判，最好用独立样本检查。

SFT 可以类比看示范题：输入客户问题和退货规则，示范答案写出适用条款、结论以及需要补充的信息。模型学习如何按这种方式回答。[监督微调](/training/sft/) 页面可以进一步了解训练目标和样本格式。RLHF 则通过人类反馈帮助模型调整回答偏好，例如更偏向有依据、愿意承认不确定的回答；[RLHF](/training/rlhf/) 页面解释这一类流程。仅凭模型卡的概括，不能断言本版本具体使用了哪种强化学习算法、奖励模型结构或完整阶段顺序。

例如，规则写“商品签收后 30 天内可退，定制商品除外”。客户说“我上周收到定制杯子，能退吗？”一个有用的示范会发现定制例外，同时提示核对商家政策中是否还有特殊约定；一个容易误导的答案只抓住“上周”和“30 天内”，忽略例外。后训练可以改善这类指令遵循，但如果训练例子覆盖不到某种例外，仍需要靠针对性的评测和数据改进。

## 评测：相同条件下看数字，再看差异

以下数字来自官方模型卡中的指令模型对照表，分别是 Llama 3.1 70B、Llama 3.3 70B 和 Llama 3.1 405B。表中分数与指定提示和评分方式绑定，不能当成真实业务的成功率。

| 评测与官方条件                | 3.1 70B Instruct | 3.3 70B Instruct | 3.1 405B Instruct |
| ----------------------------- | ---------------: | ---------------: | ----------------: |
| MMLU Pro，CoT，5-shot         |             66.4 |             68.9 |              73.3 |
| GPQA Diamond，CoT，0-shot     |             48.0 |             50.5 |              49.0 |
| HumanEval，0-shot，pass@1     |             80.5 |             88.4 |              89.0 |
| MATH，CoT，0-shot，sympy 评分 |             68.0 |             77.0 |              73.8 |

5-shot 意味着提示里给出五个示例，0-shot 则没有这类示例；CoT 表示评测采用相应的推理提示方式。HumanEval 的 pass@1 是该评测协议下单个候选通过测试的指标，并非任何软件项目一次生成就能上线的概率。MATH 的 sympy 评分是对答案做符号数学处理的一种评分条件，不能与采用其他提取和判分方法的结果直接混排。

拿 HumanEval 举例，题目给出函数说明和签名，模型补全代码，再由测试程序检查输出。若某函数测试只覆盖整数输入，代码处理浮点数或空输入是否正确，就不能仅凭这道题的通过结果确定；这也是实际开发仍要写针对业务的测试的原因。

表中 3.3 70B 在列出的 GPQA 和 MATH 测试上高于 3.1 405B，但 MMLU Pro 和 HumanEval 仍低于它。因此比较应当具体到任务，而不是说“70B 全面超过 405B”。不同厂商报告的测试集版本、提示、采样和判分脚本也可能不同；就算指标名字相同，也应检查评测配置。若拿模型卡中的数字复现，先固定模型版本、提示模板和脚本，再明确随机性和运行环境。

## 实际应用：把错例变成下一轮数据

回到英文客服例子，可以先收集获得授权且适合测试的真实问题，把订单信息和规则拆成独立字段，再按产品、国家、特殊例外分组。把一部分数据留作独立测试集，不参与提示设计或微调。先用基础提示跑一遍，记录是否判断正确、引用条款是否存在、缺资料时是否主动追问，还要看敏感信息有没有泄漏。

发现模型把“定制商品不可退”误读成“所有商品均可退”时，先检查检索：正确条款有没有送到模型？如果根本没检索到，先改善索引和召回；如果条款完整但回答忽略了例外，再考虑改提示、补示范或微调。之后用未参与修改的样本重新测试，并保留失败案例，避免只用已见过的题证明改进有效。对于影响客户权益的结论，还应安排人工复核或规则系统兜底。

官方支持语言名单没有中文，这不表示模型绝对不能输出中文，而是不能把中文视为模型卡承诺的受支持语言。模型卡将未列出的语言使用视为范围外，同时允许开发者在遵守许可和使用政策的条件下针对额外语言微调，并由开发者负责安全使用。中文客服尤其需要在自己的领域和专业词汇条件下单独评估；文本模型本身不处理语音，需要语音识别等独立组件。开放权重也不等于没有限制：部署与再分发前应阅读官方许可和可接受使用政策，根据自己的具体场景判断条款。

## 面试追问

**128K 上下文和长文本能力有什么区别？** 前者主要描述一次可处理的 token 容量；后者还包括能否定位、理解和使用不同位置的信息，需要通过长文本任务测量。

**为什么 70B 在某些题上高于 405B，不代表任何任务都更强？** 参数规模之外，后训练、测试题、提示和评分方式都会影响结果。对照表本身就展示了不同任务上的不同排序。

**25M 合成例子能否证明来自 405B 蒸馏？** 不能。合成训练数据与蒸馏可能相关，但模型卡的这一表述没有披露生成来源和完整训练流程。
