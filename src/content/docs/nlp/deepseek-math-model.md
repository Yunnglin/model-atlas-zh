## 要解决什么问题

一位学生会背公式，并不代表面对新题时知道何时使用它。语言模型也类似：它能把“圆面积等于 πr²”接着写出来，但应用题还需要读懂条件、选择公式、计算并核对单位。数学模型的目标，是让模型在这些步骤上表现得更好，而不是只储存更多公式。

DeepSeekMath 是 2024 年提出的 7B 数学模型系列。研究者先从代码模型继续学习数学和其他文本，得到 Base；再用数学指令数据训练得到 Instruct；最后从 Instruct 出发使用 GRPO 强化学习，得到 RL 版本。这里说的是第一代 DeepSeekMath，不能把后来的 DeepSeekMath-V2 或 DeepSeek-R1 的训练细节和成绩直接套进来。

假设题目是“每盒彩笔 6 支，买 4 盒，送人 5 支，还剩多少支？”一种解法是先算 6×4=24，再算 24−5=19。模型可能把“送人”误当“又买”，也可能计算正确却把题目条件抄错。理解模型时要分别看：数据是否覆盖类似问题、生成过程是否遵守条件，以及评测是否真的检查答案。以下题目和评分都是教学示例。

## 结构与数据流

DeepSeekMath-Base 以 DeepSeek-Coder-Base-v1.5 7B 为起点，继续预训练。它仍是自回归解码器语言模型：把题目和已生成内容拆成 token，根据前面的内容预测下一个 token。输出可以是一句解释、公式或代码，但它并没有因为叫“数学模型”就在内部接入一个必定正确的计算器。[Transformer](/foundations/transformer/) 介绍这一类模型的基本结构。

以官方 [DeepSeekMath-7B-Base 配置](https://huggingface.co/deepseek-ai/deepseek-math-7b-base/blob/main/config.json)为例，语言骨干有 30 层，隐藏维度为 4096，每层使用 32 个注意力头和 32 个键值头。它把每个位置表示为向量，经过因果自注意力与前馈网络，再输出下一个 token 的分布。

![DeepSeekMath 7B 语言骨干示意：题目和前缀经过分词、30 层因果解码器，输出下一 token。](/figures/deepseek-math/backbone.svg)

上面这张图说明模型内部的数据流；页面开头的训练流程图说明 Base、Instruct 和 RL 怎样逐阶段得到。模型在训练时学习数学材料，但推理时仍按同一套语言模型计算逐步生成。

当模型看到上述彩笔问题，它可能逐步生成“总共有 6×4=24 支，所以剩余 24−5=19 支”。这些步骤是模型生成的文字，不天然构成可验证的证明。即使最终数字恰好对，中间理由仍可能错误；反过来，一段正确思路也可能在最后一步算错。阅读或应用时应把答案检查与推理步骤检查分开。

### 文字推理与工具推理

文字推理是模型直接写出解题过程和答案。工具推理可以让模型写一小段 Python，交给外部执行器计算，再根据返回结果继续回答。例如把复杂分数运算交给符号计算库，有机会降低手算错误，但代码本身仍可能把题意写错。执行器、库版本与权限由应用系统提供，代码不会因为出现在回答里就自动运行。

论文分别评测不调用工具的思维链解题，以及使用 Python 的工具推理；两种设置的提示、工具和分数不能混为一谈。正式场景应隔离执行环境，限制运行时间和可访问数据，并保留代码与执行日志；对于无法确定的结果，应允许模型或应用返回“不确定”。

## 数据与训练

### 先找到数学内容

数学材料散落在网页、论坛和课程资料中，直接用关键词搜索容易漏掉，也可能把大量无关页面选进来。论文从已知数学网页出发，训练分类器在 Common Crawl 中找候选，再检查来源和结果、扩充种子并多轮迭代，最终构建约 1200 亿 token 的数学语料。可以把这看作不断改进筛子的过程：先找一批样本，用样本找更多候选，再检查筛子漏掉了什么。

具体来说，团队用 OpenWebMath 的 50 万条样本作为正例，再从 Common Crawl 选 50 万个网页作为负例，训练 fastText 分类器；对去重后的网页打分后，保留靠前的候选。第一轮后，研究者找出数学网页占比较高的网站，人工标注其中与数学相关的 URL 路径，把漏掉的页面加入种子，再训练筛选器。四轮后得到约 3550 万个数学网页。这像先用一份已知书单找书，再去相似书架上发现遗漏；网站相关不意味着站内每页都自动是数学内容。

“数学语料有 1200 亿 token”是语料规模，不等于模型只训练了 1200 亿 token，也不意味着每条内容都绝对正确或唯一。重复、题解质量、网页版权、个人信息及语言分布都需要处理。报告还对已知基准进行了去重检查，但这一措施不能证明所有潜在泄漏都被消除；现实应用仍应准备独立、更新的测试题。

### 从代码底座继续预训练

团队在代码底座上继续训练 5000 亿 token，混合比例包括约 56% 数学语料、4% 数学代码、10% arXiv 文本、20% GitHub 代码和 10% 中英文自然语言。比例描述训练混合中的使用量，与数学语料库本身的规模不是一回事，重复使用也会计入训练 token。数学材料不仅有题目和答案，也可能包含公式、说明、讨论和证明。

拿这两个数字算一下：5000 亿的 56% 是约 2800 亿次数学语料 token 的训练使用量，而数学语料库本身约有 1200 亿 token。两者不冲突：前者统计训练时读取的数量，后者统计语料规模；前者高于后者也不能推断每篇文章都恰好重复相同次数。

为什么从代码模型出发？代码和数学都涉及结构、符号与多步关系，论文在特定实验中观察到先学代码再学数学有帮助。但这不是“学会编程就一定会数学”的定理：实验模型大小、数据和训练预算有限，换一个数据集或训练流程需要重新验证。保留一般语言和代码数据，也有助于兼顾其他能力，却不能保证各项能力都不下降。

论文还做过一个较小模型的对照：使用 DeepSeek-LLM 1.3B，先训练 4000 亿 token 代码、再训练 1500 亿 token 数学数据；在不使用工具的少样本思维链设置下，GSM8K 为 21.9%，MATH 为 15.3%。将第一阶段改成一般语料、再用同样规模的数学数据时，两项分别是 19.1% 和 14.4%。这是论文表 6 的 1.3B 控制实验，帮助理解为什么研究者重视代码底座；上文正式发布的数学模型是另一套 7B 训练路线。 同一实验的 HumanEval pass@1 在代码训练后为 25.0%，再单独训练数学数据后降到 12.2%；代码与数学混合训练的结果为 29.3%。这提示领域继续训练可能改变其他能力，应同时保留代码回归测试。三个数字属于不同阶段或训练方案，不能说混合训练一定适用于所有模型。

### 指令微调与 GRPO

Base 擅长根据上下文续写，不一定自然地按照用户要求作答。监督微调（SFT）提供数学问题及解答示例，帮助模型学会呈现答案、步骤以及在适用任务中使用工具。示例答案错了或题解只有单一套路，模型也可能学到问题，因此质量和任务覆盖同样重要。

接下来，论文从 DeepSeekMath-Instruct 出发训练 RL 版本。用 [GRPO](/training/grpo/) 时，同一道题采样一组候选，奖励模型给候选评分，再计算每个候选相对于同组平均水平的优势，用于调整生成策略。论文的具体实验从 SFT 数据中选出约 14.4 万道与 GSM8K、MATH 相关的英文思维链题目，每题采样 64 个回答；这是该实验配置，不是 GRPO 必须永远使用的组大小。

在论文这组实验中，策略模型学习率为 $10^{-6}$、KL 系数为 0.04，每次探索采样之后只做一次策略更新，最大长度设置为 1024。可以把 KL 项理解为限制策略偏离参考模型的程度；这些数值描述的是该研究的配置，并非其他模型应直接照搬的默认值。比较不同 GRPO 实现时，组大小、奖励、采样和每批数据更新次数都需要一起记录。

用彩笔题举例，假设四个候选分别得到奖励 1、1、0、0，组内平均为 0.5，前两个相对更好，后两个相对更差。实际算法还涉及标准差归一化、裁剪和相对参考模型的约束；这里省略这些细节，只为解释比较方向。如果全部候选分数相同，组内相对信号就很弱，数值上的处理需要看具体实现。

值得区分两件事：GRPO 是利用一组评分进行优化的方法，奖励从哪里来是另一项设计。原始 DeepSeekMath 工作训练了奖励模型，其训练数据与答案正确性判断有关；不能把这次实验写成所有更新都直接由规则验证器打分。论文也讨论结果监督和过程监督：前者给整份回答评分，后者尝试给推理步骤提供信号。奖励模型可能误判，过程看起来有条理也不一定正确。

GRPO 不再需要像常见 PPO 配置那样单独训练价值模型，但仍需要生成多条候选、计算奖励、保存参考策略并优化模型。采样、长回答和奖励推理都消耗资源；“省掉价值模型”不等于训练免费，也不保证任何任务都比其他方法更好。

## 评测怎么看

论文分别报告 Base、Instruct 和 RL，以及是否使用工具。例如不使用工具的思维链设置下，Instruct 在 GSM8K 和 MATH 的成绩分别为 82.9% 和 46.8%，RL 分别为 88.2% 和 51.7%。这里的 GSM8K 和 MATH 使用的相关训练题属于论文定义的同领域任务；比较要保持数据划分、提示和生成设置一致。这些数字不是模型面对所有数学问题的正确率，也不能直接代表后来的版本。

GSM8K 偏文字应用题，MATH 包含较难的竞赛式问题；题目难度、答案提取和等价判断都影响结果。假设正确答案是二分之一，模型回答 `0.5`，若评测器只接受字符串 `1/2`，会把正确答案误判为错误；反过来，表达式化简或单位处理错误也可能造成误判。需要记录原始输出，并用可靠规则或人工抽样核查等价性。

只看最终答案也有局限。若模型误把 24−5 写成 24−4，却在最后写出 19，答案对了，过程仍不可信。可以同时统计最终答案正确率、关键条件提取、步骤错误、格式错误和无法判断比例。假设 20 道构造题里 15 道答案正确、其中 12 道步骤也正确，两者分别是 75% 和 60%；这只是展示计分方法，并非该模型实测。

工具解题还需记录允许调用次数、超时、代码执行是否成功，以及是否将结果反馈给模型。一次直接回答与允许反复执行、重试和挑选答案的系统有不同计算预算，不能把它们的成绩当作公平的一对一模型比较。

### 多次采样，到底在比什么？

假设对同一道题生成 5 个答案，依次为 19、19、19、20、21，正确答案是 19。**多数投票**选出现次数最多的 19；**Pass@5** 关注五次里是否至少出现一次正确答案。若五个答案变为 19、20、20、20、21，Pass@5 仍然成功，但多数投票会选错。前者衡量候选里有没有正确解，后者考察不看标准答案时靠投票能不能选对；多次生成也需要付出更多计算成本。

论文比较 Instruct 与 RL 时，在 GSM8K 和 MATH 上以温度 0.7 考察多次采样：图 7 中 RL 提高了多数投票表现，Pass@K 未出现相应提升。作者据此推测，这次训练更多是在提高正确回答出现和被选中的机会，而不是证明模型能够解决全新的题目。这个观察只对应论文所测模型、题集和采样设置，不能推广成所有强化学习都不会提升新题能力。

## 应用与错例闭环

假设一个学习助手经常把“打八折后再减 10 元”误写成“先减 10 元再打八折”。先保存题目、完整提示、模型版本、输出和正确答案，判断错误来自题意理解、运算顺序、计算还是答案提取。不要只把正确结果塞进提示词然后宣布问题解决：那样无法说明模型是否能处理新题。

整理不同金额、折扣顺序、文字表达和反例，人工检查标准答案；按题目模板或来源划分开发集与独立测试集，避免把同一模板改几个数字后同时放在两边。针对错误可尝试更清晰的要求、可检查的工具调用或高质量训练示例。改动后复测目标题型，同时检查普通算术、中文题和无解题的表现、耗时及成本。这是一套实验方案，尚未实际运行。

## 比较与面试追问

**1200 亿和 5000 亿 token 有什么区别？** 前者是数学语料库的规模；后者是混合多种数据进行继续预训练的 token 总量。

**GRPO 与奖励模型是什么关系？** GRPO 决定如何利用组内相对评分优化；原始工作用训练出的奖励模型给候选评分，其他任务也可设计其他奖励。

**不要价值模型，就完全没有其他模型了吗？** 不是。论文实验还涉及策略、奖励和参考模型，且需要采样多条回答。

**答案正确就代表推理可靠？** 不一定。过程可能出错而碰巧得到正确答案，应分别检查关键步骤和最终结果。

**RL 的 GSM8K 分数能代表所有数学任务吗？** 不能。它依赖题集、训练分布、提示方式、采样预算与评测规则。
