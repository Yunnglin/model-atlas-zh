## 要解决什么问题

你正在修改项目，函数已经写好了开头和结尾，中间缺一行：上面拿到了单价与数量，下面要返回 `amount`。如果模型只根据前面续写，它可能忽略下方已经存在的返回语句。Qwen2.5-Coder 通过代码专门训练和中间补全格式，学习利用两侧上下文生成缺失片段。

本页以官方报告的 Qwen2.5-Coder 系列为范围，包含不同大小的 Base 和 Instruct。代码、结果与排错都是教学构造；模型是否真正完成仓库修改，还要由外部工具检查。与上一代比较可读 [CodeQwen1.5](/nlp/codeqwen15-model/)。

## 结构与数据流

模型架构建立在 [Qwen2.5](/nlp/qwen25-model/) 的因果解码器之上，仍然逐个 token 生成代码或文字。官方报告区分多个规模：例如 7B 有 28 个查询头与 4 个键值头，32B 有 40 个查询头与 8 个键值头；7B 和 32B 分别有 28 层与 64 层。

下方原创教学图展示一次 FIM：先按模型约定组织前缀、后缀和标记，再让解码器生成中间内容；生成完成后，外部执行器才可能运行测试。图展示任务数据流，省略注意力、残差等层内结构；[官方报告](https://arxiv.org/html/2409.12186v3)可查看原始训练示意。

### FIM 不是把因果掩码关掉

假设前缀包含 `def total(price, count):`，后缀包含 `return amount`，正确的中间内容可以是 `amount = price * count`。FIM，即填补中间内容，会把前缀、后缀以及标记按约定顺序放到模型输入中，再预测缺失部分。模型看到“后缀”是因为它已经被放在生成位置之前；生成过程仍是因果预测。

报告列出 `<|fim_prefix|>`、`<|fim_suffix|>`、`<|fim_middle|>` 等特殊标记，并有仓库名和文件分隔标记。它们不是普通注释的任意替代品；实际调用要使用对应 tokenizer 与模型所支持的格式。Base 补全和 Instruct 对话分别使用对应格式。

把这一输入格式展开来看：先给模型一个前缀标记和已有函数开头，再给后缀标记以及 `return amount`，最后给中间部分的标记。模型从中间标记之后开始生成 `amount = price * count`。补全时，编辑器把生成的片段放回原来的缺口；测试程序再检查不同输入下返回的结果。模型看到的后缀和最终运行测试，是两件各自独立的工作。

### 仓库上下文不等于工具执行

修一个函数可能还要读调用方、测试和配置；把多个文件按仓库结构整理到输入，可以提供跨文件上下文。报告中的仓库级训练让模型接触这类序列，但它不会自动遍历你电脑里的所有文件。哪些文件实际进入上下文，由外部应用的检索和拼接决定。

当模型建议“运行测试”，这只是一段文字或工具请求。执行器需要在指定环境中运行命令，返回退出状态和输出；之后模型才能利用反馈继续修改。模型报告测试通过，如果没有对应的工具结果，不能作为测试真的通过的证据。

## 数据与训练

### 从单文件到仓库

官方报告 v3 描述文件级预训练、仓库级预训练和指令微调。文件级阶段同时使用下一 token 预测和 FIM，最长训练序列为 8192 token，报告称该阶段使用 5.2 万亿 token 的高质量数据；其整体代码相关预训练材料超过 5.5 万亿 token。它们的统计范围不同，不能把 5.2 和 5.5 都当成互不重叠的全新数据总量。

文件级材料帮助模型学习单个文件的代码模式。仓库级阶段让它接触多个相关文件，并将训练上下文扩展至 32768 token；报告还描述用 YaRN 扩展至更长上下文。可处理更长输入不意味着模型总能定位最相关文件，或者每个部署都配置相同窗口。

训练数据不仅有代码，还包含相关文本、数学与合成材料。报告通过数据混合实验选择了代码、文本和数学的比例；这些比例属于该实验与训练方案，不应被当作所有代码模型的最佳配方。公开报告也不意味着每一条数据和全部许可证信息都可下载。

报告在 7B 混合比例实验中最终选择代码、文本、数学为 70%、20%、10%。这个比例说明训练并非只看源代码：例如理解自然语言需求、计算数量，也能帮助代码任务。但报告中这是特定实验设置下的选择，不能据此断言其他任务或其他规模都应使用相同配比。仓库级阶段还使用约 3000 亿 token 的长上下文代码数据；它的统计与文件级 5.2 万亿 token 分阶段报告，不能凭数字推断去重后独立样本量。

### 指令样本与可执行反馈

指令微调让模型学习“给需求，给修改和解释”的行为。报告描述先用大量多样指令，再用更高质量样本和筛选结果继续训练；还构造了与 FIM 相关的指令样本。示范可以告诉模型怎样修改，但示范本身也会出错；自动生成与筛选的质量、覆盖范围仍需审查。

报告还描述在 SFT 之后使用离线 [DPO](/training/dpo/)：对自包含的代码，借助多语言执行环境和生成的测试构造偏好反馈；对更复杂的代码，使用语言模型裁判辅助比较，并混合通用偏好数据。可以把它想成在同一道需求下比较两个候选，告诉模型哪个更值得偏好。自动测试可能漏掉边界，裁判也可能判断错误；论文所述反馈方法不意味着每一条偏好都经过人工确认。

实际制作业务样本时，保留仓库提交、需求、修改前后文件、依赖版本与测试输出。把同一仓库的近重复代码分到训练集和测试集，可能使结果看起来更好，却不能证明面对新项目也可靠。代码和数据使用权限应按具体来源核对。

## 评测怎么看

### 补全、生成和修复是三种题

补全可以检查缺失代码能否嵌回原文件；函数生成可以运行单元测试；仓库修复还要检查模型是否找对文件、补丁能否应用、相关测试与回归是否通过。官方报告分别使用 HumanEval-FIM、CrossCodeEval、RepoEval 等评测补全，也评估代码生成、编辑和其他任务；不同基准、模型规格和评分方法不能直接混成一个分数。

例如报告的 Base 模型表中，Qwen2.5-Coder-7B 的 HumanEval 为 61.6、HumanEval+ 为 53.0，CodeQwen1.5-7B 分别为 51.8 和 45.7。这是报告规定的函数生成评测口径，不是仓库级修复成功率；对比时还要区分 Base 与 Instruct、评测代码和测试集版本。

报告的 HumanEval-FIM 使用 Python、Java 和 JavaScript 的单行补全，按生成第一行与标准答案的精确匹配计分；功能等价的不同写法也可能被判为不匹配。这和运行测试后的功能正确性是两种指标。

例如报告表 7 中，7B Base 在 Python、Java 和 JavaScript 上分别得到 79.7、88.5 和 87.6；表中的 86.2 是按各语言样本数量加权的平均，不是三个数字的简单平均。这个结果衡量的是首行精确匹配，不能直接当成实际仓库任务的通过率。

跨文件补全还要看模型实际拿到了哪些文件。报告的 CrossCodeEval 使用评测集提供的 BM25 检索结果作为跨文件上下文，最多放入 2048 token；整个输入上限为 8192 token，输出上限为 50 token。表 8 中 7B Base 的四语言平均精确匹配为 49.3、编辑相似度为 83.1：前者要求答案完全一致，后者衡量生成文字与参考答案有多相近。可以把检索器看作先替模型翻出相关文件，再让它补全；这组分数衡量的是该检索条件下的补全，不是模型自己搜索整个仓库的成绩。

对总价示例，单测应包括普通整数、零数量，以及需求明确要求的金额精度等边界。`price * count` 和 `count * price` 可能是可接受的不同写法，完全匹配评分却可能只接受其中一种；但执行测试也有盲区，没覆盖到的输入可能仍有问题。准确的评价应记录指标、用例和未覆盖的限制。

### pass@1、重试与成本

pass@1 表示按评测协议从候选中取一次时的成功情况；允许多次采样的 pass@k 与一次成功率不同。比较模型时，固定候选数、温度、超时、测试环境、可用工具和上下文；多次生成后人工挑最好的结果，不应报告成单次成功。

仓库任务还应保存模型实际看到的文件、补丁、工具调用次数、失败输出和耗时。模型可能写对算法，却因依赖缺失导致测试启动失败；也可能修改了测试来掩盖错误。仅看最终“通过”或 token 速度，无法解释这些差别。

## 应用与错例

假设补出的代码引用了 `amount`，却没有正确赋值。先检查前后缀是否按 FIM 格式完整输入，是否截断了变量定义，再运行相关测试。若输入正确但变量名与项目约定不符，检查跨文件上下文和调用方；若执行器没有安装依赖，先修环境，而不是立即判定模型不懂代码。

把错误分成上下文缺失、接口幻觉、逻辑错误、补丁无法应用与环境失败，再从开发集补充对应例子。用未见仓库和不同依赖版本做回归，固定工具预算，并检查未修改的功能。对失败的测试保留日志，确认是补丁缺陷还是环境本身没有准备好。上面是复现实验方案，未实际运行训练或模型评测。

## 比较与面试追问

**FIM 利用了后缀，为什么仍是自回归？** 后缀先按格式放入输入，模型之后逐 token 生成缺失内容；没有在生成时让注意力看到尚未生成的答案。

**仓库级训练等于能自动操作仓库吗？** 不是。模型处理输入和输出 token，读取文件、执行命令与应用补丁由外部系统负责。

**评测通过能证明完全正确吗？** 只能证明在规定环境和测试覆盖下通过；隐藏边界、未测试的功能和系统集成仍需验证。
