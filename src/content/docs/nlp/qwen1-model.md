## 要解决什么问题

用户问：“我买的茶杯破了，可以换吗？”一个实用助手要看懂中文、判断用户意图、给出清楚的下一步，并避免把商家的真实政策编出来。如果模型只是沿着文字往后续写，它可能模仿客服语气，却不一定遵守问题中的要求。第一代 Qwen 提供一个学习这条路径的起点：先训练通用文本模型，再用对话数据和人类偏好信号改善助手行为。

Qwen-7B 于 2023 年 8 月发布，第一代后来还有其他规模和对话检查点。本文关注最早的 Qwen 文本系列与报告，不把后来的 Qwen2.5、VL 图像编码器或语音接口套进第一代。开放权重、代码许可和完整训练数据是不同问题；实际使用请核对对应型号的许可及模型卡。[Qwen2](/nlp/qwen2-model/)和 [Qwen2.5](/nlp/qwen25-model/)可继续比较后续变化。

下文的客服例子、数据和评分都用于讲解，不是官方训练样本，也并非模型实测结果。

## 结构与数据流

图是依据第一代报告绘制的因果语言模型教学简图，省略位置编码、残差、归一化和具体维度；重复层不意味着所有层共享同一组权重。它展示的是文本主路径，而不是后续多模态分支的完整结构。

### 从一句中文开始

“茶杯破了，可以换吗？”先被 tokenizer 切成若干 token，并转换成模型可以处理的编号。token 不一定是一个字，也不一定正好是一个词。假设某次切分得到“茶杯”“破”“了”等片段，模型的实际词表与规则仍要由对应 tokenizer 决定。输入不同语言时，同样长的一句话可能需要不同数量的 token，这会影响上下文容量、训练和调用成本。[分词](/foundations/tokenization/)有更详细的例子。

编号映射为向量后进入多层因果 Transformer。某个位置的注意力可以读取它之前的内容，但不能看未来还没有生成的回答；前馈部分再加工表示。模型最后计算词表分数，选择一个 token，接回已有文本，再继续下一步。可以把它想成一位只能逐格写字、却能反复查看前文的记录员。记录员能根据上下文续写，不代表它手里有真实订单或最新售后政策。

拿具体型号来看，[Qwen-7B 的官方配置](https://huggingface.co/Qwen/Qwen-7B/blob/main/config.json)列出 32 层、32 个注意力头和 4096 维隐藏表示。这里的“7B”是参数规模的近似名称，不是层数；其他规格不能照搬这些数。模型卡列出的 Qwen-7B 权重许可是 Tongyi Qianwen License Agreement，使用前仍要阅读对应许可证，而不能看到开放权重就直接假定是 Apache 2.0。

报告还列出几个积木的具体选法：用 RoPE 给注意力加入位置信息；每个子模块之前用 RMSNorm 调整数值尺度；前馈网络使用带门控的 SwiGLU。输入词向量和输出词表投影使用两套权重。可以把输入表想成“把编号翻译成模型内部向量”的词典，输出表想成“根据内部状态给下一个编号打分”的词典；分开使用增加了参数和内存，但两者能分别学习。位置编码和门控并不等于模型一定能准确理解所有长文，仍需按实际输入长度测试。

同一条消息里，“茶杯没破”和“茶杯破了”只差一个“没”，但业务含义相反。模型需要利用前后位置与顺序，而不是只看到“茶杯”和“破”就回复换货。反转词、否定句、连续追问都是后续评测应该专门覆盖的例子。

### 词表设计影响什么

第一代报告使用 BPE 分词，并在已有词表基础上增加常见中文、其他语言和代码相关的表示，报告最终词表规模约 152K。词表更适合中文时，一段文本可能切成更少 token；但这不等于模型自动拥有更准确的中文知识。不同模型之间比较输入成本时，应使用各自实际 tokenizer 统计，并保证文本内容一致，不能按汉字数直接等同 token 数。

报告还讨论将数字拆分为单个数字的处理方式。对订单号 `1234`，切分和位置关系会影响模型看到的序列；不过 tokenizer 的设计不单独保证数字不会抄错。应用需要用独立校验检查订单号，尤其不要凭生成结果直接修改真实订单。

### 因果训练和逐步生成

训练时，一段文本的正确后续已存在：例如给出“茶杯破了，”，目标可能是后面的文字。模型在因果掩码下为多个位置计算下一 token 的损失，不能用后一个目标偷看当前答案。推理时模型并不知道标准后续，刚写出的内容会成为下一步条件。详细区别见[下一 token 预测](/foundations/next-token/)。

将对话模板、上下文和工具结果整理成文本，是外部应用在调用模型前所做的工作。模型输出“我已经帮您申请退款”，不代表系统真的执行了退款。操作是否发生必须查工具调用、权限、返回值和订单状态；生成文字只是其中的一步。

## 数据与训练

### 基础模型先学习续写

第一代报告描述对多语言文本和代码进行预训练。官方仓库说明首发 Qwen-7B 训练使用 2.2T token，2023 年 9 月更新的检查点增加到 2.4T；首发与更新版本的上下文配置也有变化，不能把后者配置直接当作首发配置。数据来源、规模、清洗和训练预算都会影响能力，报告不等于完整公开所有原始训练材料。预训练让模型学到语言形式、知识关联和代码模式，但记住互联网上出现过的某个说法，不等于知道这家店最新的售后规则。

具体说，官方更新说明将首发版本的 2,048 token 上下文扩展到 8,192；仓库后来列出的 Qwen-7B 最大长度为 32K。预训练时使用的序列长度、后续扩展能力和当前检查点或推理代码的限制是不同概念：把一份长资料塞进窗口只是第一步，还要确认模型能否正确使用其中的信息。

对于我们的客服应用，应该把真实适用的政策作为检索或工具结果提供，并标记生效日期。用户只说“茶杯破了”，系统还需要确认购买时间、订单与证据；如果资料缺失，合理做法是询问或转人工，而不是凭空承诺一定退款。

### Chat 模型怎样学会按对话回答

对话微调使用问题和示范回答，让模型学会按助手角色回应。一个教学示范可以写成：“很抱歉杯子损坏，请提供订单号和照片，我们会按售后规则核实。”示范保留了必要步骤，也没有提前宣称退款已完成。[SFT](/training/sft/)解释监督微调；常见的生成式 SFT 依然基于下一 token 损失，只是监督位置和训练材料围绕助手答案组织。

偏好对齐可以让标注者比较两份候选：一份礼貌但直接承诺退款，一份先询问订单并说明需要核实。后者在这个教学规则下更符合要求。人类偏好数据、奖励模型和强化学习分别扮演不同角色，不能把它们都叫做“给模型加一句系统提示”。[RLHF](/training/rlhf/)介绍常见过程。官方每个模型使用的具体训练材料与比例，应以其公开说明为准。

报告中，SFT 使用 ChatML 风格把系统、用户和助手消息分开：模型仍预测下一个 token，但系统和用户输入的位置不计入损失，助手回答的位置才作为学习目标。报告给出的这组设置为序列长度 2,048、批量 128、训练 4,000 步。比如客服问题中的“杯子破了”供模型读取，示范回复中的“请提供订单号”则为模型提供要学习的输出。

随后，团队让标注员比较不同候选回复，训练奖励模型，再用 PPO 调整策略。报告描述 PPO 开始时先暂停策略更新，仅训练价值模型 50 步；每个问题同时采样两份回复。价值模型先适应奖励信号，然后才与策略更新配合。[Qwen 技术报告第 3 节](https://arxiv.org/html/2309.16609)给出了这些设置。

这里讲的是报告中的对齐实验。官方仓库区分了公开 Chat 权重和当时尚未发布的 RLHF 模型，不能据报告讨论过 PPO 就断定每个公开 Chat 检查点都经过了这套强化学习流程。

### Base 与 Chat 的使用差别

Base 适合研究或在相应数据上继续训练；Chat 已经过对话方向的后训练。二者不是相同权重换一张标签，也不是 Chat 在所有知识任务上必然更好。比较时要匹配模型规模、对话模板、停止符和生成参数。如果角色标记不对，输出可能带出模板文字或重复生成用户消息；这类接口错误不能立刻归因于基础知识不足。

## 评测怎么看

### 把任务拆成可以核对的项目

构造 10 条中文客服消息，假设模型对其中 8 条正确识别意图，但只有 6 条同时满足“先核实、不给无依据承诺”的业务要求。意图正确率是 80%，严格流程成功率是 60%。数字只是教学例子，不是第一代 Qwen 的成绩。再检查涉及否定、订单号、破损照片和政策缺失的子集，可以发现总分没有展示的失败。

自动评分也需要规则。例如“先提供订单号”和“麻烦发一下订单编号”表述不同，但业务步骤可能相同；而“已给您退款”与“核实后处理”虽然都很客气，业务动作却不同。人工复核应看条件与事实，而不是只检查回复是否包含“抱歉”或“退款”。

### 公开榜单与业务测试为什么不同

报告中有中文理解、英文理解、数学、代码和对话等多种基准。每个分数都有特定题集、提示和评测方式；它们能帮助了解当时的研究结果，却不能直接证明一家商店的售后自动化效果。实际比较应固定版本、题目、抽样、提示、上下文长度和是否提供工具；还要将训练示例和独立测试按来源划分，避免同一模板换个商品名就进入两边。

在论文表 5 中，Qwen-7B-Chat 的 C-Eval 分别报告了零样例 59.7 和五样例 59.3；HumanEval 的零样例结果为 37.2。前者考查中文学科选择题，后者用测试检查代码，两者回答不同的问题。零样例与五样例也使用不同的提示方式，因此报告数字时要带上对应设置；这些成绩可以帮助了解论文中的测试表现，客服流程仍需要独立评测。

长对话还需检查真正输入了哪些历史消息。若应用为了节约长度删掉了用户说的“已经换过一次”，模型无法利用这条事实。应记录截断前后内容，并分别观察检索、模型回答和规则校验，避免把整个系统的问题统称为模型幻觉。

## 应用与错例

一个可审计的客服流程可以保存用户原文、检索到的政策、完整模型标识、生成参数和输出。对“订单是否符合换货条件”，让确定性程序读取订单与规则；模型负责解释和整理，不自行伪造已经执行的动作。涉及损坏图片时，本文的文本模型本身不接收图片，应使用合适的视觉系统或人工查看。

如果模型把“没有破”读成“破了”，先构造否定词位置不同的对照；如果它说已经退款，检查提示是否要求核实、工具是否被调用、结果是否被错误地写回对话。确认缺陷后再添加相应数据，并用未参与修改的新对话回归，避免只对一条旧错例过拟合。

## 比较与面试追问

**第一代 Qwen 和 Qwen-Chat 有什么区别？** 前者名称常用于基础系列，Chat 是对话方向的后训练检查点；要看完整型号，不要把两者当成只改提示词。

**中文分词更省 token，就保证答案更好吗？** 不保证。切分效率影响长度和成本，正确性还取决于训练、模型、输入事实与评测。

**模型写了“已退款”，就能认为退款成功吗？** 不能。需要独立检查工具执行及订单状态；没有授权和结果时应明确说明尚未操作。

**和 Qwen2、Qwen2.5 比较时先控制什么？** 至少控制模型规模、Base 或 Chat／Instruct、模板、数据集与生成预算。比较结果不能将所有差异归因于代际或单一结构。
