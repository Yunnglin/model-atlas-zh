## 它解决什么问题

假设一位运营人员要做一个活动页面：页面需要商品列表、价格筛选按钮，以及计算折扣的前端代码。让模型写出一段看起来漂亮的 HTML 很容易验收得太早；用户还要确认按钮能否点击、筛选是否正确、价格格式有没有错误，以及页面在小屏幕上是否可用。

DeepSeek-V3-0324 是 [DeepSeek-V3](/nlp/deepseek-v3/) 的独立更新权重。官方模型卡称它在推理、前端开发、中文写作和函数调用等方面有所改善，同时明确其模型结构与 V3 相同。更新权重像换了一位经过不同训练的员工，即使团队分工和办公楼布局相同，工作表现仍可能变化。这里的活动页面是教学构造，不是官方样本，也不是实际运行结果。

这个版本不是 [DeepSeek-R1](/nlp/deepseek-r1/)：两者在训练和使用定位上有区别；它也不是后来引入其他训练或推理变化的 V3.1。比较之前先记录准确模型名，不能用一个笼统的“DeepSeek-V3”代替所有版本。

## 结构：同一栋楼里怎样处理一条请求

一段需求先由分词器切成 token。模型按照当前位置之前已有的内容做预测，再逐个生成后续 token。输出既可能是给人的说明，也可能是遵循工具协议的请求；模型写出“已查价格”不等于真的访问了数据库，应用必须负责执行并返回结果。

官方配置列出 61 个 Transformer 层、隐藏维度 7168 和 128 个注意力头。每一层对表示做注意力与前馈计算，再传给下一层；它们不是 61 个独立聊天机器人。配置还列出 163,840 最大位置数和 YaRN 相关字段，但字段本身不代表任何部署都能以相同速度或质量处理这个长度。服务端往往对输入、输出与并发另有限额。

### MLA：让历史表示更容易保存

制作活动页面时，模型可能多轮接收需求、代码和执行日志。生成下一个 token 时，它需要利用先前上下文；如果每一层每个注意力头都完整保存键和值，历史越长，缓存开销就越大。

V3 报告中的多头潜在注意力（MLA）使用低维潜在表示来压缩键值信息，以降低缓存成本。配置里的 `kv_lora_rank: 512` 是内部表示相关参数，不意味着将模型微调方法 [LoRA](/training/lora/) 应用于此次部署。它也不意味着模型把完整历史整理成可以阅读的摘要：压缩对象是供注意力计算使用的数值表示。

具体效率依赖计算方式和推理框架；即便能节省缓存，模型权重、激活数据与设备通信仍然占资源。对于一份包含价格和税率的长需求，应检查关键条件是否实际进入上下文，并通过独立样本测试模型能否使用它们。[KV Cache](/foundations/kv-cache/) 解释为什么缓存既能加速续写，也会增加内存占用。

可以用配置估算缓存的量级：按照原版 V3 报告中的 MLA 缓存形式，每层每个历史 token 保存 512 维压缩表示和 64 维位置相关的键。假设单条请求有 8,192 个 token，每个数值占 2 字节，61 层约需 `61 × (512 + 64) × 8192 × 2` 字节，也就是 **549 MiB**。这是只计算这两种缓存的教学估算，未包含权重、运行时工作区、量化或其他开销；实际引擎若使用不同的缓存布局，结果也会不同。

### MoE：不同 token 经过不同模块

初代 V3 报告描述的混合专家网络包含路由专家与共享专家。想象一支团队里有许多可调用的工作组：每个 token 的表示由路由规则选择部分组参与，同时共享组也参与计算。0324 配置列出 256 个路由专家、一个共享专家，每个 token 选 8 个路由专家；前 3 层是稠密前馈层。专家是数学函数，不能从编号推断“第 17 号一定擅长 CSS”。

总参数与激活参数回答不同的问题：前者涉及模型需要存放的全部参数，后者描述每个 token 实际参与部分计算的规模。初代报告的 671B 与约 37B 是论文口径；模型托管页面显示的权重统计约 685B，可能涉及不同的统计范围，不能直接当作此次更新增加了 14B 参数。实际显存还受量化、并行、缓存与框架影响。

### 函数调用需要一套外部系统

如果用户问“某商品还有多少库存”，模型可以按约定格式生成函数请求，例如请求库存工具查询商品编号。应用检查调用是否被允许、执行工具，再把真实结果返回给模型；模型才能据此组织回答。参数写错、工具超时、数据库数据过期都可能导致最终答案错误，不能只统计模型有没有输出类似 JSON 的文字。

官方模型卡称更新版改善了函数调用，并支持 JSON 输出与代码补全等格式。具体格式应查对应模板和推理框架；不同产品可能增加自己的工具约束。模型能够发出请求，和应用能安全、准确地执行请求，是两个需要分别验证的环节。

## 训练：初代技术背景与 0324 公开信息

初代 V3 技术报告描述了大规模预训练：模型学习根据前文预测后续 token，并使用网页、代码、数学等多种来源；之后再通过监督微调和强化学习改善对话与任务表现。报告还讨论了混合精度训练和多 token 预测等工程设计。[V3 详解](/nlp/deepseek-v3/)逐项解释这些机制。

但这份报告对应的是初代 V3；0324 模型卡虽然说架构相同，并列出能力提升，没有逐项公开这一更新具体使用哪些新增数据、优化步骤、偏好标注和训练时长。因此，我们不能把初代报告里的训练总量写成 0324 的新增训练量，也不能从“中文写作更好”倒推出某个特定数据集或奖励模型。相同结构是可以核对的事实，训练配方是否完全相同则不能由结构直接得出。

例如可以构造一条网页开发示范：输入包含商品数据和筛选要求，目标是一份可运行页面及解释；再配合浏览器或单元测试检查结果。这能说明[SFT](/training/sft/)如何利用示范，也能说明反馈如何帮助发现执行错误，但不是声称官方使用了这份样本。网页代码评测还须区分模型写错代码、浏览器环境缺依赖、或测试脚本本身有误。

## 评测：数字说明了什么

官方模型卡列出 MMLU-Pro 从 75.9 到 81.2、GPQA 从 59.1 到 68.4、AIME 从 39.6 到 59.4，以及 LiveCodeBench 从 39.2 到 49.2，均是其所列前代 V3 与 0324 的比较。以 MMLU-Pro 为例，相差 5.3 个分数点，不应写成“准确率提升 5.3 倍”。模型卡并未在这些条目旁逐项说明所有采样、提示和题集版本，不能把数字当作任何业务场景的直接成功率。

模型卡还给出官方网页和应用当时使用的温度设置：模型温度为 0.3，API 输入的 1.0 会按其说明映射到 0.3。同样写着“温度 1.0”，本地推理框架未必执行这层映射；复现实验时应记录实际传给模型的采样值，而不是只抄接口参数。

如果要比较两版权重处理活动页面，应固定题集和验收协议：每题要求同样的布局、筛选规则与数据，分别运行生成代码并记录能否启动、按钮逻辑、筛选正确率和不同屏幕的表现。视觉美观可以由多位评审盲评，功能则用确定性的浏览器交互或测试脚本核验；评分标准要在看答案之前确定。

例如有 20 个构造任务，16 个页面能启动，其中 12 个筛选逻辑正确，则启动率为 80%，严格通过率为 60%。这只是说明分母与验收口径，不能当成模型实际成绩。也要记录失败中有多少是依赖安装或执行器故障，以免把环境问题误记成模型不会写代码。

## 应用与错例：从失败返回数据

假设页面点击“价格低于 100 元”后仍显示 120 元商品。先保存原始需求、模型版本、生成代码、输入数据、运行环境和操作录像或日志，再核对按钮是否真正调用筛选函数。若价格字段是字符串，错误可能来自字典序比较；若按钮事件没有绑定，问题则在交互实现；若测试数据本来填错，应先修数据。

把这几类错误分别加入开发集，包括边界值刚好等于 100、商品价格为空、活动结束和多币种情况；按项目或需求模板留出独立测试集。调整示范或训练后，除了回归筛选逻辑，也检查页面能否正常打开、键盘是否可以操作和原有商品是否遗漏。以上是可复现的测试设计，没有声称已经训练或部署模型。

对于库存查询，日志应保留模型发出的参数、工具是否成功执行、返回数据的时间和最终回答。工具没有返回时，助手应明确说查询失败，而不是把生成的请求当作查询结果。正确的闭环需要模型、工具、数据和验证共同工作。

## 面试追问

**架构相同，表现为什么可能不同？** 权重与后训练可以不同；输入格式、采样和工具框架也会影响结果。公开资料不足以把性能变化归因到某一项。

**MoE 每次只选几个专家，就只需保存那几个吗？** 不一定。不同输入会选择不同专家，通常仍需安排整个专家池，并考虑通信与缓存。

**模型能函数调用，就能自己访问数据库吗？** 不能。它产生符合协议的请求，实际权限、执行和返回结果由外部系统负责。

**参数字段里的 KV LoRA 就是 LoRA 微调吗？** 不应直接画等号。这里的字段涉及注意力的低维表示；训练时增量适配是另一种用途。
