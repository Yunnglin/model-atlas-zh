## 要解决什么问题

想象你让助手修一个大型软件：最早说过“接口名字不能变”，中途它要读大量代码、运行测试、查看报错，最后还要看页面截图。挑战并不是把材料塞进一个大窗口就结束了：模型要在漫长过程中保留约束、挑选有用信息，同时不能让每个 token 的计算和显存成本无限增长。

K3 的思路是同时处理三个不同问题：**沿时间处理上下文**、**沿网络深度传递信息**、**挑选部分专家计算**。它们是三个不同方向，不能简单说成“都是注意力”。

## 结构与数据流

[查看论文原始架构图（Figure 2）](https://arxiv.org/html/2607.24653v2#S2.F2)：右侧是层间信息流与视觉输入，左侧展开专家模块和 KDA。原图保留英文，可结合下方说明阅读；论文图的使用限制请查看原文许可。

### 第一步：把截图和文字送进同一个模型

假设用户附上一张报错页面截图并说“修复标题遮挡，但不要改变 API”。文字先切成 token；截图由 **MoonViT-V2** 编码，再经轻量投影映射到语言模型使用的表示空间。模型结合文字和视觉信息生成回答或工具调用。报告说明视觉编码器约 27 层、0.4B 参数；图像与视频共享视觉参数，视频还涉及帧间时间处理。投影前的压缩减少视觉 token 数，但也可能丢失细节，不能保证小字一定看清。

这条路径能处理图像与视频，**不代表模型提供原生语音波形输入或输出**。截图中一个模糊的错误码，模型可能猜错；让它引用具体区域并用高分辨率裁剪核查，比只相信一句“我看到了”可靠。

### 第二步：KDA 和 Gated MLA 分担长历史

普通注意力可以把历史想成一本可逐页查阅的笔记：查得细，但历史变长时，缓存和计算开销会上升。**KDA** 更像维护一份不断更新的工作笔记：门控决定旧信息保留多少、怎样写入新信息。它的递推状态大小不随历史 token 数线性增长，但固定大小的状态不是逐字保存整本笔记，精确回查有局限。

K3 将三层 KDA 与一层 Gated MLA 组织为重复的混合模式，主干末尾再加一层 Gated MLA。按官方配置计数，23 组产生 69 层 KDA 和 23 层 Gated MLA，加上末尾一层后共有 69 层 KDA 与 24 层 Gated MLA。MLA 路径仍要维护历史缓存，所以不能据此说整个模型的缓存都与上下文长度无关。类比只解释功能分工，不表示它们被人工安排成“摘要员”和“查阅员”。

### 第三步：Attention Residuals 看的是层与层

一段信息经过很多网络层后，有时较早层的表示仍然有用。传统残差连接让前一条路径与当前层结果相加；**AttnRes** 则通过可学习的查询，对来自嵌入及先前块的表示计算权重并融合。比如在教学例子里，一层可以分别给三个块分配 0.6、0.3、0.1；这些数字不是实测值。K3 采用分块形式控制跨层保存和读取开销。

这个选择发生在**网络深度**，不等于在历史 token 上做检索，更不是跳过所有中间层。长对话的记忆问题主要要看 KDA 和 MLA；层间表示如何合并，是 AttnRes 解决的另一件事。

### 第四步：Stable LatentMoE 让专家按需工作

MoE 可以想成一间有很多专长的工作室：每个 token 由路由器送给一小部分专家，此外还有共享专家。K3 模型卡列出 896 个路由专家，每 token 选 16 个，另有 2 个共享专家。**2.8T 是总参数规模，104B 是每 token 激活规模**；算力大致和激活路径相关，存储与加载却仍要考虑大量总权重，不能把 104B 当成完整部署的显存要求。

“Latent”指专家计算前后有投影，专家在较低维的表示上工作；“Stable”涉及训练稳定性及负载均衡。假设某些专家被所有 token 挤爆，其他专家空闲，多卡训练就可能等待最忙的一组；报告的 MoonEP 等基础设施为此处理专家分配与通信。专家只是参数模块，不能直接认作“代码专家”“数学专家”。

## 数据与训练

### 预训练：先学通用规律，再逐步拉长材料

报告列出文本四大类：网页文本、代码、数学、知识，以及图片描述、图文混排、OCR、视频与视觉代码等视觉数据。流程包含规则过滤、质量评分和去重，部分知识与数学材料还做改写并检查与来源的一致性。报告给了类别和方法，**没有公开可完整重建的数据集与各来源配比**，不应把这些描述当作现成数据清单。

视觉编码器与语言模型联合训练。报告指出 MoonViT-V2 从头训练，使用下一 token 预测目标塑造视觉表示；这不意味着每个视觉问题都只是在做 OCR。对一张折线图，模型既要辨认坐标和图例，也需要从相互关系推断趋势。

上下文扩展采取课程式分阶段：预训练从 8K 扩到 64K，后续冷却阶段再到 256K 和 1M。像练习跑步，先掌握短距离再增长，并非宣布上限后所有长度的任务都会自动做好。不同阶段的数据构造、预算与独立评测同样重要。

### 后训练：不只给答案，还要学习行动

报告描述在通用推理、智能体与编程任务上开展多种推理强度的强化学习，环境包括搜索、软件工程、内核优化和视觉工具使用；再通过多教师的 on-policy 蒸馏整合能力。以修复代码为例，一条训练轨迹可能包括阅读文件、修改、运行测试、观察失败后调整，而不只是最后提交一段漂亮解释。实际奖励、训练样本和实验细节要以报告为界，不能把示意轨迹当作官方逐条配方。

这里的“多教师”不是让多个模型同时给用户答题。官方先按三个任务领域、三档推理强度训练出九个专家策略，再把能力汇总到一个学生模型中。例如，学生自己尝试修复代码时，训练过程选择对应的编程专家，对学生生成的每个 token 比较教师和学生给它的概率，并把差异转成训练信号。因为轨迹由学生自己生成，教师可以在学生真实会走到的步骤上指导它；最终用户使用的是整合后的模型。这里的专家策略指训练出的教师模型，与模型内部 MoE 的路由专家不是一回事。

长轨迹还带来系统问题：工具运行时模型可能等待，GPU 上的缓存和沙箱里的文件状态都需要妥善保存、恢复。报告介绍缓存保留、部分 rollout 和可恢复沙箱；它们服务于训练效率，不是模型“永久记忆”功能。

### 低精度：训练与部署的格式要接近

官方报告的量化感知后训练对 MoE 的路由专家权重使用 MXFP4，并对其输入激活使用 MXFP8；注意力投影、共享专家和路由器等非路由专家组件保留较高精度。可以理解成平时练习时就见过低精度带来的舍入误差，减少切换到部署格式时的不适应。这不表示每层权重、所有激活或 KV 缓存都采用相同精度，也不保证所有硬件都有同样高效的计算，转换、内核和实际精度都要现场验证。

## 评测怎么看

官方技术报告表 2 列出 K3 在 **Terminal-Bench 2.1 为 88.3、DeepSWE v1.1 为 67.5、BrowseComp 为 91.2**；这些分别涉及终端任务、软件问题和搜索任务，不是同一种能力。报告中 K3 使用 max 推理强度，终端任务取不同框架中的最佳结果；BrowseComp 使用 300K token 触发上下文压缩。框架、工具、预算不同，会影响比较；这些数字来自报告，并非独立复现结果。

想为自己的代码助手选模型，至少分开记录：任务完成率、是否改变禁止修改的接口、测试是否真实通过、总工具次数、耗时和费用。用同一代码库、提示词、工具权限及最大预算比较，并保存失败轨迹；只看最终解释可能漏掉“模型说测试通过，实际根本没运行”。

模型能接收百万 token，不等于每个位置的信息都能稳定找出，也不等于能综合所有约束。可把同一条接口约束分别放在开头、中间和末尾，插入无关日志，并增加一组明确要求改名的反向题。先确认系统没有截断或压缩掉约束，再判断模型是否忽略了仍可见的信息。

## 应用与错例

以页面修复为例：用户给出截图、仓库和“不改 API”的要求；助手查看代码、建立修改方案、运行测试，再核对截图。若结果仍然遮挡，沿证据检查：截图是否模糊？布局条件是否复现？工具测试是否覆盖小屏？约束是否被历史压缩删除？最后把失败样例及对应条件加入独立回归集，下一轮评估修复是否有效。

这是一套**建议的工作流程**，不是已经验证过的模型表现。提交补丁前仍要检查依赖、测试和权限；模型可以提出操作，外部系统才决定工具能做什么。

## 比较与面试追问

**KDA、AttnRes 和 MoE 都在“选”，区别是什么？** KDA 更新序列历史状态；AttnRes 融合不同深度的表示；MoE 路由 token 到部分专家，作用轴不同。

**长上下文是否意味着检索完全不需要？** 不意味着。检索可能减少输入与成本、提供可核验来源，但也可能漏召回；应按任务比较直接输入与检索方案。

**专家每次只激活 16 个，为什么仍难部署？** 所有专家权重仍需可访问，且跨设备传输、缓存、低精度内核和并发都会占用资源；激活量和权重存储是两笔账。

**模型权重开放就等于训练可复现吗？** 不等于。许可、数据、训练过程与评测工具公开程度需要分别检查，K3 使用专门许可证。
