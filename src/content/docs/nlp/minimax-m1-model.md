## 要解决什么问题

想象一个工程助手要排查大型仓库里的错误：它需要看问题描述、阅读相关文件、运行测试，再根据错误日志修改代码。完整记录可能很长，而模型的推理与工具往返又会继续增加上下文。M1 关注的就是这样的长输入、长推理和工具任务。

它是一种文本模型。模型可以根据对话和工具结果生成文字或格式化的工具请求；读取文件、执行测试等步骤由外部程序完成，结果再交回模型。下面用排查代码问题作为例子，沿结构、训练和评测走一遍。

## 结构与数据流

文字经分词器转成 token，进入语言主干。官方 80K 权重配置列出 80 个层，隐藏维度为 6144。按论文描述，主干以七层 Lightning Attention 加一层普通 Softmax Attention 为一组，重复十组；每层还有前馈与其他必要模块。混合的目的，是用较多线性注意力层处理长序列，同时保留周期出现的普通注意力层。

模型采用稀疏 [MoE](/foundations/moe/)：一层中有 32 个专家，每个 token 路由到其中 2 个专家。可以把它理解为每次从多组加工模块中选择部分参与，而不是 32 个独立聊天机器人投票。总参数描述全部模型权重，激活参数描述每个 token 实际参与的计算规模；服务还需要存放完整权重及运行缓存。

拿修复仓库举例：问题、代码片段和测试日志按照对话模板送入模型。模型处理这些 token 后，可能先生成“查看测试输出”的工具请求。外部执行器运行命令并把日志写回对话，模型再基于新增信息生成修改建议。每次输出仍是逐个 token 生成；图中省略了嵌入、归一化与残差等层内细节。

### 为什么把两类注意力放在一起

普通注意力为查询和历史位置计算相关性，可以细致地比较当前内容与此前位置。随着序列增长，需要处理的位置配对变多。Lightning Attention 属于线性注意力的实现路线，通过调整计算组织、利用分块和硬件内存访问来处理长序列；它与普通 Softmax Attention 的计算方式不同。

可以把长文处理想成两种读笔记方式：线性注意力维持并更新对先前内容的压缩状态，普通注意力层再按当前位置计算与历史的匹配。这里的笔记只是帮助理解的比喻。模型并不是在两次读文档之间调用外部数据库，两种计算都发生在模型的不同层里。

举一个输入长度翻倍的量级例子：若只看完整注意力中的位置配对，从 1,000 增至 2,000 个 token，候选配对数量会从约 100 万增至约 400 万。实际运行还受因果掩码、分块、算子和设备影响。M1 既有 Lightning 层也有 Softmax 层，不能把整个模型简单写成“所有注意力都是线性复杂度”。

普通注意力层需要保留或重算历史表示，线性注意力层则有其状态缓存；因此不能只看其中一种缓存估计整个模型的运行成本。长上下文时，权重加载、并行切分、缓存、请求并发和工具耗时都应分别观察。

## 数据与训练

### 继续预训练：先让底座多读相关材料

M1 不是从空白开始训练。团队以 MiniMax-Text-01 为基础，继续处理 7.5 万亿 token。报告提高了 STEM、代码、书籍和推理相关材料的比例，并说明从网页、论坛、教材中提取自然问答，使用清洗和语义去重。这个阶段仍主要利用序列里的学习信号，让底座获得更适合推理的语言和代码能力。

这 7.5 万亿不是一次性换数据重训：论文称前 2.5 万亿 token 使用固定学习率，后 5 万亿逐渐降低学习率；STEM、代码、书籍和推理数据合计占比提高到 70%。这里说的是训练中看到的 token 数和数据混合比例，不是 7.5 万亿条不同问题，也不是后面 SFT 或强化学习样本的数量。

上下文训练长度也不是一步从短文直接跳到一百万 token。报告描述从 32K 开始，分四个阶段平滑扩展到 1M；作者观察到过快扩展会引发训练不稳定。可以类比先练习在一份短日志里找到报错，再逐渐处理多文件记录。训练长度增加是让模型有机会练习更长材料，是否能够在某种任务中找对证据仍需要单独评测。

### SFT：给模型看推理示范

接下来是监督微调，即 [SFT](/training/sft/)。团队整理了数学、编程、科学、写作、问答和多轮对话等长推理样例，其中数学和代码约占六成。模型看到问题与示范答案，通过预测示范中的 token 学习回答方式。

例如示范可能先列出测试失败信息，再根据代码逻辑提出一个修复，最后解释怎样验证。SFT 给模型提供可模仿的路线；模型训练完成后遇到真实问题，还要靠外部工具提供实际日志。示范中“测试通过”的文字，不等于用户当前仓库的测试真的执行过。

### CISPO：把反馈变成策略更新

强化学习阶段让模型对问题生成回答或工具轨迹，再根据反馈更新策略。对于可以自动检查的数学和代码任务，验证器可以检查答案或运行测试；对写作、指令遵循等任务，报告还使用模型反馈。题目、工具环境、验证规则与奖励模型共同决定了训练信号。

报告中的软件工程训练样本由公开仓库的问题、初始代码和测试组成。模型提出补丁后，容器里的程序实际编译并运行测试：通过相关测试可得到正反馈，编译失败、运行出错或测试退化则得到零分或负反馈。比如修复一个解析器，光写“我已修复”不会让测试通过；如果测试只覆盖普通输入，也可能漏掉空字符串或特殊字符，因此训练奖励需要和独立测试一起看。

论文提出 [CISPO](/training/cispo/)，裁剪重要性采样权重，再把裁剪后的数值作为停止梯度的系数用于策略优化。假设旧策略给某个 token 的概率为 0.1，更新后的策略给它 0.3，概率比为 3；如果教学示例的上限设为 2，就用 2 而不是 3 给这一项加权。该 token 仍可以贡献梯度，而具体贡献还取决于优势值。

这与“按概率筛掉某些字”不同：概率比衡量的是新旧策略对已采样 token 的相对概率。PPO 风格的裁剪目标在特定优势符号和越界方向上可能使该项梯度为零；CISPO 的设计则保留了相应的梯度路径。论文在特定实验中比较了算法，具体公式与例子可在 CISPO 页面继续阅读。

### 奖励模型可能偏爱“写得长”

开放问答和写作没有统一的标准答案，M1 使用生成式奖励模型评价回答。论文发现，这个裁判有时更偏爱长回答，即使简短回答更好；如果训练时只追逐它的分数，模型就可能越写越长，却没有解决更多问题。可以想象两份修复建议：一份用三句话准确指出错误和测试方法，另一份写了很多背景却没找到问题；篇幅不能代替修复质量。

团队在训练中持续监测回答长度与任务表现，发现模型只增加篇幅、任务表现却没有提高时，重新校准奖励模型；还通过奖励塑形、数值裁剪与归一化减轻极端分数的影响。观察长度只是发现问题的线索，最后仍要回到人工偏好和任务是否完成来检验。详见[论文第 4.2.2 节](https://arxiv.org/html/2506.13585#S4.SS2.SSS2)。

论文还记录混合架构强化学习的工程问题。生成时与训练时使用的不同计算内核曾造成 token 概率不一致；团队提高语言模型输出头的精度以改善一致性。这个例子说明，训练效果不仅取决于奖励与算法名称，也会受到生成实现、训练实现和数值精度影响。

## 评测怎么看

论文表 2 对同一系列的 40K 与 80K 思考预算分别给出结果：AIME 2024 为 83.3 与 86.0，SWE-bench Verified 为 55.6 与 56.0；在 OpenAI-MRCR 的 128K 长度设置下分别为 76.1 与 73.4。前两者中 80K 更高，而这个长文本指标中 40K 更高。40K 是训练过程中的中间检查点；80K 版本在此基础上继续强化学习，并调整了训练数据，因此这不只是对同一模型调大生成预算的消融实验。更大的预算给模型更多生成空间，但不能仅凭这组分数断定差异完全由预算造成。

论文的 AIME 分数不是每道题只问一次：作者以温度 1.0、top-p 0.95 对每题采样 32 次，报告平均通过率。SWE-bench Verified 则使用改造过的 Agentless 流程：先定位相关文件，再细化到代码位置；这项设置没有使用基于向量的检索。

SWE-bench 是软件工程问题，需要系统在仓库中产生修改，并由测试检查结果；工具框架、提示、预算和测试环境都会影响最终分数。MRCR 则要求模型在长上下文中找到目标信息。一个分数反映对应数据与协议，实际工程助手还要关心是否读取正确版本、工具调用有没有执行、补丁是否破坏其他功能。

论文还用 Qwen2.5-32B-Base 做数学强化学习算法对照，在其 AIME 2024 设置中，CISPO 以约一半的训练步数达到与 DAPO 相近的效果。这个结果是论文所述基座、数据和训练配置下的步数对比。训练步数之外，还可以记录每题采样数量、生成 token、奖励计算、硬件时间和显存，才能比较一次实验的总成本。

报告估算在生成 100K token 的特定理论计算比较中，M1 的 FLOPs 约为 DeepSeek-R1 的 25%。FLOPs 是运算量估计，不直接等于同一硬件上的四倍吞吐或四分之一费用；实际服务速度还受到权重读取、内核实现、并发和序列长度影响。

## 应用与错例

假设助手根据日志修复报错，却只改了示例文件。先保存输入问题、仓库版本、调用的工具、返回日志和补丁；再核对模型是否读到了实际生产文件、是否误把示例当作目标，以及测试命令是否覆盖需求。把错误分为证据没读到、读到但判断错、修改不完整和验证不足，后续改进才有方向。

准备开发样本时，可以加入目标文件与示例文件名称相似的案例，并给出真实工具反馈。评测时保留没参与修改的仓库，分别统计首次修复率、回归测试和工具耗时。若模型输出“已通过测试”，系统应以实际执行记录确认，而不是只读取回答文字。这套流程是便于学习的任务设计。

## 比较与面试追问

**M1 的混合注意力和 MoE 是一回事吗？** 不是。注意力层负责处理历史信息，MoE 决定前馈部分由哪些专家参与。M1 同时使用二者。

**80K 思考预算就是能稳定答对所有长题吗？** 它表示该版本的思考生成预算。复杂任务仍要看测试题、可用工具、生成长度和结果验证。

**CISPO 是奖励函数吗？** 它是使用反馈更新策略的方法；结果由规则、测试还是奖励模型评分，是另一个设计选择。

**M1 和 [M2](/nlp/minimax-m2-model/) 是同一个底座吗？** M1 报告明确以 MiniMax-Text-01 为起点；M2 是后续版本，应该分别查看各自的模型卡与训练说明。
