## 从一场长会议开始

假设你有一份很长的会议记录：开头预算是 20 万元，中间讨论后改为 18 万元，结尾补充说这个数字不含税。你问“最终预算口径是什么？”助手不仅要找到 18 万，还要把后来的“不含税”与前面的修改联系起来。

Gemini 1.5 的公开报告重点研究长文本以及音视频材料输入。上下文窗口可以想成一次摊在桌上的材料范围；桌子大，能放更多页，但不等于模型必然逐页读懂、找到正确版本或识别矛盾。上面的会议与下文例子是教学构造，不是实际模型运行结果。

Pro 与 Flash 同属 1.5 系列，定位和资源取舍不同。具体模型版本、服务的窗口、输入格式和输出限制会随时间变化；这里讨论 2024 年公开研究，不把其报告中的能力或数值当作当前所有服务的承诺。

## 公开的数据流：多种材料进入同一个问题

用户可以提供文字、图片、音频或视频，再提出文字问题。服务会对不同媒体进行必要的输入处理；模型结合可用内容生成回答。具体输入转换、视频采样、音频限制及计费由所用接口决定，不能假设任何媒体文件都原样完整进入模型。

例如一段教学录像里，某个设置弹窗只出现半秒。若实际视频处理只抽取每秒一帧，弹窗恰好落在抽样间隙，模型可能根本没有看到它。模型答错时，应先核对输入帧和时间戳，而不是立刻断定“模型看到却不理解”。同样，会议音频若被裁去句尾，转写漏掉最后一个字可能来自输入处理。

2024 年 Google 介绍 Gemini 1.5 Pro 基于 Transformer 和混合专家（MoE）研究。MoE 通常表示部分计算模块按输入参与处理；但官方没有公开足够信息来绘制每层结构、专家数量、具体路由和视觉编码器连接。Flash 的内部设计不能仅凭 Pro 的介绍推定。报告还单独说明 Flash 使用稠密 Transformer decoder、并行计算注意力与前馈分支，并从较大的 Pro 模型进行在线蒸馏；这些公开要点仍不足以还原完整网络图。

## 长上下文：能装、能找、能理解是三层问题

第一层是**容量**：服务是否接受给定长度的输入，包含系统指令、材料和输出预算。第二层是**定位**：模型能否从大量无关内容中找到指定数字或句子。第三层是**理解**：面对多个相关片段、时间变化和矛盾时，能否判断哪个结论仍有效。

会议例子中，问“哪一处提到 18 万”主要检查定位；问“最终预算及税收口径”要求组合多个片段；问“含税金额是多少”如果缺少税率，就应说明信息不足。窗口更长不能凭空补足没有提供的税率。

容量也不等于免费：更长输入可能增加预处理时间、等待、缓存和服务成本。不同服务如何计量图像、视频和音频、是否启用缓存及输出占多少预算，需要按实际版本检查，不能用原文件大小或分钟数直接推算 token。

报告还比较了当时的输出速度：对于 10,000 字符的输入，中文回答的平均每个输出字符耗时，Flash 为 5.2 毫秒、Pro 为 14.1 毫秒。这是报告使用当时流式 API 测量的一项指标，不是整次请求耗时，也不是每 token 的延迟。比如模型每秒生成文字很快，如果首次响应前仍需处理很长的会议材料，用户等待第一句话的时间依然可能很长；实际应用要分开记录首字等待与后续输出速度。

## 数据与训练：公开了什么，仍不知道什么

技术报告讨论多模态能力、长上下文研究及评测，并分析长序列上下一 token 预测的表现；这说明研究者用语言模型的预测损失观察模型是否利用更早的上下文。报告没有完整公开训练语料来源和比例、长上下文训练日程、全部后训练数据以及每个模态的内部实现。不能因为它能处理视频，就推断一定使用了某一种公开视频编码器或特定采帧训练配方。

报告明确提及 Flash 使用来自 Pro 的在线蒸馏，但没有由此公开完整的蒸馏数据、监督信号和所有训练阶段。可以把它理解成较小模型在训练时参考较大模型的指导；是否改进了特定业务任务，还要在同样的输入、预算和版本下实测。有关教师、学生与不同蒸馏方法，可先读[知识蒸馏](/training/distillation/)。

从一般方法理解，模型要回答“预算后来为什么改变”，训练或适配数据可以包含长文、问题、引用依据和期望回答。音视频任务还可以包含时间戳与对应事件。**这是教学设计，不是声称 Google 使用了这些具体训练样本。**如果标注遗漏了结尾补充条款，模型即使依照训练答案回答，也会重复错误。

长文评测还需防止同一份文档的相似问题同时进入训练和测试；视频则要按来源、节目或场景隔离。真实业务中的文档版本、授权及个人信息也需要管理。闭源权重使外部研究者无法独立复现完整训练过程，因此应把可复现的接口评测和内部实现假设分开报告。

## 评测：从找一根针到理解整段材料

### 针检索测什么

“长上下文找针”会在很长材料中的某个位置放入一条已知信息，再问模型是否能找回来；可以改变针的位置、输入长度和背景内容。Gemini 1.5 技术报告在特定合成文本检索实验中，报告 Pro 在最多 10M token 时约 **99.2%** 的检索准确率。这是研究实验、指定材料和问题下的数字，不表示所有复杂长文任务都有 99.2% 的正确率，也不等于当时每位 API 用户都能使用 10M 窗口。

研究测试长度、公开预览上限和具体服务配额是不同概念。2024 年初官方介绍 1.5 Pro 的标准窗口及 1M 预览条件；后续服务策略和版本可能变化。项目评测应记录实际模型标识、接收成功的 token 数和测试日期。

### 单点定位之外还要测什么

针检索通常有一个明确答案，但会议记录中有旧决定、补充说明和相互冲突的说法。测试可以把正确条款放在开头、中间或结尾；加入相似数字与修改历史；再分别提问单点查找、跨段组合、矛盾判断和信息不足时的回答。最好要求给出原文位置或时间戳，并检查引用是否真的支持结论。

假设 20 份独立会议记录中，模型找对预算的有 18 份，预算与税务口径都正确的有 14 份，那么单点定位率是 90%，组合正确率是 70%。这是教学计算，不是 Gemini 实测。两个指标的差距可以提示需要进一步检查跨段关系，但不能单凭一次测试定位模型内部原因。

### 长视频：采样决定能看到什么

[Gemini 1.5 技术报告的 1H-VideoQA 测试](https://arxiv.org/html/2403.05530v5)选了 40 到 105 分钟的视频，提出 125 道五选一问题，要求模型在没有示例答案的情况下作答。研究者先按每秒一帧抽取画面，再从这些帧中均匀选出 16 帧、150 帧，或提供全部采样帧：

| 输入画面           | Gemini 1.5 Pro 正确率 | Gemini 1.5 Flash 正确率 |
| ------------------ | --------------------- | ----------------------- |
| 16 帧              | 45.2%                 | 39.7%                   |
| 150 帧             | 56.3%                 | 50.8%                   |
| 每秒一帧，全部送入 | 72.2%                 | 65.9%                   |

同一套题里，Pro 从只看 16 帧到看完每秒抽出的一帧，正确率提高了 **26.9 个百分点**。可以把它想成让人概括一场电影：只给十几张截图，很容易错过故事转折；给更多截图，线索更完整，但输入量也更大。这里展示的是这套测试中的变化，不能把差值直接当成所有视频任务的收益。

如果一个动作恰好发生在两帧之间，即便提供了所有**采样帧**，也不代表模型看到了视频的每一帧。音频转写也要记录是否输入音轨、时长、分段和文字规范；图片和视频的预处理变化可能影响结论。报告同时研究长音频、长文问答等任务，但它们的指标和问题范围不同，不能把一个分数套用到其他模态。

## 应用与错例闭环

假设助手总结会议时仍采用旧预算 20 万。先保存经过授权的原始材料、版本顺序、实际送入模型的内容、问题、模型标识、输出及引用；核查结尾的修改是否真的包含在输入中，有无截断或错误的文件顺序，再检查模型是否找到却误解了最新决定。

收集不同文档长度、修改位置、冲突密度和无答案情况，按会议或项目隔离开发集与独立测试集。先改善材料排序、时间标记、证据引用和输入处理；必要时将长材料分段检索并要求核对来源。每轮分别检查定位、组合推理、引用正确率、无答案处理、延迟和成本，不能只测最初那份会议记录。

对敏感会议或影像，应依照实际服务的数据处理与权限要求决定能否上传。模型生成的摘要需要与原始证据核对；对会影响真实决策的数字，尤其要保留可追溯来源。

## 比较与面试追问

**10M token 的研究测试等于公开服务支持 10M 吗？** 不是。研究实验、预览额度及实际服务限制需要分别核对。

**针检索高分能证明长文推理同样优秀吗？** 不能。定位一条事实与处理多个版本、矛盾和无答案是不同任务。

**视频每秒取一帧就等于看了完整视频吗？** 不是。短暂事件可能落在抽帧间隙，音轨是否输入也需要单独确认。

**Gemini 1.5 Pro 的 MoE 有多少专家？** 公开材料未给出足以确认的完整结构，不应凭其他模型推测。

**更长上下文能替代所有检索系统吗？** 不一定。成本、延迟、证据定位及版本管理仍需按应用比较；长窗口和检索也可以结合。
