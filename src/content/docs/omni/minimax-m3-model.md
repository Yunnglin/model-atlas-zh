## 模型想解决什么问题

让一个助手修复大型软件仓库时，它可能需要同时看需求、源码、运行日志和页面截图。项目越大，需要翻阅的材料越多。模型如果每生成一个字都详细比较所有历史内容，计算和读写开销会不断增长；如果过早丢掉信息，又可能错过关键线索。

MiniMax M3 是面向这类任务的视觉语言模型。它结合 MoE 和 MiniMax Sparse Attention（MSA），支持较长的上下文与图片、视频输入，也可配合外部工具完成多步工作。模型生成“运行测试”请求，不等于测试已经运行；需要由外部系统执行命令、返回日志并保留证据。

下文使用的仓库修复和评测案例是教学设计，并非我们已经运行的实验。MiniMax 家族其他版本可参见 [系列概览](/nlp/minimax-family/)；不同版本的结构和训练细节不应混写。

## 结构：既要选对资料，也要读得省

### 多模态输入和 MoE 各自负责什么

图片或视频经过视觉处理后与文字一起供模型处理。比如用户发一张网页截图并说“这个按钮挡住了价格”，模型可以结合画面和文字判断需要检查哪里；视频理解还涉及抽帧和分辨率，视频里一闪而过的异常可能根本没有被采到。文字输出也不能保证画面解释正确，需要结合原图验证。

MoE 可以类比一组各有专长的处理小组：路由器为每个 token 选择部分专家参与计算，而不让全部专家每次都工作。约 23B 激活参数并不是模型只需要存储 23B 参数；全部专家权重、KV 缓存、输入图像和设备间通信都影响部署资源。MoE 选择的是部分前馈专家，MSA 则决定注意力重点看哪些上下文，两者解决不同问题。[混合专家](/foundations/moe/)和[注意力机制](/foundations/attention/)可以作为前置知识。

看一份具体配置能避免把所有稀疏模型混成一种：M3 官方权重的文本骨干配置有 60 层；前 3 层使用稠密前馈，后 57 层使用 MoE。MoE 层配置 128 个路由专家，每个 token 选 4 个，另有 1 个共享专家。注意力的 64 个查询头与 4 个键值头构成 GQA，平均每 16 个查询头共享一个键值头。这里的前馈专家选择和注意力头分组是两个不同的设置，数字对应这份模型配置，不能套给 M2。

### MSA：先查目录，再读选中的页

把长仓库日志想成一本厚书。全注意力像每次回答都认真对照前面所有页；MSA 则先用一个较轻的索引分支给上下文打分，挑出相关的连续块，再让主注意力分支重点阅读被选中的内容。

具体来说，论文在 GQA 分组基础上，对当前 token 可见的历史信息打分并聚合为块分数，每组分别选择得分高的块；同组的多个查询头共享这组选择，不同组可以选择不同块。当前 token 所在的局部块始终保留。主分支随后对选中块内符合因果限制的 token 做标准注意力计算，而不是只看每个块的一个摘要。

从 M3 官方配置看，前 3 层使用全注意力，后 57 层启用稀疏注意力；这与上面“前馈层是稠密还是 MoE”是两条独立的层配置，不能把“稀疏注意力层”和“专家层”当成同义词。对应配置中块大小是 128、最多选 16 块；用乘法可以得到最多 2048 个块内位置的预算上限，但当前块的一部分可能是因果掩码遮住的未来位置，可见位置不足时也未必凑满。实际选块和缓存的行为还要看具体实现。

举个简化例子：日志分成 100 块，某次查询的预算允许关注 5 块；索引器可能选到包含报错、配置、最近修改的几个区域，再在这些区域中计算更细的注意力。数字仅为说明，实际块大小和预算由配置决定。如果真正的关键日志没有被选中，模型就可能漏掉它；所以稀疏选择需要训练和实际任务评测，而不是默认能找到所有答案。

### 为什么按块选择

连续读取一整块通常比到处读取离散 token 更适合硬件访存；但块越大，可能连不相关的信息也一起读进来。论文同时讨论了索引和注意力算子的实现，说明理论计算量减少还要配合实际硬件和内核，才能转化成运行速度。

索引分支也要计算和读取信息，**稀疏不意味着所有计算成本都变成线性，也不意味着长上下文没有成本**。官方发布说明中的预填充和解码加速，是在其指定上下文、模型对照和实现条件下测得的结果；不能将数字直接推广到任意设备或短请求。

## 训练：公开的 MSA 方法与未知的完整配方

官方表示 M3 从训练起始阶段使用文字、图像等混合模态数据，并使用图文交错数据。可把交错样本想成一篇图文教程：说明文字、图表和后续解释彼此对应，模型需要把它们放在一起理解。但官方发布介绍没有给出全部样本来源、各种模态的精确比例或可复现的完整后训练配方；不能根据“原生多模态”猜出全部训练数据。

MSA 论文公开了索引器训练方法：先让索引器学习主注意力中哪些内容受关注，再进行稀疏选择。论文使用 KL 对齐损失训练索引分支，并通过梯度分离避免该辅助损失反向影响主干；在索引器预热时保留全注意力，待选择器有一定能力后再进行稀疏训练。这有点像先让新员工跟着熟练同事观察，再逐步独立挑选资料。

论文也报告不同规模和配置的实验。例如，论文用一个 **109B 总参数、每 token 激活约 6B 的模型**比较两条路线：一条从头训练 MSA，另一条从已训练的全注意力模型出发，换上 MSA 后继续训练。两条路线都先用 40B token 预热索引器，完整训练预算均为 3T token。可以把后者理解为“先让老员工带着新目录员熟悉书架，再让新目录员独立选页”，而不是立刻用未经训练的目录取代全部查阅。这个 109B 实验模型不是发布的 428B M3，也不能把它的训练预算直接套到 M3 上。

模型的工具行为可能还依赖任务示范和后训练；具体训练仍以官方公开的版本说明为准。

## 评测：把长、准、快分开看

官方发布报告 SWE-Bench Pro 59.0%、Terminal-Bench 2.1 66.0%。前者偏向检查真实仓库修复任务，后者关注终端环境中的多步操作。官方说明 SWE-Bench Pro 在内部基础设施上使用 Claude Code 作为脚手架，测试逻辑与官方评测对齐；Terminal-Bench 使用 Terminus 2，限制为 2 小时和最多 128K 输出 token。这里的脚手架负责组织工具调用，不能把结果理解为模型独自完成了测试。数字依赖任务版本、工具框架、预算和评测流程，不能直接当成真实项目的成功率。

评估长上下文至少要分三件事：**容量**是能否接收材料；**利用能力**是能否在不同位置找到并正确使用证据；**成本**是达到这一效果需要多少时间和资源。可以在长文不同位置放互相冲突的版本记录，要求模型指出最新记录及原文位置；还要测试跨章节推理和大量干扰信息，而不只做一次“找暗号”。

官方报告在 1M 上下文条件下对 M2 比较，宣称预填充超过 9 倍、解码超过 15 倍加速，并报告每 token 计算量约为前代的二十分之一。它们是给定对照和条件下的结果，模型架构、算子及硬件同时影响数字；这不是说所有请求或整个应用都加速同样倍数。[知乎的 MSA 解读](https://zhuanlan.zhihu.com/p/2053179886907531735)可辅助阅读两分支机制，但实现结论应以论文为准。

## 一个例子：修复上传功能

假设用户给系统一份需求、仓库代码和失败截图，要求修复上传后页面不刷新。系统先提供相关文件和图片；模型根据内容提出线索，使用外部工具读取组件、API 返回和日志，再选择可能相关的代码位置。接着它给出补丁，请工具运行测试并返回结果，最后查看新的页面截图。

一个长上下文窗口可以容纳更多历史，但并不能保证模型不会把旧日志当成最新结果。验收应固定测试环境、核实测试确实执行、确认上传成功和界面刷新，并检查修改没有破坏其他路径。如果命令失败或截图未生成，记录为未完成，不应接受“已经修好”的文字作为证据。

要把案例变成学习和改进闭环，可以用授权的历史问题构造数据，按仓库或时间划分训练与独立测试；记录模型是否找到关键文件、工具是否被正确调用、测试是否通过、长上下文位置及成本。把错例分成“漏检线索”“工具执行失败”“补丁无效”“总结与实际结果不符”，分别检查输入、模型和框架，再用保留样本验证改动。

## 局限与部署选择

稀疏选择可能漏掉罕见但关键的证据；视觉输入可能受小字、截帧和图像处理限制；长程智能体还受工具权限、执行环境和错误恢复影响。公开权重方便本地研究，但总参数规模、模型格式、内核兼容性和上下文缓存仍决定实际硬件需求。不要把供应商演示中的连续运行时长看作对所有任务的可靠性保证。

许可尤其需要单独核对：模型卡公开权重不意味着无条件商用。官方许可对商业使用列出了标识和通知条件，并针对特定收入规模要求事先书面授权；实际使用应直接查看对应权重版本的许可全文和适用约束。

## 面试追问

**MSA 与 MoE 的稀疏有何不同？** MSA 选择要关注的上下文块，MoE 选择参与前馈计算的专家；它们可以同时使用，但节省的是不同部分的计算。

**1M 上下文是否意味着模型可以准确使用任意 1M 信息？** 不意味着。需要测试信息在不同位置、多个干扰项、跨段推理和不同输入模态下的表现，同时检查部署限额。

**为什么稀疏算子理论更省仍可能没有明显加速？** 索引、调度和非连续访存都有开销，实际表现依赖硬件、内核、请求长度和并发，需要端到端测量。
