## 要解决什么问题

视频里有人指着两只杯子说“拿左边那只”。只听声音不知道指哪只，只看画面不知道具体要求。助手还要将判断说出来，于是需要区分**输入理解、证据对齐、回答内容与发声**四件事。

本页限定 Qwen2.5-Omni，沿这个虚构场景讲解；时刻与错误候选均为教学构造，未实际运行。下一代结构见 [Qwen3-Omni](/omni/qwen3-omni/)，不要把两代的编码器与声码器混画。

## 结构与数据流

官方 Figure 2 从底部输入看起：视觉、音频编码器将画面和声音变成表示，Thinker 结合文字生成内容，Talker 利用 Thinker 的表示与文字生成离散语音 token，最后通过声学解码链还原波形。Thinker 和 Talker 是协同模块，不是两个彼此独立聊天的助手。

## 把视频、答案和声音对应起来

### 看见与听见，先各走自己的输入路径

文字按文本 tokenizer 处理，图片／视频由视觉编码器处理，音频则转为声学特征后进入音频编码器。原始 2.5-Omni 的初始化涉及 Qwen2.5、Qwen2.5-VL 视觉编码器和 Whisper-large-v3 音频编码器；**不等于在推理时先调用完整 Whisper 转写接口，再把文字转给 Qwen**。

比如录音带着疑问语气，完整音频表示可能保留文字转写没有表达的线索。能否真正利用仍要评测，不能只凭端到端设计就宣布一定优于串联。

### 对齐的不只是“第几帧”，还是真实时间

假设手指在第 2 秒指向左杯，话语“左边那只”出现在相近时间。若音轨被错移几秒，即使两路内容各自清楚，模型也可能把话配到另一个动作。

2.5-Omni 的 TMRoPE 将时间、空间位置放进多模态组织中，音视频按相应时间顺序处理。位置编码给模型建立对应的条件，**不会替你修好原始素材的音画不同步或错误抽帧**。实际请求中的音轨、帧与时间戳都需要保存。

可以把输入想成一份按时间排列的记录：先有某段声音，再有相邻时刻的画面，随后又有一段声音。报告把音频与视频表示交错组织，使模型能结合时间位置理解它们，而不是把两整段互不关联的信息简单拼在一起。这个排列方式提供了对齐线索，却不是说模型已经识别出手指与“左边”一定对应；如果采样恰好漏掉指向动作，证据仍然缺失。

具体如何排？论文把带音轨视频按实际时间分成 2 秒一段，每段先放视觉表示、再放音频表示，各段依次排列。音频的时间位置编号以约 40 毫秒为单位；视频帧根据真实时间确定对应编号。例如一帧位于 1 秒、另一帧位于 1.6 秒，它们的时间编号间隔约为 15 个单位。帧内不同位置还分别带有高度和宽度信息，让模型知道画面元素位于哪里。

这种按时间组织的方式与[Qwen3-Omni](/omni/qwen3-omni/)有所不同：后者使用时间编号直接对齐音视频，音频时间单位约为 80 毫秒。两代都要保留原素材正确的时间信息。

### Talker 如何避免等整篇答案写完

Thinker 逐步产出文字与表示，Talker 流式产生语音编码，再经后续波形生成。2.5 使用流匹配 DiT 将语音码转为梅尔频谱，再由改造的 BigVGAN 生成波形；该路线包含分块处理。它与 [Qwen3-TTS-12Hz](/audio/qwen-tts/)的轻量因果解码路线不是同一张图。

早开始发声与完整回答快，是不同指标。把内部第一段 token 产生时间当成用户听到首包的时间，还漏掉解码、传输和播放缓冲。

## 数据与训练

| 环节                 | 论文描述的重点                     | 对杯子场景的意义                   |
| -------------------- | ---------------------------------- | ---------------------------------- |
| 编码器对齐           | 先固定语言模型，训练连接与编码侧   | 让声音与视觉信息接到语言空间       |
| 全参数与混合模态训练 | 解冻，加入更丰富的音视频与文本材料 | 学习“话说的对象”与“画面对象”的对应 |
| 长序列训练           | 使用更长输入                       | 在较长视频中保留事件联系           |
| Thinker 指令微调     | 各类模态对话的 ChatML 数据         | 学会根据问题组织回答               |
| Talker 后训练        | 上下文续接、DPO、声音相关指令适配  | 改善发声稳定、自然和可控           |

第一阶段的训练顺序可以想成给两位新同事分别接入同一个工作台：语言模型先保持不变，图像与音频分支各自先训练适配器，再训练对应编码器。这样模型先学习把每种输入转换成语言模型能利用的表示；进入第二阶段后，各部分才一起更新。两个分支分开训练描述的是这一阶段的安排，不代表推理时不能同时使用声音和画面。

论文对第二阶段给出了数据规模：新增约 8000 亿 token 的图像／视频相关数据、3000 亿 token 的音频相关数据，以及 1000 亿 token 的带声音视频相关数据。前两个阶段的最长序列为 8192 token，最后加入较长的音频与视频，并将训练序列长度扩展至 32768 token。这些是不同模态数据在训练中的组织方式，图片和音频也会经过编码成为模型处理的序列。

同一系统里，文字正确与语音稳定依赖不同训练信号；不能一句“都是下一 token 预测”省掉全部差别，也不能给 2.5 补上下一代才公开的全部流程。

业务适配应保留问题、同步音视频、证据时段和正确答案。只有最终文字标签，未必足够监督“为何是那只杯子”。也要准备冲突、缺证据和没有可见指向的场景，而非每题都逼模型猜一个对象。

### Talker 学的是发声，不是重新回答问题

Thinker 的任务是从多模态输入组织语义与文字；Talker 接收对应的文字和高层表示，生成离散语音 token。拿“左边的杯子”来说，Thinker 判断该选哪只，Talker 还要把答案以连续的声音说出来。它们之间共享上下文，但输出形式和训练目标不同。Talker 说得很自然不能证明 Thinker 选对了杯子。

这里 Talker 同时接收 Thinker 的高层表示和采样出的文字 token 的嵌入：前者提供上下文，后者明确要读出的文字。可以想成播报员既拿到一句台词，也拿到帮助掌握语气的背景信息。这与 Qwen3-Omni 不再直接使用高层文字隐藏表示的设计不同。

官方报告描述 Talker 分阶段学习：先通过上下文续接建立语音生成能力；再以偏好优化改善稳定性；最后做多说话人指令微调以改善自然度和可控性。报告中的偏好数据用字词错误率和标点停顿错误等信号区分候选；它并不意味着听感、真实性和业务安全都能由一个分数完全覆盖。后续业务训练也应保留不同说话人和困难词句的独立回归。

### 为什么分块能提前开始，也可能影响边界

语音不是必须等全部文字完成才开始，但分块意味着每次只处理一部分上下文。报告使用滑动窗口 DiT 限制可见范围，以便流式把语音 token 变为声音。把它想成分段播报：第一段可以早点出来，段与段之间却要衔接好。若边界出现停顿或重复，先定位切分、上下文与解码，再决定是否调整模型；换成另一代的解码器并不自动等同于复现 2.5 的行为。

更具体地说，报告中的窗口包含当前块、前面两个块和后面一个块；因此一次解码不是只看当前块，也需要等待有限的后续上下文。首包时间会受到这一等待、波形生成与传输共同影响，不能只用块数量推断实际延迟。若调整块大小或缓冲策略，应在相同硬件、输入和播放条件下同时测首包、连续性与总耗时，而不是只选一个最快的数字。

## 评测怎么看

### 三组对照，检查是否真的需要两路证据

固定模型与问题，比较完整音视频、仅画面、仅声音。对于必须结合两路的题，单路缺证据应恰当处理。若去掉视频仍答对，可能是问题只靠文字线索就能猜，不足以证明视觉推理。

### 记录完整回答链的时间线

| 时刻／结果 | 应记录什么                     | 能定位什么               |
| ---------- | ------------------------------ | ------------------------ |
| 输入       | 首段音频到达、实际帧与输入窗口 | 等待、截断、同步         |
| 理解       | 文字答案与证据时段             | 对象识别、空间指代、时序 |
| 发声       | 首个可播放音频、后续包与结束   | 声学解码、断续与总耗时   |
| 一致性     | 文字与语音是否表达同一结果     | 说错、漏说或内容分叉     |

文字答“左杯”而声音说“右杯”，应算输出一致性失败，不能因文字正确就宣布任务通过。语音内容与音色自然度也分开看。[多模态评测](/evaluation/multimodal-evaluation/)与[语音质量](/evaluation/speech-quality/)共用相关协议。

另一项可以先单独看“听写”的测试：报告表 2 中，LibriSpeech 的 test-clean／test-other 上，Qwen2.5-Omni-7B 的词错误率分别为 1.8%／3.4%，Whisper-large-v3 为 1.8%／3.6%。词错误率越低越好；这两组结果只说明报告所列英语测试集上的识别表现，不能据此断言两者在嘈杂中文或多模态对话中同样接近。识别正确也不等于模型理解了用户意图。

报告的 SEED 零样本语音生成测试还分别记录内容一致性与说话人相似度。论文表 9 中，`Qwen2.5-Omni-7B_RL` 的 `test-en` WER 为 2.33%，而 `Qwen2.5-Omni-7B_ICL` 为 2.72%；两者是该表区分的不同设置，不能当成同一个检查点随时都能达到的分数。这考的是特定文本与参考声音条件下的语音输出，不是“杯子场景”的视觉理解正确率，也不能直接代表任意声音的自然度。比较前要确认检查点、参考音频、文本规范和测试集。

## 应用与错例

关键指向没进采样帧，先改输入；左右杯都看清却选错，查空间指代和数据；文字正确但说错，查发声链；迟迟不结束，查端点与输出预算。一次对照只改变一个条件，避免同时换模型、抽帧和提示后无法归因。

开发池补充相似杯子、不同拍摄角度、噪声、时间冲突与无证据问题，独立视频验证，并回归普通对话。[全模态助手案例](/cases/omni-assistant/)提供产物清单。

### 从具体错例到下一轮数据

假设评测中模型正确听到“左边”，却选了画面右侧的杯子。先确认视频有没有镜像、时间戳是否对应、标注里的左右是以摄像头还是使用者视角为准。检查后再构造对照：相同画面改变指令，相同指令交换杯子位置；这些样本能帮助发现模型是否只记住某个位置。若只是标注口径混乱，先修标注，比增加训练轮次更直接。

用新拍摄的视频和不同环境做回归，分别记录选对对象、合理拒答、文字和语音是否一致。训练集与测试集按视频来源分开，避免同一素材的相邻片段同时出现。以上是教学方案，不代表已完成部署或实测。

## 比较与面试追问

**初始化用了 Whisper 编码器，就是完整 Whisper＋Qwen 串联吗？** 不是，编码表示接入与完整转写接口串联不同。

**有时间位置编码，为什么还可能音画对错？** 输入同步、采样和训练覆盖仍会影响对应。

**能输入图片就能生成图片吗？** 输入和输出能力分别确认；本页重点是多种输入与文字／语音输出。
