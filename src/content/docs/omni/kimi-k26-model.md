## 先理解：它要解决什么问题

你请一位程序员修复网页上传按钮。她不仅需要看懂截图，还要找项目文件、尝试修改、运行测试、查看结果，再根据错误继续调整。一个能够流畅解释问题的模型，和一套能够实际完成这项工作的系统，之间还隔着工具、运行环境和验证。

Kimi K2.6 面向这样的长程任务：它能读取文字与视觉内容，生成下一步回答或工具请求，并根据外部执行结果继续推理。官方技术博客展示了长时间编程实例；它们是特定环境下的案例，而不是每次任务必然能成功的保证。

本文的网页修复例子和评测方案是教学设计，不代表我们已经运行过模型。可以先读 [Kimi K2.5](/omni/kimi-k25-model/)，再比较后续版本在实际任务中的表现；相近的参数配置并不能证明训练过程或所有实现细节完全相同。

官方模型卡说明 K2.6 与 K2.5 使用相同架构，部署方式可以沿用。可以把这理解为两台车采用同一底盘：并不意味着它们的权重、训练数据和驾驶表现完全相同。比较版本时，仍要记录具体检查点、工具与推理设置。

## 结构：从截图到行动建议

### 视觉信息怎样参与回答

假设用户发来页面截图并说“上传按钮被遮住了”。视觉编码器 MoonViT 先把图片转换为特征表示；这些表示与文字问题一起供语言主干处理，模型才有机会把“按钮的位置”和“用户的问题”联系起来。视频则需要处理帧及其顺序，实际能看到多少细节会受抽帧、分辨率和上下文预算影响。

可以把视觉编码器想成把图片整理成模型可读笔记的助手，但笔记不是照片的无损复印件：小字太模糊、关键帧没有采到，或者图里有重叠遮挡，都会影响判断。因此模型说“按钮在右下角”，最好再用截图或定位信息核验。

截至核对时，官方模型卡将视频对话列为实验功能，并注明目前只在官方 API 支持；本地或第三方部署是否提供视频输入，需要查看各自的接口和配置。

### MoE 与 MLA 分别管什么

![Kimi K2.6 语言主干示意：61 层中首层使用稠密前馈，其余层使用路由专家和共享专家，各层通过 MLA 注意力处理上下文。](/figures/kimi-k26-k27/backbone.svg)

这张教学图将语言部分展开：首层的前馈模块是稠密网络，其余 60 层的前馈模块采用 MoE；每层都结合 MLA 注意力。图片或视频经过 MoonViT 转成视觉表示后，与文本一起送进语言主干。图省略残差连接、归一化和投影等细节。

官方配置的语言主干使用 64 个注意力头、7168 维隐藏表示，MLA 的键值潜在表示维度为 512。可以把 MLA 看成先用较紧凑的表示记录历史信息，再在注意力计算中使用它；具体缓存布局由推理实现决定。

官方模型卡列出 61 层，其中包括一层稠密前馈层；在 MoE 层有 384 个路由专家，每个 token 选 8 个专家，并有一个共享专家。可以把专家想成一组不同的处理小组：路由器按当前 token 选择一部分参与，而不是每次让所有小组同时工作。约 32B 是每个 token 激活的参数规模，约 1T 是模型总规模；其余专家的权重也需要存储或按需调度。

模型使用 MLA 注意力。注意力负责从上下文中取用相关信息；MLA 则以压缩表示等方式组织注意力的计算与缓存。它与决定哪些专家参与前馈计算的 MoE 解决的是不同问题。要在长任务中部署，还需要考虑 KV 缓存、量化方式、显卡间通信和视觉输入的额外开销。详见 [混合专家](/foundations/moe/) 和 [KV 缓存](/foundations/kv-cache/)。

### 模型不会自己操作电脑

模型可以输出“读取组件文件”的工具请求，外部程序负责检查请求、实际读取文件，并把结果回传。模型看到结果后才能决定修改哪一处；运行测试同理。官方模型卡提到交错思考与多步工具调用，但工具权限、网络、执行沙箱、失败重试与日志属于框架及运行环境。

多智能体也是同样的边界：调度系统可以把“检查 CSS”“检查上传 API”“写测试”分给多个执行单元，再由主任务汇总。并行适合互相独立的部分；如果测试必须等代码修改完成，就不能无限加速。多个执行单元还带来更多 token、工具成本和合并冲突。子任务再多也不等于最终结果正确。

### 原生 INT4 量化用于哪里

官方采用与 K2 Thinking 相同的原生 INT4 方法。配置中的低精度权重每 32 个为一组，使用 4 位表示；注意力、共享专家、输出头和视觉模块等列在排除范围内。因此估算显存时，要分别计算低位宽专家权重、其他模块、缓存和运行时占用。更多细节可以看[量化](/training/quantization/)和 [K2 Thinking](/nlp/kimi-k2-thinking/)。

## 数据与训练：哪些知道，哪些不知道

预训练可以类比大量阅读和练习，让模型学习文字、代码以及视觉内容之间的规律；后训练则更侧重遵循指令、回答问题与工具交互。一个常见的教学例子是让模型看到“问题—调用测试工具—观察失败—修正”的轨迹，再用合适的反馈改进其行为。可验证任务还可以用测试是否通过作为反馈，但如果测试覆盖不足，模型可能投机取巧：只满足测试，不满足真实需求。

这些是理解模型训练的通用方法，**不应当据此断言 K2.6 使用了某个特定数据集、训练阶段、奖励函数或者精确比例**。我们查阅的 K2.6 官方模型卡和技术博客没有提供完整训练配方；K2.5 的论文可用于理解前代公开方法，但不能直接充当 K2.6 新增训练过程的证据。官方展示的能力提升，也不能仅凭跑分断定由某一种训练技术造成。

如果自己构建网页修复数据，应先收集有授权的需求、截图、代码和可重复的测试环境；按项目或时间划分训练集与测试集，避免同一个修复补丁泄漏到两边。截图和日志可能包含账号或用户数据，需要在收集阶段处理。任务除了最终测试结果，还可记录工具失败、修改次数与无效尝试，帮助分析模型究竟卡在哪里。

## 评测：分清“会答”和“能做成”

官方模型卡给出 SWE-Bench Pro 58.6、Terminal-Bench 2.0 在 Terminus-2 框架下 66.7，以及 MMMU-Pro 79.4。这是官方报告的特定基准结果；模型卡说明编程任务结果为 10 次独立运行平均，视觉基准为 3 次平均。分数取决于模型版本、提示词、工具、运行框架和评分方法，不等于用户项目的成功率，也不能直接将不同设置的数字相减得出可靠排名。

SWE-Bench Pro 偏向检查真实软件仓库问题是否解决；Terminal-Bench 侧重终端环境中的操作；MMMU-Pro 检查多学科视觉理解。它们分别回答不同的问题：能看图不代表能修代码，能通过一个终端任务也不代表懂业务约束。模型卡还列有 BrowseComp 的普通和 Agent Swarm 配置，使用不同系统配置时应分开报告，不能将智能体框架的成绩直接当成单次模型回答成绩。

以 SWE-Bench Pro 为例，官方使用从 SWE-agent 改造的内部框架，提供 bash、文件创建与编辑等工具；Terminal-Bench 使用 Terminus-2，保留多轮推理内容。两种测试都包含真实工具调用，而不是只让模型写一段补丁。即使最后数字来自同一个模型，也要把工具能力和执行环境一起列出来；用户自己的仓库还可能有不同依赖和验收要求。

MMMU-Pro 也能看出工具的影响：官方报告不使用 Python 时为 79.4，使用 Python 时为 80.1，均为三次运行的平均值。可以把它想成做一道带图表的计算题：模型先看懂图表，再借助 Python 做计算；允许调用工具的成绩反映的是模型和工具配合完成任务的结果。两项成绩的差异不能简单当作模型视觉理解能力本身提升了 0.7 分。具体配置见[官方模型卡](https://huggingface.co/moonshotai/Kimi-K2.6)。

更贴近实际的测试可准备一组从未用于调试的网页问题：每题提供需求、代码、运行环境和验收截图，记录功能测试通过率、视觉偏差、运行时间、token 与工具调用次数，再由人检查安全和可维护性。同一套任务用固定工具及预算比较不同模型，重复执行并报告失败案例。若模型声称“已修复”但测试根本没运行，应记录为没有完成，而不是只看回答是否自信。

长任务还应单独统计“预算耗尽”。例如一个复杂题设定最多输出 8,000 token，模型在给出最终答案前就被截断；测试可以按规则判为未完成，但记录里要保留截断原因，不能直接归类成最终答案算错。再用相同题目比较不同预算下的通过率和成本，才能看清多花计算是否带来收益。这个例子是教学设想；[社区测试](https://www.zhihu.com/question/2029714522651272097/answer/2030049575298389432)也记录过输出触及上限的情况，其成绩只适用于该测试的题目与规则。

## 一个完整例子：修好被遮挡的按钮

1. **理解问题**：用户提供截图及“上传按钮在手机上点不到”。系统把截图和文字送入模型；模型提出可能是遮挡或布局问题，但此时只是猜测。
2. **读取证据**：模型请求查看组件、样式与移动端断点；执行器返回文件内容。若工具读取失败，应该反馈失败而不是凭空编造代码。
3. **提出修改**：根据证据调整层级或容器布局，并解释改动影响。具体修复取决于实际代码，不应默认所有遮挡都是 z-index 问题。
4. **验证结果**：执行相关测试并在目标尺寸生成新截图，检查按钮是否可见、可点击，桌面布局是否回归。失败后继续定位，而不是反复猜测。
5. **整理错例**：将“看错截图”“文件读取失败”“测试通过但点击仍被遮挡”等情况分类。先核验标注，再用独立样本检查数据或流程改进是否有效。

这个过程把模型、工具和人分别负责的部分摊开来看：模型提出请求和解释，工具提供实际执行记录，人确定验收要求并复核风险。最终交付需要能追溯测试输出与修改内容，不能只靠一段总结文字。

## 面试时可以怎样回答

**为什么 1T 总参数的模型不能简单按 32B 部署？** MoE 每个 token 只激活部分参数，但不同 token 可能选择不同专家；完整服务仍需处理全部权重的存放或调度，并额外承担缓存、视觉编码器和通信成本。

**为什么一次长程演示不能证明可靠性？** 它受到任务选择、运行环境、尝试次数和工具配置影响。应在固定预算下测试有代表性的独立任务，报告成功率、成本和失败情况，并说明是否使用并行智能体。

**能否根据 K2.5 的论文还原 K2.6 的训练？** 不能。前代报告能解释相关方法和背景，但具体的新增数据、训练阶段及配比，只有对应版本公开的资料才能证明。
