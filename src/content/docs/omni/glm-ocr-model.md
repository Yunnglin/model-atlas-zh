## 它解决什么问题

一张发票上有抬头、金额和密密麻麻的表格。一套好的文档识别系统不仅要看懂每个字，还要知道“金额”和“税额”分别对应哪个数字；如果把表格拆错行，即使每个字都认对，最后的数据仍可能错误。

GLM-OCR 是针对这类任务的视觉语言模型。它读图片，根据提示输出文本、公式、表格或关键字段。官方还提供文档解析流水线：先分析页面布局，分区识别，再把结果合并。可以把它想成先给试卷分题，再分别答题，最后按原来顺序装订；分题本身如果出错，后面的答案也容易串行。

文中发票例子及评测流程用于说明方法，不代表本文作者已经实测。与通用视觉模型相比，专门的 OCR 模型可能在目标任务上更省资源，但不意味着它擅长所有视觉问答或在每个业务场景都最准确。

## 结构：先看清，再组织输出

### 视觉编码器、连接器和语言解码器

CogViT 把图片转换为视觉特征。你可以把它看成负责观察字形和位置的眼睛；轻量连接器把这些视觉信息整理成语言模型能处理的表示，并通过下采样压缩视觉 token。随后 GLM-0.5B 解码器结合任务提示，一步步生成文字或结构化结果。

压缩有好处：后续模型需要处理的视觉 token 减少，时间和内存开销可能下降。但如果原图太小，或者过度缩放后一个角标只剩几个像素，模型很难凭空恢复正确内容。输入预算、字符大小和处理速度之间需要根据实际材料取舍。

[官方配置](https://huggingface.co/zai-org/GLM-OCR/blob/main/config.json)给出视觉编码器 24 层、隐藏维度 1024；文字解码器 16 层、隐藏维度 1536，有 16 个查询头和 8 个键值头。可以理解成两个查询头共享一组键值头；生成文字时需要保存的键值表示比 16 组各自独立更少。

这条路径中的“编码器—解码器”是视觉编码器加语言解码器：图像特征先投影到语言模型空间，作为前缀与文字提示一起使用。随后解码器逐个生成结果；处理表格和公式时，输出顺序和结构也很重要。

### 多 token 预测有什么用

普通自回归生成通常根据前文预测下一个 token，再继续预测后续内容。OCR 输出往往是对输入内容的忠实转写，许多后续字符具有较强规律。报告引入多 token 预测（MTP）训练目标，使模型在训练中同时学习预测后续多个 token，并在支持的推理实现中用于提高解码吞吐。

例如看到“发票号码：”后，模型需要依次输出号码字符；MTP 尝试更高效地提出多个后续候选。辅助预测头采用参数共享，减少额外内存。技术报告中，训练目标涉及每步预测 10 个 token；其推理设置平均每步生成 5.2 个 token，报告吞吐提高约 50%。这两个数分别描述训练预测范围和实际平均生成数量。部署时的速度还会受到框架、硬件、图片尺寸、批量和输出长度影响。

### 两条处理路径不能混为一谈

报告里的文档解析先使用 PP-DocLayout-V3 检测版面，裁剪文字、公式、表格等区域，再将区域交给 GLM-OCR 识别并合并。多个区域可以并行处理；如果裁剪切掉了行末数字，识别模型并不知道被切掉的内容，错误就会向下传递。输出顺序也需要正确恢复，双栏论文尤其容易把左右两栏混在一起。

关键字段提取则可以将整页图片和提示直接送进核心模型，例如要求返回“发票号码”和“金额”。这条路径不依赖报告中的显式裁剪。最终得到可解析的 JSON 不等于数字正确：例如把金额 128.00 识别成 123.00，格式完全合法，业务仍然会出错。

## 训练：先学看图，再学按任务输出

技术报告介绍了四个主要阶段，适合把它理解成逐步培养一个文档助理：

1. **视觉编码器训练**：使用大规模图文和定位数据，结合掩码图像建模、图文对齐及更大视觉模型的知识蒸馏。报告提到这一阶段的数据规模达到数百亿图文对；它不是指所有样本都是人工标注发票。
2. **视觉语言预训练**：将视觉编码器与 GLM-0.5B 连接，联合学习图文、文档解析、定位和视觉问答等任务；后续引入 MTP 目标。
3. **监督微调**：使用文字、公式、表格、字段提取样本，让模型学会按照任务生成所需结果。好比给它看图片及标准答案，学习输出格式和识别细节。
4. **强化学习**：报告采用 GRPO，根据模型生成结果和任务相关奖励继续优化。文字识别使用归一化编辑距离，表格使用 TEDS 并检查结构，字段提取同时检查字段级 F1 和 JSON 等格式约束。

例如字段抽取结果的花括号配对正确，却把税额填写到了金额字段：格式检查只能发现语法问题，字段级对比才有机会识别内容不一致。公式、表格同样不能只看字符串是否相似，还需要检查结构。奖励设计依赖标注质量和评价规则，不能保证覆盖所有真实错误。

假设标准答案有发票号、金额和税额三个字段，模型也返回三个字段，但只有发票号和金额与标准答案匹配。若按“字段名和字段值都正确”计为命中，这个教学例子的字段精确率和召回率都是 2/3，对应 F1 也是 2/3；JSON 仍然可以完全合法。实际评测还要约定金额格式、空字段和重复字段的匹配规则，不能把这个例子的判定方式当成论文公开的完整实现。

报告提供了各阶段的数据类别、部分规模与奖励设计，但没有公开全部训练样本、每份数据的来源和完整配比。我们不能把公开数据规模当作某个细分任务的数据量，也不能确认某份用户合同是否进入训练集。了解 SFT 和强化学习的一般区别，可结合 [SFT](/training/sft/) 与 [RLHF](/training/rlhf/) 阅读；报告这里列出的可计算奖励并不等同于所有强化学习都来自人工偏好。

## 评测：一页里可能同时有四种错误

官方报告给出 OmniDocBench v1.5 的综合分数 94.62，这是该模型和对应评测流水线在报告配置下的结果，不代表所有文档都能有 94.62% 的识别准确率。报告还有内部场景数据，内部测试集和实际业务之间可能有分布差异。比较模型时要核对任务、数据版本、图像预处理、版面工具、指标和运行条件，不能只看一个榜单数字。例如报告表 4 给出文字编辑距离 0.040（越低越好）和表格 TEDS 93.96（越高越好）；前者衡量文字差异，后者评价表格结构及内容。

同一表格中，PaddleOCR-VL-1.5 的文字编辑距离为 0.035、表格 TEDS 为 92.76；GLM-OCR 分别为 0.040 和 93.96。前者在这份报告的文字指标上较好，后者在表格指标上较好。选型时可以先看业务主要是识别段落，还是恢复复杂表格，再用自己的材料做对照。

可以把业务评测拆成几道独立检查：

- **文字**：字符错误率能反映替换、增加和遗漏，但要约定空格、标点及繁简处理方式。
- **版面和顺序**：检查段落是否漏掉、双栏是否串读；文字全对也可能顺序全错。
- **表格和公式**：检查单元格是否错位、合并单元格与公式上下标是否保留。可以参考结构指标，再抽样人工复核。
- **字段**：对发票号、日期、税额等逐项算准确率；金额还需校验数值、小数位及总额关系。不可读时允许标记待复核。
- **效率**：在固定硬件和并发下记录每页延迟、吞吐、内存和失败率；只测解码速度不包括 PDF 转图片、版面检测与后处理。

[知乎的一篇多模型实测](https://zhuanlan.zhihu.com/p/2015777929716585172)比较了表格、扫描件、手写和公式，并观察到具体样本中的角标和手写问题。它提供了有用的错例方向，但样本规模和测试设置有限，不能把其排名推广到所有业务。

## 实践闭环：从一张发票到下一轮改进

假设需要提取历史发票并写入财务系统。首先收集有授权的扫描件，标注字段、表格和需要人工判断的模糊区域；按票据来源、模板或时间划分训练、验证和独立测试，避免同一模板的近重复页面横跨数据集。

然后建立基线：记录图片尺寸、OCR 模型版本、提示词、是否使用版面检测和输出字段。对新票据执行识别，用程序检查字段是否缺失、数字能否解析、金额加税额是否与总额相符；不通过的样本进入人工复核，而不是自动改写成看似合理的数字。

错例应分类处理。如果是图片倾斜导致检测漏掉整行，优先检查扫描和版面检测；如果裁剪完整但“8”和“3”常认错，就收集真实易混淆样本，核对标注后考虑微调；如果识别正确却写入错误字段，要检查提示、字段映射和后处理。每次改动都用保留的独立数据重新评估，既看改善的票据，也看是否破坏了原本正常的文档。

合同、医疗记录或发票可能含敏感信息。部署时应按实际需求确定数据能否发送到外部服务、日志保留多久以及谁能查看原图。文档识别的输出也应保留原页和位置，方便后续核对，而不是只保留一串无出处的数字。

## 面试追问

**为什么 OCR 准确率不能只看字符错误率？** 字符全对但表格列错位，财务结果仍可能错误；还应看版面顺序、字段映射、表格结构和业务校验。

**为什么版面检测有时能提升效果，又可能引入新错误？** 它将复杂页面分成较简单的区域并支持并行，但检测遗漏、裁剪截断和排序错误会传递到结果中。

**强化学习奖励里的 JSON 校验能保证字段正确吗？** 不能。JSON 合法只说明格式可解析；字段内容还需要和可靠标注比较，并在实际应用中进行业务规则检查和必要的人审。
