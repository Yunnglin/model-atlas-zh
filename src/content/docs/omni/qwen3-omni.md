## 要解决什么问题

继续用“两只杯子，用户指着左杯提问”的例子。模型既要听、看、联系时刻，又要组织答案并发声。Qwen3-Omni 继承 Thinker—Talker 思路，但音频表示、专家结构与语音生成都不能直接沿用 2.5 的解释。

以下指令、时间线与错误输出都是教学构造。官方报告成绩是模型方实验，本站没有运行。本页讲 30B-A3B 发布系列，3.5／3.8 的公开范围见[家族页](/omni/qwen-omni-family/)。

## 结构与数据流

先看官方 Figure 2 底部：视觉编码器与 AuT 接入 Thinker；Thinker 生成文字并向 Talker 提供相应多模态表示；Talker 预测语音码本；上方的流式 Codec Decoder 还原声音。Thinker 与 Talker 都采用 MoE，码本编号不是专家编号。

## 音频编码器 AuT 在学什么

AuT 可以先理解为“把声音整理成能被语言模型利用的表示”。官方 Figure 3 展示训练用的音频编码器—解码器路径；Omni 使用的是相应音频编码器，不代表完整训练系统每个组件都保留在推理请求里。

本代用 AuT 提取通用音频表示，不能继续说成 2.5 的 Whisper 编码器初始化。AuT 的表示时间步与文字 token 数不同；例如四秒声音与几个字的答案，不要求位置一一对应。

## 沿着一次回答走到声音

### Thinker、Talker 与用户听见的音频不是一个东西

Thinker 的文字答案是“左边那只杯子”。Talker 还需要把相应文字与多模态条件变成音色、节奏和发音。在 3-Omni 中，报告将文字表示与发声条件解耦，使用离散文字／嵌入及多模态特征组织发声；不能照抄“把 Thinker 所有高层文字向量直接喂 Talker”来解释整条路径。

### 一帧语音为何有多个编号

Talker 主骨干预测主码本，MTP 模块生成当前帧剩余的残差码本，因果 ConvNet 形式的 Code2Wav 增量输出波形。图中的 0、1、…、15 描述这类分层码本组织：它们是同一时间片的不同信息层，不是 16 个词或 16 个说话人。

它可以逐帧推进，降低一定条件下的首包等待；但模型计算、调度、传输与播放仍决定实际延迟，不能用理论首包结果替代整套服务测量。

### 下载前先选对检查点

| 检查点    | 包含哪些模块               | 输出                            |
| --------- | -------------------------- | ------------------------------- |
| Instruct  | Thinker 与 Talker          | 文字、语音                      |
| Thinking  | Thinker                    | 文字；没有 Talker，不能直接发声 |
| Captioner | 面向音频描述微调的 Thinker | 音频内容的文字描述              |

如果拿 Thinking 权重搭语音助手，还需要另外的发声方案；不能靠添加“请用声音回答”补出缺少的模块。

## 数据与训练

### 先有模态连接，再学复杂交互

预训练先固定语言部分、训练适配与编码侧，再逐步解冻做混合模态训练，最后增加长序列材料。报告对适配器与编码器的训练顺序有具体安排，不应简化成“所有模块从第一步一起训练”。

Thinker 的后训练包含轻量 SFT、强到弱蒸馏、GSPO 等：示范建立任务格式，蒸馏迁移教师信号，反馈优化各类任务。Talker 的语音训练另有内容、音色与表现相关目标；同一个系统里，各模块不必使用完全相同的监督。

业务样本要保留实际视频、音轨、时间、用户问题、证据与目标回复。只写“有一只杯子”而不标明目标哪一只，无法帮助模型区分相似对象；音画错位还会教出错误关联。具体算法读 [GSPO](/training/gspo/)，模态任务关系读[训练全流程](/training/pipeline/)。

## 评测怎么看

先分清五项：**看对、听对、联系对、回答对、说对**。每项都要有切片，不因最终声音流畅就默认前面全对。

| 教学失败                 | 定位对照                     | 不应直接得出的结论   |
| ------------------------ | ---------------------------- | -------------------- |
| 声音中的“左边”听错       | 同样问题分别给音频与正确文字 | 整个视觉编码器无效   |
| 关键动作看漏             | 保留帧与补充关键帧对照       | 增加训练步数一定解决 |
| 文字答案对，语音漏“左边” | 同时核对文字和波形内容       | 任务已成功           |
| 首包快但不断卡顿         | 测首包、包间等待与完成时间   | 用户体验一定实时     |

复查官方报告时，看解码策略、提示与输入顺序、视频抽帧配置。Instruct 与 Thinking 的生成策略可能不同，不能把不同预算下的成绩当成纯架构对比。背景噪声、长音频、音乐与音画冲突另列测试。

所有延迟要写清起点和终点：用户说完、服务收到、首个可播放音频、最后一包，是不同时间点。硬件、并发、精度与输入长度一并保留。

## 应用与错例

先保存一条交互的完整证据，再分环节复现。关键帧丢失修输入；文字歧义补带证据的问答；语音内容漏读查码本生成与解码；调用错误型号则先纠正部署配置，不把它记作模型不会说话。

用独立视频／说话人回归，保留仅音频、仅视觉和完整输入的对照，同时检查纯文本能力。全链方案见[Omni 案例](/cases/omni-assistant/)。

## 比较与面试追问

**Thinking 比 Instruct 更会思考，就一定包含更多输出能力吗？** 不一定，输出模块不同是明确的型号边界。

**MoE 专家与语音码本有何不同？** 专家是计算模块的选择，码本是声音表示中的离散索引。

**和 2.5 最值得记住的变化？** 读 [2.5-Omni](/omni/qwen-omni/)对照音频编码器、MoE 与语音码／波形生成，不能只背版本号。
