## 它要解决什么问题

让一个助手把产品需求、网页截图和代码仓库变成可运行的网页，会遇到三个不同的开销：要从很长的材料里找到有关内容；要把庞大的模型装进设备并反复读取；还要一个接一个生成回答和工具调用。降低其中一个开销，不代表另外两个也自动解决。

MiniMax M3.1 Flash 延续 [M3](/omni/minimax-m3-model/) 的多模态 MoE 方向。官方模型卡强调三个变化：全层采用稀疏注意力、对部分路径使用量化感知训练，以及引入 DSpark 草稿头支持推测解码。它们分别作用于**读哪些上下文、怎样表示数值、怎样生成后续 token**。本文中的设计稿、数字算例和评测流程均是教学示例，未实际运行模型。

官方发布还说明，匿名名称 Space Bunny 对应的是 M3.1 Flash 的一个早期版本；它可以帮助查找相关讨论，但不意味着早期服务与后续公开权重的版本、推理设置或表现完全相同。

## 结构：三项优化不是一回事

### MSA：先找相关页，再细读

假设你有一本很厚的故障手册。每次解决问题都逐字重读前面所有页，随着手册变厚会越来越慢；另一种办法是先查索引，再仔细阅读可能相关的页。MSA 使用索引分支给上下文打分，选出部分连续块，再让主注意力分支处理选中的可见 token。

MSA 基于分组查询注意力：一个组内的查询头共享块选择，不同组可以选择不同块；当前 token 所在块保留。块内仍有多个 token，选中某块不等于只读取一条摘要。官方模型卡称，M3 中原先保留全注意力的前三层，在 M3.1 Flash 也改成了稀疏注意力。

以官方公开配置为例，语言骨干有 60 层、64 个查询头和 4 个键值头；前 3 层仍是稠密前馈，后续层使用专家前馈。这不与“所有层都使用稀疏注意力”矛盾：前者描述前馈计算，后者描述注意力读取上下文的方式。配置中有 128 个路由专家、每 token 选 4 个，并列有 1 个共享专家。具体量化、激活和缓存格式还要看所下载权重与运行框架。

配置中每块包含 128 个 token，索引选择参数为 `sparse_topk_blocks=16`。可以把它想成先挑最多 16 个候选章节，再查看这些章节中因果可见的内容；当前块和边界处理遵循实现规则，不能简单地把 16 乘以 128 当作每次实际读取量。如果索引器没有选中真正关键的条款，主注意力就可能遗漏它。索引本身也有计算和访存开销，所以全层稀疏不等于任何长度下都能线性加速，更不能保证长文所有内容都被准确利用。MSA 的机制见 [M3 深读](/omni/minimax-m3-model/)及论文；实现、块大小与硬件会影响实际收益。

### 量化感知训练：提前适应更粗的刻度

量化类似把带毫米刻度的尺换成较粗的刻度，用更少位数近似表示数值。这样可以节省权重存储和带宽，但会引入误差。量化感知训练（QAT）是在训练时考虑低精度造成的影响，让模型有机会适应这种误差。

官方模型卡说，对路由 MoE 专家和注意力路径进行量化感知训练，以降低内存占用并改善服务效率。不能因此断言模型所有参数、激活和缓存都使用同一种 4 位格式；实际权重版本和服务引擎有各自格式。仅凭模型体积变小也不能断定端到端响应一定更快，反量化、显卡内核和请求长度都会影响结果。有关 GPTQ、AWQ 与 QLoRA 的用途，可参见[量化](/training/quantization/)。

### DSpark：先拟草稿，再验证

传统自回归生成通常一个 token 接一个 token 产生。推测解码的直觉是让较轻的草稿机制先提出一串候选，再由主模型验证哪些候选可以接受；如果候选准确，一次验证可能推进多个位置。如果不匹配，就需要按实现的规则修正或回退。

官方说 M3.1 Flash 使用 DSpark 取代之前类 EAGLE 的 MTP 方案，并在发布权重中包含草稿头。一个具体例子是模型准备输出“测试已经通过”：草稿先提出后续几个 token，主模型检查后再决定接受哪些；这只是演示流程，并不代表每次验证都能接受整句。

是否真正获得加速取决于推理框架有没有启用并支持草稿头，以及候选接受率、生成长度、批量和硬件。它不保证回答事实正确：主模型可以验证 token 生成过程，却不能代替实际测试运行或事实核查。不同采样实现还须核对其分布一致性和参数设置。

## 训练：公开到什么程度

M3.1 Flash 的模型卡说明保留 M3 的 MoE 核心，并指出 QAT 涉及的专家和注意力路径。量化感知训练的通用目标是减少低精度表示引起的精度损失，但官方简述没有完整公布每阶段数据、量化训练细节、算力或优化器设置，也未给出可复现的完整后训练配方。不能把 M3 的训练资料、社区猜测或其他模型的强化学习流程直接写成 M3.1 Flash 已采用的方法。

从构建类似应用的角度，训练材料可以包含设计稿、页面实现和经过验证的测试结果。先检查图像与代码的授权，剔除个人信息，再按项目或时间划分数据，避免同一网页的近重复截图和代码同时出现在训练与测试中。监督示范可以教模型输出补丁或工具调用；测试执行结果可用于筛选，但测试覆盖不足时，补丁通过测试仍可能破坏其他功能。这些是通用实践建议，不是官方未公开训练流程的替代品。

## 评测：把任务效果和效率一起看

官方模型卡报告 DeepSWE v1.1 为 73.7、OSWorld 2.0 为 61.7，以及 BankerToolBench 为 76.2。这些是不同基准的官方报告值：分别关注软件开发、桌面操作和金融工具任务，不能直接相加或当成真实业务成功率。模型卡注明 DeepSWE 使用 mini-SWE-agent 2.4.5 和 512K 上下文；OSWorld 使用 0808 Full 版本，表中多数模型取发布时最高报告结果；BankerToolBench 使用 OpenCode 1.17.18，由 MiniMax-M2.7 担任评判模型。比较任何模型前应查看完整评测说明，包括工具、预算、采样和任务版本。

模型卡建议采样时设置 `temperature=1.0`、`top_p=0.95`，并可在对话模板设置从 low 到 max 的推理强度。例如，对同一个修复任务比较两种设置时，应保留相同仓库和测试，分别记录成功率、输出长度与耗时；这些设置是起点，不保证每个任务使用更高推理强度就更好。

官方发布还提到日常输出速度可以超过 200 token/秒、P50 超过 170 token/秒，这是特定服务观察，不是本地权重和所有硬件的性能承诺。服务层的并发、请求长度、缓存命中、网络及推测解码配置都会影响体验；单纯比较输出 token 速度，还可能忽略首 token 延迟、工具执行时间和任务是否完成。

自己的测试可以准备一组未用于调试的真实网页任务，固定仓库、图片、执行器与时间预算，记录：任务成功率及回归错误；输入和输出长度；首 token、总耗时和工具调用次数；峰值显存与成本；错误是否集中在长上下文、中英文或小字号截图。多次运行并报告失败原因，才能知道“快”是否以牺牲准确率换来。

## 例子：把设计稿做成网页

用户提供截图并要求实现商品列表。模型需要从图中识别标题、卡片间距和按钮颜色，读取现有项目，提出代码修改，再请外部执行器安装依赖、运行测试与生成新截图。长上下文帮助系统保留需求和日志，但截图是否清晰、文件是否读取成功、工具是否真的执行，仍需要逐步核验。

如果最终按钮颜色不对，可以先确认原图与渲染截图是否使用相同的色彩条件；如果上传按钮点不动，检查事件绑定、网络请求和服务返回，不能只让模型继续描述页面。复核后把错例分类：视觉理解错误、漏读上下文、修改代码错误、工具失败、测试覆盖不足。对同类问题补充有授权的示范或改进工具，再用独立样本检查是否改善。

智能体系统还应设置工具权限、操作范围和日志。模型提出“删除旧文件”只是一个请求，系统应检查是否符合任务及权限；外部网页和截图里的文字属于待分析内容，不能自动取得执行指令的权力。

## 限制与面试追问

**全层稀疏、量化感知训练和推测解码是否重复？** 不重复。它们分别减少主注意力关注范围、让部分低精度表示更可用、尝试减少生成时的串行验证轮次；是否获得实际收益要分别测量。

**模型卡写 428B，为何页面另显示 220B？** 官方文字和页面自动统计口径不同，不能直接互相替换；本文以模型卡描述为参数口径，也不猜测差异的具体原因。

**1M token 是否代表能可靠理解整份材料？** 不代表。需要测试不同位置、干扰信息、跨文档关联和图像质量，还要确认具体服务配置。

**有公开权重就能任意商用吗？** 不能直接这样推断；应阅读本版本的 MiniMax Community License、依赖组件许可证和适用服务条款。
