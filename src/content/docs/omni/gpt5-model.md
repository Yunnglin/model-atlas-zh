## 先看问题：同一个入口，为什么有时快、有时慢？

假设你让助手做两件事：一是把“明天上午十点开会”改写成一句礼貌通知，二是检查一份包含公式和图表的季度报告，找出异常并给出证据。前者可能几秒就能回答，后者需要读取材料、比较数字，有时还要使用工具。怎样让用户不必为每一道题手工挑选处理方式，同时让不同难度的请求得到合适的计算量？

OpenAI 在 2025 年介绍 GPT-5 时，用“统一系统”描述 ChatGPT 的安排：快速模型处理多数请求，thinking 模型负责更复杂的问题，实时路由器依据请求和使用情境选择。可以把路由器想成接待台，快速模型与推理模型是不同的处理路径；这只是帮助理解，不表示我们知道内部神经网络的详细构造。

上面的报告场景是教学设计，不是实际调用记录。更慢的路径不保证一定正确；复杂问题需要的也可能是外部资料、业务权限或人工确认，而不是只增加计算时间。一个用户看到的名称可能同时指系列、某个 API 模型，或者 ChatGPT 产品体验；比较时要先问清楚是哪一个。

## 从请求到结果：产品系统怎么组织

发布时的 ChatGPT 系统会考虑对话类型、问题复杂度、是否需要工具以及用户表达的意图，再决定采用哪条路径。比如简单改写可能由快速模型回答；需要比较多张图表的问题可能交给 thinking。这里的“可能”很重要：公开说明描述路由依据，并没有给出足以在外部精确预测每次选择的完整规则。

系统卡将快速模型记作 `gpt-5-main`、推理模型记作 `gpt-5-thinking`，并列出各自的小型版本。它还介绍了更高推理计算设置的 `gpt-5-thinking-pro`。这些是系统卡为说明不同组件使用的名称；它们不能随意与所有产品页面上的标签或后来版本一一等同。

API 的使用方式也不同。2025 年开发者介绍中的 `gpt-5`、`gpt-5-mini`、`gpt-5-nano` 是开发者直接选择的推理模型系列；`gpt-5-chat-latest` 对应当时 ChatGPT 使用的非推理聊天模型。开发者可以设置推理努力程度，但这并不等于在自己的应用中自动拥有了 ChatGPT 同样的路由器。今天的模型、参数和可用性可能已经变化，实际使用应核对当前官方文档。

## 架构与模态：已知什么，不知道什么

官方报告描述了图像理解、工具调用和推理表现，但没有披露足以重建 GPT-5 的完整内部结构。我们不知道发布资料所覆盖模型的准确层数、总参数、是否采用某种专家路由、视觉编码器结构或具体模态融合方式。不能因为某个开放模型使用了 MoE，或者同属 GPT 家族，就把它的架构图直接贴到 GPT-5 上。

以季度报告为例，用户给出一张收入趋势图并询问“哪个季度异常”，系统需要把图中的视觉信息与文字问题结合，再生成解释。模型可能识别错图例、误读坐标或漏掉脚注；图像能作为输入，不意味着它像数据库一样取得了每个数字的精确原始值。应让模型指出读取依据，并在有原始表格时用数据复核。

官方介绍也讨论图像、视频相关的评测与多模态理解。产品能接受哪类文件、音视频是否通过独立组件处理、能否实时输入输出，要看当时所用的产品和接口，而不能由一项视频评测推断所有模态都由同一个统一网络端到端处理。更不能把工具生成的图片自动归功于模型自身的原生图像输出能力。

## Thinking 与工具：多想一会儿，并不等于执行了操作

推理模式可以在回答前使用更多计算来处理复杂问题。它适合多步骤检查，例如先理解报表口径、比较季度数据，再说明异常可能来自什么原因；但耗时更长不一定带来正确结论，也不保证每个中间推断都可靠。API 发布时提供 `minimal`、`low`、`medium`、`high` 等推理努力选项；这些选项控制使用方式，并非公开了完整推理过程或训练算法。

工具调用则是模型提出工具请求，再由应用或平台执行并返回结果。请求可以是结构化参数，具体格式取决于工具类型。比如模型建议查询数据库中某个月的退款金额，应用需要核验调用参数、用户权限和数据库返回值，模型再基于结果作答。如果工具没有运行或返回了错误，助手不应宣称已经查到正确数字。请求工具、实际执行、核对结果是不同环节；仅凭模型说“我已查询”不能证明外部操作发生。

同一个任务也可能采用多种组合：模型自己估算一张表，或者调用计算器核对；如果计算器接收到错误的输入，结果仍会错。工具让某些步骤可检查，并不自动保证问题理解、数据来源和最终解释都正确。报告中的缺失数据应明确标记，而不是编造成完整数列。

## 训练：公开能力说明不是完整训练配方

OpenAI 披露 GPT-5 在真实编程任务、工具使用、指令遵循和安全行为等方面做过针对性训练，并介绍了安全回答方式。系统卡还说明产品路由器会参考用户切换模型、偏好与测得的正确性等信号持续改进。模型训练和路由器训练是不同对象：前者影响模型如何生成，后者影响系统选择哪条路径。

系统卡明确提到，`gpt-5-thinking` 及其 mini、nano 推理模型通过强化学习训练推理能力。可以把它想成练习解题：模型尝试回答，训练过程根据反馈调整行为；但官方没有在这份材料里公开足以复现的完整奖励函数和算法细节，不能据此断言它一定使用某个具体 RL 算法。

安全训练也有具体例子：官方介绍的 safe-completions 让模型在安全约束内尽量提供有帮助的回答。例如面对可能有危险的双用途问题，回答可以解释安全的基本概念，同时不提供会增加伤害风险的操作细节。系统卡还描述了针对讨好用户的后训练，以及在工具不可用或任务缺少关键材料时奖励模型如实承认无法完成。这些是官方披露的训练方向，不代表每次回答都能做到。

对于更细的内容，例如每种数据来源占比、完整语料、训练步骤、奖励设计、模型结构和具体参数，公开资料不足以复原。可以借助 [SFT](/training/sft/) 和 [RLHF](/training/rlhf/) 等通用概念理解可能的训练环节，但不能将某个开源模型的算法细节写成 GPT-5 的已证事实。类似地，模型在基准上会调用工具，并不能反推出官方一定用某一种可验证奖励算法训练。

从可复现角度，可以自己设计一个小规模报告助手：先准备经过授权的图表、问题和正确答案；训练或配置工具使用时记录模型版本、数据划分和工具输出，再保留独立样本测试。公开 GPT-5 权重不可用时，这只是学习其应用思路，不是复现 OpenAI 的训练。

## 评测：先看任务与条件，再看分数

OpenAI 发布材料报告 GPT-5 在 AIME 2025 的无工具设置下为 94.6%，在 SWE-bench Verified 为 74.9%，在 MMMU 为 84.2%。其中 SWE-bench 使用官方声明的 477 个经过其内部基础设施验证的任务子集，排除另外 23 个在该设施中未能可靠通过的任务；官方还说明 GPT-5 使用了强调充分验证解答的简短提示。开发者材料的详细表格将相应 GPT-5 推理模型标为 high；不同任务是否允许工具、推理预算以及系统设置都必须一起阅读。不能把有工具的成绩直接和无工具成绩比较，也不能把 74.9% 解释成任意软件项目的成功率。

看一眼指标各测什么：AIME 关注指定数学题的答案，SWE-bench 关注在软件仓库里解决给定问题，MMMU 涉及多个学科的视觉与文本理解。数学题高分不等于部署环境安全；软件修复通过特定测试，也不保证所有边界和隐藏风险都被覆盖。评测包含模型、提示、执行环境、工具与评分器，单独写一个数字不足以复现。

官方还报告：在启用网页搜索、使用代表 ChatGPT 流量的匿名提示的特定比较中，GPT-5 回答包含事实错误的可能性比 GPT-4o 低约 45%。这是相对减少，而不是“幻觉率等于 45%”或“所有问题都减少 45%”。另一组 LongFact 和 FActScore 比较采用不同的事实核查与搜索条件，不能把它们拼成一个无条件结论。高风险问题仍要核对原始来源。

社区评测可以补充具体体验。知乎作者 toyama nao 在 2025 年的测评中既讨论了指令遵循，也记录长文本统计遗漏等问题；那是其题目、设置与当时版本下的观察，不等于官方基准，也不能推导模型内部结构。单篇评价或点赞数不是模型能力的统一排名。

## 应用闭环：报告助手怎样检查错例

准备一组真实授权的图表与问题，区分图像可读性、表格推算、缺失数据和多步工具调用。按报告来源与时间划分开发集和独立测试，避免同一张图改个标题同时出现在两边；记录图像清晰度、提示、模型版本、路由或推理设置、工具权限和输出长度。

假设助手回答“第三季度收入下降 20%”，但把增长率图中的百分比误看成收入金额。先保存图片、提示、工具记录与原始表格，确认它究竟读错轴、算错比例，还是把不同单位混在一起；再增加有相似坐标和脚注的开发样本，优化提示或数据预处理。最后在保留的独立测试集上复测，同时记录正确率、无法回答的情况、工具失败、延迟与费用。这个流程是教学设计，未实际运行 GPT-5。

对需要执行的动作，比如发送通知或修改账目，还要由应用提供权限控制和执行结果核验。模型提出建议可以帮助人审查，业务系统记录才是操作是否发生的依据。为旧模型做案例时，应固定快照和环境；产品自动路由或模型更新会让同名入口的表现变化。

## 面试追问

**GPT-5 是一个模型还是一个系统？** 发布时官方同时使用系列模型和 ChatGPT 统一系统的说法；系统包含快速模型、thinking 模型和路由器，API 直接选择模型的行为需要单独看。

**Thinking 一定让答案更正确吗？** 不保证。更多推理计算可能帮助复杂任务，但数据不完整、模型误解或工具输入错误仍会导致失败，应以独立测试验证。

**为什么不能根据能力榜推断是否使用 MoE？** 评测只观察特定任务下的输入输出，不足以确定未公开的内部层与路由结构。
