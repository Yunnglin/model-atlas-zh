## 先理解它要做什么

用户说“上传文件后页面没有刷新”，并提供截图和代码仓库。解决这个问题不止是写几行代码：模型需要读需求、定位组件、检查接口返回、修改代码、运行测试，最后确认截图和功能都符合要求。每一步都可能得到新的证据，导致下一步改变。

Kimi K2.7 Code 是针对这类长程编程工作的模型。官方称它基于 [K2.6](/omni/kimi-k26-model/) 并增强工程任务表现；模型会生成文本和工具请求，实际读文件、执行命令与保存日志由外部系统完成。本文网页修复及评测案例为教学构造，不代表我们已经运行模型。

## 结构：视觉输入、专家路由与工具反馈

### MoonViT 如何帮助看代码之外的证据

如果用户给出一张页面截图，MoonViT 视觉编码器先提取视觉表示，语言主干结合文字需求与视觉信息生成回答或工具请求。比如按钮被弹窗挡住，截图能提供布局线索，但小字、遮挡与缩放都可能让模型看错。视频则依赖实际预处理和抽帧；没有采到的瞬间不能指望模型准确描述。

视觉编码器相当于把图片整理为模型可处理的表示，不是把截图里的每个像素无损保存成文字。页面上出现的命令或提示也只是待分析内容，执行器必须依据用户任务和权限决定能否执行。

### MoE、MLA 和 256K 上下文

![Kimi K2.7 Code 语言主干示意：61 层中首层使用稠密前馈，其余层使用路由专家和共享专家，各层通过 MLA 注意力处理上下文。](/figures/kimi-k26-k27/backbone.svg)

这张教学图将语言部分展开：首层的前馈模块是稠密网络，其余 60 层的前馈模块采用 MoE；每层都结合 MLA 注意力。图片或视频经过 MoonViT 转成视觉表示后，与文本一起送进语言主干。图省略残差连接、归一化和投影等细节。

官方配置的语言主干使用 64 个注意力头、7168 维隐藏表示，MLA 的键值潜在表示维度为 512。可以把 MLA 看成先用较紧凑的表示记录历史信息，再在注意力计算中使用它；具体缓存布局由推理实现决定。

官方模型卡列 61 层，其中包括一层稠密前馈层；在 MoE 层有 384 个路由专家，每个 token 选择 8 个专家及一个共享专家。可以把 MoE 看作许多处理小组：路由器根据当前输入选择部分小组工作。约 32B 激活参数说明每次 token 处理涉及部分参数，部署时仍要考虑约 1T 总参数的存放或调度，以及缓存、视觉模块和跨设备通信。

模型使用 MLA 注意力，用于组织注意力表示和缓存；MoE 决定哪些前馈专家参与，两者处理不同问题。长上下文可以容纳更多代码和工具输出，但能放进去不等于模型始终找得到关键函数；日志越长，也会占用缓存并影响成本。[MoE](/foundations/moe/)和 [KV 缓存](/foundations/kv-cache/)可补充这一部分。

多轮编程时，模型卡所述的 `preserve_thinking` 会保留先前轮次的思考内容。例如第一轮分析过上传回调，第二轮看到测试失败后可以继续参考这段历史；但它也会占用上下文预算，而且不同接口对 `reasoning_content` 等字段的支持可能不同。评估长任务时应记录实际传回的历史和截断方式，不能只看模型名义窗口。

### 工具请求和真实执行不是一回事

模型可以请求搜索文件或运行测试；框架检查请求后调用外部工具，再将退出码、输出和错误返回。模型随后根据证据继续修改或解释。官方模型卡提到交错思考与多步工具调用，但模型权重不会自动提供终端、网络、文件权限或可靠的测试环境。

例如模型写“测试通过”，需要有对应命令和真实退出码支持。测试没有运行、执行报错被忽略或只运行了无关测试，都不能算完成。工具调度、重试、审计和访问控制是系统的一部分；同一权重换不同框架，得到的工程结果也可能不同。

### 原生 INT4 量化用于哪里

官方采用与 K2 Thinking 相同的原生 INT4 方法。配置中的低精度权重每 32 个为一组，使用 4 位表示；注意力、共享专家、输出头和视觉模块等列在排除范围内。因此估算显存时，要分别计算低位宽专家权重、其他模块、缓存和运行时占用。更多细节可以看[量化](/training/quantization/)和 [K2 Thinking](/nlp/kimi-k2-thinking/)。

## 训练：公开信息和教学思路

官方描述 K2.7 Code 建立在 K2.6 上，面向长程编程与智能体任务，并报告推理 token 使用有所降低。模型卡没有完整披露这一版本新增代码数据的来源、规模、具体训练步骤、奖励函数与算力。因此不能因为它擅长写代码，就断言用了某个特定强化学习算法，也不能把 K2.5 或 K2.6 的训练细节直接当作 K2.7 的完整配方。

理解一般方法时，可以把监督微调想成给模型看“需求、代码、正确修改和工具反馈”的示范；可验证任务还可用测试结果提供反馈。举例说，一段补丁通过新增测试可以得到正面信号，但如果测试只检查返回值、没覆盖权限和并发，模型仍可能留下严重问题。奖励或训练标签依赖验证器质量，无法代替独立验收。

自己构建工程任务时，应收集有权使用的需求、修改前后的代码和可重复运行的测试，过滤秘密信息；按仓库或时间划分训练、开发和测试，避免相同补丁或近重复问题跨集合。记录代码版本、执行环境、依赖以及失败日志，保证一次成功不是依赖偶然环境。

## 评测：分数背后有哪些条件

官方模型卡报告 Kimi Code Bench v2 中，K2.7 Code 为 62.0，K2.6 为 50.9。前者是官方内部工程基准；这是 11.1 个百分点的差距，约为相对提升 21.8%，不能把相对百分比误写成百分点。Program Bench 分别为 53.6 和 48.3；MCP Atlas 分别为 76.0 和 69.4。这些是官方报告的特定版本和设置，并非所有真实项目的成功率。

Program Bench 的任务与日常修补已有代码不同：按模型卡介绍，参与者只能使用可执行程序和文档来重建行为，不能查看源码、反编译或联网，随后对 200 个任务用超过 24.8 万个模糊测试生成的行为测试检查结果。例如一个命令行工具正常输入时输出正确，遇到空输入或非法参数仍可能暴露差异。这个基准主要观察输出行为能否匹配，不能单靠它证明生成代码的设计质量、可维护性或真实部署安全性。

评测配置同样重要：模型卡说明 Kimi 两个版本使用 Kimi Code CLI 的思考模式和指定采样配置；其他模型使用不同框架和设置。MCP Atlas 的报告使用 100 次工具调用预算，并对三次运行取平均。内部基准、工具能力和软件任务分别测试不同方面；跨模型比较前应核实任务集、工具、预算、执行环境和成功判定。

再看 Kimi Claw 24/7 Bench：官方用 OpenClaw 环境设计了 17 个专业场景，共 610 个检查点。可以把一个场景想成“接到任务后查资料、调用工具并交付结果”，检查点则分别检查过程或结果中的具体要求。官方报告 K2.7 为 46.9，K2.6 为 42.9，按检查点通过率在三次运行上取平均；这并不表示 46.9% 的完整场景都成功了。把场景拆成检查点有助于发现模型到底卡在哪一步，但分数仍取决于环境和判分规则。

官方还称 K2.7 的思考 token 使用相较 K2.6 约减少 30%，这是其比较条件下的结果，不意味着每一个问题都省 30%，也不自动等于总耗时或费用减少同样比例。应同时记录任务成功率、输入输出 token、工具调用、总耗时和失败原因。

## 例子：修复文件上传

1. **理解**：提供问题描述和截图，模型指出可能涉及上传回调和页面状态；这只是初步假设。
2. **取证**：执行器按权限读取组件与接口代码，必要时运行复现；若日志显示接口实际失败，就不能只修前端刷新。
3. **修改**：模型基于已有证据提出补丁，保留现有接口约定，并为失败和成功路径添加适当验证。
4. **验收**：实际运行相关测试，检查退出码与输出，并通过新的页面截图确认按钮可见、上传成功后列表变化；必要时再测其他页面是否回归。
5. **改进数据**：将定位错误、工具失败、测试漏覆盖、截图误读等错例分类，检查标注和环境，选择可授权样本改进，再用独立仓库或任务复测。

这个流程把模型决策、工具执行和人工验收分开。修复案例中，模型给出看似合理的补丁只是中间产物，完整测试和可复现的执行记录才有助于判断任务是否完成。

## 限制与面试追问

**为什么编程模型不等于完整 coding agent？** 模型提出文字或工具请求，框架还需提供执行环境、权限控制、上下文管理与日志；结果由系统整体决定。

**1T 总参数和 32B 激活参数分别是什么意思？** 前者是模型规模，后者描述每 token 参与的约当参数量；不意味着部署只需存储 32B，也不直接给出实际推理成本。

**怎样比较 K2.7 与 K2.6？** 固定任务、提示、框架、预算和工具版本，多次运行，既比较成功率也看 token、耗时与错误类型。官方内部基准提供线索，但应用方仍应独立验证。

**能够从模型卡还原训练流程吗？** 不能。结构和结果公开不等于新增数据、训练阶段或奖励细节已经完整披露；没有证据时应明确标为未知。
