## 要解决什么问题

想象你要依据一张产品设计稿做网页：系统不仅要看清布局，还要找到相关代码、修改页面、运行测试并检查截图。单纯回答“页面有一个蓝色按钮”不够；它还需要理解目标、使用工具并根据结果修正。但模型说“我测试过了”，不一定代表测试真的执行成功。

Kimi K2.5 是 Moonshot AI 2026 年发布的视觉语言模型，建立在 Kimi K2 文本底座之上，继续接受图文混合预训练。它支持图片和视频理解，也面向工具调用和智能体任务。官方介绍了 Agent Swarm：由编排者拆分任务、协调多个子任务并汇总结果。这里要区分模型能力和完整应用：本地加载一份权重，不会自动带来搜索、浏览器、多进程调度或正确权限。

下面用设计稿场景理解这一模型，再分别看具体训练阶段和评测设置。

## 结构与数据流

模型主要由 MoonViT-3D 视觉编码器、MLP 投影器和 K2 混合专家语言主干组成。图片被切成视觉块，视觉编码器提取特征；投影器把特征转换到语言模型可处理的表示空间，文字问题与视觉信息一起输入语言模型，模型再逐步生成回答或工具请求。[Kimi-VL](/omni/kimi-vl-model/) 可作为理解 MoonViT 家族的前置材料。

### 图片和视频怎样进入模型

MoonViT-3D 使用适应不同分辨率的视觉表示。对于视频，论文描述将最多四个连续帧的图像块组织成时空块，共用视觉编码过程；在投影器之前按时间聚合，将这一组的时间维度压缩约四倍。可以把它理解为将连续四张相似截图整理成较紧凑的记录，给后续语言模型留下更多空间，但这并不意味着四帧的每个细节都被无损保留。

例如视频中一个按钮只闪现一帧：如果预处理没有采到这一帧，或时间聚合损失了细节，模型可能无法准确回答。系统处理视频还涉及抽帧策略、分辨率和时间标记；不能把“视觉编码器支持视频”理解为无限长、逐帧无损输入。原生分辨率设计同样不意味着任意大小图片都无需预处理或没有像素预算。

模型能力和接口支持也要分开：截至核对时，[官方模型卡](https://huggingface.co/moonshotai/Kimi-K2.5)将视频对话标为实验功能，并注明目前只在官方 API 支持；使用其他部署框架时需检查其实际视频接口。

### MoE、MLA 与资源

语言主干采用混合专家网络：在 MoE 层，每个 token 的路由选择部分专家参与前馈计算。模型卡列有 384 个路由专家、每 token 选择 8 个及一个共享专家；61 层中第一层是稠密前馈层，并非所有层都使用专家路由。模型还使用 MLA 注意力。MoE 决定哪些前馈专家参与，MLA 组织注意力中的表示与缓存；二者不是同一个机制。[MoE](/foundations/moe/) 与 [KV 缓存](/foundations/kv-cache/) 可帮助理解这两处成本。

约 32B 激活参数描述每个 token 的部分计算量，部署仍需要考虑约 1T 总参数、视觉模块、缓存、权重量化、设备之间通信等。256K 上下文是容量上限，不保证每个视觉帧或长文中的细节都被准确使用；服务商也可能配置更小的上限。

### 工具和子智能体在模型外执行

设计稿任务可以拆成“分析页面结构”“检查现有组件”“编写测试”等子任务。编排者发出子任务请求，外部系统启动相应执行单元、分配工具权限，等待结果后再提供给编排者汇总。子任务若可以独立进行，墙上等待时间可能缩短；若后一步必须依赖前一步，仍需要串行等待。多开执行单元也会消耗更多算力和工具调用预算。

官方 K2.5 产品介绍曾描述最多 100 个子智能体、1500 次工具调用的配置，这是该产品和时期的能力描述，不是权重本身自动提供的保证。执行器、调度、上下文传递和访问控制属于完整系统；若工具没有运行，模型生成“已完成”的文字不能算执行证据。截图里的文字或网页内容也可能含有误导，应用应把它们作为待分析数据而非直接执行的指令。

## 数据与训练

### 图文联合预训练

论文描述从接近训练末期的 Kimi K2 检查点继续训练，联合阶段使用约 15T 视觉与文本 token，并训练视觉编码器和语言模型；这 15T 不是 15T 张图片，也不等同于 K2 底座从零训练的全部数据。视觉编码器另有独立训练与短暂投影对齐阶段，后续还进行高质量数据和长上下文训练。公开报告描述了阶段和类型，但没有公开全部样本与精确来源，不能断言某份私有资料在训练集中。

把三个阶段放在一起更容易理解：第一阶段从 SigLIP 初始化视觉编码器，用图片或视频生成描述的损失训练它，论文表中列约 1T token；接着短暂训练投影器，让视觉特征对接语言模型。第二阶段从接近训练末期的 K2 检查点继续进行 15T token 的图文联合预训练，视觉编码器和语言模型一起更新。第三阶段逐步把训练序列从 32K 拉长到 256K，论文表中列出两个阶段分别为 500B、200B token，并加入长文、长视频和推理数据。

打个比方，第一阶段先练习看图描述，第二阶段让读图和语言能力一起成长，第三阶段再练习处理更长的材料。三个数字来自论文表 3 的不同训练阶段，阅读时要和各自的序列长度及可训练组件一起看。

报告研究了何时引入视觉数据：在其固定文本与视觉预算的实验中，较早、较低比例地混入视觉数据取得较好结果。这个结论属于具体实验条件，不是说所有多模态模型都应采用同一比例。图片描述、OCR、视频与屏幕数据有助于覆盖任务，但标签可能错配、截图可能含隐私，仍要做清洗、授权检查与质量审核。

### 后训练与视觉工具使用

监督微调让模型学习按指令组织答案与工具调用。论文讨论一种 zero-vision SFT 实验：在这一特定阶段使用纯文本的程序化工具任务，观察视觉工具能力是否能从联合预训练中迁移；随后该研究采用视觉强化学习来改善模型忽略图片等问题。这里的 zero-vision 指这一段 SFT 使用纯文本，不包括此前的图文联合预训练。

报告描述视觉强化学习任务包括定位、计数、图表和需要视觉信息的科学问题；可验证任务可以依据答案或位置等结果给奖励，开放任务需要其他评价方法。奖励规则可能漏掉重要约束，例如按钮坐标落在按钮附近却点中了旁边的危险操作，因此训练奖励与实际任务成功仍要分开检查。

### 并行智能体训练

论文提出并行智能体强化学习（PARL）：训练可更新的编排者，子智能体在该训练设置中冻结，把其输出作为环境反馈。这样可以聚焦任务拆分与协调，缓解多个执行者同时更新带来的不稳定。论文讨论任务结果、并行和完成等奖励；奖励鼓励拆分不代表越多子任务越好，重复搜索、互相依赖或结果冲突都可能让系统变慢或变错。

具体来说，论文用任务最终结果作为主要奖励，另外给“创建子智能体”和“完成子任务”两个辅助奖励。前者鼓励编排者尝试并行，后者防止它只顾着多派任务、却不管任务是否完成；训练过程中这两个辅助奖励的权重逐渐降到零，最终仍以整体任务结果为主。就像培养项目负责人：一开始鼓励他学会分工，但最后考核的是项目是否做好，而不是开了多少个小组。

论文还用“关键步骤”衡量并行过程中的步骤预算：每一阶段先计入主智能体的动作，再加上这一批并行子任务中最长的一条；所有阶段相加。例如第一阶段主智能体用 1 步派出两个子任务，它们分别用 3 步和 5 步，则该阶段计 `1 + max(3, 5) = 6` 步；第二阶段主智能体用 1 步汇总，且没有子任务，总计 `6 + 1 = 7` 个关键步骤。它是便于训练和比较的步骤指标，不等同于真实秒数；网络、工具排队和不同步骤的耗时都可能改变实际延迟。

例如，检查设计稿和阅读现有组件可以同时开始；但要验证修改后的截图，必须先等页面代码完成并运行。即使前两项各用 10 秒、截图验证也用 10 秒，整项工作仍受后续串行步骤影响，不会因为开了两个子任务就变成 10 秒。实际系统还要计入汇总、工具排队和失败重试；这个算例用于理解依赖关系，不是论文的实测时延。

## 评测怎么看

模型看图、写代码和执行工具是不同能力。论文报告 K2.5 在 MMMU-Pro 得分 78.5，在 BrowseComp 的 Agent Swarm 设置下得分 78.4；前者是多学科图文问题，论文的图像评测使用三次独立运行平均；后者是带搜索系统的任务，不能把它们比较为同一种准确率，也不能直接当成一般网页开发成功率。模型版本、提示、工具、采样、上下文管理和预算都会影响结果。

同一报告的 BrowseComp 对照还列出单智能体 60.6%、加入上下文管理 74.9%、Agent Swarm 78.4%。它们展示的是三种系统配置：增加上下文管理会改变历史信息处理方式，增加多智能体还会改变任务拆分与工具调用方式。判断并行是否划算，除了看分数，还要看总 token、工具调用和实际等待时间。

论文的短视频基准采用 128 帧均匀采样、最大空间分辨率 896，长视频基准采用 2048 帧、空间分辨率 448；不同基准的预处理不同。比较两个系统时，如果一个看 16 帧、另一个看 2048 帧，差异不只是模型能力，也有输入和计算预算的影响。截图任务还应记录分辨率、浏览器缩放、坐标映射和页面状态。

用设计稿做构造测试，可分别检查：颜色与布局识别、代码是否能运行、截图与目标的差异、测试是否真的执行、是否保留正确链接与交互。假设 20 个任务里 16 个页面能启动，只有 12 个同时通过功能与视觉检查，两项分别为 80% 和 60%；这是教学算例，不是模型实测。对于并行系统，还应比较墙上耗时、总 token、工具次数和失败重试成本。

## 应用与错例闭环

假设系统把设计稿中的“取消”误实现为“提交”。先保留输入截图、预处理结果、任务拆分、子任务输出、补丁、运行日志和最终截图。检查模型是否读错文字、子任务收到的局部上下文是否缺失、汇总时是否覆盖了正确结果，以及测试是否只检查按钮存在而未检查行为。

收集经过授权和脱敏的错例，标注布局、文字、动作和预期结果；按项目或设计来源划分开发与独立测试集，避免同一模板反复出现在两边。先修正提示、工具权限和测试覆盖，再依据证据考虑训练；改动后同时复测功能、视觉、失败恢复、延迟和成本。

## 比较与面试追问

**K2.5 是从零开始训练的吗？** 官方描述其建立在 K2 Base 检查点上，继续进行视觉与文本联合训练。

**四帧时间压缩是否保留所有动作细节？** 不保证。抽帧和聚合都可能丢失短暂事件，应按任务验证。

**zero-vision SFT 是否说明模型没用过视觉数据？** 不是。那是后训练中的特定实验，模型此前进行视觉文本联合预训练，后续还有视觉强化学习。

**Agent Swarm 是否会随着权重下载自动可用？** 不会。多执行单元、工具、权限和调度需要外部系统支持。

**32B 激活参数能直接决定显存吗？** 不能。总权重、缓存、视觉模块、精度及部署方式都要考虑。
