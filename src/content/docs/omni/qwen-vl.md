## 要解决什么问题

一张发票上同时写着“合计 108.00”“税额 6.48”“价税合计 114.48”。问题是“含税一共付多少钱？”模型不仅要认出数字，还要把问题与正确字段联系起来。回答 108.00 可能字全读对了，字段却选错了。

下面始终使用这张**虚构教学发票**。图片尺寸、坐标、回答和评分例子用于解释机制，不是实际模型运行结果。本页限定 Qwen2.5-VL 初始 3B／7B／72B 报告；其他版本不能直接套用配置。[系列脉络](/omni/qwen-vl-family/)另读。

## 结构与数据流

可以分成三段：**视觉编码器提取图片信息 → Merger 把视觉信息整理到语言模型能接收的维度 → Qwen2.5 语言模型结合问题生成答案**。Merger 可以先理解为“压缩、接线”，不是提前替模型写出 OCR 文本。

下面用依据论文核对的原创教学图展示本例，省略层内残差、归一化和其他输入路径。完整结构见官方[报告 Figure 1](https://arxiv.org/html/2502.13923v1#S2.F1)。

## 沿着一张发票走一遍

### 第一步：不是把任何图片都压成一个小正方形

预处理会结合像素预算调整大小，并把高宽处理到 28 的倍数。动态分辨率保留不同图片的长宽与细节需求，**不等于原文件绝不缩放**。实际送入模型的图片才是排错依据。

假设处理后的发票是宽 840、高 560 像素。按 14×14 的 patch 切分，横向有 60 块、纵向有 40 块，共 2,400 个视觉块。这些块是像素区域，不是“一个块对应一个汉字”。

### 第二步：ViT 先看局部，也安排全局交流

视觉编码器让块之间交换信息。论文的 32 层视觉编码器主要使用窗口注意力，在第 8、16、24、32 层使用全注意力（从 0 计数的索引为 7、15、23、31）。112×112 像素窗口相当于 8×8 个 patch。

大白话说，平时先在小范围内读细节，间隔几层再联系整张图。窗口降低大图的部分计算成本，但不是所有层都变成线性成本，也不能据此保证任意小字都看得清。[注意力](/foundations/attention/)与 [ViT](/cv/vit/)解释基础机制。

### 第三步：四块合一，减少交给语言模型的长度

Merger 把空间上相邻的 2×2 个 patch 特征合在一起，再用两层 MLP 投到语言模型的输入维度。本例从 2,400 个块变成 **600 个视觉 token**。这是单张静态图的简化计数，不包含问题文字、角色标记等额外 token。

如果高宽都扩大两倍，patch 数量和合并后的视觉 token 都变为四倍：600 → 2,400。更高分辨率可能帮小字，却也提高视觉计算和后续语言处理成本；不是“高宽翻倍，费用只翻倍”。

N_{\mathrm{visual}}=\frac{H}{14}\frac{W}{14}\frac{1}{4}=\frac{HW}{28^2}
$$

这里 H、W 是**预处理后的**高宽。本例是 560×840÷784＝600。视频还涉及时间分组，不能直接把原始视频帧数乘进去。

### 第四步：图片表示与问题一起进入语言模型

语言模型得到视觉表示与“含税一共付多少钱？”的文字 token，逐步生成回答。它必须把“含税”对应到“价税合计”，而不是随便抄最醒目的数字。输入接入后，输出仍常用[下一 token 预测](/foundations/next-token/)组织；它没有要求先把图片完整转成一段 OCR 文字再回答。

视频则还要表达时间。2.5-VL 的 MRoPE 将时间维与绝对时间对齐，并配合动态 FPS 训练；同一个事件在不同采样速度下，仍应对应真实时刻。论文的视觉输入还会把相邻两帧组成时间方向上的 patch；模型看到的是采样并分组后的帧，不能把“支持长视频”理解为逐帧看完原视频。

例如，同一段开门录像，一种输入每秒取一帧，另一种每两秒取一帧。第一种输入的相邻帧通常相隔一秒，第二种则相隔两秒；如果只告诉模型“这是第几张图”，它不容易分清动作快慢。时间位置与实际间隔对齐后，模型才有条件区分这两种节奏。它依然无法看到被抽帧漏掉的动作：如果门在两帧之间打开又关上，仅靠这两帧不能断言中间没有人经过。选取帧率时还要在覆盖和成本之间取舍。

## 数据与训练

### 预训练：视觉与语言怎样接上

论文 2.2.2 节将训练分成三个阶段，不能一概说“只训连接层”。视觉编码器先有自身初始化，语言部分来自 Qwen2.5：

| 阶段     | 哪些部分学习                                 | 用什么材料                               | 本例中帮助什么                   |
| -------- | -------------------------------------------- | ---------------------------------------- | -------------------------------- |
| 第一阶段 | 训练视觉侧，语言模型保持冻结；细节按报告表 2 | 图片描述、视觉知识、OCR 等               | 把图中数字、文字与语言表示接起来 |
| 第二阶段 | 全模型解冻                                   | 更丰富图文、视频、数学、Agent 与纯文本等 | 将字段、布局与问题联系起来       |
| 第三阶段 | 继续长序列训练                               | 增加视频、Agent 与长上下文数据           | 跨页、跨帧及长材料中的关联       |

报告表 2 分别列出约 1.5T、2T、0.6T token，序列长度分别为 8192、8192、32768；这些是三个阶段的训练配置，不代表每个样本都有这么长，也不等于最终可推理上下文的保证。视觉编码器另有从头训练的初始化过程，不能误会为直接沿用 Qwen2-VL 的视觉权重。

这些是原报告的阶段安排，不是所有 VL 模型或后续 Qwen 版本必须照做的流程。

### 后训练：会读字之后，还要学按问题作答

原报告的后训练包含 SFT 与 DPO，**这两阶段冻结 ViT**。SFT 提供图文／视频／文本指令答案，包含筛选后的推理材料；DPO 使用偏好对，改进图文与纯文本回答。不能反过来说 ViT 在全部训练期间都冻结。

报告称 SFT 数据约 200 万条，按条数看，纯文本和多模态各占一半；多模态样本包含图文和视频，但一条样本的视觉 token 可能很多，所以“条数各一半”不等于 token 数或计算量各一半。报告中的 DPO 数据则使用图文与纯文本偏好对，不应把 SFT 的视频数据自动算入 DPO。

给本例做 SFT，可以保留图片、问题、答案 `{"total":"114.48","currency":"CNY"}`，有定位任务时再提供对应坐标。问“税额”与问“价税合计”应给不同答案；图片相同，问题条件不同。答案不存在或看不清的样本也应覆盖。

偏好对则可把“有证据地给出 114.48”与“编造其他金额、混淆字段或格式失效”区分。**这些是教学用业务适配设计，不声称官方采用了这张发票或这个具体偏好对。**

## 评测怎么看

### 先拆四项，再看一个总分

| 检查项   | 本例怎样判断                      | 错了应先查什么             |
| -------- | --------------------------------- | -------------------------- |
| 感知     | 价税合计区域实际写的是不是 114.48 | 缩放、裁剪、像素与文字识别 |
| 字段理解 | 问“含税总额”是否选对字段          | 近邻字段、布局与语义       |
| 输出结构 | JSON 能否解析，字段与单位是否合规 | 模板、答案掩码、解析器     |
| 证据定位 | 返回框是否覆盖目标字段            | 坐标系、原图到输入图的变换 |

假设一个候选输出合法 JSON，但金额是 108.00：**格式正确，任务仍失败**。本业务可以预先约定金额精确匹配，114.48 计正确，108.00 计错误。论文里的 DocVQA、OCRBench、OmniDocBench 等各有任务和评分规则，不能拿这些分数替代你的金额验收。

### 用官方成绩练习读表

[技术报告表 5](https://arxiv.org/html/2502.13923v1#S3.T5)给出了三个规格在文档视觉问答与文字识别相关任务上的结果；DocVQA 使用测试集：

| 模型规格 | DocVQA 测试集 | OCRBench |
| -------- | ------------: | -------: |
| 3B       |          93.9 |      797 |
| 7B       |          95.7 |      864 |
| 72B      |          96.4 |      885 |

DocVQA 是根据文档图片回答问题，OCRBench 覆盖多种文字识别及理解任务。两列采用不同的基准和计分规则，不能直接比较 95.7 与 864 的大小，也不能说 7B 在自己的发票数据上一定达到 95.7%。这张表适合先观察不同规格的取舍；选型还要测实际票据、响应时间和显存。

视频评测也要看输入条件。报告表 8 中，7B 在 Video-MME 上无字幕得 65.1、有字幕得 71.6；报告对每段视频设置最多 768 帧、视频 token 总数最多 24,576。字幕让模型获得了额外文字信息，不能把两项当成完全相同输入下的纯视觉成绩，也不能因此推断任意视频都适用同样的采样方式。

### 做一次能区分原因的对照

固定同一权重、模板和输出预算，比较整图、较高像素预算、目标局部裁剪。裁剪后答对，只说明证据更容易被利用；它提示输入细节或干扰可能有关，**不能单独证明网络里的哪层出了问题**。

保留原始／处理后尺寸、`min_pixels`／`max_pixels`、图像数量、视觉 token 数、问题、生成设置与逐题结果。视频另记实际帧和时间戳；训练成本比较还要固定精度和硬件。[多模态协议](/evaluation/multimodal-evaluation/)提供共用检查项。

如果还要求返回金额所在的框，要明确坐标相对于哪张图。例如把处理图上坐标换回原图时，横向和纵向应分别按实际缩放比例换算；裁剪过的图还要加回裁剪区域的左上角偏移。若预处理同时缩放和裁剪，只凭一个统一倍率可能把框画错。先用已知矩形检查变换，再评估模型定位，才能区分坐标还原错误和模型真的看错位置。这里是常见处理流程的教学例子，坐标格式与变换以实际使用的模型接口为准。

## 应用与错例

若模型把 114.48 读成 114.4B，先看小字是否可见与转写是否正确；若读成 108.00，先查字段选择；若值正确但框偏移，先检查坐标变换。三个问题需要不同数据，不能统一叫“OCR 不好”。

改进时从开发池补相似字段、低清晰度和缺字段样本；测试按票据模板和来源独立留出。既测原错例类别，也测普通发票与无答案请求。完整闭环见[视觉问答案例](/cases/visual-qa/)。

## 比较与面试追问

**Merger 是 OCR 引擎吗？** 不是。它处理视觉向量并对齐输入维度，文字和字段理解仍由整体训练学到。

**分辨率翻倍，视觉 token 为什么可能翻四倍？** 高和宽都增加，面积变四倍；先确认预处理没有另外限像素。

**只训练连接层就够吗？** 那是一种策略，原报告的不同阶段对参数冻结有不同安排，应区分预训练与后训练。

**能回答金额就证明定位正确吗？** 不证明，回答和坐标是不同输出约束。[Qwen3-VL](/omni/qwen3-vl/)再看多层特征与时间表示的后续变化。
