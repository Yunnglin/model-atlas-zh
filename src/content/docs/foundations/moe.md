## 用大白话理解

Dense 网络在相关层对每个 token 使用同一套稠密计算。稀疏 MoE 放入多组专家，路由器为当前 token 选择其中一部分。这样可以增加总容量，而不让每个 token 都经过所有专家。

专家常是网络中的前馈子模块，不是把几台完整聊天机器人投票拼在一起。它们的分工通过训练形成，不能未经验证就贴上“数学专家”“中文专家”的标签。

## 跟着例子走

假设一层有多个专家，每步只选择少数参与。计算量减少不代表其他权重消失：部署仍要存放或调入它们，还可能跨设备通信。这个教学例子不指定任何实际模型的专家数量。

## 路由器怎么安排一个 token

假设一个 MoE 层有四个专家，路由器为当前 token 打分后选择专家 1 和专家 3。两位专家各自处理相同的输入，得到两个输出；假设权重分别是 0.6 和 0.4，那么合并结果就是 `0.6 × 专家 1 输出 + 0.4 × 专家 3 输出`。接下来的 token 可以选不同专家。

![MoE 路由示例：路由器从四个专家中选择专家一和专家三，分别计算后按零点六和零点四加权合并。](/figures/foundations/moe-routing.svg)

这里的数字是为了讲清过程设定的。真实路由器的打分、选择数量、归一化以及是否有共享专家，取决于具体模型。专家通常处理的是向量，合并也是逐元素运算。

[DeepSeek-V3](/nlp/deepseek-v3/)提供了一个实际配置：除前三层外，其前馈模块采用 MoE；每个 MoE 层包含一个共享专家和 256 个路由专家，每个 token 选择其中 8 个路由专家。报告将整个模型描述为总参数 671B、每个 token 激活约 37B。激活参数包含专家之外的其他参与计算的模块，因此不能简单用 671B 乘以 8/256 来估算。

## 训练与部署

如果大量 token 都被送到同一专家，负责它的设备可能排队，其他设备却在等待。训练时可以监控各专家接收的 token 数，并采用负载均衡策略。DeepSeek-V3 的报告介绍了根据负载调整路由偏置的方法，同时使用一个较小的序列级辅助损失。

部署时，专家可能分布在不同设备上。一个批次的 token 需要先按选择结果发送给对应设备，专家算完后再把结果传回并合并。因此即使每个 token 只运行少数专家，通信时间、批量大小和各专家负载仍会影响实际速度。

## 评测与面试

能力与速度分开测，同时报告总参数、激活参数、硬件和并发条件。小批量、设备间带宽不足或专家分布不均，都可能让稀疏模型没有预想的快。

**MoE 是否每层都稀疏？** 不一定，要查看具体架构；某些层或模块仍然是稠密计算。

**激活参数等于推理显存需求吗？** 不等于，模型权重、缓存、运行时与通信缓冲都要计入。
